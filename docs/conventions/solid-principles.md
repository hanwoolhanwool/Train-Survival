# SOLID 원칙 준수 규칙

이 프로젝트의 모든 C# 코드는 아래 SOLID 원칙을 준수한다.
예시는 이 프로젝트의 실제 인프라(`EventBus<T>`, `ServiceLocator`, `PoolManager` 등)를 기준으로 한다.

---

## S — 단일 책임 원칙 (Single Responsibility)

**클래스 하나는 변경 이유가 하나여야 한다.**

- MonoBehaviour 하나에 이동·전투·UI 갱신을 몰아넣지 않는다. 역할별로 컴포넌트를 분리한다.
  - 예: 체력은 `Health`가 담당한다. 사망 연출·점수 처리는 `Health.Died` 이벤트를 구독하는 별도 컴포넌트가 담당.
- "Manager"라는 이름으로 잡다한 기능을 모으지 않는다. `PoolManager`는 풀링만 한다.
- 클래스 설명에 "그리고(and)"가 들어가면 분리를 검토한다.

## O — 개방-폐쇄 원칙 (Open-Closed)

**확장에는 열려 있고, 수정에는 닫혀 있어야 한다.**

- 새 동작 추가가 기존 클래스의 `switch`/`if-else` 수정으로 이어지면 안 된다.
  - 나쁨: `switch (enemyType)` 분기 추가
  - 좋음: ScriptableObject 데이터 또는 인터페이스 구현체 추가로 확장
- 밸런싱 수치·타입별 차이는 ScriptableObject로 분리해 코드 수정 없이 확장한다.
- 시스템 간 반응 추가는 기존 코드 수정 대신 `EventBus<T>` 구독 추가로 처리한다.

## L — 리스코프 치환 원칙 (Liskov Substitution)

**하위 타입은 상위 타입을 대체해도 동작이 깨지지 않아야 한다.**

- 인터페이스/베이스 클래스의 계약(사전·사후 조건)을 하위 타입이 임의로 강화하거나 무력화하지 않는다.
  - 예: `IDamageable.TakeDamage` 구현체가 예외를 던지거나 특정 호출 순서를 요구하면 안 된다.
- 오버라이드에서 베이스 동작이 필요한 경우 `base.Awake()` 호출을 누락하지 않는다 (`MonoSingleton<T>` 상속 시 특히 주의).
- "구현했지만 동작 안 함"(빈 구현, `NotSupportedException`)이 필요해지면 인터페이스 분리(I)를 검토한다.

## I — 인터페이스 분리 원칙 (Interface Segregation)

**사용하지 않는 멤버에 의존하게 만드는 큰 인터페이스를 금지한다.**

- 인터페이스는 역할 단위로 작게 유지한다.
  - 예: `IDamageable`(피격), `IPoolable`(풀 콜백)은 별개 인터페이스다. 하나로 합치지 않는다.
- 구현체가 인터페이스 멤버 일부를 빈 몸통으로 두고 있다면 인터페이스가 너무 크다는 신호다.

## D — 의존성 역전 원칙 (Dependency Inversion)

**상위 정책은 하위 구현이 아니라 추상에 의존한다.**

- 구체 클래스 직접 참조 대신 인터페이스에 의존한다.
  - 예: 투사체는 `Enemy`가 아니라 `IDamageable`을 찾아 피해를 준다.
- 전역 서비스는 `ServiceLocator.Get<T>()`로 조회하되, `T`는 가능하면 인터페이스로 등록한다.
- 시스템 간 직접 참조 대신 `EventBus<T>` 발행/구독으로 결합을 끊는다.
- **어셈블리 의존성은 항상 단방향** (Utilities ← Core ← Systems ← Gameplay ← UI). 하위 계층이 상위 계층을 참조해야 할 것 같으면 이벤트나 인터페이스를 Core로 내려서 역전시킨다.
