## 1. 결론 요약

**전용 서버(Dedicated Server) 인프라는 두지 않는다.**
**"호스트 = 서버"인 리슨 서버(Listen Server) 방식**을 채택하며, 구현 스택은
**NGO(Netcode for GameObjects) + Steamworks(릴레이·로비·초대)** 로 **확정**한다.

| 항목 | 결정 |
|---|---|
| 토폴로지 | 리슨 서버 (호스트 = 권위 서버, 최대 4인) |
| 기준 좌표계 | **열차 원점 고정 + 월드 스크롤** — 열차는 월드 좌표를 이동하지 않는다 (§4.1) |
| 권위 모델 | 월드 상태 = 호스트 권위 / 자기 캐릭터 이동 = 소유자 권위 / 사격 = 클라이언트 판정 + 호스트 적용 (§4) |
| 네트워크 솔루션 | **NGO (com.unity.netcode.gameobjects) — 확정** |
| 트랜스포트 | 개발·CI = UnityTransport(직결) / 릴리스 = Steam 릴레이 (Facepunch 계열 커뮤니티 트랜스포트) |
| 후순위 대안 | Photon Fusion 2 (§3.3의 전환 조건 충족 시에만 재검토) |
| 연결/로비 | Steamworks 릴레이 + 프렌드 초대 (자체 인프라 0) |
| 세이브 | **게임 중간 저장 없음** — 런 단위 완주 (기획서 §9.1). 업적·수집품 등 메타 진행만 로컬 저장 |
| 호스트 마이그레이션 | 불채택 (호스트 이탈 = 세션 종료) |
| 전용 서버 | 불채택 (추후 커뮤니티 요구 시에만 재검토) |

## 2. 판단 근거 (기획서 기반)

### 2.1 1~4인 협동 PvE — 전용 서버의 존재 이유가 없음

- 경쟁(PvP) 요소가 전혀 없으므로 치팅 방지를 위한 중립 서버가 불필요하다.
- 세션 인원이 최대 4명이라 호스트 PC 한 대가 시뮬레이션을 감당할 수 있는 규모다.
- 기획서의 레퍼런스인 **Raft, Deep Rock Galactic이 정확히 이 구조(호스트 세션)** 를 사용한다.
- 소규모 팀 전제(기획서 §9.3 아트 톤 근거)에서 전용 서버는 서버 비용·운영 부담만 생기고 얻는 것이 없다.

### 2.2 시뮬레이션 복잡도는 높음 — "권위 구조"가 핵심

기획서의 아래 요소들이 전부 **"누가 진실(state)을 소유하는가"** 를 강하게 요구한다.

| 기획 요소 (기획서 근거) | 네트워크 요구사항 |
|---|---|
| 밤 웨이브의 다수 몬스터 AI (§5) | AI는 호스트 단독 시뮬레이션 (이동 방식은 §4.3). 클라이언트는 결과만 수신 (스냅샷 + 보간) |
| 집게로 몬스터를 낚아채 바퀴에 처형 (§3.2) | 물리 상호작용 + 즉사 판정이 얽혀 클라이언트 각자 계산 시 결과가 갈라짐. 그랩 확정·물리 시뮬레이션은 호스트 소유 |
| 칸 단위 파괴 + 연결부 파괴 시 후방 연쇄 이탈 (§9.1) | 열차 구조 자체가 변하는 대형 상태 변화. 원자적(atomic)으로 호스트가 결정 후 전파 |
| 연료·탄약·식량 등 공유 자원 (§2, §6) | 4명이 동시에 꺼내 쓰는 인벤토리는 호스트 권위 없이는 복제(dupe) 버그의 온상 |

즉, "서버를 어디에 둘 것인가"의 답은 **호스트 PC**지만,
"서버 로직이 있느냐"의 답은 **반드시 있어야 한다**이다.

### 2.3 세션 구조 — 월드는 호스트에 귀속

**게임 중간 저장은 없다** (기획서 §9.1 확정). 런은 호스트 세션에서 한 번에 완주하며, 업적·수집품 등 메타 진행만 각자 로컬에 저장한다. 즉 월드의 진실은 살아 있는 호스트 세션에만 존재한다. 이에 따라 결정한 부속 규칙:

- **호스트 이탈 = 세션 종료.** 호스트 마이그레이션은 구현 비용이 매우 커서 이 규모에는 비추천 (DRG·Raft도 마이그레이션 없음).
- **재접속(rejoin) 허용.** 사망 규칙(§9.1: 팀원 1명 이상 생존 시 부활)과 일관되게, 생존자가 있으면 재접속 가능으로 한다.
- **접속 끊김 ≠ 사망.** 게임오버 조건이 "전원 사망"이므로 연결 끊김과 사망을 구분한다. 끊긴 플레이어는 게임오버 판정에서 제외한다.

### 2.4 필요한 백엔드는 릴레이/매치메이킹뿐

- 직접 IP 연결은 NAT 문제로 사실상 불가능 → 친구 초대·로비·릴레이는 플랫폼 서비스에 위임한다.
- PC 우선(§1)이면 **Steamworks(무료 릴레이 + 프렌드 초대)** 로 **자체 서버를 하나도 띄우지 않고 출시 가능**하다.

## 3. 네트워크 솔루션 — NGO + Steam 확정

### 3.1 선정 근거

| 근거 | 설명 |
|---|---|
| 비용 0원 | NGO(무료·오픈소스) + Steam 릴레이(무료) 조합은 출시 후 러닝 코스트가 영구히 없음. 유료 PC 패키지 판매 모델과 정합 |
| Unity 공식 스택 | Unity 6·Multiplayer Center(이미 설치됨)와의 통합이 매끄럽고, 리슨 서버 + 서버 권위가 기본 모델 |
| 오픈소스 | 문제 발생 시 내부 코드를 직접 분석 가능. 벤더 락인 없음 |
| Steam 생태계 | 프렌드 초대·로비가 플랫폼 기능으로 해결. PC/Steam 우선 방침(기획서 §1)과 일치 |
| 규모 적합 | 4인 세션은 NGO의 검증된 범위 내 |

- **NGO의 약점(클라이언트 예측 미내장)은 §4의 권위 완화로 소거된다.** 협동 PvE에서는 예측 시스템 자체가 불필요해지는 구조를 채택한다.

### 3.2 트랜스포트 이원화

- **개발·CI**: UnityTransport 직결 — Steam 클라이언트 의존 없이 로컬 멀티 테스트·GameCI 자동화 유지.
- **릴리스**: Steam 릴레이 (Facepunch/Steamworks.NET 기반 커뮤니티 트랜스포트).
- NGO는 트랜스포트 교체가 설정 수준이므로 이원화 부담이 적다. 트랜스포트 선택은 빌드 설정/실행 인자로 전환한다.

### 3.3 후순위 대안 — Photon Fusion 2

Photon Fusion 2는 기술적으로 정당한 대안이다 (틱 기반 동기화, 클라이언트 예측·랙 보상 내장, Host Mode = 리슨 서버). 다만 아래 트레이드오프로 후순위로 설정한다.

| 항목 | Fusion 2 | NGO + Steam (채택) |
|---|---|---|
| 클라이언트 예측/랙 보상 | 내장 | 미내장 → §4 권위 완화로 불필요화 |
| 러닝 코스트 | CCU 기반 지속 과금 | **0원** |
| 인프라 의존 | Photon Cloud (개발 루프·CI에도 의존 발생) | 개발 시 의존 없음 (Steam은 릴리스만) |
| 소스 공개 | 비공개 | 오픈소스 |

**전환 조건 (아래에 해당할 때만 재검토):**
1. 집게·사격의 네트워크 손맛이 §6.3의 처방으로도 목표 품질에 도달하지 못할 때
2. 플랫폼 확장(콘솔 등)으로 Steam 비종속 릴레이가 필요해질 때

- 참고: PUN2는 구세대로 검토 제외. Quantum(완전 결정론)은 이 장르에 과함. 절충안 FishNet(무료 + 예측 내장)은 Fusion 전환 검토 시 함께 재평가.

## 4. 권위(Authority) 분담표

협동 PvE의 업계 표준에 따라 **플레이어 소유 요소는 권위를 완화**한다. 이 완화로 클라이언트 예측·랙 보상 시스템이 통째로 불필요해지며, NGO의 약점이 소거된다. (PvP가 없으므로 치팅 리스크는 수용 — DRG·Raft와 동일한 판단.)

| 상태/판정 | 소유자 | 비고 |
|---|---|---|
| 자기 캐릭터 이동/시점 | **각 클라이언트 (소유자 권위)** | 지연 0. 예측·보정 코드 불필요 |
| 원격 플레이어 위치 표시 | 소유자 클라이언트 (수신 측은 표현만) | 수신한 스냅샷을 보간해 표시 (NGO NetworkTransform 보간). 몬스터와 동일한 스냅샷+보간 원칙 |
| 사격 명중 판정 | **쏜 클라이언트** | 로컬 레이캐스트로 판정 → 호스트에 보고. 지연 0 |
| 데미지 적용·사망 확정 | 호스트 | 클라이언트의 명중 보고를 받아 확정 |
| 몬스터 AI·스폰·웨이브 진행 | 호스트 | 클라이언트는 스냅샷 수신 + 보간 |
| 집게 그랩 확정·끌기 물리 | 호스트 | 발사·명중 연출은 로컬 선반영 (§6.3) |
| 공유 인벤토리·자원(연료/탄약/식량) | 호스트 | 획득/소모 요청 → 호스트 승인 방식 |
| 개인 인벤토리 (핫바 소지품, 기획서 §3.4) | 호스트 | 개인 소유물이라도 증감 확정은 호스트 — 복제(dupe) 방지. 잔량은 `NetworkVariable`로 동기화, 엔진 투입은 요청 RPC → 호스트가 (인벤토리 차감 + 연료 충전) 원자적 확정 |
| 열차 상태 (칸 구성, 파괴, 연쇄 이탈, 속도) | 호스트 | 원자적 상태 변화로 전파 |
| **월드 스크롤 속도 (= 체감 열차 속도)** | 호스트 | `NetworkVariable` 단일 값. 연료·감속·초가속 연출의 유일한 제어 파라미터 (§4.1) |
| Day 진행·날씨·지역 전환 | 호스트 | 전역 타임라인 단일 소유 |
| **대기실 상태 (멤버 목록·난이도)** | 호스트 | 출발 전 대기 화면의 상태. 멤버는 호스트의 `ConnectedClientsIds`에서만 파생시키고 **클라이언트가 자기 자리를 직접 주장하지 않는다** — 유령 칸·중복을 막는 유일한 방법이다. 계약·구현 근거는 [게임 준비 화면 구현 계획](../plans/features/게임-준비-화면-구현-계획.md) §7이 소유한다 |

### 4.1 기준 좌표계 — 열차 원점 고정 + 월드 스크롤 (확정)

**열차는 월드 좌표를 이동하지 않는다.** 열차를 원점 부근에 고정하고, 지형·트랙·배경이 열차를 지나쳐 스크롤된다. "열차가 실제로 이동"하는 대안은 아래 사유로 기각한다.

| 판단 축 | 열차 실제 이동 | **열차 고정 + 월드 스크롤 (채택)** |
|---|---|---|
| **연출 상한 (결정적 사유)** | 최종장 초가속 → 공간 왜곡(기획서 §8.2)은 극한 속도에서 물리·좌표 정밀도가 붕괴해 사실상 구현 불가 | 스크롤 속도 파라미터를 올리기만 하면 됨. 빛줄기 왜곡은 셰이더/포스트프로세스로 처리 — **연출 상한이 없음** |
| 부동소수점 정밀도 | 16일+ 연속 주행 시 원점에서 수백 km 이탈 → 물리 지터·렌더링 떨림·이펙트 붕괴 | 항상 원점 부근. 영구 안전 |
| 네트워크 동기화 | 호스트 권위(열차) 위에 소유자 권위(플레이어)가 올라타는 **이동 플랫폼 지터 문제** 발생. 부모 기준 로컬 좌표 동기화 등 별도 체계 필요 | 열차가 정지 프레임이므로 **월드 좌표 = 열차-로컬 좌표**. `NetworkTransform`을 보정 없이 그대로 사용. 문제가 원천적으로 존재하지 않음 |
| 플레이어/건축 물리 | 달리는 플랫폼 위의 캐릭터 컨트롤러·리지드바디는 플랫폼 속도 상속 처리가 상시 필요 | 열차 위 = 정지 바닥. 일반적인 1인칭 이동 코드 그대로 |
| 속도 변화 연출 | 실제 가감속 물리 필요 | 연료 고갈 감속·추격 위기·가속 게이지(§8.2)까지 **스크롤 속도 변수 하나로 제어** |

부속 규칙:

- **모든 게임플레이 오브젝트(플레이어·몬스터·건축물·투사체·집게 로프)는 열차 기준 프레임(=월드 좌표)에서 시뮬레이션·동기화한다.**
- 지상의 몬스터·자원·이탈한 칸 등 "월드에 속한" 오브젝트는 스크롤 속도만큼 열차 반대 방향으로 이동시킨다(컨베이어 방식). 몬스터가 열차에 승차하면 자연스럽게 동일 프레임이 되므로 전환 처리가 없다.
- 지형은 타일 스트리밍(전방 생성 → 후방 회수)으로 처리하며 `PoolManager` 풀링을 활용한다. 무한 트랙 구조상 어차피 필요한 시스템이므로 월드 스크롤 고유의 추가 비용이 아니다.
- 스크롤 속도는 호스트 권위 `NetworkVariable` 단일 값으로 동기화한다 (§4 분담표).

### 4.2 호스트 → 소유자 위치 개입 규약

§4의 권위 분담은 "자기 캐릭터 이동 = 소유자 권위"지만, 호스트 권위 이벤트가 플레이어 위치를 움직여야 하는 경계 케이스가 존재한다: **플레이어가 서 있는 칸의 파괴·연쇄 이탈(기획서 §9.1), 몬스터의 넉백, 몬스터에게 붙잡힘.** 이를 방치하면 §7이 경고하는 "나중에 동기화를 끼워 넣을 수 없는" 코드가 된다. 다음 두 갈래로 규정한다.

| 유형 | 처리 | 예시 |
|---|---|---|
| **임펄스형** (순간 힘, 이후 제어권 유지) | 호스트가 소유자에게 임펄스 RPC 전송 → **소유자 클라이언트가 로컬 적용**. 권위는 소유자 유지 | 넉백, 폭발 밀림, 이탈하는 칸이 발밑에서 사라질 때의 낙하 시작 |
| **구속형** (지속 구속, 조작 불능) | 플레이어를 일시적으로 **호스트 구동 상태로 전환**(상태 머신: `Grabbed`/`Carried`). 구속 해제 시 소유자 권위로 복귀 | 몬스터에게 붙잡혀 끌려감, 처형·구출 연출 |
| **상시 외력형** (월드가 주는 지속 변위) | 소유자 클라이언트가 호스트 권위 `NetworkVariable`(월드 스크롤 속도, §4.1)을 읽어 **매 프레임 로컬 적용**. 별도 RPC 없음, 권위는 소유자 유지 | 지면에 있는 플레이어의 컨베이어 밀림 |

- 상태 전환(소유자 권위 ↔ 호스트 구동)은 호스트가 확정하고 권위 이벤트로 전파한다 (EventBus 권위 규약, [`architecture-rules.md`](../conventions/architecture-rules.md) 참조).
- 플레이어 이동 컴포넌트는 처음부터 이 상태 머신을 전제로 작성한다. "일단 로컬 이동만 만들고 나중에 추가"를 금지한다 (§7).

### 4.3 몬스터 내비게이션 — NavMesh 불사용, 커스텀 조향 (확정)

기준 좌표계(§4.1)의 귀결로, **몬스터 이동에 Unity NavMesh를 사용하지 않는다.**

**기각 사유 (NavMesh):**

- NavMesh 데이터는 월드 공간에 정적으로 베이크된다. 스크롤 구조에서 지형 타일은 매 프레임 후방으로 이동하므로, 타일에 부착된 NavMesh를 매 프레임 재배치해야 하고 그 위의 NavMeshAgent는 발밑 메시가 미끄러지는 상태가 된다 — 엔진 전제와 정면 충돌.
- NavMeshAgent에 컨베이어 변위를 매 프레임 외부 합성(`Warp`/`Move`)하면 에이전트 자체 조향과 상시 경합한다.

**채택안 (커스텀 조향):**

- 추격 목표가 **항상 원점 고정 열차**라서 경로 탐색 문제가 본질적으로 단순하다. 범용 경로 탐색이 불필요한 구조.
- **지상**: 열차를 향한 조향(steering) + 레이캐스트 기반 국소 장애물 회피 + 컨베이어 변위 가산. 셋 다 단순 벡터 합성이라 호스트 단독 시뮬레이션(§4)에 부담이 없다.
- **열차 위**: 칸 프리팹에 정의된 웨이포인트 그래프. 열차 구성 변경(증설·파괴·이탈)은 이산 이벤트이므로 그 시점에만 그래프를 재계산한다.
- **몬스터 이동속도 > 스크롤 속도** 제약을 몬스터 데이터(ScriptableObject)로 강제한다 — 추격 성립 조건.
- **재검토 조건**: M2 계측에서 지상 지형이 국소 회피로 감당할 수 없는 복잡도(협곡·미로형 장애물 등)를 요구하게 될 때만, 타일 단위 경로 그래프 등 상위 솔루션을 재검토한다.

## 5. 현 프로젝트 세팅 적합성

현 세팅(Unity 6 / URP / `Game.*` 어셈블리 구조 / GameCI) 기준 평가. 구조적으로 갈아엎을 것은 없다.

### 5.1 그대로 맞는 것

- **어셈블리 단방향 의존성** (`Utilities ← Core ← Systems ← Gameplay ← UI`): 네트워크 세션/전송은 `Game.Systems`, 권위 로직은 `Game.Gameplay`에 배치. "서버 로직과 클라이언트 표현의 분리"(§7)를 어셈블리 경계로 강제 가능. UI가 최상위라 "UI는 상태를 소유하지 않는다" 원칙도 구조적으로 보장.
- **씬 흐름 `Boot → Main → Game`**: NGO의 `NetworkManager`(DontDestroyOnLoad)를 Boot에 두는 표준 패턴과 일치.
- **기타**: C# 9.0 제약, Input System, PC Standalone 타깃, `com.unity.multiplayer.center`(설치됨) 모두 문제없음. `com.unity.ai.navigation`은 §4.3 확정으로 몬스터 AI에는 사용하지 않는다 — 패키지 제거 여부는 M2에서 판단.

### 5.2 보완 필요 (통합 작업)

| 항목 | 내용 |
|---|---|
| 패키지 설치 (🔶 일부 완료) | `com.unity.netcode.gameobjects` ✅ 설치 완료. Steam 트랜스포트(Facepunch 계열)는 미도입 — §8 구현체 선정 후 추가 |
| **PoolManager ↔ NGO 스폰 통합** (✅ 반영됨) | 네트워크 오브젝트는 서버의 `NetworkObject.Spawn()`으로 생성·복제되므로 `PoolManager.Spawn` 경로를 그대로 탈 수 없음 → **`INetworkPrefabInstanceHandler` 어댑터로 PoolManager를 NGO의 스폰 핸들러로 등록**해 "스폰/소멸은 PoolManager 경유" 규칙을 유지. `Systems/Networking`의 `PooledNetworkPrefabHandler` + `NetworkPrefabPoolRegistrar`로 구현 완료. 밤 웨이브 물량에는 풀링이 필수라 기존 인프라가 오히려 이득 |
| 네트워크 세션 추상화 (✅ 반영됨) | `INetworkSessionService` / `NgoNetworkSessionService`로 세션 시작·종료를 서비스로 격리. 트랜스포트 전환(§3.2)도 이 구현 내부에 격리됨 |
| **EventBus 권위 규약** (✅ 반영됨) | `EventBus<T>`는 호스트/클라이언트 구분이 없으므로, **"권위 이벤트"(호스트 확정 후 발행: 자원 소모 확정, 칸 파괴 등)와 "로컬 표현 이벤트"(발사 이펙트, UI 갱신 등)를 구분하는 컨벤션**을 [`architecture-rules.md`](../conventions/architecture-rules.md)에 추가 완료. 클라이언트가 미확정 상태를 진실처럼 소비하는 버그 예방 |
| CI 유지 | §3.2 트랜스포트 이원화로 Steam 클라이언트 의존 없이 GameCI 테스트·빌드 유지 |

## 6. 기획 기능별 실현성 평가

### 6.1 기능별 난이도

기획서의 요구 기능 중 NGO + Steam으로 막히는 것은 없다.

| 기획 기능 | 구현 방식 | 난이도 |
|---|---|---|
| 공유 자원·인벤토리·제작 | NetworkVariable + RPC, 호스트 승인 | 쉬움 |
| 열차 칸 증설·파괴·연쇄 이탈 | 호스트가 상태 확정 후 전파 (트위치 반응 불필요) | 쉬움 |
| Day/날씨/지역 진행 | 호스트 단일 타임라인 동기화 | 쉬움 |
| 사망/부활/게임오버 | RPC + 상태 머신 | 쉬움 |
| 밤 웨이브 몬스터 동기화 | 호스트 조향 AI(§4.3) + 위치 동기화 | **주의 필요 (§6.2)** |
| 집게(하푼) 전투 활용 | 호스트 물리 + 로컬 연출 선반영 | **주의 필요 (§6.3)** |
| Steam 로비·초대·릴레이 | Facepunch 트랜스포트 (검증된 커뮤니티 경로) | 보통 |
| 재접속(rejoin) | NGO 후발 접속 동기화 + 커스텀 상태 복원 (식별 방식은 §8) | 보통~주의 |
| 메타 진행 저장 (업적·수집품) | 네트워크와 무관한 로컬 직렬화 | 쉬움 |

### 6.2 리스크 A — 밤 웨이브 물량과 대역폭

몬스터 수십 마리의 위치를 매 틱 동기화하면 릴레이 대역폭이 부담된다. 처방:

- 동기화 주기 하향(10~15Hz) + 클라이언트 보간. **화면상 움직임의 부드러움은 보간으로 보장되므로 손실 없음.**
- 거리/시야 기반 동기화 우선순위.
- **기획 피드백 필요**: 동시 존재 몬스터 상한을 정하고, 웨이브를 "한 번에 대량"이 아닌 "지속 유입으로 체감 물량"으로 설계하면 네트워크와 밸런스가 함께 풀린다.

### 6.3 리스크 B — 집게 손맛 (본 프로젝트 네트워크 구현의 최고 난이도 구간)

"부드러움"의 문제가 아니라 **"원격 클라이언트의 당기는 조작 반응이 왕복 지연(30~80ms)만큼 늦게 시작하는" 반응성**의 문제다. 처방:

- 발사음·로프 발사·명중 훅 이펙트는 **입력 즉시 로컬 재생** (지연 0).
- 끌려오는 위치만 호스트를 따르되, **로프의 탄성 연출로 시작 지연을 시각적으로 흡수** (낚싯대가 즉시 휘면 물고기가 30ms 늦게 딸려오는 것은 인지되지 않는 원리).
- 이 제약은 물리 상호작용의 본질적 한계로 **Fusion 등 어떤 스택을 써도 동일하게 발생** → 스택 전환의 사유가 아니라, 스택 무관하게 프로토타입에서 최우선 검증할 항목.

### 6.4 프로토타입 우선순위

**"호스트 1 + 클라이언트 1로 집게로 물체를 낚아채는 수직 슬라이스"를 최우선으로 제작**해 최고 리스크(§6.3)를 먼저 소진한다. 여기서 손맛이 확보되면 나머지는 물량 작업이다.

- 수직 슬라이스는 **§4.1의 월드 스크롤 기반으로 제작**한다(열차 고정 + 지형 스크롤). 좌표계는 이후 전환 비용이 가장 큰 결정이므로, 프로토타입 단계부터 확정 구조를 따른다.

## 7. 설계상 핵심 주의점

**리슨 서버라도 서버 로직과 클라이언트 표현을 처음부터 분리해야 한다.**

- "혼자 할 땐 그냥 로컬로 돌리고 나중에 멀티를 붙이자"는 이 장르에서 가장 흔한 실패 패턴이다.
- 특히 **열차 연쇄 이탈, 집게 물리** 같은 시스템은 나중에 동기화를 끼워 넣는 것이 거의 불가능하다.
- **1인 플레이도 "혼자 호스트인 세션"으로 취급한다** (기획서 §1: 1~4인). 싱글/멀티 코드 경로를 나누지 않는다.

## 8. 미결 사항

| 항목 | 내용 |
|---|---|
| Steam 트랜스포트 구현체 선정 | Facepunch.Steamworks vs Steamworks.NET 기반 트랜스포트 — 패키지 도입 시점에 유지보수 상태 비교 후 확정 |
| Steam AppID | Steam 릴레이·로비 테스트에 AppID 필요. 개발 중에는 임시 AppID(Spacewar, 480) 사용 가능하나 릴리스 전 자체 AppID 발급 필요 |
| 동시 존재 몬스터 상한 | §6.2 대역폭 관리를 위한 수치 — 프로토타입 계측 후 기획과 협의 |
| 중도 난입(drop-in) 허용 범위 | 재접속만 허용 vs 신규 난입 허용 — 밸런스 논의 필요 |
| 재접속 유예 시간 | 끊긴 플레이어의 슬롯 유지 시간 TBD |
| 재접속 식별 방식 | "같은 플레이어로 복귀"에는 Steam ID ↔ 플레이어 슬롯 매핑 + 인벤토리·스탯 커스텀 복원이 필요 (NGO 후발 접속 동기화는 NetworkObject/NetworkVariable만 복원). 설계는 재접속 구현 시점에 확정 |
| 트랙 커브·경사 표현 | 열차 원점 고정 + 월드 스크롤(§4.1)에서 직선 주행은 문제없으나, 커브·경사는 별도 처방 필요 — 배경·카메라 연출로만 표현 vs 지형 스크롤 벡터 회전. 지역 비주얼 설계(M4) 전 결정 |
| 전용 서버 재검토 조건 | 출시 후 커뮤니티의 상시 서버 요구가 클 경우에만 (Valheim 사례) |

### 해소된 항목

- ~~네트워크 솔루션 선정~~ → **NGO + Steam 확정** (§3, v1.1). Photon Fusion 2는 후순위 (§3.3 전환 조건부).
- ~~기준 좌표계(열차 실제 이동 vs 월드 스크롤)~~ → **열차 원점 고정 + 월드 스크롤 확정** (§4.1, v1.2). 결정 사유: 초가속 연출(기획서 §8.2) 실현 가능성 + 이동 플랫폼 동기화 문제 원천 소거.
- ~~호스트 권위 ↔ 소유자 권위 경계 케이스~~ → **임펄스형/구속형 개입 규약 확정** (§4.2, v1.2).
- ~~몬스터 내비게이션 방식 (NavMesh vs 커스텀 조향)~~ → **NavMesh 불사용, 커스텀 조향 확정** (§4.3, v1.3). 결정 사유: 정적 베이크 전제가 스크롤 지형과 구조적 충돌 + 추격 목표(원점 고정 열차)의 단순성.
- ~~누적 스크롤 오프셋 동기화 방식~~ → **① 호스트 권위 누적 거리 `NetworkVariable` + 클라 속도 외삽·스무딩 보정 확정** (v1.6, M1 착수). 결정 사유: 지형 타일·지상 자원 위치의 공용 기준값이므로 표류 허용(③)은 자원 방식 ①과 결합 불가, ②(각자 적분+주기 보정)는 ①과 동일 결과에 보정 로직만 추가됨. 구현: `WorldScrollController`가 속도·누적 거리를 모두 소유, 클라이언트는 수신 값 사이를 속도로 외삽하고 오차를 스무딩으로 흡수.
- ~~지상 자원 스폰·위치 동기화 방식~~ → **① 호스트 스폰 NetworkObject + 스폰 시점 (누적 거리, 오프셋) 전송 → 위치 로컬 유도 확정** (v1.6, M1 착수). 결정 사유: 정지 자원의 상시 위치 동기화(③)는 대역폭 낭비이자 누적 거리 기준과 이중 진실이 되고, 시드 결정론(②)은 호스트가 상태(소멸·점유)를 소유해야 하는 그랩 검증 전제와 맞추려면 결국 엔티티화가 필요. 그랩 확정 시에만 30 Hz 동기화(슬라이스 스펙 §2.4)로 전환하고, 취소 낙하 시 낙하 지점을 새 (누적 거리, 오프셋)으로 재바인딩해 월드 소속으로 복귀.
