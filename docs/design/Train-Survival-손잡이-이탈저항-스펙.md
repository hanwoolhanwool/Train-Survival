## 1. 목적

밤 방어전에서 연결부가 뚫려 후방 칸이 이탈할 때, **플레이어가 협력해 이탈 칸을 되살릴 수 있는** 상호작용을 만든다.
이탈 칸의 손잡이를 집게로 잡아 뒤로 밀려나는 것을 저항하며, **잡은 인원 수에 따라 감속→정지→끌어당김**으로 결과가 갈린다.
이로써 인원 수가 곧 난이도이자 협력 여지가 되게 한다(1인 = 지연만, 다수 = 회수 가능 + 역할 분담).

## 2. 범위

### 이번 증분 (구현)
1. **이탈 칸 비공격 대상화** — 연결부가 먼저 끊겨 이탈한 칸·그 연결부는 몬스터 공격 대상에서 즉시 제외.
2. **손잡이 잡기 + 이탈 저항** — 이탈 중인 칸의 손잡이를 집게로 잡으면 저항력이 걸리고, 인원 비례로 이탈 이동이 감속/정지/역전(끌어당김)된다.
3. **이탈 이동의 호스트 권위 승격** — B의 CarView 로컬 연출을 **호스트 시뮬레이션 + 복제**로 올린다(칸의 생존이 게임플레이 결과이므로).

### 후속 증분 (문서에만, 확장성 확보)
- ~~**재결합(연결부 재생성)** — 슬롯까지 끌어당긴 칸을 수리 망치로 재연결.~~
  → **2026-08-01 구현 완료 (§4.1)**. 이번 증분의 '붙잡힌 채 정지' 위에 재결합이 얹혔다.
- **선제적 잡기** — 연결부가 끊기기 전에 손잡이를 미리 잡아 두는 전략(이번엔 이탈 중인 칸만 잡기 가능).
- **다중 그랩·엄호 역할** — 엄호 사격은 기존 리볼버로 이미 가능. 손잡이당 다중 그랩·추가 손잡이는 데이터로 확장.

## 3. 개념 모델

편성 배치는 칸 끝마다 `손잡이 | 연결부 | 손잡이` 구조다. 손잡이는 **각 칸의 앞·뒤 끝에 하나씩**, 항상 시각적으로 존재한다.

- **표현(항상)**: 손잡이 앵커는 씬에 정적 배치되어 게임 시작부터 상시 존재한다(런타임 생성 없음).
  칸의 스케일 왜곡을 피해 칸의 자식이 아니라 씬 루트 홀더(`Train_Handrails`)에 두고, 칸의 이탈
  오프셋을 따라 위치를 계산해 칸과 동행한다(기관차는 파괴·이탈 불가라 앵커 없음).
- **잡기 가능(이탈 중만)**: 칸이 이탈해 뒤로 밀려나는 동안에만 그 칸의 손잡이가 집게 표적이 된다. 붙어 있는 칸·소실된 칸의 손잡이는 표적 아님.

## 4. 저항 모델 (호스트 권위)

이탈한 칸 `c`의 이동을 호스트가 매 프레임 시뮬레이션한다. 상태량은 **이탈 오프셋** `offset_c`(슬롯 기준 후방 이동 거리, m).

```
targetPush  = scrollSpeed + ejectExtraSpeed         // 관성을 다 잃었을 때 도달할 목표 후퇴 속도(데이터)
pushSpeed_c = moveTowards(pushSpeed_c, targetPush, ejectDeceleration * dt)   // 관성 램프 (아래)
resistance  = grabberCount_c * pullPerGrabber       // 손잡이 잡은 인원 × 1인 견인력(데이터)
netVelocity = pushSpeed_c - resistance              // +면 후퇴, -면 슬롯으로 전진
offset_c    = clamp(offset_c + netVelocity * dt, 0, ∞)
```

- `netVelocity > 0`: 칸이 뒤로 멀어진다(저항이 밀림보다 약함 → 감속만).
- `netVelocity < 0`: 칸이 슬롯 쪽으로 당겨진다(다수 협력 → 끌어당김). `offset`은 0에서 멈춘다
  (슬롯 도달 = **붙잡힌 채 정지** — 손을 놓으면 다시 밀려난다. 여기서 §4.1 재결합으로 확정한다).
- `offset_c > lostDistance` 이고 `grabberCount_c == 0`: 칸 **영구 소실**(회수 불가, 기획서 §9.1). 손잡이 앵커 despawn.

**관성 램프** (2026-07-28 도입, `979927e`): 분리된 칸은 즉시 최고 후퇴 속도로 밀리지 않는다.
분리 순간 `pushSpeed_c = 0`(= 열차와 같은 속도)에서 시작해, 감속도 `ejectDeceleration`(m/s²)만큼
매 프레임 목표 `targetPush`로 다가간다. 스크롤이 느려져 목표가 낮아지면 같은 비율로 따라 내려온다.

- 분리 연출에서 속도 점프가 사라지고, **분리 직후일수록 저항으로 되돌리기 쉬워진다**(밀림이 아직 약하므로).
- 이는 **밀림 측 램프**다. 잡기/놓기 순간의 **저항 측** 속도 점프는 아직 남아 있으며
  [개선 계획 §5](../plans/M3/M3-테스트-피드백-개선-계획.md)에 TBD로 걸려 있다 — 그쪽이 적용되면
  `resistance`도 같은 형태의 램프를 타게 되어 위 수식이 한 번 더 바뀐다.

인원 비례 난이도는 전부 데이터에서 나온다. 아래는 램프가 목표에 도달한 **정상 상태** 기준이며,
램프 도중에는 `pushSpeed_c < targetPush`라 같은 인원으로도 더 유리하다:

| 상황(4인 예시) | grabberCount | netVelocity | 결과 |
|---|---|---|---|
| 아무도 안 잡음 | 0 | +targetPush | 후퇴 → 소실 |
| 1인 잡음 | 1 | targetPush - 1×pull | 감속(약간 벌어짐) |
| 2인 잡음 | 2 | targetPush - 2×pull < 0 | 끌어당김(슬롯 복귀) + 남은 2인은 엄호/재결합 |

→ `pullPerGrabber`를 `targetPush`의 약 0.6~0.8배로 잡으면 "1인=지연, 2인=회수"가 성립. 값은 SO로 분리해 밸런싱한다.

현재 데이터(2026-08-01): `scrollSpeed 6 + ejectExtraSpeed 2 = targetPush 8`, `pullPerGrabber 6`,
`ejectDeceleration 4` → 정상 상태에서 0인 +8(후퇴) · 1인 +2(지연) · 2인 −4(끌어당김).
정상 상태에서는 의도대로 **끌어오기에 2인이 필요**하다. 다만 램프(0 → 8 m/s, 4 m/s²)를 타는 동안
`pushSpeed_c`가 `pullPerGrabber`(6)보다 작은 **분리 후 1.5 s 구간에서는 1인만으로도 칸이 되돌아온다** —
목표 도달은 2 s. "빨리 붙잡을수록 적은 인원으로 된다"가 데이터에서 나오는 셈이다.

### 4.1 재결합 (설계 확정 2026-08-01 · **구현 완료 2026-08-01**)

슬롯에 도달해 붙잡힌 칸을 **수리 망치 우클릭**으로 편성에 다시 붙인다. 설치·수리·칸 건설과 같은
도구·같은 조작(우클릭)으로 모아 도구 일관성을 지킨다.

**확정 조건** (전부 충족해야 호스트가 확정한다)

| 조건 | 이유 |
|---|---|
| 칸이 이탈 중이고 살아 있다 (`Attached == false`, `Health > 0`) | 파괴·소실 칸은 회수 대상이 아니다 |
| `offset == 0` (슬롯 도달) | 끌어오기를 끝낸 상태에서만 붙는다 |
| 앞 칸(`index-1`)이 편성에 붙어 있다 | 앞에서부터 순차 재결합 — 편성 중간에 뜬 칸이 생기지 않는다 |
| 요청자 인벤토리에 자원 `RecoupleCost`개 | 아래 비용 |
| 호스트 거리 재검증 | 기존 망치 확정 경로와 동일 패턴 |

**비용**: 자원 **2개** (칸 신규 건설 5개보다 저렴). `TrainExpansionSettings`에 `RecoupleCost`로 분리한다.
회수가 재건보다 항상 이득이 되게 해, 힘들여 끌어오는 선택에 경제적 유인을 준다.

**확정 결과**

- `CarState.Attached = true` — 체력은 **그대로 유지**한다(이탈 중에는 손상되지 않으므로).
- `CouplingState[index-1]`: **뚫렸던(`Broken`) 자리만** `Broken = false`, `Health = MaxHealth × 0.5` —
  급하게 다시 이은 연결이라는 서사. 이어서 망치 좌클릭으로 마저 수리하는 행동이 자연스럽게 이어지고,
  재결합 직후 같은 연결부가 다시 뚫릴 위험이 긴장감으로 남는다.
  **연쇄 이탈로 함께 떨어졌을 뿐 뚫리지 않은 연결부(예: 연결부 1이 뚫려 칸2·칸3이 함께 이탈했을 때의
  칸2↔칸3)는 체력을 그대로 되찾는다** (2026-08-01 구현 시 확정) — 그 자리는 손상된 적이 없으므로
  절반 페널티를 물리면 방어에 성공한 연결부를 벌하는 셈이 된다.
- 칸 위 건축물(`StructureState`)은 이탈 중에도 데이터가 보존되므로 **함께 복귀**한다 —
  건축물을 없애는 재건(`RebuildSlot`)과 달리, 이것이 회수의 실질 이득이다.
- 이탈 시뮬 흔적 초기화: `_ejectOffsets[index] = 0`, `_ejectPushSpeeds`/`_ejectSettled` 리셋,
  잡고 있던 인원의 그랩 해제 처리 — 해제는 **손잡이 앵커가 스스로** 한다(§5), 재결합 확정 경로가
  집게를 직접 알지 않는다.

**조준·HUD 표시**

칸 건설(M3 피드백 — 건설 포트의 망치 통합)에서 만든 조준 안내·테두리 프리뷰 틀을 그대로 따른다.
같은 도구의 같은 조작이므로 표시 방식이 갈리면 배우는 규칙만 늘어난다.

- **조준 지점**: 이탈 칸의 앞 연결 지점 = **슬롯 기준 고정 좌표**(`CarBuildAimLogic.AnchorZ`,
  칸 건설과 같은 계산). 칸이 아직 멀리 있어도 지점은 열차 쪽에 고정되어 있어, 겨누는 위치가
  도망가지 않고 사거리(망치 `MaxRange`) 안에 늘 머문다.
- **건설 조준과의 관계**: 상호 배타다. 이탈했지만 소실되지 않은 칸이 있는 자리는
  `FindBuildSlot`이 건설 후보에서 빼므로, 같은 지점에서 "칸 건설"과 "재결합"이 동시에 성립하지 않는다.
- **조준 성립 조건**(안내를 띄우는 조건 — 확정 조건보다 느슨하다): 그 칸이 이탈 중이고 살아 있으며
  소실 전이고, 위 지점을 사거리 안에서 겨눈다. **`offset > 0`이어도 성립**시킨다 —
  그래야 "아직 더 끌어와야 한다"를 알려줄 수 있다.
- **테두리 프리뷰**: 이어질 연결부 자리에 와이어 박스를 그린다(칸 건설의 `CarBuildGhostView` 재사용,
  상자 크기만 연결부 자리에 맞춘다). **초록 = 지금 우클릭하면 붙는다**, **붉은색 = 조건 미충족**.
  지어질 부피를 그리는 칸 건설과 달리 칸은 이미 눈에 보이므로, 강조할 것은 "이어질 연결부 자리"다.
- **안내 문구**(위에서부터 먼저 걸리는 것 하나만 표시 — 구조적 순서 → 진행 → 비용):

  | 상태 | 문구 | 색 |
  |---|---|---|
  | 앞 칸(`index-1`)이 편성에 없다 | `앞 칸이 비어 있어 재결합할 수 없다` | 붉은색 |
  | `offset > 0` (아직 슬롯 미도달) | `칸을 슬롯까지 끌어와야 한다 (N m 남음)` | 붉은색 |
  | 자원 부족 | `재결합 자원 부족 (N개 필요)` | 붉은색 |
  | 전부 충족 | `우클릭 — 재결합 (자원 N개)` | 노란색 |

  "앞 칸이 비어 있다"는 앞 칸이 파괴돼 빈 슬롯인 경우와 아직 이탈 중인 경우를 함께 덮는다
  (전자는 칸 건설, 후자는 그 칸부터 재결합해야 한다).
- **부위 체력 라벨 억제**: 재결합 조준이 성립하는 동안에는 `HammerTargetLocalEvent`를 끈다 —
  우클릭의 의미(재결합 vs 돔 설치)가 겹쳐 보이지 않게 한다. 칸 자체의 수리는 조준 지점을 벗어나
  칸 몸체를 겨누면 그대로 된다.
- **이벤트**: `CarRecoupleAimLocalEvent`를 신설한다(조준 여부·칸 인덱스·비용·자원 충족·앞 칸 유무·
  남은 거리·테두리 상자). 칸 건설의 `CarBuildAimLocalEvent`와 필드 의미가 달라 한 타입에 섞지 않는다.
  프리뷰 뷰와 HUD가 두 이벤트를 모두 구독한다.

**순수 로직**: `TrainStateLogic.Recouple(cars, couplings, index, couplingHealth)` 신설 +
EditMode 경계 검증(앞 칸 미부착 시 거부, 파괴 칸 거부, 연결부 체력 절반).
조준 성립·안내 상태 판정도 순수 함수로 분리해 EditMode로 덮는다(문구 우선순위 포함).

**알려진 제약 — 최소 3인 동시 필요**

손잡이는 칸당 앞·뒤 2개뿐이라 잡을 수 있는 인원 상한이 2인인데, 끌어오기에 정확히 2인이 필요하다.
따라서 망치를 쥘 3번째 사람이 반드시 있어야 한다 — **2인 세션에서는 재결합이 성립하지 않는다.**
현재 정식 검증이 2인이라, 이 기능은 3인 이상 세션을 구성해야 플레이 검증할 수 있다.
완화가 필요하면 선택지는 ① 손잡이당 다중 그랩 허용(§11) ② `pullPerGrabber` 상향으로 1인 끌어오기
③ 슬롯 도달 시 고정(latch) 도입 — 셋 다 이번 결정에서는 채택하지 않았다.

**파생 효과**: 지금은 끌어온 칸이 슬롯을 점유하면 그 자리에 새 칸도 지을 수 없다
(`FindBuildSlot`이 파괴·소실 자리만 후보로 본다). 재결합이 들어오면 이 막다른 길이 해소된다.

## 5. 손잡이 앵커 (집게 표적)

NGO 중첩 NetworkObject 제약을 피하고 기존 집게 파이프라인을 재사용하기 위해, **손잡이 앵커는 독립 NetworkObject**로 다룬다. 개정(2026-07-28): 동적 스폰(`IPoolable` + `PoolManager`)을 폐기하고 **씬 정적 배치(InScenePlaced)**로 전환 — 향후 열차 재생성/재결합 시 앵커 수명 관리가 단순해진다.

- **배치(정적)**: 씬 루트 홀더 `Train_Handrails` 아래에 파괴 가능 칸마다 앞·뒤 앵커를 저작한다
  (기관차 제외, `carIndex` 직렬화 배선). Train(NetworkObject) 하위 중첩을 의도적으로 피한 배치다.
  칸 소속은 계층이 아니라 `carIndex`로 연결되므로 기능은 동일하다.
- **위치(각 피어 로컬 계산)**: 복제된 이탈 오프셋(`ITrainState.GetEjectOffset`)을 읽어
  `기준 슬롯 위치 + back × offset`으로 매 프레임 배치 — CarView와 동일 소스라 전 피어 위치가
  일치하며, 위치 복제(NetworkVariable)가 필요 없다(`SynchronizeTransform` off).
- **잡기(IGrabbable)**: `IsAvailableForGrab` = `ITrainState.IsCarGrabbable(carIndex)`(이탈 중이고
  소실 거리 전). 집게 명중→호스트 승인→`TryClaimGrab`으로 그 칸의 `grabberCount` 증가.
- **집게 앵커 모드**: 집게는 이 표적을 **플레이어 쪽으로 릴 감지 않는다**(무거운 칸). `IGrabbable`에 `GrabKind { Reel, Anchor }`를 추가하고, `HarpoonController`의 견인 루프는 `Anchor`면 릴을 건너뛰고 로프만 유지한다. 우클릭 시 `ReleaseGrab` → `grabberCount` 감소.
- **소실 처리**: despawn하지 않는다 — 소실 칸(offset ≥ `LostDistance`, 0인)은 `IsCarGrabbable`이
  false가 되어 잡기만 차단되고, 앵커는 씬에 남아 다음 판(씬 재로드)·재결합에 대비한다.
- **잡기 불가 전환 시 자동 해제** (2026-08-01 추가): 잡고 있는 도중 `IsCarGrabbable`이 false가 되면
  (재결합으로 편성 복귀, 소실 거리 초과) 호스트가 그 자리에서 `ReleaseGrab`한다. 앵커는 despawn하지
  않으므로 집게 쪽 "대상 소멸" 검사에 걸리지 않는다 — 집게는 앵커 그랩 중 **점유가 풀린 것을 보고**
  로프를 함께 끊는다(`GrabKind.Anchor` 전용 경로). 소실 거리 밖 칸은 표현도 이미 사라져 있어,
  보이지 않는 것을 붙잡고 있는 상태가 없어진다.

집게의 발사·명중·승인 핸드셰이크(NetworkObjectReference + GrabValidation)는 그대로 재사용한다. 달라지는 것은 승인 이후 "릴 대신 홀드"뿐이다.

## 6. 이탈 이동의 권위 승격 (B 로컬 연출 → 호스트 상태)

B에서 CarView가 로컬로 뒤로 흘려보내던 연출을 폐기하고, `offset_c`를 **호스트가 계산 + 복제**한다.

- 저장: `TrainState`에 `NetworkList<float> _ejectOffsets`(칸 수 길이, 기본 0). 호스트만 갱신. 이동 중인 칸만 매 프레임 델타 전송(소수라 부담 작음).
- 표현: CarView는 `ITrainState.GetEjectOffset`을 읽어 `localPos = 원위치 + back * offset`으로 배치. 파괴(체력0)는 즉시 소멸(오프셋 무관).
- 밀림 속도(`pushSpeed_c`)의 **판정 진실은 호스트 로컬 배열**이다 — 복제하지 않는다.

### 6.1 클라 표시 = 결정적 재시뮬 (2026-07-31 도입, `24b8cf8`)

원안은 "복제 오프셋을 그대로 표시"였으나, 그러면 30 Hz 틱 계단으로 칸이 움직여
**탑승한 클라이언트에게 월드가 떨려 보였다**. 클라이언트도 호스트와 **같은 수식을 같은 입력으로 매 프레임
적분**하는 방식으로 바꿨다(연료 소모율과 같은 "같은 입력으로 재계산" 패턴).
해결 과정 전체는 [트러블슈팅 로그](../plans/M3/M3-이탈칸-탑승-월드떨림-해결.md)에 있다.

- **재시뮬 입력 3가지**: 스크롤 속도(`NetworkVariable`) · 설정 SO(공유) · **손잡이 잡은 인원**.
  앞의 둘은 이미 있었고, 빠져 있던 인원을 **`NetworkList<int>`로 복제**하는 것이 이번에 추가됐다
  (판정 진실은 여전히 호스트 배열 — 복제본은 클라 표시 재시뮬의 입력일 뿐이다).
- **관성 램프(§4)는 클라가 분리 관측 시점부터 로컬로 다시 밟는다** — 시작 시차 오차는 수 cm 수준.
- **복제 오프셋은 드리프트 보정 목표로만 쓴다**: 저속 지수 감쇠(`EjectDisplayCorrectionRate`, 기본 3/s)로
  수렴시키고, 오차가 스냅 거리(10 m, 후발 접속 등) 이상이면 즉시 목표로 붙는다
  (`EjectMotionMath.StepDisplayOffset`).
- **효과**: 표시 이동이 복제 도착 타이밍과 무관해져, 프레임당 전진량이 항상 매끈하고 호스트와 같은 경로를 그린다.
- **알려진 트레이드오프**: ① 잡기/놓기 순간 저항 반영이 복제 지연만큼 늦어 수십 cm 드리프트가 생겼다가
  ~1 s에 걸쳐 흡수된다(떨림이 아닌 완만한 수렴) ② 후발 접속으로 이탈 중인 칸을 처음 보면 램프를 0부터
  밟아 최대 ~3 m 드리프트가 생기며 같은 방식으로 수렴한다.
- 손잡이 앵커(§5)·건축물도 같은 `GetEjectOffset`을 소비하므로 **한 소스로 함께 부드러워진다.**

## 7. 권위 분담 (네트워크 §4)

| 요소 | 권위 | 비고 |
|---|---|---|
| 이탈 칸 이동(offset) | 호스트 | `NetworkList<float>` 복제. 클라는 이를 **드리프트 보정 목표**로만 쓰고 표시는 재시뮬(§6.1) |
| 밀림 속도(pushSpeed) | 호스트 | 복제 없음(호스트 로컬 배열). 클라는 같은 수식·같은 입력으로 재계산 |
| 손잡이 잡은 인원(grabberCount) | 호스트 | 판정은 호스트 배열, **표시 재시뮬 입력용으로 `NetworkList<int>` 복제** (§6.1) |
| 손잡이 앵커 존재 | 씬 정적 배치 | InScenePlaced NetworkObject — 스폰/despawn 없음 |
| 손잡이 앵커 위치 | 각 피어 로컬 계산 | 복제 오프셋 기반(CarView와 동일 소스), 위치 복제 없음 |
| 그랩 점유/해제 → grabberCount | 호스트 | 집게 승인 파이프라인 재사용 |
| 저항·소실·잡기 가능 판정 | 호스트 | 순수 로직으로 분리해 EditMode 검증, `IsCarGrabbable`은 복제 데이터 기반 |

## 8. 데이터 스키마 (SO)

전부 `TrainDurabilitySettings`에 들어갔다(별도 `HandrailSettings`는 만들지 않았다). 괄호 안은 현재 값.

| 필드 | 값 | 의미 |
|---|---|---|
| `EjectExtraSpeed` (m/s) | 2 | 스크롤 위에 더해지는 후퇴 속도 — §4의 `targetPush` 구성분. |
| `EjectDeceleration` (m/s²) | 4 | **관성 램프의 감속도** — 분리 직후 0에서 `targetPush`까지 다가가는 비율 (§4). |
| `PullPerGrabber` (m/s) | 6 | 손잡이 1인당 상쇄 속도. |
| `LostDistance` (m) | 45 | 이 거리 넘고 아무도 안 잡으면 영구 소실. |
| `EjectDisplayCorrectionRate` (1/s) | 3 | **클라 표시 드리프트 보정률** — 재시뮬 값을 복제 목표로 수렴시키는 지수 감쇠 계수 (§6.1). 표현 전용이라 게임플레이 판정에 영향 없음. |

`EjectDisplayCorrectionRate`는 에셋에 직렬화되어 있지 않아 현재 코드 기본값 3으로 동작한다 —
튜닝하려면 인스펙터에서 한 번 값을 만져 에셋에 기록시켜야 한다.

## 9. 순수 로직 (EditMode 대상)

`EjectMotionMath`로 분리됐다(`TrainStateLogic`이 아니다). 아래가 실제 API — 원안의
`ComputeNetEjectVelocity`는 램프 도입으로 **속도 계산이 2단계로 쪼개지면서** 이름·시그니처가 바뀌었다.

| 함수 | 역할 |
|---|---|
| `ComputeTargetPushSpeed(scrollSpeed, ejectExtraSpeed)` | 관성을 다 잃었을 때의 목표 밀림 속도 (§4). |
| `StepPushSpeed(pushSpeed, target, deceleration, dt)` | 목표를 향한 관성 램프 한 스텝 (`MoveTowards`). |
| `ComputeNetVelocity(pushSpeed, grabberCount, pullPerGrabber)` | 순 속도 — **램프 후 속도를 받는다**(원안은 scrollSpeed를 직접 받았다). |
| `StepOffset(offset, netVelocity, dt)` | 오프셋 적분, clamp ≥ 0. |
| `IsCarLost(offset, lostDistance, grabberCount)` | 영구 소실 판정. |
| `StepDisplayOffset(display, target, velocity, dt, correctionRate, snapDistance)` | **클라 표시 전용** — 재시뮬 + 드리프트 수렴 + 스냅 (§6.1). |

경계 검증: 0인=후퇴, 임계 인원에서 부호 전환, 슬롯(0) 고정, 소실 조건, 램프의 목표 수렴(상승·하강 양방향),
30 Hz 계단 복제 아래 호스트 경로 추종(드리프트 ±0.3 m)과 프레임 전진량 매끈함(±0.02 m).
현재 `EjectMotionMathTests` 11개.

## 10. 구현 단계

1. **Feature 1** — 이탈 칸/연결부를 타겟 레지스트리에서 즉시 제외(이탈 시 unregister) + IsAlive 방어 + 테스트.
2. **이동 권위 승격** — `_ejectOffsets` 도입, 호스트 시뮬레이션, CarView가 오프셋으로 배치(B 로컬 연출 제거).
3. **손잡이 앵커** — `HandrailAnchor`(IGrabbable Anchor) 스폰/이동/소멸 + grabberCount, 집게 Anchor 모드.
4. **저항 결합** — grabberCount를 이동 시뮬레이션에 연결, 데이터 밸런싱값.
5. **손잡이 표현** — 칸 앞뒤 끝 손잡이 메시(씬).
6. 검증 — EditMode(순수 로직) + 호스트1·클라N 런타임 정성 확인.
