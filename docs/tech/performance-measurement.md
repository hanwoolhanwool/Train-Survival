**Unity 6 게임의 성능 측정 자동화 — 그리고 측정 도구가 거짓말한 다섯 번**

작성일: 2026-09-02 · 갱신: 2026-09-03 (적용·재측정 반영) · 프로젝트: Train Survival (협동 생존 크래프팅 · 1~4인 · PC/Steam) ·

## 요약

아트·렌더링 예산 문서를 세우고 3주간 폴리곤 수를 **네 번**(2026-08-23·27·30·31) 실측해 기록했다.
그런데 **프레임 시간(ms)은 한 번도 잰 적이 없었다** — 착수 47일째까지 0회다.
그 상태로 "무엇을 먼저 최적화할지" 우선순위 7개를 정해 두고 있었다.

측정을 자동화하고 그 순위를 실측으로 검증했다. **결과는 1순위가 적용하면 안 되는 항목이었고, 3순위는
이미 충족돼 있었으며, 최하위였던 7순위가 단독 최대 효과였다.**

| | 값 |
|---|---|
| 병목 판정 | **GPU** (gpu 1.02 > cpuMain 0.86 > cpuRender 0.40 ms) |
| 프레임 시간 | **1.24 ms** — 이 저장소 최초의 ms 기록 |
| 반복 측정 편차 | **0.7~0.8 %** (60초 × 3회) |
| 1순위 GPU Resident Drawer | **cpuMain +16.7 % 회귀 → 적용 불가** |
| **적용한 것** | 섀도우 캐스케이드 4 → 2 → **gpu p95 −6.3 %** · 셰도우 캐스터 **−37~39 %** · 회귀 0건 |
| 산출물 | C# 2,373줄 · node 904줄 · 테스트 23케이스 · 커밋 13개 |

**이 문서에서 가장 중요한 절은 [4.3 측정 도구가 거짓말한 다섯 번](#43-측정-도구가-거짓말한-다섯-번)이다.**
성능 작업의 실제 난이도는 최적화가 아니라 **자기 측정값을 의심하는 데** 있었다.

## 1. 문제 — 자가 없는 채로 순위를 정하고 있었다

아트·렌더링 예산 문서에는 "미확정 · 확인 필요" 목록이 있었다. 6건 중 **4건이 "재는 방법이 없어서"**
남아 있었고, 그 문서가 스스로 적어 둔 말이 문제를 정확히 요약한다.

| 미결 항목 | 문서가 적어 둔 말 |
|---|---|
| 드로우콜 1,110 | "**CPU 바운드인지 GPU 바운드인지 모르는 채로** 최적화 순서를 정하고 있다" |
| 빌드에서의 밀리초 | "지금까지 잰 것은 전부 에디터 게임 뷰의 삼각형 수다" |
| 그림자 패스의 몫 | "우선순위 3·4의 값어치가 여기 달렸다" |
| 타일 교체 스파이크 | "실제로 튀는지는 플레이 검증에서 판정하고" |

우선순위 1(GPU Resident Drawer)은 **드로우콜**을 줄이는 조치이고, 3·4(그림자)는 **GPU**를 줄이는
조치다. **어느 쪽이 병목인지 모르면 둘 중 무엇을 먼저 할지도 정할 수 없다.**

### 1.1 원인은 체크박스 하나였다

`FrameTimingManager`를 호출해 봤다.

| 필드 | 값 |
|---|---:|
| `cpu_main_thread_frame_time_ms` | 0.0008 |
| **`cpu_render_thread_frame_time_ms`** | **0** |
| **`gpu_frame_time_ms`** | **0** |

범인은 `ProjectSettings.asset`의 한 줄이었다.

```yaml
enableFrameTimingStats: 0   # ← 착수 전 상태. 지금은 1 이다
```

**예산 문서가 19일간 답하지 못한 질문이 체크박스 하나에 막혀 있었다.** 켜면 CPU 메인 / CPU 렌더 / GPU 세 값이
채워지고, **셋 중 가장 큰 것이 병목**이다. 이것이 CPU/GPU 바운드 판정의 표준 방법이고 우회로는 없다.

> 비용은 GPU 타임스탬프 쿼리(통상 프레임당 0.05 ms 미만)다. **재지 않아 생긴 공백보다 싸다**고
> 판단해 벤치 빌드 전용이 아니라 **항상 켜기로** 했다 — 벤치 빌드와 배포 빌드의 조건이 갈리면
> "잰 건 그 빌드고 배포는 다른 빌드"라는 새 변수가 생긴다.

## 2. 선택지 — 어디서 잴 것인가

### 2.1 측정 장소

측정 자동화는 정의상 **사람이 창을 보고 있지 않은 상태**에서 돈다. 그 제약이 선택지를 셋 중 하나로 좁혔다.

| 후보 | 자동화 가능? | 실측으로 확인한 이유 |
|---|:---:|---|
| 에디터 편집 모드 | ❌ | `Render` 카테고리 카운터 **697종을 전량 열거**해 확인 — 드로우콜·삼각형·SetPass가 **전부 0**이다. 리소스 계열(`Render Textures Bytes` 등)만 살아 있다 |
| 에디터 플레이 모드 | ❌ | 창 포커스를 잃으면 `Time.frameCount`가 고정된다 — 이 프로젝트에서 이미 확인된 사실이고, 예산 문서도 같은 이유로 물러섰다 |
| **빌드 Player** | ✅ | `Application.runInBackground`로 백그라운드 주행이 성립한다 |

**측정 장소는 사실상 강제됐다.** 남은 선택은 "에디터에서도 눈으로 볼 수 있게 할 것인가"뿐이었고,
개발 중 즉시 피드백을 위해 HUD를 두되 **기록·판정에는 쓰지 않기로** 정했다(포커스 문제로 신뢰 불가).

### 2.2 버린 것 — 마이크로 벤치(L1)

Unity 공식 성능 테스트 확장(`com.unity.test-framework.performance`)은 현업에서 마이크로 벤치의
사실상 표준이다. **도입하지 않기로 했다.**

- 순수 로직이 프레임을 먹는다는 신호가 **아직 하나도 없다** — `Rigidbody` 0개, 물리 쿼리 17건뿐이고
  병목 후보는 드로우콜 1,110 쪽이다.
- 반면 도입하면 `manifest.json` 변경 → **CI Library 캐시 무효화** → asmdef 신설 → CI 잡 추가가 따라온다.
- **순서가 맞지 않는다.** 무엇이 느린지조차 모르는 상태에서 함수 단위부터 재는 것은 거꾸로다.

> 이 결정으로 착수 전 미결이 **7건에서 2건으로** 줄었다. 표준이라고 다 채택하지 않는다는 것이
> 이 절의 요지다 — "L2가 `cpu_main_thread` 바운드를 지목하면 그때 연다"고 조건을 적어 두고 미뤘다.

### 2.3 절대값이 아니라 델타로만 판정한다

측정 머신이 이 PC 하나뿐이다. 에디터·Blender·브라우저가 같이 돈다. GPU 온도에 따라 클럭도 변한다.
**전용 벤치 머신(대형 스튜디오의 표준)은 채택할 수 없었다.**

그래서 판정 규칙을 이렇게 정했다:

> **절대값으로 판정하지 않는다.** 같은 머신에서 연속으로 잰 A와 B의 **차이**로만 판정하고,
> 리포트에 머신·GPU 드라이버·해상도·빌드 종류를 함께 남긴다. 그 전제가 깨지면
> **리포트가 스스로 경고를 띄운다.**

## 3. 결정과 구조

### 3.1 3층 구조 — 층마다 답하는 질문이 다르다

```
스모크 (-smoke)     "게임이 뜨긴 하나?"     빌드 Player · 초~분 단위
   ↓
L2 씬 벤치           "게임이 느려졌나?"      빌드 Player · 로컬 · 분 단위
   ↓ (회귀 검출 시에만)
L3 심층 캡처         "어디가 느린가?"        Profiler .raw · 수동
```

**스모크는 덤으로 얻었다.** 벤치 주행기가 하는 일은 "빌드를 인자로 띄워 Boot → Main → 인게임을
통과시키고, 정해진 시간을 버틴 뒤 종료 코드를 내고 죽는다"인데, **이것은 스모크 테스트의 정의 그 자체**다.
지표 수집을 건너뛰는 분기 하나로 이 저장소에 없던 **자동 부팅 검증**이 같이 섰다.

```bash
TrainSurvival.exe -smoke 30          # 종료 코드 0 = 인게임까지 살아서 들어갔다
TrainSurvival.exe -perfrun forest-day-60s
node tools/perf/compare.js Perf/runs/*.json   # 회귀면 비 0 종료
```

스모크가 잡는 것: 씬 등록 누락 · **`ClosedByRemote`**(프리팹 해시 오염) · `LogType.Exception` · 크래시.
**네 가지 모두 그전까지 사람이 손으로 확인하던 것**이다(PlayMode 테스트는 3개뿐이었다).

### 3.2 어셈블리 단방향 의존을 지키면서 게임 상태를 강제하기

이 프로젝트는 어셈블리 의존이 단방향으로 고정돼 있다(`Utilities ← Core ← Systems ← Gameplay ← UI`).

문제: 주행기는 `Game.Systems`에 있고, **밤으로 바꾸는 기능은 `Game.Gameplay`에 있다.** 주행기가
게임플레이를 직접 부를 수 없다.

해결: **주행기는 무엇을 원하는지만 알리고, 적용은 게임플레이 쪽이 한다.**

```
[Game.Systems]  PerfRunner
                  │  EventBus<PerfRunStartedEvent>.Publish(...)
                  ↓
[Game.Core]     PerfRunStartedEvent  (시간대 · Day · 웨이브 토글)
                  ↓
[Game.Gameplay] PerfScenarioApplier → DayCycleController.ServerJumpTo(day, phase)
                                    → IWaveSpawnToggle.ServerSetSpawnEnabled(true)
```

역방향으로 값을 받아야 할 때(측정 중 몬스터 수)도 같은 원칙을 썼다 — 조회 계약 `IPerfSceneStats`를
**Core에 두어** 구현(Gameplay)과 소비자(Systems)가 만나게 했다.

> **벤치 전용 경로를 만들지 않았다.** 상태 강제는 QA 핫키가 이미 쓰는 서비스만 경유한다.
> 벤치가 실제 플레이와 다른 코드를 타면, 재는 것이 게임이 아니게 된다.

### 3.3 씬 파일을 건드리지 않는다

주행기·적용기·HUD는 **씬에 배치하지 않고 `[RuntimeInitializeOnLoadMethod]`로 인자가 있을 때만 자기 생성**한다.
이 프로젝트에서 씬 YAML 저장은 수천 줄짜리 재정렬 diff를 만든다 — 벤치 하나 때문에 Boot 씬이 매번
바뀌면 **그 리뷰 비용이 벤치의 값어치를 넘는다.**

### 3.4 평균 FPS를 쓰지 않는다

60초 중 1초가 200 ms여도 평균은 거의 움직이지 않는다. **평균은 스파이크를 감춘다.**

| 값 | 쓰임 |
|---|---|
| p50 | 평상시 체감 |
| **p95** | "가끔 버벅인다"의 정체 — **회귀 게이트의 주 판정값** |
| p99 · max | 스파이크 |
| `>33.3ms 프레임 수` | 30 FPS 밑으로 떨어진 절대 개수 |

스파이크는 **인덱스와 시각을 함께** 기록한다. 6.67초 간격으로 규칙적으로 찍히면
(= 타일 교체 주기 40 m ÷ 6 m/s) **범인이 그 자리에서 증명된다.**

## 4. 검증

### 4.1 기준선

개발 빌드를 굽고 60초 × 3회 주행했다. 측정 구간 60초는 **활성 타일 9장이 정확히 한 번 전량 교체되는
길이**다(40 m ÷ 6 m/s × 9 = 60.0).

| 지표 | 낮 (숲 주행) | 밤 (Day 5 · 몬스터 12마리 상시) |
|---|---:|---:|
| **병목** | **GPU** | **GPU** |
| gpu p50 / p95 | 1.026 / 1.095 | 0.991 / 1.035 |
| cpuMain p95 | 1.115 | 1.169 |
| cpuRender p95 | 0.512 | 0.515 |
| 드로우콜 p50 | 1,032 | 1,011 |
| SetPass p50 | 32 | **54** |
| 삼각형 p50 | 1,085,838 | 1,035,055 |
| GC/프레임 | 7,218 B | **8,786 B** |
| 33 ms 초과 프레임 | **0** | **0** |
| 측정 프레임 수 | 48,251 (**1.24 ms/frame**) | 51,002 (1.18 ms/frame) |
| **반복 3회 편차** | **gpu 0.8 % · cpu 0.7 %** | gpu 0.6 % |

측정 환경: RTX 4060 Ti · Ryzen 5 7500F · 1920×1080 · 개발 빌드 · Windows 11.

**편차 1 % 미만**이 이 자의 신뢰도다. 시드 고정·해상도 고정·워밍업 300프레임 폐기·3회 중앙값이
실제로 들었다는 뜻이고, 그래서 회귀 게이트를 착수 시 +10 %에서 **+5 %로 조일 수 있었다**
(노이즈의 6배 = 거짓 실패 없이 5 % 회귀를 잡는 폭).

### 4.2 §7 우선순위를 실측으로 판정했다

설정을 바꾸고 → 빌드하고 → 3회 주행하고 → 되돌리는 절차를 항목마다 반복했다.
먼저 **대조군**(아무것도 바꾸지 않고 다시 굽고 다시 잰 것)이 기준선과 **−2.1 %~+0.8 %**로 일치하는 것을
확인해 환경 드리프트를 배제했다.

| 실험 | gpu p95 | cpuMain p95 | 드로우콜 | 판정 |
|---|---:|---:|---:|---|
| **캐스케이드 4→2 + TilesAhead 5→3** | **−14.7 %** | **−6.2 %** | −34.9 % | ✅ 채택 권고 |
| TilesAhead 5→3 단독 *(문서 7순위)* | −9.5 % | −3.5 % | −25.9 % | ✅ **단독 최대** |
| 캐스케이드 4→2 단독 *(문서 4순위)* | −7.5 % | −3.1 % | −8.2 % | ✅ 순수 이득 → **적용함**(§4.7에서 −6.3 %로 재확인) |
| 포인트 라이트 그림자 *(문서 3순위)* | — | — | — | ✅ **이미 충족돼 있었다** |
| **GPU Resident Drawer** *(문서 **1순위**)* | −9.4 % | **+16.7 %** | −74.8 % | ❌ **적용 불가** |

**1순위와 7순위가 자리를 바꿨다.**

- **1순위가 회귀인 이유**: 드로우콜은 1,032 → 260으로 **−74.8 %** 줄었는데 **프레임은 나빠졌고 병목이
  GPU에서 CPU로 옮겨갔다.** GPU 구동 렌더링의 준비 비용(인스턴스 데이터 업로드·컬링 디스패치)이
  드로우콜 제출을 아낀 몫보다 크다 — **드로우콜 1,000개 규모에서는 수지가 맞지 않는다.**
  문서가 근거로 든 "드로우콜 1,110이 그대로다"라는 **진단은 맞았지만, 그것이 프레임 시간의 원인이 아니었다.**
- **3순위가 이미 충족된 이유**: 프리팹·씬의 포인트 라이트 **8개 전부** 그림자가 꺼져 있었다.
  문서의 "미착수"가 사실과 달랐고, 그림자 비용은 전부 디렉셔널 라이트 몫이었다.

### 4.3 측정 도구가 거짓말한 다섯 번

**이 절이 이 작업에서 가장 값비쌌던 부분이다.** 세 번 모두 "그럴듯한 개선"으로 보였다.

#### ① Unity 6에는 `Draw Calls Count`라는 카운터가 없다

첫 3회 주행에서 드로우콜이 **전부 0**으로 기록됐다. **예외도 경고도 없었다.**

`ProfilerRecorder`는 **없는 이름을 줘도 예외를 던지지 않고 계속 0을 돌려준다.** 그래서 60초를 세 번
주행하고 결과 파일까지 남긴 뒤에야 알았다.

카운터 **6,368종을 전량 열거**해 확인한 결과, 드로우콜은 제출 경로별로 쪼개져 있었다:

| 실제 이름 | 값 |
|---|---:|
| `SRP Batcher Draw Calls Count` | **1,017** |
| `Standard Draw Calls Count` | 10 |
| `BRG Draw Calls Count` | 0 |

네 경로를 합산한 **1,027**이 예산 문서의 에디터 게임 뷰 값 **1,110**과 맞아떨어져,
합산이 옳다는 것이 **교차 검증**됐다.

#### ② "GPU −70.8 % 개선"은 화면이 비어 있었던 것

`m_GPUResidentDrawerMode: 0 → 1`만 켜고 재니 **GPU가 70.8 % 빨라졌다.** 그런데 같은 결과에서
삼각형이 **1,085,838 → 2,450 (−99.8 %)**이었다.

**빨라진 게 아니라 아무것도 안 그려진 것이다.**

| 구성 | SRP Batcher | BRG | 삼각형 | gpu p50 |
|---|---:|---:|---:|---:|
| 기본 | 1,013 | 0 | 1,080,832 | 1.02 ms |
| Resident Drawer만 | **0** | **0** | **2,450** | **0.28 ms** ← 안 그려서 빠른 것 |
| Resident Drawer + `m_BrgStripping: 2` | 0 | **249** | 1,084,642 | 0.94 ms |

범인은 `GraphicsSettings.asset`의 `m_BrgStripping: 0` — "Entities Graphics가 있을 때만 BRG 셰이더
변형을 유지"라는 뜻이다. 이 프로젝트는 DOTS를 쓰지 않으므로 **빌드에서 BRG 변형이 스트리핑되고,**
Resident Drawer는 BRG로 그리므로 **그릴 셰이더가 없다.**

> 이것을 못 잡았다면 "1순위 최적화로 GPU 70 % 개선"이라고 보고하고, **빈 화면이 나오는 빌드를
> 배포할 뻔했다.** 삼각형 수를 함께 보지 않았으면 놓쳤을 것이다.

#### ③ 4K를 쟀다고 믿을 뻔했다

GPU 부하 상태에서 판정이 유지되는지 보려고 `-screen-width 3840`을 넘겨 측정했다.
**수치가 1080p와 완전히 똑같이 나왔다.**

확인해 보니 **내가 짠 주행기가 시나리오 값으로 해상도를 조용히 덮어쓰고 있었다.** 결정론상
시나리오가 이기는 것이 맞지만(창 크기가 GPU 시간을 지배하므로 실행자가 바꾸면 비교가 불가능해진다),
**침묵한 것이 문제였다.** 수치가 우연히 똑같아서 알아챘지, 아니었으면 4K 측정값으로 읽었을 것이다.

→ 실행 해상도가 시나리오와 다르면 **경고를 찍도록** 고쳤다.

#### ④ 도구가 노이즈 위에서 "회귀 2건"이라고 단정했다

최적화를 적용하고 검증하는데 이런 표가 나왔다.

```
gpu p95        1.095   2.842   +159.6 %  [XX] 기준선 +5 % 초과
cpuMain p95    1.115   2.231   +100.1 %  [XX] 기준선 +5 % 초과
셰도우 캐스터    225     141     -37.3 %  [--]
   반복 편차: gpu p95 206.2 % · cpuMain p95 25.9 %
X 회귀 2건
```

**"회귀 2건"만 보면 이 최적화는 실패다.** 그런데 두 가지가 어긋난다 — **반복 편차가 206 %**
(정상 0.8 %)이고, **셰도우 캐스터는 의도대로 −37 % 줄어 있다.**

렌더 워크로드는 줄었는데 시간만 3배다. **같은 일을 더 느리게 하고 있다** — 변경이 나쁜 게
아니라 머신이 느려진 것이다. 확인해 보니 측정 중 다른 프로세스가 CPU 코어 2개를 쓰고 있었다.

**노이즈가 임계보다 크면 통과든 실패든 우연이다.** 편차 값 자체는 처음부터 출력하고 있었지만
표의 판정 옆이 아니라 아래에 있었고, **나조차 판정을 먼저 읽었다.**

→ 반복 편차가 게이트 임계를 넘는 지표는 **판정을 무효로 돌리고**, 하나라도 있으면 회귀 여부를
말하지 않는다. 종료 코드는 **2(비교 불가)** — 0(통과)도 1(회귀)도 거짓말이기 때문이다.

```
? 판정 불가 — 반복 편차가 게이트 임계보다 크다 (gpu p95, cpuMain p95)
  이 실행에서는 통과든 회귀든 우연이다...
  렌더 카운터는 머신 부하와 무관하니 그쪽만 참고할 수 있다.
```

#### ⑤ 설정을 바꾸고 재빌드를 빠뜨렸다

재측정을 돌리면서 URP 에셋만 되돌리고 **빌드를 안 했다.** 즉 옛 빌드로 "새 설정"을 쟀다.
gpu −0.7 %라는 밋밋한 결과가 나왔는데, **셰도우 캐스터가 212 → 214로 안 줄어** 들통났다.
적용됐다면 130 대여야 한다.

→ 재측정 스크립트에 **빌드 전 에셋값 검사**와 **측정 후 셰도우 캐스터 출력**을 넣었다.

#### 이 다섯에서 얻은 규칙

> **값이 0이거나 극적으로 좋아지면, 개선을 의심하기 전에 측정을 의심한다.**
> 드로우콜이 줄었다면 **삼각형도 함께 봤는가**, 카운터 이름이 실제로 존재하는가,
> 내가 넘긴 인자가 실제로 적용됐는가, **반복 편차가 임계보다 작은가**,
> 그리고 **내가 바꾼 것이 실제로 빌드에 들어갔는가.**

**다섯 번 모두 렌더 카운터가 진실을 말해줬다.** 드로우콜·삼각형·셰도우 캐스터는 머신 부하와
무관하므로, 시간 지표가 거짓말할 때 대조군 역할을 한다. 그래서 게이트에서 제외하고
**정보 열로 항상 표시**한다 — 판정하지 않는 값이 판정을 구한 셈이다.

지금은 결과 JSON이 **머신·드라이버·해상도·빌드 종류·강제 조건·몬스터 수**를 함께 싣고,
비교 도구가 기준선과 다르면 **표 위에 경고를 먼저 띄운다.**

### 4.4 야간 측정 — 스스로 적어 둔 한계를 지웠다

낮 주행만으로 순위를 뒤집는 것은 위험하다고 판단해, 문서에 **"야간에서 부호가 뒤집힐 수 있다"**는
한계를 명시해 두었다. 그리고 야간 시나리오를 만들어 실제로 확인했다.

| 실험 (야간 기준선 대비) | gpu p95 | cpuMain p95 | 결론 |
|---|---:|---:|---|
| 캐스케이드 2 + TilesAhead 3 | −13.9 % | −8.1 % | 낮과 같다 |
| GPU Resident Drawer | −8.9 % | **+10.6 %** | **여전히 회귀** |

**가설은 틀렸다.** "객체가 늘면 Resident Drawer가 유리해진다"고 봤는데, 몬스터 12마리로는
드로우콜이 늘지 않는다(1,036 → 1,011로 오히려 감소).

부수적으로 **밤이 낮보다 가볍다**는 것도 확인됐다(gpu −3.6 %). 해가 없어 그림자 지오메트리가 줄고,
몬스터 12마리가 그 몫을 채우지 못한다. 대신 밤은 다른 것을 압박한다 — **SetPass +68.8 % · GC +21.7 %**.

### 4.5 마커가 타일 교체 비용을 분리했다

게임 고유 `ProfilerMarker` 4종을 심어 스파이크의 범인을 특정할 수 있게 했다.

| 마커 | p50 | max |
|---|---:|---:|
| `Game.TileStream.Spawn` | 0.000 | **1.537 ms** |
| `Game.TileStream.Update` | 0.007 | 1.671 ms |
| `Game.WorldScroll.Update` | 0.001 | 0.057 ms |
| `Game.Wave.Spawn` | 0.000 | 0.075 ms |

**타일 교체 프레임은 평소의 약 2배(1.2 → 2.7 ms)가 된다.** 실재하지만 33 ms 근처도 아니라,
예산 문서가 걱정하던 "분산 활성화(프레임당 N개)"는 필요 없다는 것이 확정됐다.

> `Game.Wave.Spawn`이 대부분 0인 것은 **측정 구간 내내 몬스터가 cap이라 스폰이 없었기 때문**이고,
> 몬스터가 죽은 실행에서만 0.075 ms가 찍히는 것을 확인해 **이름 오류가 아님을 교차 검증**했다.
> ①의 교훈을 그대로 적용한 것이다.

### 4.6 해소된 미결

| 미결 | 답 |
|---|---|
| CPU 바운드인가 GPU 바운드인가 | **GPU** |

| 빌드 드로우콜 vs 에디터 1,110 | **1,032** — 사실상 같다. **빌드가 더 배칭해 주지 않는다** |
| 그림자 패스의 몫 | 캐스케이드 4→2로 셰도우 캐스터 **−37~39 %** · 삼각형 −12~14 % · gpu **−6.3 %**(§4.7 확정치). "지오메트리의 절반"까지는 아니다 |

### 4.7 적용 — 자를 만든 값어치가 여기서 증명됐다

판정만 하고 멈추면 자는 자일 뿐이다. **캐스케이드 4→2를 실제로 적용하고 다시 쟀다.**

그런데 **기준선과 비교하니 gpu p95 −25.6 %**가 나왔다. 4차 실험값(−7.5 %)의 3배가 넘는다.
너무 좋아서 의심스러웠고, **캐스케이드 4 빌드를 다시 구워 대조군을 세웠다.**

| 비교 방식 | 낮 gpu p95 | 밤 gpu p95 |
|---|---:|---:|
| 기준선(다른 날 · 다른 빌드) 대비 | −25.6 % | −25.0 % |
| **대조군(같은 코드 · 캐스케이드 4) 대비** | **−6.3 %** | **−6.6 %** |

**차이 약 20 %는 캐스케이드와 무관한 환경 요인**(시간대 · GPU 클럭 · 빌드 차이)이었다.
§2.3에서 *"절대값이 아니라 같은 머신에서 연속으로 잰 델타로만 판정한다"*고 정해 둔 규칙이
여기서 실제로 값을 했다 — **대조군을 안 세웠으면 4배 부풀린 수치를 커밋 메시지와 이 문서에
박았을 것이다.**

#### 무엇과 무엇을 비교했는가

"수정 전"이 어느 시점인지가 결과 해석을 바꾸므로 정확히 적는다.
**대조군은 작업 시작 전 원본이 아니라, 지금 코드에서 캐스케이드만 4로 되돌린 빌드다.**

| | 대조군 | 적용본 |
|---|---|---|
| `m_ShadowCascadeCount` | **4** | **2** |
| 그 외 코드 | 동일 (측정 인프라·`ProfilerMarker` 전부 포함) | 〃 |
| buildGUID | `b3d3c14d` | 낮 `217c64f1` · 밤 `71f7c213` |
| 낮 실행 | 09-03 **08:38~08:40** | 09-03 **02:48~02:50** |
| 밤 실행 | 09-03 **08:42~08:45** | 09-03 **08:55~08:59** |

두 빌드 사이 `Assets/` 변경은 **캐스케이드 한 줄뿐**이다(그 구간의 유일한 커밋은 `tools/perf/*.js`라
빌드에 들어가지 않는다). 그래서 델타를 캐스케이드에 귀속할 수 있다.

> **낮과 밤의 통제 수준이 다르다.** 밤은 대조군과 적용본 사이가 **약 10분**이라 제대로 통제된
> 비교지만, **낮은 약 5시간 50분이 벌어져 있다.** 낮 적용본을 먼저 재고 대조군을 나중에
> 세웠기 때문이다. 그래서 **−6.3 %의 일차 근거는 밤(−6.6 %)이고, 낮은 보조 증거**다.
> 두 값이 거의 같고 셰도우 캐스터가 양쪽 −37~39 %로 일치하므로 결론은 흔들리지 않지만,
> **"같은 창에서 쟀다"고 말할 수 있는 것은 밤뿐이다.**

> **4차 실험값(−7.5 %)과 여기 −6.3 %는 빌드가 다르다.** 4차는 `ProfilerMarker`를 심기 전
> 빌드였고, 여기는 심은 뒤다. 두 값을 나란히 볼 때 감안해야 한다.

**최종 확정치**

| 지표 | 낮 | 밤 |
|---|---:|---:|
| gpu p95 | **−6.3 %** | **−6.6 %** |
| 셰도우 캐스터 | 225 → 141 (−37.3 %) | 212 → 130 (−38.7 %) |
| 삼각형 | −13.6 % | −12.2 % |
| 드로우콜 | −7.5 % | −9.4 % |
| cpuMain p95 | +3.0 % (편차 3.2 % 안) | −4.3 % |
| 33 ms 초과 프레임 | 증가 없음 | 증가 없음 |

기준선도 이 상태로 갱신했다. 갱신 사유("최적화로 좋아졌다")를 커밋 메시지에 적는 것이
이 프로젝트의 규약이고, **나빠진 뒤 조용히 갱신하면 게이트가 무력화되기 때문**이다.

## 5. 남은 한계

**① 프레임이 1.24 ms라 지금은 어느 것도 병목이 아니다.**
이 문서의 순위는 "그 조건에서의 상대 효과"이지 "지금 급한 일"이 아니다. 성능 작업을 더 하는 것보다
콘텐츠를 채우는 것이 우선이라는 판단은 이 측정 **덕분에** 근거를 갖게 됐다.

**② 아직 안 잰 것 — 기차역·5지역 순회.**
시나리오는 에셋만 추가하면 늘어나도록 만들어 두었지만(시간대·Day·웨이브·정착 시간이 전부 필드),
실제로 재지는 않았다.

**③ 육안 확인을 아직 안 했다.**
캐스케이드 2는 적용했지만(§4.7) **근거리 그림자 해상도가 열차 갑판에서 계단현상으로 보이는지는
아직 눈으로 확인하지 않았다.** 이 항목만은 수치로 답할 수 없고, 이상하면 설정 한 줄로 되돌린다.

**③′ TilesAhead 5→3 은 보류했다.**
gpu −9.5 %로 **단독 최대 효과**였지만 전방 시야가 **200 m → 120 m**로 줄어 몬스터 사전 인지에
직결된다. 성능이 아니라 게임플레이 판단이고, 안개 거리와 함께 정해야 한다.

**④ GC 7,218 B/프레임의 정체를 모른다.**
낮 주행 3회에서 정확히 같은 값이 나온다. 게임 코드인지 개발 빌드의 프로파일러 자체 할당인지
구분되지 않았다. 게이트는 지금 값을 봉인해 **악화만 막고 있다.**

**⑤ CI에 얹지 못했다.**
"스모크는 GPU 없이도 도니 CI에 넣을 수 있다"고 적었다가 **플랫폼을 빠뜨린 것을 발견했다** —
산출물은 `StandaloneWindows64`이고 CI는 `ubuntu-latest`다. Windows 러너 추가는 값어치보다 비싸
로컬 게이트로 남겼다.

**⑥ 측정 머신이 하나다.**
절대값은 다른 하드웨어로 이전되지 않는다. 이 자는 **같은 머신에서의 델타**에만 유효하고,
리포트가 그 사실을 스스로 밝히게 해 두었다.

**⑦ 대역폭을 재지 못한다 — 이 자의 사각지대다.**
이 프로젝트의 성능 결정을 훑어보니, **설계 단계에서 내린 것 중 절반이 대역폭 근거**였다:

| 결정 | 아끼는 것 | 근거로 적힌 말 |
|---|---|---|
| 배경에 `NetworkObject` 0개 | 대역폭 | 붙이면 대역폭이 **장식 개수에 비례**한다 |
| 정지 자원의 상시 위치 동기화 없음 | 대역폭 | "자원 수가 늘어도 대역폭이 거의 증가하지 않는다" |
| 낮/밤·지역을 누적 시간의 순수 함수로 | 대역폭 | "**추가 복제가 0**이다" |

셋 다 **한 번도 실측된 적이 없고, 이 도구로도 못 잰다** — NGO 통계 카운터를 수집하지 않기
때문이다. as-built 명세도 *"4인 세션 기준 대역폭 실측 전"*이라고 미결로 적어 두었다.
프레임 시간을 재는 자를 만들었더니, **재지 못하는 축이 무엇인지가 오히려 또렷해졌다.**

**⑧ 과거 최적화는 소급 검증하지 않았다.**
이 저장소의 `perf` 커밋 4건은 **전부 폴리곤 감축**이고(Mesh LOD · 소스 감축 · LOD3 · LOD0 승격),
넷 다 **삼각형 수로만 기록**돼 있다. 지금 도구로 되돌려 재면 ms 환산이 가능하지만 하지 않았다 —
프레임이 1.2 ms인 지금은 *"폴리곤을 얼마나 줄였나"*보다 *"줄인 것이 ms로 얼마였나"*가 더
궁금한 질문인데, **그 답이 '거의 0'일 가능성이 높고** 그렇다면 앞으로 폴리곤 감축의 우선순위를
낮춰야 한다는 뜻이 된다. 실제로 이번 측정에서 **삼각형 −13.6 %가 gpu −6.3 %**였고,
4차의 TilesAhead도 **삼각형 −15.6 %에 gpu −9.5 %**였다 — **둘은 선형이 아니다.**
