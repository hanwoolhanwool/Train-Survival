## 1. 한눈에 보는 프로젝트

## 2. 개발 6원칙

모든 기능 구현 전에 상기할 것. 위반 시 후반에 되돌리기 매우 어렵다.

1. **멀티플레이 우선 설계.** "일단 로컬로 만들고 나중에 멀티를 붙이자"는 금지 패턴이다 (네트워크 문서 §7). 특히 열차 연쇄 이탈·집게 물리는 나중에 동기화를 끼워 넣을 수 없다.
2. **1인 플레이 = 혼자 호스트인 세션.** 싱글/멀티 코드 경로를 나누지 않는다. 게임 시작은 항상 `ServiceLocator.Get<INetworkSessionService>()`의 `StartHost()`.
3. **상태 변경은 호스트에서만.** 게임 상태(자원·열차·몬스터·Day)의 진실은 호스트가 소유하고, 클라이언트는 요청·표현만 담당한다 (§4 권위 분담표).
4. **인프라 경유.** 스폰/소멸은 `PoolManager.Spawn/Despawn`(네트워크 오브젝트는 `PooledNetworkPrefabHandler` 경유로 동일 규칙 유지), 시스템 간 통신은 `EventBus<T>`(권위/로컬 표현 이벤트 구분), 전역 서비스는 `ServiceLocator`.
5. **C# 9.0 한계 준수.** file-scoped namespace 등 C# 10+ 문법 금지. 어셈블리 의존성은 단방향(`Utilities ← Core ← Systems ← Gameplay ← UI`), `Game.Core`는 netcode 무의존 유지.
6. **열차는 움직이지 않는다.** 모든 게임플레이 오브젝트(플레이어·몬스터·건축물·투사체·로프)는 열차 원점 고정 좌표계에서 시뮬레이션·동기화한다. 속도감·가감속·초가속 연출은 전부 월드 스크롤 속도(호스트 권위 `NetworkVariable`) 하나로 표현한다. 지상 오브젝트는 스크롤 속도만큼 반대로 이동(컨베이어), 지형은 타일 스트리밍 + 풀링 (네트워크 문서 §4.1).

## 4. 권위 분담표 (요약)

구현 중 "이 판정은 어디서 하지?"가 생기면 이 표를 따른다. 상세 근거는 네트워크 문서 §4.

| 상태/판정 | 소유자 |
|---|---|
| 자기 캐릭터 이동/시점 | 각 클라이언트 (소유자 권위) |
| 원격 플레이어 위치 표시 | 소유자 클라이언트 (수신 측은 스냅샷 보간으로 표현만) |
| 사격 명중 판정 | 쏜 클라이언트 (로컬 레이캐스트 → 호스트 보고) |
| 데미지 적용·사망 확정 | 호스트 |
| 몬스터 AI·스폰·웨이브 | 호스트 |
| 집게 그랩 확정·끌기 물리 | 호스트 (발사·명중 연출은 로컬 선반영) |
| 공유 인벤토리·자원 (연료/탄약/식량) | 호스트 (요청→승인) |
| 개인 인벤토리 (핫바 소지품) | 호스트 — 증감 확정은 호스트, 잔량은 `NetworkVariable` 동기화 (기획서 §3.4) |
| 열차 상태 (칸·파괴·연쇄 이탈·속도) | 호스트 |
| 월드 스크롤 속도 (= 체감 열차 속도) | 호스트 (`NetworkVariable` 단일 값) |
| Day·날씨·지역 전환 | 호스트 |

**EventBus 권위 규약**: 상태를 변경하는 구독자는 **권위 이벤트**(호스트 확정 후 발행)만 구독한다. 연출·UI는 **로컬 표현 이벤트**를 즉시 발행/구독해도 된다. 이벤트 타입 XML 주석에 어느 쪽인지 명시하고, 애매하면 권위 이벤트로 취급한다 (아키텍처 규칙 §3).

**호스트 → 소유자 위치 개입 규약** (네트워크 문서 §4.2): 호스트 권위 이벤트가 플레이어 위치를 움직여야 할 때(칸 이탈, 넉백, 붙잡힘) —
- **임펄스형** (넉백, 낙하 시작): 호스트가 소유자에게 임펄스 RPC → 소유자가 로컬 적용. 권위는 소유자 유지.
- **구속형** (붙잡혀 끌려감, 처형 연출): 일시적으로 호스트 구동 상태(`Grabbed`/`Carried`)로 전환, 해제 시 소유자 권위 복귀. 상태 전환은 호스트가 확정하고 권위 이벤트로 전파.
- **상시 외력형** (지상 컨베이어 밀림): 소유자 클라이언트가 월드 스크롤 속도 `NetworkVariable`을 읽어 매 프레임 로컬 적용. RPC 없음, 권위는 소유자 유지.

## 5. 개발 로드맵

리스크가 큰 것부터 소진하는 순서다. 네트워크 문서 §6.4의 "집게 수직 슬라이스 최우선" 결정을 반영했다.
각 마일스톤은 **항상 호스트 1 + 클라이언트 1 구성으로 검증**한다 (원칙 1·2).

### M1 — 집게 수직 슬라이스 (최우선)

프로젝트 최고 리스크(집게의 네트워크 손맛, 네트워크 문서 §6.3)를 가장 먼저 소진한다.

- **범위**: 열차(기관차 + 2칸 = 총 약 40 m, 원점 고정) + 월드 스크롤 기반 지형(직선 트랙) + 1인칭 플레이어 이동/시점 + 집게 1단계 발사→명중→릴 회수→자원 획득. 호스트 1 + 클라이언트 1. 조작·수치·검증 기준의 상세는 [수직 슬라이스 스펙](../design/Train-Survival-수직슬라이스-스펙.md)이 확정한다.
- **핵심 구현 지침**:
  - **처음부터 월드 스크롤 구조로 제작한다** (원칙 6, 네트워크 문서 §6.4). 좌표계는 이후 전환 비용이 가장 큰 결정이므로 프로토타입도 확정 구조를 따른다.
  - 플레이어 이동 컴포넌트는 §4의 개입 상태 머신(소유자 권위 ↔ 호스트 구동) 골격을 포함해 작성한다 — M1에서는 상태 전환이 일어나지 않아도 구조를 먼저 깐다.
  - 발사음·로프 발사·명중 훅 이펙트는 입력 즉시 로컬 재생 (지연 0).
  - 끌려오는 위치는 호스트를 따르되, 로프 탄성 연출로 시작 지연(30~80ms)을 시각적으로 흡수.
  - 미스 페널티(릴 회수 수 초, 기획서 §3.2 확정)를 이 단계부터 포함 — 손맛 평가에 페널티 텐션이 필수.
- **완료 기준**: 슬라이스 스펙 §3의 손맛 검증 기준(정량 Q1~Q5 + 정성 블라인드 테스트)을 통과한다. 미달이면 연출 처방 개선을 반복하고, 그래도 미달이면 Fusion 2 전환 조건(네트워크 문서 §3.3)을 검토한다 — 단, 이 제약은 스택 무관하게 발생하므로 연출 처방을 먼저 소진할 것.
- **진행 상태 (2026-07-22 갱신)**: **M1 완료** — 구현 완료 · 정량 검증(Q1~Q5, 프로파일 ②·③) 완전 종결 · **정성 블라인드 테스트 통과** (2026-07-22).
  - 범위 전체(집게 파이프라인·월드 스크롤/타일/자원·플레이어 이동·기관차+2칸 고정 구성·HUD·EditMode 테스트)가 커밋됐고, 실제 구현 구조는 [as-built 명세 3편](../specs/README.md)(집게·월드·플레이어)이 기록한다. 네트워크 §8 미결이던 누적 스크롤 오프셋·지상 자원 위치 동기화는 명세대로 해소·구현됐다.
  - 스펙 원안 대비 확장 3건: ① 실패(빗나감·거부·취소) 시 훅이 즉시 소멸하지 않고 총구로 되감겨 복귀하는 연출 ② 발사·견인 모습의 비소유 클라이언트 브로드캐스트 ③ 미스 브로드캐스트 — 코스메틱 재시뮬레이션이 경계 사례에서 "명중"으로 재현해 1.5 s 동안 대상에 붙어 있던 화면 불일치를 해소 (2026-07-21). 몬스터 그랩은 `IGrabbable` 인터페이스만 준비된 상태다 (M5 확장 대상).
  - **정량 실측 결과 — 프로파일 ② (RTT 60 ms ± 10, 클라이언트 측, 통과 판정 기준)**: **Q1** 전 발사 Δ0 프레임 통과 · **Q2** 평균 67~72 ms (57~85) ≪ 예산 250 ms 통과 · **Q3** 전 견인 워프/역행 0 통과 · **Q4** 101발사 · 거부 0 = 불일치율 0 % (표본 100회+ 충족) **통과** · **Q5** 호스트 측 100발사 계측에서 Δ0 · 워프/역행 0 · 거부 0으로 로컬 체감과 동일 **통과** (호스트 표본은 `LocalSendRpcTarget` 경유·Q2 0 ms로 프로파일 ② 표본과 분리 집계). 계측은 `HarpoonSliceMetrics` 허브 + UTP Network Simulator(순수 클라이언트에만 자동 적용하는 `NetworkLatencyProfileDriver`)로 수행 — 기존 `DebugSimulator`는 NGO 2.x에서 무효라 Multiplayer Tools 패키지를 도입했다. 중복 시뮬레이터 제거(하단, 467a08f) 후 재계측에서도 Q2 평균 66 ms (57~76, n=23)로 동일 대역 — 기존 프로파일 ② 수치의 유효성을 교차 확인했다.
  - **프로파일 ③ (RTT 120 ms ± 20 + 로스 2 %, 참고 계측)**: Q2 평균 125 ms (113~135)로 프로파일 정상 적용 확인, 워프 0 유지. 단 **견인 5회 중 초반 2회에서 역행 총 3프레임 감지** (최대 프레임 이동 0.16~0.19 m, 이후 3회 정상) — 로스 시 30 Hz 견인 스냅샷 유실을 짧은 보간 버퍼가 흡수하지 못한 것으로 추정. Q3 기준("③에서도 역행 없음")의 엄격 적용 시 미달이나 표본 5회·비연속·미세 규모라 **연출 처방(견인 보간 버퍼 확대) 후보로 기록**하고 정량 파트는 종결로 간주한다. 단 이 계측은 Boot 씬 시뮬레이터 중복 부착 상태(하단)에서 수행됐다. → **정상 환경 재계측으로 종결 (2026-07-22)**: 미해결 이슈 수정 반영 상태에서 프로파일 ② Q2 평균 72 ms (64~85, n=33) · 워프/역행 0, 프로파일 ③에서도 역행 미재현 — 기존 역행은 중복 시뮬레이터 계측 아티팩트로 판단, 연출 처방 불필요.
  - **해소된 이슈**: Boot 씬 `NetworkSimulator`·`NetworkLatencyProfileDriver` 중복 부착 (ce0156c 유입) — 빈 프리셋의 두 번째 시뮬레이터가 같은 UTP 시뮬레이터 스테이지를 함께 조작해 인공 지연이 비정상 적용됐고, **원격 플레이어 캐릭터가 이동 시 순간이동하던 문제의 원인**으로 확인. 1세트만 남기고 제거(467a08f)해 증상 해소, 프로파일 ② 재계측으로 정상 적용 확인.
  - **남은 검증**: **없음 — 정성 블라인드 테스트 통과로 완료 기준 전부 충족 (2026-07-22)**. 호스트/클라이언트를 모르는 상태로 양쪽을 번갈아 플레이, 지연·이질감 없음 응답 (슬라이스 스펙 §3.3 통과 기준 충족). **미해결 이슈 4건은 해소됐다** (2026-07-21, 가이드 v1.11): ① 총구 시차 → 조준점 수렴 발사 ② SphereCast 초기 겹침 관통 → 캐스트 전 겹침 검사 ③ 게스트 그랩 확정 순간이동 → 예측 고정(A, B는 롤백) ④ 세션 종료 어설션 → Multiplayer Tools 패키지 원인 확정·에디터 워크어라운드. 프로파일 ③ 견인 역행은 수정 반영 상태 재계측에서 미재현으로 종결 (2026-07-22) — 상세는 as-built harpoon §11.

### M2 — 코어 루프 (낮/밤 1사이클)

- **범위**: Day 타임라인(낮→밤→Day+1) + 밤 몬스터 웨이브(호스트 AI, 소수) + 기본 총기 1종(리볼버) + **통합 핫바 5칸(무기+자원, 자유 배치) + 엔진 연료 투입(기획서 §3.4)** + 연료 소모→감속(= 월드 스크롤 속도 하향).
- **핵심 구현 지침**:
  - 자원 흐름은 **채집 → 개인 인벤토리 → 엔진 투입 → 연료 충전** (기획서 §3.4, v0.3): 획득 즉시 연료 충전이 아니다. 개인 인벤토리 증감도 호스트 확정 (네트워크 문서 v1.7 §4), 잔량은 `NetworkVariable` 동기화. 엔진 투입은 요청 RPC → 호스트가 (차감 + 충전) 원자적 확정.
  - 몬스터 이동은 **NavMesh가 아닌 커스텀 조향** (네트워크 문서 §4.3 확정): 지상 = 열차 향 조향 + 국소 회피 + 컨베이어 변위 가산, 열차 위 = 칸 웨이포인트 그래프. 이동속도 > 스크롤 속도 제약을 몬스터 데이터로 강제.
  - 몬스터 동기화는 처음부터 10~15Hz + 클라이언트 보간으로 구현 (풀 틱 동기화로 시작하지 말 것, 네트워크 문서 §6.2).
  - 몬스터 스폰은 `PoolManager` 프리웜 + `PooledNetworkPrefabHandler` 경유.
  - 사격: 로컬 레이캐스트 판정 → 호스트 보고 → 호스트가 데미지·사망 확정 → 권위 이벤트 발행.
  - **동시 존재 몬스터 상한을 이 단계에서 계측·확정**하고 기획에 피드백한다 (미결 사항).
- **완료 기준**: 2인이 낮 채집 → 밤 방어 → Day+1 루프를 끊김 없이 반복할 수 있다.
- **진행 상태 (2026-07-24 갱신)**: **시스템 구현 완료 · 완료 기준(2인 루프 검증) 미통과** — M2 범위 6개 항목이 모두 코드 + EditMode 테스트까지 커밋됐고, as-built 명세 5편([cycle](../specs/cycle/day-night-cycle.md)·[monsters](../specs/monsters/wave-and-steering.md)·[combat](../specs/combat/revolver-fire.md)·[inventory](../specs/inventory/hotbar.md)·[fuel](../specs/world/fuel-loop.md))으로 실제 구현 구조를 기록했다. 이후 커밋(엔진 투입 든 칸 소모·몬스터 속도 하향·발사 프레임 정합 등)은 이 시스템들 위의 버그 수정 단계.
  - **구현 완료 내역**: ① Day 타임라인(`DayCycleController` — 호스트 누적 시간 `NetworkVariable` + 각 피어 순수 파생) ② 밤 웨이브(`MonsterWaveSpawner` + 호스트 조향 AI `MonsterAgent`, 12Hz 스냅샷 보간, `PoolManager`+NGO 스폰) ③ 리볼버(`RevolverController` — 로컬 판정→호스트 거리 재검증→`IDamageable.ApplyDamage`) ④ 통합 핫바 5칸(`PlayerInventory` — `NetworkList` 동기화, 증감·swap 모두 호스트 확정) ⑤ 엔진 투입(`EngineFuelPort` — 근처+시선 판정, 요청 RPC로 차감+충전 원자적 확정) ⑥ 연료 소모→감속(`FuelTank`가 `IWorldScrollSpeedControl`로 스크롤 속도 수렴).
  - **검증 현황**: **정식 2인 루프 검증은 미실시**. **1인 루프**로 낮 채집 → 밤 방어 → Day+1 사이클이 종단 동작하고 반복 가능함을 확인했으나, 밤 웨이브 난이도로 사망 — **밸런스(웨이브 규모·몬스터 수치·연료 곡선) 조정 필요**. 순수 로직은 EditMode로 전 경계 검증됨(`DayTimelineMath`·`WaveMath`·`MonsterSteering`·`MotionSnapshotBuffer`·`RevolverCylinder`·`HotbarLogic`·`FuelMath`).
  - **완료까지 남은 것**: ① **밸런스 조정 후 2인 루프 정성 검증**(완료 기준 충족 시 '완료'로 갱신) ② **미결 3건 결정** — 동시 존재 몬스터 상한(대역폭 계측 후, `WaveSettings`에 데이터 구조·잠정값 `MaxAliveCap=12` 존재) · 부활 대기 시간 n값(현재 고정 5 s) · `com.unity.ai.navigation` 패키지 제거 여부(커스텀 조향 확정으로 미사용).

### M3 — 열차 시스템

- **범위**: 칸 증설/연결 + 칸 단위 파괴 + 연결부 파괴 시 후방 연쇄 이탈 + 수리 망치 + 칸 위 건축물 개별 파괴 + 연료 소모 증가 트레이드오프.
  - **칸 종류 → 건축물로 전환 (2026-08-01 확정)**: 원안의 "온실칸 등 1~2종"을 폐기하고, 기관차 외에는
    **모두 동일한 단일 확장 칸**(`CarType.Standard`)으로 통일했다. 칸의 개성은 종류가 아니라 **칸 위에
    설치하는 건축물**(`StructureState`)이 만든다 — 결정 근거·파생 변경은
    [M3 개선 계획 「칸 종류 → 건축물 전환」](../plans/M3/M3-테스트-피드백-개선-계획.md) 참조.
    기획서 §7의 칸 종류 목록(온실칸·무기고칸 등)은 M5+ 장기 비전으로 남으며, 실현 형태는 건축물이 된다.
- **핵심 구현 지침**:
  - 열차 구성은 호스트가 소유하는 단일 상태 모델(칸 리스트 + 연결부)로 정의하고, 변화는 원자적으로 확정 후 전파. 클라이언트에서 부분 적용된 중간 상태가 보이면 안 된다.
  - 파괴/이탈은 권위 이벤트로 발행 — 방어 목표 UI, 이탈 연출 등이 이를 구독.
  - 이탈한 칸의 회수는 **가능으로 확정·구현·검증 완료**(2026-08-01) — 손잡이로 슬롯까지 끌어온 뒤 수리 망치로 재결합.
    방식·비용은 [손잡이-이탈저항 스펙 §4.1](../design/Train-Survival-손잡이-이탈저항-스펙.md) 참조. 3인 세션 플레이 검증 통과.
- **완료 기준**: 클라이언트 2인 환경에서 연쇄 이탈이 양쪽 화면에서 동일하게 재생되고, 재접속 시 열차 상태가 정확히 복원된다.
- **진행 상태 (2026-08-01 갱신)**: **M3 완료** — 범위 전체가 구현·커밋됐고, **완료 기준(연쇄 이탈 양쪽 화면 동일 재생 · 재접속 시 열차 상태 복원)을 2인 정식 테스트에서 통과**했다 (2026-08-01). 이탈 칸 재결합은 3인 세션 검증까지 마쳤다. EditMode 173개 통과.
  - **구현 완료 내역**: ① 칸 증설·재건(`ITrainExpansion`, 슬롯 사전 확보 방식) ② 칸/연결부/건축물 개별 파괴(`TrainState` 단일 상태 모델 + 권위 이벤트) ③ 연결부 파괴 시 후방 연쇄 이탈(순차 파괴 규칙) ④ 수리 망치 1도구 통합 — 수리·건축물 설치·칸 건설·이탈 칸 재결합 ⑤ 손잡이 & 이탈 저항(`HandrailAnchor` + 집게 앵커 모드, 호스트 시뮬 오프셋 복제) ⑥ 칸 수 비례 연료 소모 트레이드오프(HUD 소모율 표시 포함). 설계·구현 현황은 [손잡이-이탈저항 스펙](../design/Train-Survival-손잡이-이탈저항-스펙.md)과 [M3 개선 계획](../plans/M3/M3-테스트-피드백-개선-계획.md)이 기록한다.
  - **남은 항목은 전부 TBD로 이월 (2026-08-01 결정)** — M3 완료를 막지 않으며, 재개 시점은 정하지 않는다:
    ① **수리 시 자원 소모 여부** — §7 추적표의 미결. 현재 수리는 무료(`RepairHammerSettings`에 비용 필드 없음)이고, 재결합 2개·칸 건설 5개만 비용이 있다.
    ② **칸 건설(망치 통합) 플레이 검증 4항목** — 코드·EditMode는 통과했으나 2인 플레이 검증 미실시. 조준 프리뷰·자원 차감·중간 슬롯 재건·자원 부족 표시.
    ③ **손잡이 회수 모션 가속도 램프 + 전원 해제 순간 속도 점프** — [개선 계획 §5](../plans/M3/M3-테스트-피드백-개선-계획.md).
    ④ **열차 위 원격 플레이어 표시 떨림·위치 밀림** — 이탈 칸 경로가 아닌 플레이어 복제 경로 ([트러블슈팅 로그](../plans/M3/M3-이탈칸-탑승-월드떨림-해결.md)).
    ⑤ **열차 도메인 as-built 명세 미작성** — M1·M2는 `docs/specs/`에 명세를 남겼으나 `specs/train/`은 없다.
    ⑥ **손잡이 바 메시 · 손잡이당 다중 그랩 허용** — [손잡이-이탈저항 스펙 §11](../design/Train-Survival-손잡이-이탈저항-스펙.md) 후속.

### M4 — 지역·난이도·날씨

- **범위**: 지역 전환(숲→사막 우선 2종) + 지역별 자원/온도 규칙 + Day 비례 난이도(수→체력→패턴) + 지역 마지막 밤 대형 웨이브 + 날씨 이벤트 1종(모래폭풍).
- **핵심 구현 지침**:

  - 지역별 일수(3~5일)는 **기준안 숲 5일 / 사막 4일로 착수**하되 데이터에서 조정 가능하게 (2026-08-01 확정).
  - 다음 지역 예고 연출은 "마지막 1~2일" 트리거로 데이터화.
  - **트랙 커브·경사는 M4에서 다루지 않는다** (2026-08-01 보류 결정) — 직선 스크롤을 유지하고 지역 정체성은 지형 프리팹·색채로만 표현한다. 스크롤 벡터 회전은 `WorldScrollMath`의 위치 유도 공식·몬스터 조향·손잡이 이탈 시뮬까지 재검증 대상이 되므로, 결정 시한을 후반부 지역(M7)으로 이월했다.
- **완료 기준**: 숲 5일 → 사막 진입의 전체 흐름이 플레이 가능하고, 밸런스 수치가 에셋 수정만으로 바뀐다.

  - **밸런스 초기값 판단**: 기획서 §4의 난이도 지수(숲 1 / 사막 4)를 배율로 직역하면 밤 웨이브가 4배가 되어 밸런스가 무너지므로, 사막은 **물량 ×1.6 · 체력 ×1.3 · 자원 밀도 1/2**로 착수한다. 전부 `RegionDefinition` 필드라 에셋 수정만으로 조정된다.

### M5 — 전투·생존 확장

- **범위**: 무기 3축 확장(샷건·볼트액션·근접·터렛/거치 기관총) + 탄약 3종 제작 + 장비(의류/방어구·체온 연동) + 요리 시스템 + 집게 2~3단계 + 집게 전투 활용(몬스터 그랩·처형).

### M6 — Steam 통합·수명 주기

- **범위**: Steam 트랜스포트(Facepunch 계열, 구현체는 도입 시점에 유지보수 상태 비교 후 확정) + 로비/프렌드 초대 + 재접속(rejoin) + 메타 진행 저장(업적·수집품, Steam 업적 연동 검토) + 사망/부활/게임오버 규칙.
- **핵심 구현 지침**:
  - 트랜스포트 전환은 빌드 설정/실행 인자로 — CI는 계속 UnityTransport 직결 유지.
  - Steam 릴레이·로비 테스트에는 AppID가 필요 — 개발 중에는 임시 AppID(Spacewar, 480), 릴리스 전 자체 발급 (네트워크 문서 §8).
  - 재접속의 "같은 플레이어로 복귀"는 NGO 후발 동기화만으로 안 된다 — Steam ID ↔ 플레이어 슬롯 매핑 + 인벤토리·스탯 커스텀 복원 설계 필요 (네트워크 문서 §8).
  - 접속 끊김 ≠ 사망: 끊긴 플레이어는 게임오버 판정에서 제외 (네트워크 문서 §2.3).
  - **게임 중간 저장은 없다** (기획서 §9.1 확정) — 런은 단일 세션으로 완주. 세이브/로드 시스템을 만들지 않는다.
- **완료 기준**: Steam 릴레이로 외부 네트워크의 친구와 세션을 시작·완주할 수 있고, 중도 이탈한 클라이언트가 재접속으로 같은 플레이어로 복귀한다.

### M8 — 아트·연출 패스

**이 문서의 로드맵은 M7까지만 정의돼 있었다.** M8은 [M8 착수 준비](../plans/M8/M8-착수-준비.md)가
신설한 마일스톤이며, 이 절은 그 정의를 로드맵에 편입한 것이다 (v1.31).

- **범위**: 프리미티브 → 실제 에셋 교체 + 낮/밤 시각 연출 + 렌더 예산 실측·조정.
- **착수 경위**: *"낮과 밤이 갑작스럽게 바뀐다 — 시간이 흘러간다는 표현이 없다"*는 관찰에서
  출발했다. 조사 결과 시각 연출이 미구현인 것과, 그보다 먼저 **비출 대상 자체가 프리미티브**
  라는 것이 확인되어 **"에셋과 연출 중 무엇을 먼저 하는가"**가 실제 결정 사항이 됐다.
  - **결론: 에셋 → 연출 A안 → 렌더 실측 → 연출 B안.** 조명 연출의 산출물은 색·명암·그림자
    **튜닝값**인데, 캡슐 위에서 잡은 값은 실제 모델이 들어오는 순간 다시 잡아야 한다 —
    재작업이 가능성이 아니라 확정이다.
  - **M8은 예산을 쓰는 마일스톤이다.** 지금 프레임이 여유로운 것은 최적화의 결과가 아니라
    비어 있기 때문이고(타일당 배경물 실측 **3개** — 아트 예산 §6의 1.7 M tris는 타일당 40개
    가정 위의 미래 수치), 그 여유는 M8이 에셋을 넣는 만큼 소모된다.
- **핵심 구현 지침**:
  - **시각 연출은 순수 로컬 표현** — 네트워크 상태를 새로 만들지 않고, 게임플레이 계약
    (`DayPhase` 열거·`DayPhaseChangedEvent`·`IDayCycleService` 시그니처)을 건드리지 않는다.
    호스트·클라가 서로 다른 연출 모드여도 게임플레이가 갈라지지 않는다.
  - **fog 소유권은 `WeatherVisualController` 단독 유지** (착수 준비 결정 ②) — 낮/밤 컨트롤러는
    ambient + Directional Light만 제어한다. 날씨와 충돌하지 않게 하는 경계다.
  - **셰이딩은 URP Simple Lit 일괄** (결정 ⑦) — "PBR 제거" 의도를 만족하면서 A·B안이 모두
    성립한다. Unlit은 조명을 받지 않아 연출 자체가 불성립이다.
  - **프리팹 편집 후 `GlobalObjectIdHash` 정규화** — 누락 시 클라이언트 접속이 거부된다
    (`ClosedByRemote`). 1차 검증에서 실제로 발생했다.
  - **씬 모델 교체는 YAML 직접 편집** — 열차칸은 `Game.unity`에 직접 배치돼 프리팹이 아니고,
    에디터 씬 저장은 수천 줄 재정렬 diff를 만든다.
  - 밸런스·연출 수치는 전부 데이터(SO)로 뺀다.
- **완료 기준**: 캐릭터·무기·기관차·열차칸이 실제 모델로 보이고, 낮에서 밤으로 넘어가는 것이
  **시간이 흐르는 것으로 읽히며**, 그 상태에서 밤 웨이브 최대 물량(동시 12 + 플레이어 4 +
  자원 12)이 목표 프레임을 유지한다.
- **차수 편성** (착수 준비 §4): 1차 에셋 적용 → 2차 연출 A안 → 3차 렌더 실측·조정 →
  4차 연출 B안(+배경 조형물). **3차가 4차의 선행 조건**이다 — 광원이 회전하면 매 프레임
  그림자맵을 다시 그리므로, 캐스케이드 축소와 배경 LOD 없이 B안에 착수하면 비용이 배수로 붙는다.

## 6. 고난이도 구간 상세 지침

### 6.1 집게(하푼) — 프로젝트 최고 난이도

문제는 "부드러움"이 아니라 **원격 클라이언트의 당기는 조작이 왕복 지연만큼 늦게 시작하는 반응성**이다 (네트워크 문서 §6.3).

- **로컬 선반영 계층과 권위 계층을 처음부터 분리 설계한다**: 입력 → (즉시) 로컬 연출 발행 → 호스트에 그랩 요청 → 호스트 확정 → 권위 이벤트 → 위치 동기화. 이 파이프라인이 자원 채집·몬스터 그랩·열차 매달린 적 뜯어내기에 전부 재사용된다.
- 로프는 시작점(플레이어)과 끝점(대상)을 잇는 순수 연출 — 탄성 곡선으로 지연을 흡수하며, 물리 시뮬레이션 대상이 아니다.

### 6.2 밤 웨이브 물량

- 동기화 10~15Hz + 보간, 거리/시야 기반 우선순위 (네트워크 문서 §6.2).
- 웨이브 설계는 "한 번에 대량"이 아닌 "지속 유입으로 체감 물량" — 웨이브 데이터 스키마를 이 전제로 설계한다.
- 몬스터 상한은 M2에서 릴레이 대역폭 계측 후 확정.

### 6.3 열차 상태 모델

- 열차 = 호스트 소유의 단일 직렬화 가능 상태 (칸 배열·연결부·각 칸 위 건축물·속도·연료). 이 모델이 재접속 시 후발 동기화·상태 복원의 원천이 된다. **M3에서 이 모델을 설계할 때 재접속(M6) 복원을 미리 고려할 것.** (중간 저장은 없으므로 세이브 포맷 고려는 불필요 — 기획서 §9.1)
- 메인 칸(기관차)은 파괴 불가 — 불변식으로 코드에 강제.
