# 상호작용 중재 — 겨눈 것 하나만 E키를 받는다

> **종류**: 아키텍처 명세 · **상태**: 구현 완료 (2026-08-25) · **플레이 검증 대기**
> **최종 갱신**: 2026-08-28 · **관련 문서**: [건축 시스템](../train/construction.md) ·
> [무기 전투 §6.7](../combat/weapon-combat.md) · [연료 루프](../world/fuel-loop.md) ·
> [플레이어 이동](network-movement.md)

## 1. 개요·목적

**보고된 결함은 한 줄이었다** — *"건축물이 동시에 2개 타겟팅된다. 특히 상자와 작업대."*

원인은 구조에 있었다. 상호작용 주체가 **다섯**인데 서로를 모른다. 각자 근접을 재고, 각자 시선을
재고, 각자 안내를 띄우고, 각자 E키를 소비한다. 열차 위에서는 이것들이 나란히 붙어 있어
**둘 다 성립하는 프레임이 정상**이고, 그때 안내가 겹쳐 뜨고 E 한 번에 둘이 함께 반응했다.

| 주체 | 컴포넌트 | 왜 겹치는가 |
|---|---|---|
| 창고 | `TrainStorage` | 상자와 작업대는 갑판 셀 하나 간격이다 |
| 제작 | `CraftingStation` | 위와 같음 · 기관차 고정 지점은 화구와 **거의 같은 자리** |
| 연료 투입구 | `EngineFuelPort` | 위와 같음 |
| 보따리 | `StorageBundle` | 갑판에 여럿 놓이고 서로 붙는다 |
| 거치 무기 | `MountedWeaponOperator` | 좌석 옆에 상자·작업대를 짓는다 |

**이 명세가 하는 일**: 후보를 한 곳에 모아 **하나만 고르는** 중재 축을 정의한다.
판정은 겨냥이 먼저다.

**이 명세가 하지 않는 일**: 서버 재검증은 각 호출부가 자기 기준점으로 그대로 한다. 중재는
**로컬 표시·입력 판정 전용**이며 네트워크를 타지 않는다. 무엇이 상호작용 가능한지(반경·등급·소유)를
정하는 것도 각 주체의 몫이다 — 중재는 **이미 성립한 것들** 중에서만 고른다.

## 2. 범위 (Scope)

**포함**: 후보 제출·초점 확정(`InteractionArbiter`), 선정 규칙(`InteractionArbitrationLogic`),
후보·초점 자료형(`InteractionCandidate`·`InteractionFocus`·`InteractionSource`),
창 독점(`Capture`/`Release`), 조준 정렬도 조회(`LocalInteraction.GetLookDot`).

**미포함**: 자원 채집·집게 그랩(월드 대상은 조준 레이가 이미 하나를 고른다), 핫바·인벤토리 UI
입력(E키를 쓰지 않는다), 사다리·좌석 같은 **상태 전이형** 상호작용.

## 3. 요구사항 → 설계 해석

| 요구 | 해석 | 설계 |
|---|---|---|
| 안내는 하나만 뜬다 | 표시와 입력이 **같은 관문**을 통과해야 한다 | `IsFocused`가 유일한 관문 — 안내·E키 둘 다 이것으로 막는다 |
| 겨눈 쪽이 이긴다 | 거리보다 **조준이 먼저** | 정렬도 1순위 · 근사 동률에서만 거리가 넘겨받는다 |
| 누가 먼저 도는지에 답이 갈리면 안 된다 | `Update` 순서는 **보장이 아니다** | 초점은 **직전 프레임** 제출분으로 확정 |
| 열린 창 위로 남의 안내가 겹치면 안 된다 | 창은 초점을 **붙잡아야** 한다 | `Capture`/`Release` — 먼저 연 쪽이 우선 |
| 같은 입력이면 같은 승자 | 순서 의존이 없어야 한다 | 순수 함수 · 2패스 · 전순서 타이브레이크 |

## 4. 시스템 구조

```
각 주체 (5종)                    InteractionArbiter            InteractionArbitrationLogic
─────────────                   ──────────────────            ───────────────────────────
근접·시선 판정 통과
  └─ Submit(정렬도, 거리) ──────▶ Pending 목록에 쌓기
                                   (인스턴스당 하나 · 최선값)
                                        │
                                   프레임이 넘어가면
                                        └─ Advance() ────────▶ SelectFocus(후보들)
                                                                  ① 최고 정렬도 확정
                                   _focus ◀─────────────────────  ② 거리 → 종류 → 인스턴스
                                        │
  IsFocused() ◀────────────────── 독점 중이면 _captured 우선
        │
  ├─ 안내 표시
  └─ E키 처리
```

**2층으로 나눈 이유**: 선정 규칙은 `Time`도 `GameObject`도 필요 없다. 순수 함수로 떼어 내면
EditMode에서 **후보 배열을 직접 만들어** 규칙만 검증할 수 있다. 파사드는 프레임 경계와 정적
수명만 맡는다.

## 5. 데이터 구조

```csharp
enum InteractionSource { None, MountedWeapon, Storage, Bundle, Crafting, EngineFuel }

readonly struct InteractionCandidate { Source, InstanceKey, LookDot, SqrDistance }
readonly struct InteractionFocus     { Source, InstanceKey }   // Matches(source, key)
```

- **`InstanceKey`** — 같은 주체가 **실물로 여럿**일 때의 구분자. 보따리는 인스턴스마다 컴포넌트가
  붙으므로 `NetworkObjectId`를 낸다(판 안에서 고유하고 모든 접속자가 같은 값을 본다).
  창고·제작대처럼 **한 컴포넌트가 여러 건축물을 대신 판정**하는 쪽은 0이다.
- **`LookDot`** — 카메라 전방과 대상 방향의 내적. 1이 정면.
- **열거 순서는 게임 규칙이 아니다** — 정렬도와 거리가 완전히 같을 때의 **최종 타이브레이크**일
  뿐이고, 결정론을 위해 존재한다.

## 6. 상세 로직·상태

### 6.1 선정 — 조준이 먼저다

| 순위 | 기준 | 왜 |
|---|---|---|
| ① | 정렬도가 최고치의 **0.02 이내** | 같은 것을 겨눴다고 볼 오차 |
| ② | 그중 **가장 가까운 것** | 겨냥이 같으면 손에 닿는 쪽 |
| ③ | 종류 → 인스턴스 순서 | 결정론 — 여기까지 오면 게임적으로 구분 불가 |

> **거리를 먼저 보면 안 된다.** 옆에 붙은 상자를 정면으로 봐도 조금 더 가까운 작업대가 이긴다.
> 사람이 겨눈 것과 시스템이 고른 것이 어긋나면 그것이 결함으로 보인다.

### 6.2 2패스인 이유 — 근사 비교는 비추이적이다

정렬도 비교에 **오차 허용**이 들어가는 순간 "A≈B, B≈C, A<C"가 가능해진다. 순차 fold로 승자를
갱신하면 **제출 순서에 따라 답이 갈린다.**

그래서 **1패스에서 최고 정렬도를 먼저 확정**하고, 2패스는 그 기준선을 고정값으로 쓴다.
기준선이 상수이므로 이후 비교는 전순서이고, 결과는 순서와 무관하다.

> 1패스에서도 `None` 후보를 거른다 — 빈 후보가 기준선을 올려 진짜 후보를 전부 떨어뜨리는 것을
> 막는다.

### 6.3 프레임 규약 — 직전 프레임으로 확정한다

`Update` 실행 순서는 보장되지 않는다. **같은 프레임에 제출하고 같은 프레임에 묻는** 구조는
누가 먼저 도느냐에 따라 답이 달라진다. 늦게 도는 주체는 자기가 제출하기 전에 물어 놓고
"후보가 나 하나"라는 답을 받는다.

> **초점은 직전 프레임의 제출분으로 확정한다.** 한 프레임(≈16 ms) 늦는 대신, 순서와 무관하게
> **모두가 같은 답**을 받는다.

이 규약 때문에 호출부에는 **단락 금지** 규칙이 붙는다:

```csharp
// IsFocused를 먼저 물어 프레임을 넘긴다 — 단락되면 중재가 갱신되지 않는다.
bool focused = InteractionArbiter.IsFocused(source) && ready;
```

`ready && IsFocused(...)`로 쓰면 후보가 성립하지 않는 프레임에 `Advance`가 호출되지 않아
초점이 **옛 값으로 굳는다**.

### 6.4 독점 — 열린 창이 초점을 붙잡는다

창을 연 주체(창고·제작·보따리)와 좌석에 앉은 거치 무기는 `Capture`로 초점을 붙잡고, 닫을 때
`Release`한다. 붙잡힌 동안 다른 후보는 초점을 얻지 못한다 — 열린 창 위로 창고·연료 안내가
겹치는 것을 막는 장치다.

- **빼앗지 않는다** — 이미 다른 주체가 붙잡고 있으면 `Capture`는 무시된다(먼저 연 창이 우선).
- **남의 것을 대신 풀지 않는다** — `Release`는 자기가 붙잡고 있을 때만 듣는다.

### 6.5 제출 중복 — 인스턴스당 하나

같은 인스턴스가 한 프레임에 두 번 내면 **더 잘 겨눈 쪽만** 남는다. 제작대는 종류가 넷이라
`CraftingStation` 하나가 여러 지점을 판정하는데, 그중 **가장 잘 겨눈 지점 하나**를 대표로 낸다 —
여러 종류가 동시에 성립해도 후보는 "제작" 하나다.

## 7. 인터페이스·의존성 (경계)

- **`LocalInteraction.GetLookDot`** — 통과/탈락만 돌려주던 `IsLookingAt`으로는 동시에 성립한
  후보를 가릴 수 없다. **정렬도 자체를 내는** 경로를 열고, `IsLookingAt`은 그 위의 얇은 래퍼가
  됐다. 폴백 규약은 같다(플레이어 없음 = −1, 카메라 없음·지점 겹침 = 1).
- **의존 방향** — 다섯 주체가 `Game.Gameplay.Player`를 참조한다. 중재자는 **누구도 참조하지
  않는다**(주체를 열거로만 안다).
- **네트워크 없음** — 정적 클래스이고 RPC도 `NetworkVariable`도 쓰지 않는다.

## 8. 설계 포인트 (SOLID)

- **SRP** — 규칙(순수)·프레임 경계(파사드)·판정 주체(각 컴포넌트)가 분리된다.
- **OCP** — 주체 추가는 열거 항목 하나와 `Submit`/`IsFocused` 두 줄이다. 중재 로직은 안 바뀐다.
- **DIP** — 중재자는 구체 컴포넌트를 모른다. 주체는 값(정렬도·거리)만 낸다.

## 9. Unity 특화

- **정적 상태의 수명** — `[RuntimeInitializeOnLoadMethod(SubsystemRegistration)]`으로 초기화한다.
  도메인 리로드를 끈 상태에서 정적 값이 **다음 판까지 살아남는** 것을 막는다.
- **프레임 카운터** — `Time.frameCount`로 경계를 잡는다. 테스트는 `internal` 오버로드에
  프레임 번호를 직접 넘겨 시간 없이 검증한다.
- **정지·씬 전환** — 프레임을 건너뛰어도 마지막 제출분으로 확정하고 목록을 비운다.

## 10. 테스트 케이스 (EditMode)

**선정 규칙 8** — 빈 후보 · 단일 후보 · 창고vs제작(겨눈 쪽) · 근사 동률(가까운 쪽) ·
**제출 순서 무관** · 완전 동률(종류→인스턴스) · 승자 인스턴스 보존 · `None` 무시.

**프레임 중재자 8** — 직전 프레임 확정 · **Update 순서 무관** · 아무도 안 내면 초점 해제 ·
인스턴스당 최선값 유지 · 독점이 남을 막음 · 독점은 빼앗기지 않고 해제는 주인만 · 독점의
인스턴스 구분 · `Reset` 전체 초기화.

## 12. 확장 여지

- **새 주체**는 열거 항목 + 두 줄이면 들어온다.
- **인스턴스 구분이 필요한 주체**는 `InstanceKey` 오버로드를 쓴다(보따리가 실증).
- 안내 문구 자체의 우선순위(같은 초점 안에서 무엇을 먼저 쓸지)는 각 주체가 그대로 소유한다.
