# 문서 지도 (`docs/`)

이 저장소의 문서는 **역할이 다른 5계열**로 나뉜다. 문서를 찾거나 새로 쓸 때 아래 기준으로 위치를 정한다.

| 계열 | 폴더 | 무엇을 담는가 | 언제 갱신하는가 |
|---|---|---|---|
| **가이드** | [`guide/`](guide/) | 프로젝트 전체의 단일 진실 원천 — 원칙·아키텍처 결정·마일스톤 로드맵·미결 추적 | 마일스톤 착수/완료, 결정이 바뀔 때 |
| **설계** | [`design/`](design/) | 게임이 **무엇이고 왜 그런가** — 기획·세계관·네트워크 아키텍처·아트 예산·비주얼 가이드 | 게임 내용·방향이 정해지거나 바뀔 때 |
| **규약** | [`conventions/`](conventions/) | 코드를 **어떻게 쓰는가** — SOLID·아키텍처 규칙·커밋 컨벤션 | 규칙을 새로 정하거나 고칠 때 |
| **명세** | [`specs/`](specs/) | **as-built** — 구현된 코드와 실제로 일치하는 구조 기록 | 구현이 끝난 뒤, 코드가 바뀔 때마다 |
| **계획** | [`plans/`](plans/) | 차수별 구현 계획과 플레이 검증 항목 (마일스톤별 폴더) | 착수 전 계획, 검증 후 결과 기록 |

## 계열 구분의 핵심

**`design/` vs `specs/`** — 같은 시스템을 다뤄도 시점이 다르다. `design/`은 **구현 전**의 의도·범위·TBD를
담고, `specs/`는 **구현 후**의 실제 구조를 담는다. specs에 "예정"이나 "TBD"가 들어가면 그 문서는 이미 틀렸다.

**`guide/` vs `plans/`** — `guide/`는 프로젝트 수명 전체를 관통하는 결정을 담고, `plans/`는 특정 차수의
작업 단위를 담는다. 차수가 끝나면 plans 문서는 **동결**되고, 그 결과가 guide와 specs에 반영된다.
