## 1. 진행 순서와 근거

```
1단계 폴더 재편  →  2단계 리팩터링 조사  →  3단계 누락 문서 생성  →  4단계 specs 갱신·모순 해소
   (완료)              (보고서만)            (계획·검증 짝)          (as-built 19편)
```

| 왜 이 순서인가 | 근거 |
|---|---|
| **폴더 재편이 맨 앞** | 이후 생성할 모든 문서가 최종 위치에서 만들어진다. 나중에 하면 새 문서까지 두 번 옮기고 링크를 두 번 고친다 |
| **specs가 맨 뒤** | specs는 **as-built(구현 일치)** 문서다. 코드가 굳기 전에 쓰면 확정적으로 다시 쓴다 |
| **리팩터링이 문서 생성보다 앞** | 코드 구조가 바뀌면 3·4단계 문서 내용이 바뀐다. 이번엔 **보고서만** 쓰므로 코드는 안 바뀌지만, 보고서가 4단계 specs의 "남은 한계" 절 입력이 된다 |

**완료·검증 표시 방침** (사용자 요청 사항)

- 각 문서 머리에 **상태 배지**를 통일 형식으로 넣는다: `상태: 구현 완료 · 플레이 검증 통과 (날짜)`
- 검증 항목은 체크박스로 쓰고 **실제로 통과한 항목만** `[x]` 표시한다
- **검증 미실시 항목을 통과로 표시하지 않는다** — 사후 기록이라도 사실이 아닌 표시는 문서 전체의 신뢰를 깎는다.
  기록이 없어 판단 불가한 항목은 `[~] 기록 없음 (사후 작성)`으로 명시한다

> **이 방침이 중요한 이유**: 3단계는 "없던 문서를 만드는" 작업이라 가장 쉽게 창작으로 흐른다.
> 근거 없는 검증 통과 표시는 포트폴리오에서 **가장 치명적인 종류의 거짓**이다.

**예상 공수**: 1.5~2일 (문서 12~14편)
