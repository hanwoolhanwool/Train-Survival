작성일: 2026-08-08 · 대상: `feat/m5-combat-survival` · 상태: **계획 (착수 전)**

> **5차 목표** (개발 가이드 §5 M5 차수 분할): 집게 2~3단계 티어 + 몬스터 그랩·처형 —

## 1. 선행 리팩터 — 획득 확정 폴리모피즘 이관

**현재 문제**: `HarpoonController.ServerUpdateTow`(`HarpoonController.cs:327-351`)가 도착 판정 후
`_serverTowTarget as ResourceNode`로 캐스팅해 **인벤토리 수납 + 채집 카운터 증가**를 직접 한다.
몬스터가 그랩 대상이 되면 여기에 종류 분기가 하나 더 늘어 OCP가 깨진다 (명세 §8 OCP 항목이
"`IGrabbable` 확장만으로 대상을 늘린다"고 적어둔 계약과 어긋난다).

**설계**: 도착 시 무슨 일이 일어나는지를 **대상이 결정**하게 한다.

| 변경 | 내용 |
|---|---|
| `IGrabbable.CompleteGrab()` → `bool TryCompleteGrab(in GrabCompletion ctx)` | `ctx` = (그래버 clientId, 그래버 `GameObject`, 그래버 집게 등급). 대상이 필요한 것만 읽는다 |
| `ResourceNode` | 인벤토리 수납(`IResourceInventory.ServerTryAdd`) + `ISharedResourceCounter` 증가 + 소멸을 **자기 안에서** 수행. 수납 실패(가득) = `false` |
| `MonsterGrabTarget` (신규) | 소멸하지 않고 **무력화 진입** 후 `true` — "도착했지만 대상은 남는다" |
| `HandrailAnchor` | `false` (획득 개념 없음 — 앵커는 도착 판정 자체를 타지 않는다, `ServerUpdateTow`가 앞서 return) |
| `HarpoonController` | `false`면 기존 "해제 + `ForceRelease` RPC" 경로 그대로. **`ResourceNode`·`ISharedResourceCounter` 참조가 사라진다** |

- `ISharedResourceCounter` 증가가 World 도메인(`ResourceNode`)으로 옮겨가 **어셈블리 방향이 더 자연스러워진다**
  (Harpoon이 World의 서비스를 알 필요가 없어진다 — 명세 §7 DIP 항목 갱신 대상)
- 무게 등급 게이트는 **순수 함수로 분리**해 EditMode 대상으로 만든다 (§2·§4가 공유)

## 2. 집게 티어 3단계 (제작대 업그레이드)

**획득 방식** (결정 2026-08-08): 제작대에서 재료를 소모해 **플레이어의 집게 등급을 1→2→3으로 승급**한다.
핫바 아이템을 늘리지 않으므로 "집게는 1번 슬롯·버릴 수 없다"(기획서 §3.4)와 충돌하지 않는다.

| 층 | 파일 | 내용 |
|---|---|---|
| 데이터 | `HarpoonSettings` 확장 | 티어 배열 `Tier[3]` — 사거리·릴 속도·미스 페널티·쿨다운·**그랩 무게 상한**. 공통 수치(투사체 반경·속도·보간·되감기·타임아웃)는 현행 유지 |
| 복제 | `HarpoonController`에 `NetworkVariable<byte> _tier` | 게스트도 코스메틱 훅 속도·사거리가 필요하다 (비소유 사본이 같은 궤적을 재생) — 변종 인덱스 규약과 동일 |
| 승급 | `CraftingRecipe._outputHarpoonTier` (0 = 미사용) | `IsItemOutput`과 같은 규약의 세 번째 산출 종류 |

**승급 확정 경로** (원자성 유지):

`CraftingStation.RequestCraftServerRpc`가 지점·거리를 재검증한 뒤(현행 그대로),
승급 레시피면 ① 플레이어의 `IHarpoonTierHolder`(Crafting 쪽 인터페이스, `HarpoonController`가 구현)를 조회해
**목표 등급 = 현재 + 1**인지 확인 → ② `PlayerInventory.ServerTryConsume(recipe)`(신규 — `CraftingLogic`에
산출 없는 소모 함수 추가) → ③ 둘 다 성공할 때만 `ServerSetTier`. 어느 하나라도 실패하면 아무것도 반영하지 않는다
(재료 보존 원자 규약 = 무기 산출과 동일).

- 제작 창: 이미 보유한 등급·건너뛴 등급의 줄은 **목록에서 제외** (지점 필터와 같은 자리에서 판정)
- 표시: 핫바·HUD의 집게 라벨을 "집게(2단계)"로 (`HotbarItemLabels` 경유 — 무기 표시명 통합 규약)
- 미스 페널티 완화는 티어 수치로 성립 (기획서 §3.2 "상위 단계일수록 회수 속도 증가")
- **순환 방지**: 3단계 승급 재료는 **원목(2단계로 채집)** 까지만 쓴다. 3단계 전용 자원(광맥)을
  3단계 승급 재료로 넣으면 잠금이 풀리지 않는다

## 3. 상위 자원 2종 (무게 등급)

**무게 등급**을 `ResourceCatalog.Entry._grabWeight`(1~3, 미등재 = 1)로 둔다 — **기존 5종은 전부 무게 1**이라
1단계 집게의 기존 채집 경로가 그대로 유지된다(회귀 없음).

| 종류 | 값 | 무게 | 지역 | 발열 | 건자재 | 쓰임새 |
|---|---|---|---|---|---|---|
| 원목 (`Timber`) | 6 | 2 | 숲 | **12** (목재 6의 2배) | O | 연료 압박 완화 + 집게 3단계 승급 재료 |
| 광맥 (`OreVein`) | 7 | 3 | 사막 | 0 | X | **탄약 대량 제작** 3종 (신규 레시피 append) |

- 값 대역 규약 유지 (자연 자원 1~15 · 제작품 16+ · 한 번 배정한 값 불변) — 6·7이 잔여 대역의 앞자리
- **종류가 의미를 가지려면 쓰임새가 있어야 한다**(1차 결정 규약)는 기준을 두 자원 모두 충족한다:
  원목 = "2단계를 만들면 연료 문제가 풀린다", 광맥 = "3단계를 만들면 탄약 경제가 풀린다"(포수 지원 — §7.2 협동 함의)
- 신규 레시피 3종(광맥 1 + 화약 원료 2 → 탄약 대량)은 `RecipeCatalog` **append**(인덱스 = RPC 식별자, 순서 불변)
- 지역 스폰은 `Region_Forest`·`Region_Desert`의 `_resourceSpawns` **에셋 수정만**
- 노드 외형은 종류 색(기존 규약)으로만 구분되므로 **"왜 안 잡히는지" 안내가 필요**하다 →
  `GrabVerdict.InsufficientTier` 추가 + `GrabValidation`(순수)에 등급·무게 인자 추가 →
  거부 사유를 소유자 RPC로 받아 HUD에 "강화 집게가 필요하다" 표시 (기존 거부 RPC 경로 재사용)

## 4. 몬스터 그랩·무력화·처형

**신규 `MonsterGrabTarget`** (`Gameplay/Monsters/`) — `NetworkBehaviour`, `IGrabbable`, `Kind = Reel`.
`MonsterAgent`(이동)·`MonsterHealth`(체력)와 나란한 세 번째 관심사로 분리한다 (SRP — 기존 두 파일의 책임 불변).

| 축 | 설계 |
|---|---|
| 그랩 가능 | `MonsterHealth.IsAlive && !claimed && !무력화중`. 무게 등급은 `MonsterSettings._grabWeight` — 일반형·돌진형 1 / 돌격형·도약형 2 / **3은 향후 대형 변종 자리로 예약** |
| 견인 중 | `MonsterAgent.ServerSetTowed(true)` (신규 서버 API) — 조향·중력·**공격까지 정지**하고 위치를 견인 값으로 대입. 끌려오는 동안 때리지 못한다 |
| 표시 동기화 | 견인 중에는 `MonsterSettings._towSyncHz`(신규 · 30 Hz)로 기존 스냅샷 채널의 주기만 올린다 — 별도 위치 채널을 만들지 않아 클라이언트 보간 경로가 하나로 유지된다 |
| 예측 고정 | `BeginPredictedTow`/`CancelPredictedTow`는 **no-op**. 자원은 각 피어가 컨베이어로 로컬 유도하기 때문에 예측이 필요했지만, 몬스터는 원래부터 서버 스냅샷 보간만 하므로 그랩 전환 순간의 스냅 원인(§11 수정안 A의 RTT 간극)이 존재하지 않는다 |
| 무력화 | 도착 시 `TryCompleteGrab` → 그로기 진입 (`NetworkVariable<float>` 잔여 시간, `MonsterSettings._stunDuration`). 이동·공격 정지 + 표현(색·자세) |
| 처형 | `MonsterHealth.ApplyDamage`가 그로기면 `MonsterSettings._stunnedDamageMultiplier`(기본 999 ≈ 즉사)를 곱한다. **무기 종류를 보지 않는다** — 근접 처형과 "아군 앞으로 끌어와 협동 처치"(§3.2) 두 축이 한 규칙으로 성립하고, 배율을 3배로 낮추면 협동 쪽으로 기울 수 있다 (에셋 조정) |
| 그로기 해제 | 잔여 시간 경과 시 정상 복귀 (다시 그랩 가능) |
| 열차에 매달린 몬스터 뜯어내기 | **별도 코드 없이 성립** — 갑판 위 몬스터를 그랩하면 릴 감기가 플레이어 쪽으로 끌어온다 |
| 견인 중 사망 | 다른 플레이어의 사격으로 죽으면 despawn → `ServerUpdateTow`의 기존 스폰 검사가 `ForceRelease`로 정리 (경로 재사용, 신규 처리 없음) |

- 프리팹: `Monster.prefab`에 `MonsterGrabTarget` 1개 추가 — ⚠ `GlobalObjectIdHash` 오염 주의(4차 전례,
  컴포넌트는 YAML 직접 편집 + 접속으로 최종 판정)

## 5. 소규모 ① 스튜 섭취 시 즉시 체온 상승

현재 보온 버프는 *단열 계수*라 "환경을 덜 춥게" 만들 뿐 체온을 직접 올리지 않아 먹은 순간의 피드백이 약하다.

- `FoodCatalog.Entry._instantBodyTemperature`(℃) 추가 — 스튜 초기값 **+4 ℃** 제안, 구운 식사 0
- `PlayerTemperature.ServerAddBodyTemperature(float)` 신규 진입점 — 가산 후 **즉시 복제**(`SyncThreshold` 무시,
  기아 0 교차 즉시 복제와 같은 규약)
- **쾌적 상한(32 ℃)까지만 클램프** — 사막 낮에 스튜를 먹어 더위 피해를 입는 역효과를 만들지 않는다
  (단열의 음수 = 역효과는 장비 축이 이미 담당한다). 상한을 넘기고 싶으면 에셋으로 조정 가능하게 필드로 둔다
- `PlayerFoodConsumer`가 (차감 + 허기 회복 + 버프 + **체온 가산**)을 같은 원자 확정 안에서 호출.
  사망 중 차단은 4차의 `IsAlive` 통합이 이미 처리한다

## 6. 소규모 ② 창고 동시 경합(G2) QA 수단

사람이 두 피어를 같은 프레임에 조작할 수 없어 3·4차 연속 미검이다. **한 번의 입력으로 전 피어가 동시에
같은 이동을 요청**하게 만든다.

- `QaDebugHotkeys`에 **숫자패드 4** 추가 → 호스트가 `SendTo.Everyone` 트리거를 뿌리고, **각 피어가 수신 프레임에
  자기 이동 요청 RPC를 발행**한다 (창고 슬롯 0 ↔ 개인 슬롯 0). 서버 도착이 붙어 경합이 재현된다
- 판정: 두 요청 중 하나만 반영되거나 갱신된 상태 기준으로 처리되어 **아이템 총량이 보존**되는지 —
  총량을 콘솔에 출력해 눈으로 확인 가능하게 한다 (기존 키 규약대로 호스트 확정)

## 8. 작업 순서 (커밋 단위 제안)
