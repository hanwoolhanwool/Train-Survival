# M8 1차 구현 계획 — 에셋 적용 (프리미티브 → 실제 모델)

작성일: 2026-08-15 · 대상: 신규 브랜치 (`feat/m8-art-pass` 제안) ·
상태: **착수 전 결정 ①~⑤ 대기 (§1)**
(차수 편성: [M8-착수-준비.md](M8-착수-준비.md) §4 — 1차 = 에셋 적용.
상위 결정 ①·②·④·⑤·⑥·⑦ 확정 · 예산 기준: [아트·렌더링 예산](../design/Train-Survival-아트-렌더링-예산.md) §2·§3)

> **1차 목표**: **캐릭터·무기·기관차·열차칸이 프리미티브에서 실제 모델로 교체되어,
> 화면에 보이는 것이 "무엇인지 설명 없이 읽힌다."** 동시에 이 교체는 뒤따르는 차수의
> 전제를 확정한다 — 2차(낮/밤 연출)는 **빛을 받을 표면**을 얻고, 3차(렌더 실측)는
> **측정할 실물 부하**를 얻는다. 지금 프레임이 여유로운 것은 최적화의 결과가 아니라
> 비어 있기 때문이며(착수 준비 §1.1), 1차는 그 여유를 처음으로 소비하는 작업이다.

## 0. 범위

**코어** (교체 대상 — 착수 준비 결정 ⑤):

1. **캐릭터** — TP 전신(동료 3명의 시야 + 내 그림자) · FP 팔 뷰모델(결정 ①에 따름)
2. **무기·도구 6종** — 집게(Harpoon) · 리볼버 · 샷건 · 라이플 · 수리 망치 · 마체테
   (`HotbarItemType.cs:7-21`). 현재 근접 `Blade` 큐브 1개만 존재한다
3. **기관차** — `Car_Locomotive`
4. **열차칸 4량** — `Car_1` ~ `Car_4`

**부수 (교체에 필수로 딸려오는 것)**:

5. **Simple Lit 전환** — 착수 준비 결정 ⑦. 신규 모델과 **잔존 프리미티브 전부** 일괄 적용
6. **LOD 3단 생성** — LOD0 원본 / LOD1 50 % @15 m / LOD2 25 % @35 m (아트 예산 §2.2)
7. **머티리얼 통합** — 캐릭터당 1~2개 (파츠 분할이 tris보다 비싸다)
8. **4인 색 구분** — 메시 변형이 아니라 `MaterialPropertyBlock`

**비범위**: 몬스터·보스·자원·건축물 모델(이월) · 애니메이션·리깅(결정 ②) ·
배경 조형물(3차 실측 후 판단) · 낮/밤 연출(2차) · 렌더 설정 조정(3차)

## 1.5 에셋 수용 판정

**판정은 반입 전에 끝낸다.** 스케일·축·피벗이 틀린 채로 들어오면 프리팹 배선과 씬 좌표를
다시 만져야 하므로, 늦게 발견할수록 비싸다.

### 1.5.1 치수 기준 — 이 프로젝트의 실측 좌표계

모델이 맞춰야 할 값은 취향이 아니라 **이미 코드·데이터가 쓰고 있는 수치**다.

| 대상 | 기준 | 출처 |
|---|---|---|
| **캐릭터 키** | **1.8 m** (캡슐 기본 높이 2 × `localScale.y` 0.9) | `Player.prefab` — `Body` |
| **캐릭터 폭** | **0.7 m** (어깨 기준) | 〃 `localScale.x/z` 0.7 |
| **캐릭터 피벗** | **발밑 (0, 0, 0)** — 루트가 발밑이고 `Body`가 `y = 0.9`로 올라가 있다 | 〃 `localPosition` |
| **열차칸 길이** | **12 m 이하** | `TrainLayoutSettings.asset` `_carLength: 12` |
| **열차칸 폭** | **3 m** | 〃 `_carWidth: 3` |
| **갑판 상면 높이** | **3 m** | 〃 `_deckHeight: 3` |
| **칸 중심 간격** | 13.5 m (길이 12 + 연결 간격 1.5) | 〃 `_couplingGap: 1.5` |
| **차륜 즉사 존** | y ≤ 1.2 m — 칸 하부 조형이 이 높이를 침범해도 판정은 무변 | 〃 `_wheelKillHeight: 1.2` |

> 열차칸 모델이 12 m를 넘으면 **연결 간격을 먹어 칸끼리 겹쳐 보인다.** 폭 3 m는 갑판 판정
> 규약(`|x| ≤ 2`)과 값이 다른데, 이는 기존 설계 사안이므로 1차에서 건드리지 않는다 —
> **모델은 `_carWidth: 3`을 따른다.**

### 1.5.2 폴리곤 밀도 기준선

| 대상 | 권장 tris | 근거 |
|---|---|---|
| TP 전신 (LOD0) | 8,000 ~ 12,000 | 아트 예산 §2 |
| FP 팔 뷰모델 | 5,000 ~ 8,000 | 〃 |
| 무기·도구 (각) | 2,000 ~ 5,000 | 〃 |
| **기관차** | **8,000 ~ 15,000** | **신규 제안** — 랜드마크성이 있고 상시 화면에 있다 |
| **일반 열차칸 (각)** | **4,000 ~ 8,000** | **신규 제안** — 4량 반복이므로 절제한다. 합계 15k + 8k×4 ≈ **47k로 캐릭터 4명(48k)과 같은 규모** |

기관차·열차칸 예산은 아트 예산 문서에 없어 **이 계획서에서 처음 제안하는 값**이다.
1차 실측(§4 A8) 후 조정한다.

**밀도 일관성이 개별 통과보다 중요하다.** 아트 예산 §3.2가 지적한 그대로다 — *"31.7 k는
세미리얼 밀도. 이에 맞춰 몬스터·열차를 만들면 기획서 §9.3의 제작비 이점이 사라진다."*
1차는 캐릭터와 열차를 **동시에** 넣는 첫 차수이므로, 캐릭터 확정 tris가 나오면 그것을
기준선으로 삼아 나머지의 상대 밀도를 맞춘다. 한 모델만 정밀하고 나머지가 거칠면 정밀한
쪽이 튄다.

### 1.5.3 반입 전 체크리스트 (Blender에서 확인)

| 축 | 확인 항목 | 실패 시 |
|---|---|---|
| **폴리곤** | 통계 오버레이의 **`Tris` 값** (Faces가 아니다 — quad면 약 2배) | 조건부 수용 → 폴리곤 조정 |
| **스케일·단위** | 1 unit = 1 m, **Apply Scale 완료**. 캐릭터 1.8 m / 칸 12×3 m (§1.5.1) | 원본에서 수정 |
| **축 방향** | FBX export = **Y-up, −Z forward** | 원본에서 수정 |
| **피벗** | 캐릭터 = 발밑 / 무기 = 그립 / 열차칸 = 바닥 중심 | 원본에서 수정 |
| **머티리얼** | 캐릭터당 1~2개. 파츠별 분할은 tris보다 비싸다 | 조건부 수용 → 아틀라스 통합 |
| **텍스처** | 2048 아틀라스 1장 (팔레트면 256²도 가능). **PBR 맵 제거 대상 확인** | 조건부 수용 → §2.2에서 처리 |
| **지오메트리 위생** | N-gon · 겹친 버텍스 · 뒤집힌 노멀 · UV 겹침 | 다수면 **반려** |
| **본** (리깅 있을 때) | 인간형 55~70본. FP 팔이면 **손가락 본 필수** (집게·망치 그립) | 결정 ②와 함께 판단 |
| **명명** | `Character_*` / `Weapon_*` / `Train_*` (준비물 3) | 반입 시 정리 |

### 1.5.4 판정 3단계

| 판정 | 조건 | 처리 |
|---|---|---|
| **수용** | 체크리스트 전 항목 충족 | 그대로 반입 |
| **조건부 수용** | tris 초과 · 머티리얼 분할 · PBR 잔존 — **원본 품질 자체는 정상** | §2.2 보완 후 반입. **검토된 캐릭터 모델이 이 경로다** (결정 ④) |
| **반려** | ⓐ 스케일·축·피벗이 틀렸는데 원본 수정 불가 ⓑ 지오메트리 위생 실패(뒤집힌 노멀·N-gon 다수) ⓒ 밀도 기준선 **2배 초과** | 원본 재작업. 해당 대상은 **프리미티브 유지**하고 1차를 닫는다 |

**반려가 1차를 막지 않는다.** 대상별로 독립 판정하고, 통과한 것만 교체한다 — 결정 ③에서
"미보유 무기는 프리미티브 유지"로 정한 것과 같은 원칙이다.

### 1.5.5 반입 후에만 드러나는 것

Blender에서 판단할 수 없어 Unity 반입 후 확인해야 하는 항목이다. §4 검증과 연결된다.

| 항목 | 확인 | 연결 |
|---|---|---|
| Simple Lit 룩 | PBR 제거 후 실제 색·명암이 의도대로인가 | §2.3 |
| 방향광 반응 | 라이트 회전 시 명암이 변하는가 — **2차 착수 조건** | A5 |
| LOD 팝핑 | 15 m·35 m 전환이 거슬리는가 | A3 |
| 그림자 실루엣 | 스타일라이즈드 톤에서 실루엣이 읽히는가 | 3차 기준선 |
| 1인칭 시점 높이 | 카메라 y와 모델 눈높이가 어긋나지 않는가 | A1~A2 |

## 2. 설계

### 2.1 현재 배선 — 무엇을 어디서 갈아끼우는가

| 대상 | 현재 | 위치 |
|---|---|---|
| 캐릭터 몸체 | 내장 **Capsule** (`m_Mesh` fileID 10208) | `Prefabs/Player.prefab:589` — `Body` |
| 근접 무기 | 내장 **Cube** (10202) | 〃 `:921` — `MeleePivot/Blade` |
| 총구 기준점 | 빈 Transform (메시 없음) | 〃 `Muzzle` |
| 집게 로프 | LineRenderer (연출, 메시 아님) | 〃 `Rope` |
| 기관차·열차칸 | 프리미티브 조합, **씬 직접 배치** (프리팹 아님) | `Scenes/Game.unity` — `Car_Locomotive`, `Car_1`~`Car_4` |
| 씬 전체 | MeshFilter **40개** — Cube(10202) · Cylinder(10206) · Sphere(10207) | 〃 |

**교체는 메시·머티리얼 레벨에서 끝난다.** `Body`·`Blade`는 게임플레이 코드가 Transform으로만
참조하므로, 같은 이름·같은 로컬 위치를 유지한 채 `MeshFilter`/`MeshRenderer`를 바꾸면
스크립트 배선은 그대로다. **콜라이더는 메시와 분리해 현재 형상을 유지한다** — 판정을 시각
모델에 맞추는 것은 체감 조정이므로 1차에서 건드리지 않는다(M7 잔여 ⑥과 같은 성격의 결정이다).

### 2.2 임포트 전 보완 (착수 준비 결정 ④)

순서를 지킨다 — **반입 후 고치는 것보다 반입 전에 확정하는 편이 싸다.**

1. **실제 `Tris` 확정** — Blender 통계 오버레이의 `Tris` 항목. 31.7 k는 quad 해석 기반
   **추정치**이며(아트 예산 §3.1), 이 값이 §3.3 판정의 근거였다
2. **폴리곤 조정** — §2 기준(TP 전신 8~12 k / FP 팔 5~8 k / 무기 2~5 k)에 맞춘다
3. **PBR 제거** — metallic/roughness/normal 맵 제거, 단색 또는 팔레트 아틀라스로
4. **머티리얼 통합** — 파츠별로 쪼개져 있으면 1~2개로 합친다
5. **포즈 확정** — 결정 ②의 선택에 따라

### 2.3 Simple Lit 전환 (착수 준비 결정 ⑦)

| 항목 | 내용 |
|---|---|
| 셰이더 | `Universal Render Pipeline/Simple Lit` |
| 근거 | metallic/smoothness 계산은 없애고 **방향광·ambient 반응은 유지** — 2차(A안)·4차(B안)가 성립하는 최소 조건 |
| 적용 범위 | 신규 모델 + 잔존 프리미티브(결정 ⑤가 ⓑ면 전부) |
| 확인 | 전환 후 **Directional Light를 수동으로 회전**시켜 명암이 실제로 변하는지 눈으로 확인한다. 이것이 2차 착수 가능 여부의 판정이다 |

### 2.4 LOD·머티리얼

| 항목 | 기준 | 비고 |
|---|---|---|
| LOD 단계 | LOD0 원본 / LOD1 50 % @15 m / LOD2 25 % @35 m | 아트 예산 §2.2 |
| LOD1~2 그림자 | **3차에서 `Shadow Casting Mode: Off`로 전환** | 1차에서는 켠 채로 두어 **실측 기준선**을 남긴다 |
| 머티리얼 수 | 캐릭터당 1~2개 | 파츠 분할이 tris보다 비싸다 |
| 텍스처 | 2048 아틀라스 1장 (팔레트면 256²도 가능) | 아트 예산 §2.2 |
| 4인 색 구분 | `MaterialPropertyBlock` | 머티리얼 인스턴스 분기 금지 — SRP Batcher 효율 유지 |

### 2.5 열차 — 씬 YAML 직접 편집

열차칸은 프리팹이 아니라 **씬에 직접 배치**돼 있다(§2.1). 에디터로 씬을 저장하면 수천 줄
재정렬 diff가 생기므로, `Game.unity`의 해당 `MeshFilter`/`MeshRenderer` 블록만 직접 편집한다.

## 4. 테스트·검증 계획

**EditMode**: 에셋 교체이므로 신규 테스트는 없다. **452개 전량 통과 유지**가 확인 대상이다
— 이 차수에서 테스트가 깨진다면 그것은 에셋이 아니라 **프리팹 배선을 잘못 건드렸다는 신호**다.

**플레이 검증** (호스트 1 + 클라 1, 가이드 §5 원칙):

| # | 항목 | 통과 기준 |
|---|---|---|
| A1 | 클라이언트 접속 | **거부(ClosedByRemote) 없이 접속** — 해시 정규화 확인 |
| A2 | 4인 색 구분 | 각 피어가 서로를 다른 색으로 본다 |
| A3 | LOD 전환 | 15 m·35 m 부근에서 팝핑이 눈에 거슬리지 않는다 |
| A4 | 무기 전환 | 핫바 전환 시 뷰모델이 바뀌고 발사·타격 판정이 이전과 동일 |
| A5 | 조명 반응 | Directional Light 회전 시 **모델 명암이 변한다** (2차 착수 조건) |
| A6 | 열차 외형 | 5칸이 연결된 하나의 열차로 읽히고, 건축물 배치·이탈 칸 동작이 이전과 동일 |
| A7 | 그랩·수납 | 집게 파지·인벤토리 수납이 이전과 동일 (콜라이더 무변경 확인) |
| A8 | 기준선 기록 | **Frame Debugger로 SetPass/Batches/tris 기록** — 3차 실측의 비교 기준 |

> A8은 1차의 산출물이면서 **3차의 입력**이다. 교체 전 수치를 함께 남겨야 "에셋이 얼마를
> 먹었는가"를 말할 수 있다 — **교체 착수 전에 한 번 측정해 둔다.**
