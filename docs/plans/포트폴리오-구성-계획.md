### 0.1 이 스냅샷이 말해주는 강점 3가지

1. **테스트 가능하게 설계된 게임 코드** — 순수 로직(`*Math`·`*Logic`)이 MonoBehaviour에서 분리돼
   있어 EditMode 620개가 성립한다. 게임 포트폴리오에서 드문 지점이다.
2. **의사결정이 문서로 추적된다** — docs 커밋이 128개(전체의 29%)다. "무엇을 만들었나"가 아니라
   **"왜 그렇게 정했나"**가 남아 있고, 이건 시니어 평가 기준에 직접 걸린다.
3. **멀티플레이 권위 모델을 처음부터 설계했다** — 후반에 붙인 네트워크가 아니라 M1 수직 슬라이스를
   네트워크 리스크 소진용으로 먼저 잡았다(개발 가이드 §5 M1).

### 0.2 이 스냅샷이 말해주는 약점 2가지

## 1. 읽는 사람의 시간 계층 → 산출물 구조

채용 담당자·리드는 **선형으로 읽지 않는다.** 이탈 지점마다 다음 층으로 넘어갈 이유를 줘야 한다.

| 층 | 시간 | 보는 것 | 이 층에서 전달할 단 하나 |
|---|---|---|---|
| L0 | ~30초 | README 상단 (배너·한 문단·핵심 지표) | "이건 장난감이 아니라 **아키텍처가 있는 멀티플레이 프로젝트**다" |
| L1 | ~3분 | README 전체 (아키텍처 다이어그램·기술 하이라이트 3개·문서 인덱스) | "이 사람은 **결정을 근거로 한다**" |
| L2 | ~15분 | 기술 문서 1편 | "이 문제는 **쉬운 문제가 아니었고**, 해결 과정이 남아 있다" |
| L3 | 그 이상 | 코드 · as-built specs · 커밋 로그 | "문서와 코드가 **일치한다**" |

**3일 예산 배분의 근거**: L0·L1은 **모든 지원에서 100% 소비**되고, L2는 관심 있는 곳만 본다.
따라서 **README에 절반, 기술 문서에 절반**을 쓴다. L3은 이미 존재하므로 **정리만** 한다.

### 2.2 결정 — 기술 문서 3편은 **A · B · C**

세 편이 하나의 서사로 이어진다는 점이 결정적이다:

> **A(좌표계를 뒤집었다) → B(그래서 권위 규약을 새로 정의해야 했다) → C(그 규약 위에서 가장 어려운 손맛을 만들었다)**

D~F는 **README 본문의 불릿**으로 흡수한다(문서 1편씩 쓸 시간이 없고, 서사에도 종속적이다).

편당 **1,500~2,500자 / 5절**. 개발 블로그 이식이 가능하도록 저장소 상대 링크 의존을 최소화한다.

|---|---|---|
| 1. 문제 | 무엇이 어려웠는가 — **증상부터**, 용어 설명은 최소 | 15% |
| 2. 선택지 | 검토한 대안과 **버린 이유** ← 여기가 평가 포인트 | 25% |
| 3. 결정과 구조 | 채택안 + 다이어그램/코드 스니펫 (10~20줄) | 30% |
| 4. 검증 | 수치·테스트·플레이 검증 결과 | 20% |
| 5. 남은 한계 | 알면서 남긴 것 ← **신뢰도를 올리는 절** | 10% |

기존 `docs/specs/`(as-built 명세)와 **역할이 다르다** — specs는 구현 기록, tech는 **서사**다.

## 6. 시각 자료 확보 — 이 계획의 최대 리스크

**문제**: 플레이 가능한 씬(`Game.unity`)에는 내장 프리미티브 참조가 **36개** 남아 있고,
실제 모델이 배치된 씬(`Game_ArtTest.unity`)은 **아트 검수용**이다. 즉 **잘 돌아가는 화면과
잘 보이는 화면이 서로 다른 씬에 있다.**

| 노선 | 내용 | 비용 | 위험 |
|---|---|---|---|
| ① ArtTest 정지컷만 | `Game_ArtTest`에서 스크린샷 3~5장, GIF 없음 | 1.5h | 플레이 장면이 없어 "만들다 만 것" 인상 |
| ② Game.unity 아트 이식 | 열차·캐릭터 모델을 플레이 씬에 반입 후 캡처 | **0.5~1일** | 3일 예산 잠식 · 열차 높이/궤도 배선 재작업 필요(`train-art-layout.md` §7) |
| ③ **다이어그램 중심 + 정지컷 최소** | 아키텍처·권위·집게 파이프라인 다이어그램 3장을 주력, ArtTest 정지컷 2~3장을 보조 | 2.5h | 화려함은 포기 |

**추천: ③.** 근거 — 목적이 **취업 지원(기술 평가)**이지 위시리스트 확보가 아니다.
이 층의 독자는 **구조 다이어그램에 더 반응**하고, 아트 완성도는 3일로 뒤집을 수 없다.
③을 택할 경우 README §3(한 문단 소개)에 **"아트 패스 진행 중(M8)"을 명시**해 미완성이
숨긴 결함이 아니라 **알려진 진행 단계**로 읽히게 한다.

## 7. 배제 항목과 근거

| 배제 | 근거 |
|---|---|
| 데모 빌드 배포 | 밸런스·안정화가 붙어야 의미가 있고, 깨진 빌드는 없느니만 못하다. CI가 이미 빌드를 만들므로 **필요 시 언제든 추가 가능** |
| 트레일러 영상 | 아트 패스 미완(§6) 상태에서 영상은 약점을 확대한다 |
| 신규 기능 개발 | 3일에 들어갈 수 없고, 포트폴리오 가치를 올리지도 않는다 |
| 코드 리팩터링 | 지금 코드는 이미 규약을 따른다. 리팩터링은 화면에 보이지 않는다 |
| 밸런싱·플레이 검증 | M8 2차 검증 대기분이 있으나 **포트폴리오와 독립적** |
