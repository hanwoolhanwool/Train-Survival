# 뷰랩 파지 포즈 편집 계획 — 팔 본 오프셋을 사람이 직접 잡는다

작성일: 2026-08-18 · 상태: **착수 전 결정 대기 (①~④)** · 브랜치: `feat/weapon-hold`
(선행: [무기-손-파지-계획.md](무기-손-파지-계획.md) A안 완료 ·
[무기-파지-품질-업그레이드-계획.md](무기-파지-품질-업그레이드-계획.md) C1~C3 완료 후
남은 품질 미달을 닫는 도구 계획. 확장 대상은 [뷰랩-씬-계획.md](뷰랩-씬-계획.md)의 ViewLab)

> **목표**: 파지 자세가 어긋날 때 **사람이 뷰랩에서 팔을 직접 잡아 고치고**, 그 결과가
> 본편에 그대로 실리게 한다.
> - 지금은 손목 각도를 **클립이 100% 결정**해 데이터로는 손댈 수 없다 (§1.2 실측).
> - 조정 대상을 무기 피벗(FP)에서 **TP 파지 3층**(소켓 · IK 타깃 · **팔 본 오프셋**)으로 넓힌다.
> - 저장 대상은 파지 데이터의 단일 출처인 `WeaponHoldSettings.asset` (§2.5).
>
> **구현 중 하드코딩은 허용하되, 계획서 완료 시점에는 §4의 SOLID·판정-표현 분리(MVP)
> 기준을 전부 통과해야 닫힌다** — 앞선 두 파지 계획과 같은 규약.

## 1. 왜 필요한가

### 1.1 증상

파지 자세가 "하자 있게" 보인다 (사용자 지적 2026-08-18). 구체적으로 **팔을 뻗은 모양이
어색하고, 총을 쥔 손의 엄지가 하늘이 아니라 옆을 향한다.**

무기 자체의 방향은 데이터로 이미 잡았다 — 실측상 총구 (0.04, −0.11, 0.99) ≈ 정면,
총 위 (0.03, 0.99, 0.11) ≈ 하늘 (커밋 `c257874`). **그런데도 어색한 이유는 무기가 아니라
손목·팔이 어색하기 때문이다.**

### 1.2 근본 원인 — 손목 각도가 데이터 밖에 있다

| 항목 | 실측 | 의미 |
|---|---|---|
| 리볼버: 클립 손 위치 vs IK 목표 | 0.040 m 차 | IK가 손을 **거의 안 움직인다** |
| 리볼버: 클립 손 회전 vs IK 목표 | 4.9° 차 | 손목 각도 ≈ 클립 그대로 |
| 샷건: 위치 / 회전 차 | 0.042 m / 6.6° | 동일 |

C3에서 **IK 목표를 클립 실측값으로 채운** 결과다("IK가 켜져도 클립 자세가 무너지지 않게"
— 업그레이드 계획 C1 반입 결과). 의도는 맞았지만 부작용으로 **IK가 아무것도 교정하지
않는 상태**가 됐다. 즉 지금 손목은 Torch Idle(횃불 자루를 쥔 손목)이 그대로 나오고,
총을 쥔 손목이 아니다. `WeaponHoldSettings`의 어떤 값을 바꿔도 이건 안 바뀐다.

### 1.3 왜 도구가 필요한가 — 계산으로 못 맞춘다

- **손가락 본이 없다.** `RightThumbProximal`~`RightLittleProximal` 전부 없고 손은 `R_Hand`
  단일 본이다(실측). 엄지 방향을 코드로 알아낼 방법이 없어 "엄지가 위"를 계산으로
  정의할 수 없다 — **눈으로 보고 돌리는 수밖에 없다.**
- 에디터 프리뷰 렌더로는 IK 솔버가 돌지 않아 실제 화면과 어긋난다. 지금까지 렌더로
  수치를 맞춰 왔으나 실기와 차이가 나는 것이 이번 차수에서 드러났다.
- 치비 비율(팔 0.475 m)에 표준 인체 클립을 리타게팅한 구조라, 남은 오차는 **개별 조정으로
  흡수**하는 것 외에 일반해가 없다.

## 2. 설계

### 2.1 현재 파지 파이프라인 (조정 지점 표시)

```
Base Layer(로코모션)
  → Hold 레이어(팔 클립, ArmsOnlyMask)        ← ③ 팔 본 오프셋을 여기 뒤에 얹는다(신규)
  → OnAnimatorIK: WeaponHoldIk (손 위치·회전)  ← ② IK 홀드 타깃 (기존 데이터)
  → LateUpdate: PlayerAimView.ApplyBodyPitch (가슴·머리 절차 회전)
  → HeldWeaponSocket: 오른손 본 아래 무기 부착  ← ① 소켓 오프셋 (기존 데이터)
```

### 2.2 조정 대상 3층

| 층 | 무엇 | 현재 데이터 | 뷰랩에서 조정 |
|---|---|---|---|
| ① 소켓 | 무기 ↔ 손 (무기가 손 어디에 어떤 각도로) | `Entry.SocketLocal{Position,EulerAngles,Scale}` | 기존 조정 UI 재사용 (pos/rot/scale) |
| ② IK 타깃 | 손 ↔ 조준 피벗 (손이 어디를 향해 가는가) | `Entry.{Right,Left}HandLocal{Position,EulerAngles}` + 잔여 가중치 2종 | 기존 조정 UI + 가중치 슬라이더 |
| ③ **팔 본** | 어깨·상완·전완·손의 회전 보정 (**신규**) | 없음 — 이 계획이 만든다 | 씬 뷰 핸들로 본을 직접 회전 |

③이 이번 계획의 본체다. ①②는 이미 데이터에 있으나 **뷰랩에서 만질 수 없어서** 지금까지
렌더-수치-커밋 왕복을 했다 — 같은 UI에 얹어 왕복을 없앤다.

### 2.3 팔 본 오프셋 — 적용 지점과 형태

- **형태**: 본별 **로컬 회전 오프셋**(Quaternion). 위치·스케일은 건드리지 않는다 —
  스키닝이 깨지고, 필요한 것은 자세지 비율이 아니다.
- **대상 본**: `RightShoulder`(R_Clavicle) · `RightUpperArm` · `RightLowerArm` · `RightHand`
  (+ 양손 무기는 왼팔 4종). twist 본(`R_UpperarmTwist01` 등)은 Humanoid 매핑 밖이라
  **1차 비범위** — 필요해지면 이름 기반으로 추가.
- **적용 시점**: `OnAnimatorIK` **이후**여야 IK가 오프셋을 지우지 않는다. `LateUpdate`에서
  `ApplyBodyPitch`와 같은 규약으로 본에 곱한다.
  - **순서 주의**: 같은 `LateUpdate` 안에서 가슴 회전(`PlayerAimView`)이 팔의 부모를 돌리므로,
    팔 오프셋은 **가슴 회전 뒤**에 적용해야 결과가 안정적이다. 실행 순서 보장 방법은
    결정 ③에서 고른다.
- **정정 (2026-08-18): 팔꿈치도 내장 IK로 통제된다.** 초안에서 "2본 IK는 팔꿈치 방향을
  스스로 정해 통제 불가"라고 적었으나 **틀렸다.** Unity 내장 Humanoid IK에
  `Animator.SetIKHintPosition(AvatarIKHint.RightElbow, worldPos)` +
  `SetIKHintPositionWeight`가 있다(리플렉션으로 실재 확인 — `UnityEngine.AnimationModule`,
  enum 값 `LeftElbow`/`RightElbow`/`LeftKnee`/`RightKnee`).
  → **손목(IK 회전 목표) · 팔꿈치(엘보 힌트) 둘 다 데이터로 통제할 수 있다.**
  → 이 사실은 [무기-파지-품질-업그레이드-계획.md](무기-파지-품질-업그레이드-계획.md)
    **B축의 주 논거("팔꿈치 힌트가 내장 IK 대비 리깅 패키지의 핵심 이득")도 무너뜨린다** —
    B축 재평가 시 반영할 것.
- **그래서 본 오프셋(ⓐ)이 필요한 경우는 좁아진다**: IK가 만지지 않는 **어깨(clavicle)** 와,
  IK를 아예 끈 상태의 정지 자세뿐이다. 결정 ①에서 이를 감안해 고른다.

### 2.4 ViewLab 확장 — 기존 구조와 병목

조사한 현행 구조(파일:줄):

- 대상 표현이 `List<Transform> _pivots` + `List<Renderer[]> _pivotRenderers` + `int _pivotIndex`
  **평행 배열**이고 추상 타입·enum이 없다 (`ViewLabController.cs:52-54`, `:89-90`).
- 저장이 `AimPivot` 직속 자식 + `ViewLabMath.FindChildByName`(**직속 1단계만** 탐색)에
  하드코딩돼 있다 (`ViewLabController.cs:505-553`, `ViewLabMath.cs:132-149`).
  팔 본은 `Body/Character_*/…/R_Hand`로 깊고, **Girl·Man 두 아바타에 각각** 있다.
- 수치 필드 버퍼가 `_fields = new string[7]` 고정 + 인덱스 하드코딩 (`:76`, `:587-624`).
- 조작은 **씬 뷰 트랜스폼 핸들 + OnGUI 패널**뿐 — 키보드 핫키는 계획 단계에서 미채택
  (뷰랩 계획 §2·§8). 이 규약을 이어받을지는 결정 ④.

**필요한 일반화** (최소 침습 순):

1. **조정 대상 추상화** — `ViewLabTarget`(이름 · Transform · 종류 · 표시 토글 · 저장 경로)로
   묶고 `_pivots` 평행 배열을 대체. 무기 피벗은 "종류=FP피벗", 팔 본은 "종류=본"으로 들어온다.
2. **저장 라우팅** — 대상 종류별로 쓰기 위치가 다르다: FP 피벗 → `Player.prefab`(현행 유지),
   파지 3층 → `WeaponHoldSettings.asset`. 대상이 자기 저장 방법을 알게 한다.
3. **필드 버퍼 가변화** — `string[7]` → 대상이 요구하는 필드 수만큼.
4. **본 조정 시 Animator 경합 처리** — 씬 뷰에서 본을 돌려도 다음 프레임 Animator가
   덮어쓴다. 조정 중에는 **핸들이 만든 회전을 매 프레임 읽어 오프셋으로 환산**해 보관하고,
   `LateUpdate`에서 그 오프셋을 다시 적용한다(= 화면상 유지). 이 왕복이 ③의 핵심 난점이다.

### 2.5 저장 대상 — 단일 출처 원칙의 연장

뷰랩 계획 §8-①은 "오프셋 SO 신설"을 기각했다. 근거는 **"피벗 TRS의 단일 출처가
`Player.prefab`이므로 거기 쓴다"**였다. 파지 데이터는 단일 출처가 이미
`WeaponHoldSettings.asset`이므로, **같은 원칙을 적용하면 SO에 쓰는 것이 맞다.**
새 SO를 만드는 것이 아니라 이미 있는 SO에 쓰는 것이라 §8-①과 충돌하지 않는다.

- 팔 본 오프셋만 담을 자리가 없으므로 `WeaponHoldSettings.Entry`에 필드를 추가한다
  (무기별 자세가 다르므로 엔트리 단위가 맞다 — OCP: 무기 추가 = 엔트리 추가).
- Girl↔Man은 **공용 값 1벌**을 쓴다 (LSP — 모델별 분기 금지). 두 아바타의 팔 축 차이는
  9° 수준으로 실측됐고, 그 편차는 수용한다. 뷰랩에서 Girl/Man을 오가며 절충점을 잡는다.

## 4. 아키텍처 마감 기준 (SOLID · 판정-표현 분리)

| 원칙 | 적용 | 검사 |
|---|---|---|
| **SRP** | 포즈 적용(본편) / 조정 UI(뷰랩) / 데이터(SO)가 각각 분리. `WeaponHoldIk`에 "그리고 본도 돌린다"가 붙지 않게 한다 | 리뷰 |
| **OCP** | 무기·본 추가는 데이터와 대상 목록만 — 조정 UI 무수정 | 6번째 무기 사고 실험 |

| **ISP** | 뷰랩은 본편 컴포넌트를 **읽기만** 한다 — 조정 결과는 SO로만 흐른다 | 본편 코드가 뷰랩을 참조하지 않음 |
| **DIP** | 무기 컨트롤러 구체 타입 무의존 유지 (`HotbarItemType` + SO) | grep 0건 |
| **판정-표현 분리** | 전부 표현 전용 — 사격·수리 판정 경로 diff 0 | 판정 코드 diff 0건 |
| **순수 로직 분리** | 오프셋 합성·미러·환산은 `ViewLabMath`/`WeaponHoldMath`에 두고 EditMode | 테스트 존재 |
| **도구가 본편을 왜곡하지 않을 것** | 뷰랩은 본편 프리팹 인스턴스를 그대로 쓴다(사본 금지 — 뷰랩 계획 §3) | 씬 검토 |

## 5. 구현 순서

| 단계 | 작업 | 하드코딩 허용 | 마감 조건 |
|---|---|---|---|
| **V0** | 뷰랩에 **TP 파지 모드** 신설 — Hold 레이어 구동(`HoldPose` 주입) + TP 월드모델 표시 + `HeldWeaponSocket` 경로 재현. 지금 뷰랩은 FP 피벗만 본다 | 무기 목록 인라인 | 뷰랩 Play에서 본편과 같은 파지 화면이 나온다 |
| **V1** | 조정 대상 추상화(§2.4-1) + ①소켓·②IK 타깃을 조정 UI에 연결 + `WeaponHoldSettings` 저장(§2.4-2) | 필드 인덱스 인라인 | 뷰랩에서 값 조정 → 저장 → 본편 Play 반영 (왕복 검증) |
| **V2** | **③ 팔 본 오프셋** — 본 선택·씬 뷰 핸들 회전·Animator 경합 처리(§2.4-4) + 본편 적용부 | 본 목록 인라인 | 손목·팔꿈치를 사람이 잡아 저장하면 본편에 그대로 나온다 |
| **V3** | 좌우 미러(기존 `MirrorRotation` 재사용) · Girl↔Man 절충 확인 · EditMode | — | §4 전 항목 + §6 검증 통과 |

**전례 함정 (선반영)**

- Play 중 씬 뷰 핸들 값은 Stop 시 소실 — dirty 표시 + 저장 버튼 (뷰랩 계획 §7).
- 본은 Animator가 매 프레임 덮어쓴다 — §2.4-4의 오프셋 환산 없이는 핸들이 "튕긴다".
- `Player.prefab`은 NetworkObject — SO에만 쓰면 해시 위험이 없지만, V1에서 프리팹 경로를
  건드리게 되면 `GlobalObjectIdHash` 확인 필수.
- 열린 씬(.unity) 외부 편집·`git checkout` 되돌리기 금지 — "modified externally" 모달이
  MCP 전체를 막는다 (이번 차수에 2회 발생).

## 6. 테스트·검증 계획

- **EditMode**: `ViewLabMath` 확장분(오프셋 환산·대상 종류별 저장 경로 해석) +
  `WeaponHoldMath` 확장분(본 오프셋 합성·항등). 기존 527건 통과 유지.
- **왕복 검증(핵심)**: 뷰랩에서 손목을 눈에 띄게 돌려 저장 → 본편 Play에서 **같은 자세**가
  나오는지. 이 왕복이 성립하지 않으면 도구로서 의미가 없다.
- **플레이 검증**: 무기 5종 파지 · Girl↔Man 전환 · 피치 전 구간 · 달리기 중 상체 합성 ·

## 9. 선(先) 실험 — 도구 없이 30분 안에 확인할 것 (2026-08-18 추가)

2. 홀드 타깃 **회전**을 클립 실측값에서 **A안 계산값**(손끝이 전방·손 위쪽이 하늘,
   오른손 euler ≈ (7.95, 241.69, 294.91))으로 되돌린다 — 지금 값은 *횃불 쥔 손목*이다

"엄지가 위"를 계산으로 정의할 수 없기 때문이다(§1.3). 도구의 존재 이유는 그대로다.
