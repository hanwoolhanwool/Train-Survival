## 1. 왜 필요한가

### 1.1 증상

파지 자세가 어색하다 (사용자 지적 2026-08-18). 구체적으로 **팔을 뻗은 모양이 어색하고,
총을 쥔 손의 엄지가 하늘이 아니라 옆을 향한다.**

무기 자체의 방향은 데이터로 이미 잡혔다 — 실측 총구 `(0.04, −0.11, 0.99)` ≈ 정면,
총 위 `(0.03, 0.99, 0.11)` ≈ 하늘 (`c257874`). **어색함의 원인은 무기가 아니라 손목·팔이다.**

### 1.2 근본 원인 — 손목 각도가 데이터 밖에 있다

| 항목 | 실측 | 의미 |
|---|---|---|
| 리볼버: 클립 손 위치 vs IK 목표 | **0.040 m** 차 | IK가 손을 **거의 안 움직인다** |
| 리볼버: 클립 손 회전 vs IK 목표 | **4.9°** 차 | 손목 각도 ≈ 클립 그대로 |
| 샷건: 위치 / 회전 차 | 0.042 m / 6.6° | 동일 |

C3에서 **IK 목표를 클립 실측값으로 채운** 결과다("IK가 켜져도 클립 자세가 무너지지 않게").
의도는 맞았지만 부작용으로 **IK가 아무것도 교정하지 않는 상태**가 됐다. 지금 손목은
Torch Idle(횃불 자루를 쥔 손목)이 그대로 나온다. `WeaponHoldSettings`의 어떤 값을 바꿔도
이건 안 바뀐다 — **E1·E2가 정확히 이 지점을 되돌린다.**

### 1.3 왜 도구가 필요한가 — 계산으로는 못 맞춘다

- **손가락 본이 없다.** `RightThumbProximal`~`RightLittleProximal` 전부 없고 손은 `R_Hand`
  단일 본이다(실측). 엄지 방향을 코드로 알 수 없어 **"엄지가 위"를 계산으로 정의할 수 없다.**
  통제 수단(§2.3)이 갖춰져도 **넣을 숫자는 눈으로 찾아야 한다.**
- 에디터 프리뷰 렌더로는 IK 솔버가 돌지 않아 실기와 어긋난다. 이번 차수에 렌더로 맞춘
  수치가 실제 화면과 달랐던 것이 그 증거다.
- 치비 비율(팔 0.475 m)에 표준 인체 클립을 리타게팅한 구조라, 남은 오차는 개별 조정으로
  흡수하는 것 외에 일반해가 없다.

### 1.4 이번 차수에 확정된 사실 (재조사 불요)

| 사실 | 값 | 출처 |
|---|---|---|
| 손 본 스케일 | `RightHand.lossyScale = 100` (Girl·Man 공통) | 실측 — 소켓은 루트 배율로 정규화 중 |
| 무기 로컬 축 | **총구 +Y · 총 위 +Z** | 정사영 렌더 판별 |
| 어깨 높이 / 팔 길이 | y ≈ **1.082** / **0.475 m** | 실측 (치비 비율) |
| 머리·가슴 보정각 | −22° / −6° (`PlayerAnimationSettings`) | Base 클립이 고개를 17.4° 숙이는 것을 상쇄 |
| Hold 마스크 | **`ArmsOnlyMask`** (Body·Head 제외) | 머리를 포함하면 보정각과 이중 적용돼 하늘을 본다 (`bd6a123`) |
| 엘보 힌트 | `AvatarIKHint.{Left,Right}Elbow` **내장 IK에 실재** | 리플렉션 확인 (`65793c7`) |
| 손가락 본 | **없음** | 실측 |

## 2. 설계

### 2.1 현재 파지 파이프라인 (조정 지점 표시)

```
Base Layer(로코모션)
  → Hold 레이어(팔 클립, ArmsOnlyMask)          ← E4: 가중치를 낮춰 영향 축소
  → OnAnimatorIK: WeaponHoldIk (손 위치·회전)    ← ② IK 타깃 · E1~E3
  → LateUpdate: PlayerAimView.ApplyBodyPitch (가슴·머리 절차 회전)
  → HeldWeaponSocket: 오른손 본 아래 무기 부착    ← ① 소켓 오프셋
```

### 2.2 조정 대상 3층

| 층 | 무엇 | 현재 데이터 | 뷰랩에서 |
|---|---|---|---|
| ① 소켓 | 무기 ↔ 손 | `Entry.SocketLocal{Position,EulerAngles,Scale}` | 기존 pos/rot/scale UI 재사용 |
| ② IK 타깃 | 손 ↔ 조준 피벗 (+ **엘보 힌트**) | `Entry.{Right,Left}HandLocal{Position,EulerAngles}` + 잔여 가중치 2종 (+ 힌트 위치 신설) | 같은 UI + 가중치 슬라이더 |
| ③ 팔 본 오프셋 | 어깨(clavicle) 회전 보정 | 없음 | 씬 뷰 핸들 — **§2.3에 따라 용처가 좁다** |

①②는 이미 데이터에 있으나 **뷰랩에서 만질 수 없어** 지금까지 렌더–수치–커밋 왕복을 했다.

### 2.3 통제 수단 — 무엇으로 무엇을 잡는가 (핵심)

Unity 내장 Humanoid IK가 조작하는 것은 **상완·전완·손** 3본이다. 어깨(clavicle)는 안 만진다.

| 잡고 싶은 것 | 수단 | 가능? |
|---|---|---|
| 손 위치 | `SetIKPosition(AvatarIKGoal.RightHand)` | ✅ (이미 사용 중) |
| **손목 각도(엄지 방향)** | `SetIKRotation` + 회전 가중치 | ✅ — 지금 목표가 클립값이라 무력할 뿐 (E2) |
| **팔꿈치 방향** | `SetIKHintPosition(AvatarIKHint.RightElbow)` + `SetIKHintPositionWeight` | ✅ **내장 IK에 실재** (E3) |
| 어깨 회전 | IK 대상 밖 → 본 오프셋(③)이 유일 | ⚠ 필요 시에만 |
| 손가락 | — | ❌ **본 자체가 없다** |

> **정정 이력**: 초안은 "2본 IK는 팔꿈치를 통제할 수 없다"고 썼으나 **틀렸다.**
> 이 사실은 [무기-파지-품질-업그레이드-계획.md](무기-파지-품질-업그레이드-계획.md)
> **B축(Animation Rigging)의 주 논거도 무너뜨렸다** — 해당 계획서에 철회 기록 반영됨(`65793c7`).

**따라서 결정 ①의 권장은 ⓑ**다: 클립에서 IK 목표를 떼어내고 엘보 힌트를 더하면
손목·팔꿈치가 모두 데이터로 잡힌다. 본 오프셋(ⓐ)은 어깨에만 남는 좁은 보완이고,
클립 폐기(ⓒ)는 상체 자세를 버리는 대가가 크다.

### 2.4 ViewLab 확장 — 기존 구조와 병목

조사 결과(파일:줄):

- 대상 표현이 `List<Transform> _pivots` + `List<Renderer[]> _pivotRenderers` + `int _pivotIndex`
  **평행 배열**이고 추상 타입·enum이 없다 (`ViewLabController.cs:52-54`, `:89-90`).
- 저장이 `AimPivot` 직속 자식 + `ViewLabMath.FindChildByName`(**직속 1단계만**)에 하드코딩
  (`ViewLabController.cs:505-553`, `ViewLabMath.cs:132-149`). 파지 데이터는 SO에 있고
  팔 본은 `Body/Character_*/…`로 깊으며 **Girl·Man 두 아바타**에 있다.
- 수치 필드 버퍼가 `_fields = new string[7]` 고정 + 인덱스 하드코딩 (`:76`, `:587-624`).
- 조작은 **씬 뷰 핸들 + OnGUI 패널**뿐 — 키보드는 뷰랩 계획 §2·§8에서 명시적으로 미채택.

**필요한 일반화** (최소 침습 순):

1. **조정 대상 추상화** — `ViewLabTarget`(이름·Transform·종류·표시 토글·저장 라우팅)로
   평행 배열을 대체. 무기 피벗은 "FP피벗", 파지 값은 "SO 필드", 팔 본은 "본"으로 들어온다.
2. **저장 라우팅** — FP 피벗 → `Player.prefab`(현행), 파지 3층 → `WeaponHoldSettings.asset`.
3. **필드 버퍼 가변화** — `string[7]` → 대상이 요구하는 수만큼.
4. **본 조정 시 Animator 경합** — 씬 뷰에서 본을 돌려도 다음 프레임 Animator가 덮어쓴다.
   핸들이 만든 회전을 **오프셋으로 환산해 보관**하고 `LateUpdate`에서 재적용해야 한다.
   (③을 채택할 때만 필요 — ⓑ만 하면 불요)

### 2.5 저장 대상 — 단일 출처 원칙의 연장

뷰랩 계획 §8-①은 "오프셋 SO 신설"을 기각했다. 근거는 **"피벗 TRS의 단일 출처가
`Player.prefab`이므로 거기 쓴다"**였다. 파지 데이터는 단일 출처가 이미
`WeaponHoldSettings.asset`이므로 **같은 원칙을 적용하면 SO에 쓰는 것이 맞다.**
새 SO를 만드는 게 아니라 기존 SO에 쓰는 것이라 §8-①과 충돌하지 않는다.

- Girl↔Man은 **공용 값 1벌** (LSP — 모델별 분기 금지). 축 편차 9°는 수용하고,
  뷰랩에서 두 아바타를 오가며 절충점을 잡는다.

## 5. 구현 순서

### E단계 — 선 실험 (도구 없이, 결정 불요)

| # | 작업 | 마감 조건 |
|---|---|---|
| E0 | **현재 상태(`65793c7`) Play 확인** | 개선 폭 기록 — 이후 범위 판단의 기준 |
| E1 | `IkResidualWeight` 0.4 → 1.0 | IK가 손을 실제로 움직인다 |
| E2 | 홀드 타깃 회전을 *총 쥔 손목*으로 복원 | 엄지 방향이 바뀌는 것이 화면에서 보인다 |
| E3 | 엘보 힌트 추가 (`WeaponHoldIk` + SO 필드) | 팔꿈치 방향이 힌트를 따라간다 · EditMode 추가 |
| E4 | Hold 레이어 가중치 0.3~0.5로 하향 | 상체 분위기는 남고 팔은 IK가 지배 |

  `GlobalObjectIdHash` 확인 필수.
- **열린 씬(.unity) 외부 편집·`git checkout` 되돌리기 금지** — "modified externally" 모달이
  MCP 전체를 막는다 (이번 차수 2회 발생, `user32` BM_CLICK/ENTER로 해제).

## 6. 테스트·검증 계획

- **EditMode**: `WeaponHoldMath` 확장(힌트 위치 산출·가중치 합성) + `ViewLabMath` 확장
  (대상별 저장 경로 해석). 기존 **527건 통과 유지**.

  나오는가. 이게 성립하지 않으면 도구로서 의미가 없다.
- **플레이 검증**: 무기 5종 파지 · Girl↔Man 전환 · 피치 전 구간 · 달리기 중 상체 합성 ·
  `HeldItem = None` 복귀 · ClosedByRemote 없음.
