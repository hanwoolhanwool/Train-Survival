# UI 구현 계획 — IMGUI 프로토타입 → uGUI 정식 UI

작성일: 2026-08-20 · 대상: 전 마일스톤 횡단 (M8 이후) · 상태: **착수 전 — §10 미결 5건** ·
렌더 방식: **uGUI + TextMeshPro 확정** (§1 결정 ①) ·
비주얼 규격: [비주얼·UI/UX 가이드](../../design/Train-Survival-비주얼-UIUX-가이드.md) §7·§9·§11~§14 ·
현재 구조: [specs/ui/hud-architecture.md](../../specs/ui/hud-architecture.md) ·
분할 설계안: [리팩터링 조사 보고서 §4.3](리팩터링-조사-보고서.md)

> **이 계획의 목표**: 지금의 UI는 **작동하지만 프로토타입이다.** 모든 정보가 글자로만 나오고,
> 아이콘이 없고, 프롬프트가 화면 중앙에 고정돼 1인칭 몰입을 끊는다.
> 이 계획은 **정보를 바꾸지 않고 표현만 바꾼다** — 무엇을 보여줄지는 이미 결정돼 있고(가이드 §9),
> 남은 것은 그것을 읽히게 만드는 일이다.

> **핵심 전제 — 버리는 작업이 없다.** 가이드 §18의 실측대로 `UnityEngine.UI`·TMP 사용이 **0건**이라,
> 지금 들어가면 기존 uGUI 자산을 폐기할 일이 없다. 디자인 토큰(`UiPalette`·`UiMetrics`)과
> HUD 계층 규약(A/B/C/D)은 **이미 완료돼 있어 그대로 재사용한다**(§18 이행 1~3번 완료).

### 0.1 실측이 말하는 문제 3가지

1. **아이콘이 하나도 없다.** 핫바 5칸이 `목재 12` 같은 글자다. 가이드 §9.4의
   "아이템 자체를 크게, 슬롯 배경은 최소화"가 **아이콘 없이는 성립할 수 없다.**
   → 아이콘 세트는 다른 모든 화면의 **선행 조건**이다(§5 0차).
2. **프롬프트가 화면 중앙 고정이다.** `InventoryHud`의 5종 프롬프트(엔진·칸 건축·재연결·망치·판자)가
   전부 화면 중앙 텍스트다. 가이드 §9.4·§16이 명시적으로 금지한 기본값이다.
3. **`InventoryHud`가 1,169줄에 관심사 7개**다. uGUI 전환은 어차피 View를 새로 쓰므로,
   **분할과 전환을 두 번 하지 않고 한 번에 처리한다**(§6.4).

> 플레이가 개선되는" 단위여야 하고, IMGUI ↔ uGUI 병존 기간은 차수별로 짧게 끊는다.

## 4. 공통 인프라 — 화면보다 먼저 필요한 것

### 4.1 폰트 (TMP)

- 가이드 §13.1의 2단 타이포 — Display(로고·배너) / UI 한글 고딕(본문).
- **라이선스 확인이 선행**(가이드 §19 미결). 미확정 상태에서는 임시 폰트로 진행하되,
  **TMP Font Asset 참조를 `UiTheme` 한 곳에 모아** 교체가 1파일로 끝나게 한다.
- 한글 글리프 범위 — 동적 폰트 아틀라스 + 자주 쓰는 음절 정적 프리로드.

### 4.2 아이콘 세트 (약 55종)

| 그룹 | 수 | 출처 |
|---|---|---|
| 아이템 (무기·도구·장비) | 16 | `HotbarItemType` (None·Resource 제외) |
| 자원 | 22 | `ResourceType` (None 제외) |
| 구조물 | 7 | `StructureKind` |
| 상태·버프 | ~10 | 체력·허기·갈증·체온·동상·버프 4종 |

- 형태 규칙(선 굵기·모서리·최소 크기)은 가이드 §19 미결 → **0차에서 확정**한다.
- 전량을 한 번에 만들지 않는다 — **1차는 핫바에 실제로 뜨는 것부터**(무기 5 + 도구 2 + 1지역 자원 5).

### 4.3 Canvas 구조

```
UIRoot (DontDestroyOnLoad 아님 — 씬별)
├─ Canvas_HUD        Screen Space - Camera   sortingOrder 0   ← A/B/C 계층
├─ Canvas_World      World Space (풀링)                        ← 프롬프트·네임플레이트
├─ Canvas_Banner     Screen Space - Overlay  sortingOrder 10  ← D 계층
├─ Canvas_Window     Screen Space - Overlay  sortingOrder 20  ← 인벤토리·창고·제작
└─ Canvas_System     Screen Space - Overlay  sortingOrder 30  ← 세션 메뉴·게임오버·로딩
```

- **캔버스를 나누는 이유**: uGUI는 한 캔버스 안에서 하나만 바뀌어도 그 캔버스 전체를 리빌드한다.
  매 프레임 변하는 HUD와 거의 안 변하는 창을 같은 캔버스에 두면 창까지 매 프레임 리빌드된다.
- `CanvasScaler` = Scale With Screen Size, 기준 1920×1080, Match 0.5.
  `UiMetrics.ScaleFor`가 이미 배율을 계산하므로 **두 체계가 어긋나지 않게** 0차에서 정합을 맞춘다.
- Safe Area 적용 — 가이드 §17 "1080p / 1440p / 16:10에서 Safe Area 유지".

### 4.4 컴포넌트 프리팹 라이브러리 (가이드 §14)

| 그룹 | 프리팹 | 상태 |
|---|---|---|
| HUD | `StatusBar` · `ItemSlot` · `Prompt` · `Nameplate` | Normal / Warning / Critical |
| Navigation | `MenuItem` · `Tab` · `BackButton` | Default / Hover / Selected / Disabled |
| Settings | `OptionRow` · `Dropdown` · `Slider` · `Toggle` | Focus / Editing |
| Notification | `Banner` · `Toast` · `Tooltip` | Info / Warning / Urgent |

- **데이터 기반 재사용**이 원칙 — 화면마다 새로 그리지 않는다.
- 상태 색은 반드시 `UiPalette` 경유. 프리팹에 색 리터럴을 박지 않는다
  (`UiThemeBinder` 컴포넌트가 토큰 → `Graphic.color`를 대입).

### 4.5 문자열 분리

- 하드코딩 한국어를 `UiStrings` 정적 테이블로 옮긴다 — **키만 만들고 번역은 하지 않는다**(비범위).
- 새로 만드는 화면은 처음부터 키를 쓴다. 기존 화면은 전환하는 차수에서 함께 옮긴다.

| **5차** | **협동 UI 신규 4종** — 네임플레이트·부활 카운트다운·팀원 상태·피격 인디케이터(18~21) | 4인 플레이 가독성 | 2일 |
| **6차** | **프론트엔드** — 메인 메뉴·로비·설정·업적·로딩·조작 가이드(22~27) + 세션 메뉴·게임오버 이관 | IMGUI 전량 소멸 | 3일 |

**합계 14일** (병행 없음 기준)

### 5.1 이 순서인 이유

- **0차가 먼저인 이유**: 아이콘·폰트 없이 1차를 시작하면 핫바가 여전히 글자다. 0차를 건너뛰면
  1차를 두 번 하게 된다.
- **1차가 상태 기둥+핫바인 이유**: 플레이 중 **가장 오래 시야에 있는 것**이고, 지금 가장 안 읽힌다.
- **2차가 3차보다 앞인 이유**: 창은 열어야 보이지만 프롬프트는 **플레이 내내 계속 나온다.**
  가이드가 지목한 최대 몰입 저해 요소이기도 하다.
- **5차가 신규인데 6차보다 앞인 이유**: 프론트엔드는 **한 번 보고 지나가는 화면**이고,
  협동 UI는 **매 세션 내내 쓴다**. 결정 ③(플레이 완성도 우선)의 직접 귀결이다.
- **6차가 마지막인 이유**: 로비·설정은 없어도 플레이가 성립한다. 대신 분량이 가장 크다(3일).

### 5.2 차수별 완료의 의미

각 차수는 **그 차수만 끝나도 플레이가 개선되는** 단위다. 중간에 멈춰도 IMGUI와 uGUI가
계층 단위로 갈려 있어 화면이 뒤섞이지 않는다 — 캔버스가 계층별로 나뉘어 있기 때문이다(§4.3).

## 6. 설계

### 6.1 유지되는 규약 — UI는 상태를 소유하지 않는다

렌더 방식이 바뀌어도 [hud-architecture §4.2](../../specs/ui/hud-architecture.md)의 규약은 그대로다.

```
OnEnable  → EventBus<T>.Subscribe (자기 관심사만)
콜백      → 로컬 필드에 미러링 + 뷰 갱신        ← 여기만 바뀐다
OnDisable → Unsubscribe
```

**바뀌는 것은 한 줄뿐이다** — `OnGUI`에서 매 프레임 그리던 것을, 이벤트 시점에 uGUI 요소를
갱신하는 방식으로 옮긴다. 구독 대상·읽기 인터페이스(`ILocalHotbar`·`ITrainState`·`ICraftingStation`)·
변경은 요청 RPC만이라는 원칙은 **한 글자도 바뀌지 않는다.**

> **즉시 모드 → 보존 모드 전환의 실질적 함의**: 지금은 상태를 안 읽어도 매 프레임 다시 그려서
> 갱신 신호가 필요 없었다. uGUI에서는 **갱신 신호를 빠뜨리면 화면이 옛 값에 멈춘다.**
> 그래서 각 뷰는 구독 목록과 갱신 지점이 1:1로 대응하는지 확인하는 절차를 차수마다 둔다(§7).

### 6.2 어셈블리 — 변경 없음

`Game.UI`의 참조(`Game.Gameplay`·`Game.Systems`·`Game.Core`·`Game.Utilities`·`Unity.InputSystem`)에
**TMP 참조만 추가**된다. 의존 방향은 그대로 단방향이고, UI는 여전히 최상단이라 누구도 참조하지 않는다.

### 6.3 뷰 구성 — `BossHudView` 패턴 유지

기준형은 계속 `BossHudView`(147줄)다. uGUI 뷰도 같은 크기를 목표로 한다 —
**뷰 하나 = 관심사 하나 = 프리팹 하나.**

```
CoreLoopHud (635줄, 관심사 6개)
├─ HealthBarView        체력          ~90줄 + Prefab
├─ TimeLineView         Day·국면·지역  ~80줄 + Prefab
├─ FuelView             연료          ~70줄 + Prefab
├─ SurvivalStatsView    허기·체온·버프  ~120줄 + Prefab
├─ AmmoView             탄약·무기      ~80줄 + Prefab
└─ KillCountView        처치 수        ~60줄 + Prefab
```

### 6.4 `InventoryHud` 분할 — 전환에 흡수 (3차)

[리팩터링 조사 §4.3 1안](리팩터링-조사-보고서.md)의 6분할을 **그대로 채택하되, 별도 작업으로 하지 않는다.**
uGUI 전환이 어차피 View를 새로 쓰므로, 분할을 먼저 하면 같은 코드를 두 번 만지게 된다.

| 신설 뷰 | 담당 | 차수 |
|---|---|---|
| `HotbarView` | 핫바 5칸 + 선택 표시 | 1차 |
| `BuildPromptView` (→ 5개 월드 앵커 뷰) | 엔진·칸 건축·재연결·망치·판자 | 2차 |
| `InventoryPanelView` | 가방 + 장비 4부위 | 3차 |
| `StoragePanelView` · `BundlePanelView` | 창고 · 보따리 | 3차 |
| `HudDragState` | 드래그 상태 기계 (공유) | 3차 |

**`BuildSpendPreview` SSOT 위반**도 3차에서 함께 해소한다 — 조사 보고서 §4.3 A안
(미리보기 계산을 `HotbarLogic`의 전용 메서드로 내리고 UI는 호출만). 재배선이 없고 0.5일이며,
**이 계획에서 유일하게 실제 버그로 이어질 수 있는 항목**이다.

### 6.5 월드 앵커 프롬프트 (2차 — 이 계획의 핵심)

가이드 §9.4의 요구는 셋이다.

1. **대상 근처에 뜬다** — 월드 스페이스 캔버스를 대상 트랜스폼에 부착.
2. **흔들림 보정** — 갑판 진동을 그대로 따라가면 읽을 수 없다.
   프롬프트 위치를 **저역 통과 필터**로 따라가게 한다(계산은 순수 함수 → EditMode 대상).
3. **오브젝트명 → 입력 키 → 결과**가 한 덩어리로 읽힌다.

- 프롬프트는 **풀링**한다 (`PoolManager.Spawn/Despawn` — CLAUDE.md 제약). 조준 대상이 바뀔 때마다
  생성/파괴하면 GC가 튄다.
- 거리 LOD — 근거리 전체 / 중거리 키만 / 원거리 숨김.

### 6.6 네임플레이트 (5차)

- 월드 스페이스 캔버스 + 거리 LOD 3단(가이드 §10) — 근거리 이름+상태 / 중거리 이름 / 원거리 생략.
- **1차 식별자는 캐릭터 자체**이므로 이름표는 최소 배경 + `TextSteam` 소형.
- 위급 상태(빈사·이탈)에서만 §7.2 위험색을 허용한다.

## 7. 테스트·검증 계획

### 7.1 EditMode — 순수 계산만 (현행 방침 유지)

uGUI 렌더 자체는 테스트하지 않는다. 대신 **계산을 뷰에서 분리해 고정**한다.

| 차수 | 신규 테스트 대상 | 고정할 것 |
|---|---|---|
| 0차 | `UiTheme` 바인딩 · `CanvasScaler` ↔ `UiMetrics` 정합 | 두 배율 체계가 어긋나지 않는다 |
| 1차 | `StatusBarMath` (충전 비율 → 단계·길이) | 임계 경계에서 단계가 뒤집히지 않는다 |
| 2차 | `PromptAnchorMath` (흔들림 보정 · 거리 LOD 경계) | 진동 입력에 대한 출력 안정성 |
| 5차 | `NameplateLodMath` · `HitDirectionMath` (피격 방향 → 화면 각도) | 카메라 뒤쪽 처리 |

기존 38항목(`UiPaletteTests` 11 · `UiMetricsTests` 7 · `HudBannerQueueTests` 11 ·
`HudTransientFadeTests` 9)은 **전부 유지된다** — 토큰과 계층 인프라는 렌더 방식과 무관하다.

### 7.2 차수별 회귀 점검 (즉시 모드 → 보존 모드 전환 고유)

각 차수 종료 시 **구독 목록과 갱신 지점의 1:1 대응**을 점검한다.
`OnGUI`는 안 읽어도 매 프레임 다시 그렸지만 uGUI는 신호를 빠뜨리면 옛 값에 멈춘다(§6.1).

### 7.3 플레이 검증

차수별 `UI-N차-플레이-검증-항목.md`를 짝 문서로 만든다(plans 관례).
공통 통과 기준은 **가이드 §17 Acceptance Checklist 중 UI 관련 6항목**이다.

- ☐ HUD가 손·무기·조준점을 가리지 않는다
- ☐ 정상 상태에서 HUD 요소 수가 **3개 이하**
- ☐ 상호작용 프롬프트가 대상과 연결되고 **흔들림 중에도 읽힌다**
- ☐ UI와 3D 월드가 같은 재질 어휘를 공유한다
- ☐ 한국어 텍스트에서 설정 UI 정렬이 무너지지 않는다
- ☐ 1080p / 1440p / 16:10에서 Safe Area 유지
- ☐ 상태색을 흑백으로 바꿔도 단계가 구분된다 (색각 이상 대응)
