# 사다리 승하차 구현 계획 — 승차 램프 대체

> 상태: **1차 A~D 구현 완료** (2026-08-23) · EditMode 871/871 · **1-E 플레이 검증 대기** — 결과는 §9

---

## 0. 이 계획이 만들어진 경위

승차 램프는 [레벨 디자인 구현 계획 §10.9 ①](레벨-디자인-구현-계획.md)의 마지막 잔여다.
씬에 아직 **흰 큐브 7.64 × 3.71 × 2.00 m**(`Train/BoardingRamp`)가 그대로 있고, 모델 생성만
기다리는 상태였다. 그 모델을 만드는 대신 **사다리로 바꾼다** (2026-08-23 사용자 결정).

바꾸는 것이 단순 교체가 아닌 이유가 둘이다.

- **램프는 걸어 올라가면 끝이지만 사다리는 오르기 상태가 필요하다.** 중력·컨베이어 밀림이
  꺼진 별도 이동 모드를 `NetworkPlayerController`에 들여야 한다 — 이동 규칙에 손대는 첫 기능이다.
- **램프는 하차·낙하 대역을 가로지른다.** 칸 옆으로 7.64 m 뻗어 x 2.00~9.64를 차지하는데,
  [레벨 가이드 §4.2](../../design/Train-Survival-레벨디자인-가이드.md)는 3.3 < \|x\| ≤ 4 를
  "지면 높이 유지, 조형물 금지"로 잡아 뒀다. 사다리는 칸 옆면(\|x\| ≈ 2.45)에 붙어 **그 대역을 비운다.**

## 1. 범위

**포함**

- 사다리 볼륨(`BoardingLadder`)과 오르기 이동 규칙
- 진입·이탈 판정, 상단 올라서기(mantle)
- 후미 칸 추적 배치 — 기존 램프 배치기를 일반화해 재사용
- 씬의 `BoardingRamp` 제거
- 판정 순수 함수 + EditMode 테스트

**제외** (이 차수에서 하지 않는다)

| 항목 | 왜 미루나 |
|---|---|
| 오르기 애니메이션 | 캐릭터 FBX에 climb 클립이 없다 — idle/walk/run/jump/defeat/turn 6종뿐이다 (결정 ③) |
| 몬스터의 사다리 이용 | 몬스터 주행은 지상 대역(\|x\| 4~24) 전제다. 열차 등반은 별개 설계다 |
| 사다리 파괴·수리 | 칸 내구도 체계와 묶인다 |
| 여러 명 동시 오르기 | `CharacterController` 끼리 서로 밀어내는 것을 1차에서는 방치한다 (§6) |

## 3. 설계

### 3.1 이 기능의 진짜 문제는 좌표계다

열차는 원점 고정이고 월드가 −Z로 흐른다. `NetworkPlayerController.UpdateMove`는 접지 표면을
프로브해 **지상(`WorldFrameSurface`)이면 `_standingOnWorldFrame`을 켜고 스크롤 속도(6 m/s)만큼
로컬로 뒤로 민다.** 사다리는 열차 소속이므로 **붙는 순간 이 밀림이 꺼져야 한다.**

> **이 전환을 놓치면 증상이 이상하게 나타난다.** 사다리를 잡았는데 몸이 초당 6 m로 뒤로 흘러
> 사다리를 뚫고 나간다. "충돌이 안 먹는다"로 보이지만 원인은 콜라이더가 아니라 좌표계다.

반대로 **칸 무빙 플랫폼 델타(`_ridingCar`)는 계속 적용해야 한다.** 사다리는 칸에 붙어 있고
이탈 칸은 실제로 움직인다 — 델타를 끄면 칸이 떠나가는데 사람만 제자리에 남는다.

### 3.2 오르기 상태를 어디에 두나 — `PlayerMovementState`가 아니다

`PlayerMovementState`(Normal/Grabbed/Carried)는 **호스트 권위 `NetworkVariable`** 다. 사다리를
여기에 넣으면 잡을 때마다 RPC 왕복이 생기고, 호스트가 사다리 위치까지 알아야 한다. 붙는 판정은
전적으로 소유자 로컬 정보(내 캡슐이 볼륨 안인가 · 내 입력이 어디를 향하나)로 결정된다.

→ **`NetworkPlayerController`의 로컬 필드**로 둔다. 위치는 `OwnerNetworkTransform`이 이미 복제하므로
남의 화면에서도 올라가는 것이 보인다. 복제가 필요해지는 시점은 **포즈를 넣을 때**(3차)이고,
그때 `PlayerAnimationDriver`에 `Climbing` 파라미터를 Jump와 같은 연출 RPC 규약으로 올린다.

### 3.3 판정은 순수 함수가 소유한다

프로젝트 관례대로([SOLID 규칙](../../conventions/solid-principles.md)) 계산은 전부
`LadderClimbLogic`(`Game.Gameplay.Player`, `static`, 엔진 상태 무의존)에 두고, 컨트롤러는
입력을 읽고 트랜스폼을 움직이는 일만 한다.

```csharp
public static class LadderClimbLogic
{
    // 붙을 것인가 — 볼륨 안 + 이동 입력이 사다리 쪽 + 아직 안 붙음
    public static bool ShouldAttach(bool insideVolume, Vector3 wishDirection,
        Vector3 ladderApproachDirection, bool alreadyClimbing, float dotThreshold);

    // 이번 프레임 수직 이동량 (사다리 축 = 월드 +Y)
    public static Vector3 ComputeClimbMotion(float verticalInput, float climbSpeed, float deltaTime);

    // 떨어질 것인가, 왜
    public static LadderDetachReason ResolveDetach(float feetY, float bottomY, float topY,
        bool jumpPressed, bool insideVolume);

    // 사다리 평면으로 몸을 붙여 둔다 — 이게 없으면 오르는 동안 옆으로 샌다
    public static Vector3 ResolvePlaneCorrection(Vector3 position, Vector3 ladderOrigin,
        Vector3 ladderNormal, float holdDistance);

    // 점프 탈출 속도 — 법선 방향으로 밀어내고 위로 띄운다
    public static Vector3 ComputeJumpOffVelocity(Vector3 ladderNormal, float pushSpeed, float upSpeed);
}

public enum LadderDetachReason { None, Jump, TopReached, BottomReached, LeftVolume }
```

### 3.4 사다리 — `BoardingLadder` (`Game.Gameplay.Train`)

열차 부속이므로 `Train` 폴더다. 표현·데이터만 갖고 판정은 하지 않는다.

| 멤버 | 뜻 |
|---|---|
| `TopY` / `BottomY` | 오를 수 있는 구간 (월드 y). 상단은 갑판 상면과 같다 |
| `ApproachDirection` | 오르는 사람이 **바라보는** 방향 = 사다리 법선의 반대 (−X 쪽 칸 안으로) |
| `Origin` | 사다리 중심선의 수평 좌표 — 몸을 붙여 둘 기준 |
| `BoxCollider (isTrigger)` | 진입 볼륨 |

**볼륨을 트리거로 두는 이유**: `CharacterController`는 `OnTriggerEnter/Exit`를 받는다.
매 프레임 `OverlapBox`를 도는 것보다 싸고, "지금 볼륨 안인가"는 컨트롤러가 bool 하나로 들고 있으면 된다.

### 3.5 진입 — 세 조건이 동시에 참일 때

1. 사다리 볼륨 안에 있다
2. 이동 입력이 사다리 쪽이다 — `Dot(wishDirection, -ladderNormal) ≥ 0.3`
   (약 72° 안. 옆걸음으로 스치기만 해도 붙으면 짜증난다)
3. `MovementState == Normal` · 살아 있다 · 이미 오르는 중이 아니다

붙는 프레임에 하는 일:

```
_climbing = true
_verticalSpeed = 0            // 낙하 속도를 끌고 들어가면 붙자마자 미끄러진다
_horizontalVelocity = zero
_standingOnWorldFrame = false // 컨베이어 밀림 차단 (3.1)
위치를 사다리 평면으로 스냅
```

### 3.6 오르내리는 동안

| 항목 | 규칙 |
|---|---|
| W / S | 월드 +Y / −Y, 속도 **2.4 m/s** (걷기 4.5의 절반보다 조금 빠르게 — 느리면 쫓길 때 답답하다) |
| A / D | **무시한다.** 사다리는 한 줄이다 — 좌우를 살리면 몸이 사다리를 벗어나고 §3.7의 `LeftVolume`이 오작동한다 |
| 시선 | 자유. 오르면서 뒤를 볼 수 있어야 한다 |
| 중력 | 없음 |
| 컨베이어 밀림 | 없음 (3.1) |
| 칸 델타 | **적용한다** (3.1) |
| 평면 유지 | 매 프레임 `ResolvePlaneCorrection` 으로 사다리 중심선에서 `holdDistance`(0.45 m) 떨어진 자리로 되당긴다 |

### 3.7 이탈 — 네 가지

| 사유 | 판정 | 처리 |
|---|---|---|
| `Jump` | 스페이스 | 법선 방향 수평 3 m/s + 위로 점프 속도의 0.7배로 튕겨낸다. 그냥 놓으면 사다리에 다시 붙는다 |
| `TopReached` | 발 y ≥ `TopY` | 갑판 위로 올려놓는다 (§3.8) |
| `BottomReached` | 발 y ≤ `BottomY` | 해제. 다음 프레임 접지 프로브가 지상을 잡아 컨베이어 밀림이 다시 켜진다 |
| `LeftVolume` | 볼륨 밖 | 해제 + 자유낙하. **칸 이탈·파괴로 사다리가 사라지면 여기로 들어온다** (§6) |

사망·구속 상태 전환(`Grabbed`/`Carried`)에서도 즉시 해제한다 — 하푼에 잡힌 채 사다리에 붙어 있으면
견인과 오르기가 같은 프레임에 트랜스폼을 다툰다.

### 3.8 상단 올라서기가 이 기능에서 가장 까다롭다

사다리 꼭대기에서 그냥 해제하면 **갑판 옆 허공**이라 그대로 떨어진다. 램프에는 없던 문제다.

상단 도달 프레임에 `CharacterController.Move`로 처리한다.

- 수평: 법선 반대(갑판 안쪽)로 **1.0 m** ⚠ — 계획 시점의 0.7(캡슐 반경의 2배)은 **틀렸다**.
  매달린 몸은 사다리 중심선(x 2.45)에서 유지 거리 0.45만큼 바깥, 즉 **x 2.90**에 있다.
  캡슐 전체가 갑판(±2.30, 반경 0.35) 안에 들어가려면 x ≤ 1.95여야 하므로 0.95 이상이 필요하다.
  1.0을 쓰면 x 1.90 · 캡슐 바깥 끝 2.25로 갑판 안이다 (§9 실측)
- 수직: 발이 갑판 상면 + 0.05
- **수직을 먼저, 수평을 나중에** 옮긴다 — 한 벡터로 주면 대각선 이동이 갑판 모서리에 걸린다

> 한 프레임 순간이동이라 1인칭 카메라가 튈 수 있다. **먼저 순간이동으로 만들고 실제로 튀는지 본다** —
> 0.15초 보간은 튈 때 넣는다. 안 튀는데 미리 넣으면 올라서는 감각만 굼떠진다.

### 3.9 배치 — 후미 추적 로직을 물려받는다

`BoardingRampPositioner`는 이미 필요한 일을 정확히 한다: `TrainInitializedEvent`·`CarStateChangedEvent`를
받아 살아 있는 마지막 칸을 찾고, **X·Y는 씬 값을 두고 Z만** 맞춘다.

→ **`BoardingAccessPositioner`로 개명해 램프·사다리 공용으로 쓴다.** 램프가 사라지는데 이름만 남으면
다음 사람이 "램프가 어디 있지"부터 헤맨다.

- `BoardingRampAnchor` → `BoardingAccessAnchor` (`RearEdge` / `RearCenter` 그대로)
- 직렬화 필드는 `FormerlySerializedAs`로 흡수 — `Game.unity`는 기본값 `RearEdge`라 회귀 없음
- `Game_ArtTest` 씬 값: `anchor = RearCenter(1)` 유지, `_zOffset`은 사다리에 맞게 재조정

### 3.10 사다리 규격 — 에셋 반입 전에 자리부터 못 박는다

모델은 블렌더에서 오는 중이다. **치수는 이 표가 기준이고 모델을 여기에 맞춘다** —
반대로 하면 갑판 높이·바퀴·클리어 존이 전부 흔들린다.

| 항목 | 값 | 근거 |
|---|---:|---|
| 상단 | y **3.566** | `TrainLayoutSettings.DeckHeight`. 갑판 상면과 같아야 올라선 다음 바로 걷는다. **QA 높이 토글(F2)이 갑판을 올리면 사다리도 따라가야 한다** — 씬 상수가 아니라 설정에서 읽는다 |
| 하단 (메시) | y **0.5** | 지면(y 0)에 닿이면 초당 6 m로 흐르는 지면을 긁는다 |
| 하단 (볼륨) | y **0.2** | 메시보다 낮게 — 지상에 선 사람이 닿을 수 있어야 한다 |
| x | **2.45** | 칸 옆면 2.3 + 두께. 바퀴(x 1.63~2.37)를 피하고, 하차·낙하 대역(3.3 < \|x\|)에 안 들어간다 |
| 폭 | **0.70** | 캡슐 지름 0.7과 같다 — 몸은 사다리 평면에 스냅된다 (§3.6) |
| 볼륨 | 앞 **0.85** × 폭 **0.9** × 높이 3.566 | 캡슐 반경 0.35 + 여유 |
| 오르는 속도 | **2.4 m/s** | 3.07 m 구간을 1.28초에 오른다 |
| 유지 거리 | **0.45** | 사다리 중심선에서 몸 중심까지 |
| 올라서기 안쪽 이동 | **1.0** ⚠ | §3.8 — 0.7로는 갑판 가장자리에 걸린다 |

### 3.11 램프 제거에 딸린 것

- 씬 `Train/BoardingRamp` 삭제 (Cube + `M_Default` + `BoxCollider` + `BoardingRampPositioner`)
- `NetworkPlayerController.CoplanarSurfaceTolerance`(0.3)의 **주석**이 근거로 드는 것이
  "승차 램프 상단이 지붕보다 최대 ~15 cm 높게 겹치는 저작 여유"다. 램프가 사라지면 그 근거는
  없어지지만 **값은 유지한다** — 이탈 칸과 정적 지형이 같은 평면으로 겹치는 상황은 그대로 있다.
  주석만 고친다.
- [train-art-layout §7.5](../../specs/world/train-art-layout.md)의 "승차 램프" 절과 §8.3
  "남은 프리미티브" 표를 갱신한다.

## 4. 구현 순서 (차수 분할)

각 지점에서 **컴파일되고 테스트가 통과하는지**가 커밋 경계다.

| 단계 | 내용 | 산출 |
|---|---|---|
| **1-A** | `LadderClimbLogic` + `LadderDetachReason` + EditMode 테스트 | 게임에 아무 변화 없음. 판정이 먼저 선다 |
| **1-B** | `BoardingLadder` 컴포넌트 · `BoardingAccessPositioner` 개명 | 씬에 붙기 전이라 여전히 무변화 |
| **1-C** | 씬 배선 — 램프 제거 + **프리미티브 사다리**(큐브 3개: 기둥 2 + 볼륨) 배치 | 모델 없이 자리와 볼륨만. 여기서 이미 올라갈 수 있어야 한다 |
| **1-D** | `NetworkPlayerController` 오르기 분기 | 기능 완성 |
| **1-E** | 플레이 검증 (별도 문서) | |
| **2차** | 사다리 모델 반입 → 프리미티브 교체 | 에셋 도착 후. [반입 규약](../../specs/world/train-art-layout.md) |
| **3차** | 오르기 포즈 — climb 클립 확보 + `Climbing` 파라미터 복제 | |

**1-C를 1-D보다 먼저 두는 이유**: 볼륨과 좌표를 눈으로 확인한 뒤 이동 코드를 짜야, 안 붙을 때
원인이 "판정이 틀렸나 자리가 틀렸나"로 갈리지 않는다.

## 5. 테스트·검증 계획

**EditMode** (`LadderClimbLogicTests`) — 최소 이만큼은 고정한다.

| 대상 | 케이스 |
|---|---|
| `ShouldAttach` | 볼륨 밖이면 안 붙는다 / 입력이 사다리 쪽이 아니면 안 붙는다 / 이미 오르는 중이면 다시 안 붙는다 / 세 조건이 맞으면 붙는다 |
| `ComputeClimbMotion` | 입력 0이면 이동 0 / 위·아래가 부호로 갈린다 / 속도 × dt 를 넘지 않는다 |
| `ResolveDetach` | 상단 초과 = `TopReached` / 하단 미만 = `BottomReached` / 점프가 최우선 / 볼륨 밖 = `LeftVolume` / 구간 안 + 입력 없음 = `None` |
| `ResolvePlaneCorrection` | 옆으로 밀린 위치가 유지 거리로 되당겨진다 / 이미 맞으면 안 움직인다 |
| `ComputeJumpOffVelocity` | 법선 성분이 양수 / 수직 성분이 양수 |

**플레이 검증** — 별도 문서(`사다리-승하차-플레이-검증-항목.md`)로 뺀다. 핵심 항목:

- 지상에서 달려와 붙는가 (열차가 6 m/s로 앞서 나가는 중에)
- 오르는 동안 뒤로 안 흐르는가 (§3.1 — **이것이 첫 번째 확인 항목이다**)
- 꼭대기에서 갑판으로 올라서는가, 카메라가 튀는가 (§3.8)
- 점프로 떨어지면 사다리에 다시 안 붙는가
- 두 벌 접속에서 **남이 오르는 것이 보이는가** (위치 복제만으로)
- 오르는 중 후미 칸을 이탈시키면 어떻게 되는가 (§6)

### 9.1 에셋 — `Train_Ladder`

블렌더의 Meshy `Worn Brass Ladder`는 **상단에 갈고리가 달린 1.9 m짜리 한 단**이었다.
그대로 3.07 m로 키우면 폭이 1.39 m가 되고 **가로대 간격이 0.57 m로 벌어져** 사람 사다리가 아니게 된다.

→ **두 단을 이어 붙였다.**

| 처리 | 값 | 이유 |
|---|---|---|
| 아래 단 | 갈고리 정점 194개 삭제 | 이음매에 갈고리가 튀어나온다 |
| 위 단 | 갈고리 유지 · z +1.87 | 원본 길이 1.902보다 살짝 겹쳐 이음매 마디를 감춘다 |
| 정규화 | 최대 치수 1 · **원점 = 발치** | 씬에서 사다리가 설 y에 그대로 놓는다 |
| `globalScale` | **3.07** | 높이 3.070 · 폭 0.699 · 두께 0.267 · 가로대 간격 0.31 |
| tris | 4,957 · Mesh LOD 3단 | |

**갈고리 방향은 씬에서 뒤집었다.** 반입 상태로는 −X(칸 쪽)를 향해 칸 몸통에 파묻혔다 —
FBX 기본 회전에 yaw 180을 합성해(반입 규약 §10.2) 바깥으로 돌리니 갑판 위 손잡이로 읽힌다.

### 9.3 구현에서 드러난 것

**① 올라서기 거리가 계획값의 1.4배였다** (§3.8) — 계획은 "캡슐 반경의 2배"로 0.7을 잡았는데,
**매달린 몸이 이미 칸 옆면 바깥 0.6 m에 있다**는 것을 안 셌다. 실측으로 1.0으로 고쳤다.

**② 사다리가 통째로 옮겨가는 경우를 볼륨 이탈에만 맡길 수 없다** — 트리거 콜백은 물리 갱신 시점에
와서 한 프레임 늦는데, 그 사이 평면 보정이 먼저 순간이동시킨다. `IsPlaneCorrectionTooFar`
(상한 0.5 m)를 더해 **보정이 감당할 범위를 넘으면 따라가지 않고 떨어지게** 했다.

**③ 씬 배선은 스크립트 컴파일 뒤에 해야 한다** — 씬을 저장하기 전에 컴파일이 돌면 도메인 리로드가
미저장 변경을 통째로 버린다(실제로 한 번 날렸다). 1-C를 1-D보다 앞에 둔 계획은 순서가 반대였다:
**컴포넌트 코드가 다 컴파일된 뒤 배선하고 곧바로 저장**하는 것이 맞다.
