# 천막 구현 계획 — 사막을 건너는 그늘

> **상태**: **1·2차 구현 완료 (2026-08-30) · 플레이 검증 대기** — as-built는 §5.3·§6.1, 판정은 §5.4·§6.3
> **기준 커밋**: `feat/region-biomes` = `29df33f` · EditMode **1,339/1,339**
> **핵심**: 사막 낮 45 ℃에서 **16초면 체력이 깎이기 시작하는데 피할 곳이 없다.**
> 그늘 시스템은 이미 다 서 있고 **건축물만 없다.**

---

## 0. 이 계획이 만들어진 경위

사용자 지시 — *"현재 천막이 없어 사막을 건널 수 없다. 천막은 이전 온실돔과 비슷하며,
천막에 들어갈 경우 햇빛을 피해 온도가 내려간다는 설정이다."*

사막 지역은 [사막 지역 구현 계획](사막-지역-구현-계획.md) 1~4차로 **화면이 다 섰다.**
그런데 **살아서 건널 수단이 없다.** 원인은 2026-08-16에 미뤄 둔 결정 하나다 —
[건축 시스템 개편 계획](건축-시스템-개편-계획.md) §1.2가 온실 돔을 *"통행 차단 문제로
이번 개편에서 제외, **출입 구조 포함해 차후 재설계**"* 로 남겼고, 그 재설계가 이 문서다.

### 0.1 시스템은 이미 다 서 있다 ★

이 계획이 싼 이유다. **더위 완화 경로는 M5 3차에 완성돼 지금도 살아 있다.**

| 이미 있는 것 | 위치 | 상태 |
|---|---|---|
| 그늘 효과 계산 | `TemperatureMath.ResolveAmbient` | 동작. 더울 때만 적용 |
| 그늘 판정 | `PlayerTemperature.ResolveShelter` → `hasShade` | 동작. **칸 단위** |
| 그늘 계수 | `TemperatureSettings._shelterFactor = 0.8` | 배선됨 |
| 그늘 제공 플래그 | `StructureCatalog` 돔 엔트리 `_providesShade: 1` | **켜져 있다** |
| 발자국 복제 | `StructureEntry.FootprintWidth/Length` (byte) | **직렬화까지 돼 있다** |

**없는 것은 딱 둘** — 설치 가능한 건축물(`_placeable: 0` · `_viewPrefab` 비어 있음)과
가변 크기 설치 입력.

## 1. 확정 결정 6건 (2026-08-30, 사용자 결정)

| # | 결정 | 영향 |
|---|---|---|
| ① | **새 종류 `StructureKind.Tent = 9` 신설** | 돔(0)은 온실로 남긴다 · §4.1 |
| ② | **가변 크기 차양** — 우클릭 2회로 시작점·끝점 | 이 계획의 본체 · §4.2 |
| ③ | **그늘은 발자국 안에서만** | 칸 단위 boolean을 깬다 ⚠ · §4.4 |
| ④ | **칸 경계를 넘으면 칸별로 쪼개 여러 채 생성** | 복제 규약 무변경 · §4.3 |
| ⑤ | ~~비용 = 셀 넓이 비례~~ → **⑤′ 개정: 크기 무관 · 한 채 = 기둥 넷 = 4** | §4.5 ⚠ |
| ⑥ | **점유는 4기둥 셀만** — 내부는 비어 다른 건축물이 들어간다 ★ | 점유와 효과 범위가 갈린다 · §4.6 |

### 1.1 결정 ①의 근거 — 돔을 덮어쓰지 않는다

돔 엔트리를 천막으로 개명하는 쪽이 코드 변경 0으로 가장 쌌다. 그러나 **돔은 "온실"이고
작물 재배라는 미구현 역할이 이름에 남아 있다.** 값 0은 직렬화 규약상 어차피 유지해야 하므로
(`StructureKind` 주석), 덮어쓰면 그 역할이 갈 곳이 없어진다. `Tent = 9`를 세우고 돔은
`_placeable: 0`인 채로 둔다.

### 1.2 결정 ③이 깨는 것 ⚠

`ResolveShelter`는 주석에 *"효과 범위는 칸 단위 boolean 유지 (건축 개편 계획 §5 —
**의식적 선택**)"* 이라고 못박혀 있다. 결정 ③은 이 선택을 천막에 한해 뒤집는다.

**비대칭이 생긴다** — 난방기·강화 난방로는 칸 어디서든 듣고, 천막만 발자국 안에서 듣는다.
받아들이는 근거는 사용자 설정이다: *"천막에 들어갈 경우"*. 지붕이 있는 자리와 없는 자리가
같으면 크기를 정하는 의미가 사라진다.

**종류를 코드가 알지 않게 한다** — 카탈로그에 효과 범위 필드를 두고 데이터가 소유한다
(`GetHeaterFuelPerSecond`로 강화 난방로를 판별하는 기존 규약과 같은 방식).

## 2. 실측 기준선 — 이 계획이 쓰는 자

### 2.1 사막은 얼마나 위험한가

| 값 | 출처 |
|---|---|
| 사막 낮 **45 ℃** / 밤 2 ℃ | `Region_Desert.asset` `_dayAmbientTemperature` |
| 쾌적대 **10~32 ℃** | `TemperatureSettings._comfortMin/_comfortMax` |
| 표류율 **0.012 ℃/s per ℃** | `_driftRatePerDegree` |
| 고온 경고 **38 ℃** · 피해 **39 ℃** | `_heatWarnThreshold` / `_heatDamageThreshold` |
| 피해량 **3 HP/s per ℃** | `_damagePerDegreePerSecond` |

**계산** — 낮 초과분 45 − 32 = 13 ℃ → 표류 0.156 ℃/s.
정상 체온 36.5에서 **경고까지 9.6초 · 피해 시작까지 16.0초.**
사막은 Day 6~9 **4일**이다. 그늘 없이는 갑판 위조차 못 버틴다.

### 2.2 그늘이 들으면 얼마가 되는가

`ResolveAmbient` = `Lerp(45, ComfortCenter 21, 0.8)` = **25.8 ℃** → 쾌적대 안.
표류가 멈추고 회복(`_recoveryRate 0.35`)으로 돌아선다. **그늘 하나로 완전히 해결된다.**

> **밤에는 아무 일도 없다** — `hasShade && regionAmbient > ComfortMax`가 조건이라
> 밤 2 ℃에는 적용 자체가 안 된다. 코드 주석 그대로 *"지붕이 햇빛은 가려도 난방은 되지 않는다"*.
> **난방기와 역할이 겹치지 않는다**(건축물 1종 = 역할 1개 계약 유지).

### 2.3 설치 격자

| 값 | 출처 (**에셋 실값** — 코드 기본값과 다르다 ⚠) |
|---|---|
| 칸 길이 **15 m** · 폭 **4.6 m** | `TrainLayoutSettings.asset` (코드 기본값은 12·3) |
| 격자 셀 **1 m** | `_structureCellSize` |
| 갑판 가장자리 제외 **1행씩** | `_deckEdgeRows: 1` → `DeckLength` = 13 |
| 칸 본체 **4열** | `BodyColumns(4.6, 1)` = floor(4.6) |
| 판자 증축 좌우 **각 1열** | `TrainExpansionSettings._maxPlankColumns: 1` |
| **칸당 설치 격자 = 폭 4열(판자 포함 최대 6) × 길이 13행** | 위 값들의 곱 |
| 기본 편성 **3칸** | `ResolveCarIndexAt` 주석 |

기존 건축물 발자국 — 난방기 1×1 · 화덕 1×1 · 창고 2×1 · 제작대 2×1.
**열 좌표는 고정 예약계**다 — 열 0~1이 좌측 판자 자리라 칸 본체는 열 2부터 시작한다
(`StructureGridLogic.FirstBodyColumn`). 천막도 이 좌표계를 그대로 쓴다.

### 2.4 돔이 못 들어간 진짜 이유 ⚠

**돔 4×4는 칸에 들어간다** — 본체가 정확히 4열이라 폭이 딱 맞는다.
문제는 **폭 전체를 먹어 옆으로 지나갈 틈이 없다**는 것이었다(판자가 없으면 4열이 전부다).
2026-08-16의 "통행 차단" 진단이 정확했다.

**천막은 이 문제가 원천적으로 없다** — 점유가 4기둥뿐이라(결정 ⑥) 폭을 다 덮어도
안쪽이 뚫려 있다. 폭 상한은 그 칸의 유효 열 수(판자 포함 4~6)에서 읽어 클램프한다(§4.2).

## 3. 실측이 찾아낸 어긋남 3건 ⚠

### 3.1 설치는 좌클릭이 아니라 우클릭이다

사용자 설명은 *"처음 좌클릭"* 이었으나 `RepairHammerController`는
**좌클릭 홀드 = 수리 · 우클릭 = 설치**다. 천막만 좌클릭으로 하면 망치의 의미가 갈린다.
**우클릭 2회(시작 → 끝)로 맞춘다.** 조작 뜻은 그대로 살아 있다.

### 3.2 `StructureEntry`는 칸을 넘지 못한다

`CarIndex`가 byte 하나다. 열차 전체를 덮는 단일 엔트리는 그릇에 담기지 않는다.
결정 ④(칸별 분할)가 이걸 우회한다 — **칸이 이탈·파괴돼도 그 칸 몫만 사라진다**는
부수 효과가 오히려 옳다.

### 3.3 발자국은 이미 엔트리에 실려 복제된다

`TrainState.cs:925`가 카탈로그 값을 복사해 넣고 있다. 가변 크기는 **이 복사원을
카탈로그 고정값에서 사용자 드래그 값으로 바꾸는 것**이지, 새 복제 필드가 필요한 일이 아니다.
**복제 규약 무변경.**

## 4. 설계

### 4.1 종류와 카탈로그

`StructureKind.Tent = 9` 신설. 카탈로그 엔트리:

| 필드 | 값 | 근거 |
|---|---|---|
| `_displayName` | 천막 | |
| `_providesShade` | **1** | 기존 경로를 그대로 탄다 |
| `_providesHeat` | 0 | 역할 1개 계약 |
| `_placeable` | **1** | |
| `_footprintWidth/Length` | 1×1 | **최소값** — 실제 크기는 드래그가 정한다 |
| `_maxHealth` | 30 | 천이라 돔(50)보다 약하다 |
| **`_resizable`** (신설) | 1 | 가변 크기 플래그 |
| **`_costPerCell`** (신설) | 0.25 | 셀 4개당 자원 1 (결정 ⑤) |
| **`_shelterScope`** (신설) | Footprint | 결정 ③. 기본값은 Car(기존 규약) |
| **`_occupancy`** (신설) | Corners | 결정 ⑥. 기본값은 Solid(기존 규약) · §4.6 |

### 4.2 가변 크기 설치 — 우클릭 2회

1. 망치로 천막을 고르고 **첫 우클릭** → 그 셀이 **시작 앵커**로 고정된다
2. 조준을 옮기면 시작 앵커 ~ 현재 셀의 사각형이 고스트로 그려지고 **셀 수·비용이 표시**된다
3. **두 번째 우클릭** → 확정. 자원이 모자라면 거절(기존 비용 지불 경로 재사용)
4. 도중에 무기를 바꾸거나 조준이 열차를 벗어나면 **앵커 취소**

**폭은 그 칸의 유효 열 수(판자 포함 4~6)로 자른다.** 길이는 칸 경계에서 잘려 다음 칸으로 넘어간다.

### 4.3 칸 경계 분할 (결정 ④)

드래그 사각형을 칸별로 잘라 **칸마다 엔트리 1채**를 만든다. 3칸에 걸친 천막 = 엔트리 3개.
각 엔트리는 자기 칸 안의 `CellX·CellZ·FootprintWidth·FootprintLength`만 든다.
비용은 **전체 셀 수 기준으로 한 번** 계산해 지불한다(칸마다 반올림하면 쪼갤수록 비싸진다).

### 4.4 그늘 판정 (결정 ③)

`ResolveShelter`가 엔트리를 순회할 때, 카탈로그의 효과 범위가 `Footprint`면
**플레이어의 셀 좌표가 그 엔트리의 발자국 사각형 안인지** 본다. `Car`면 지금처럼 칸 단위.

필요한 데이터(`CellX`·`CellZ`·발자국)는 **이미 복제되고 있다**(§3.3). 플레이어 셀 좌표는
`ResolveCarIndexAt`이 이미 칸을 찾으므로 그 안에서 로컬 좌표로 환산한다.

### 4.5 비용 (결정 ⑤′ — 2026-08-30 개정) ★

**천막이 드는 재료는 덮은 넓이가 아니라 세운 기둥이다.** 한 채는 기둥 넷이므로
**크기와 무관하게 한 채 = 4**다. 2×2든 칸 하나를 통째로 덮든 같다.

| 드래그 | 채 | 비용 |
|---|---:|---:|
| 2×2 · 4×4 · 칸 하나 전체(4×13) | 1 | **4** |
| 두 칸에 걸침 | 2 | **8** |
| 열차 전체(3칸) | 3 | **12** |

칸을 넘으면 칸마다 한 채가 서므로(결정 ④) **기둥도 실제로 그만큼 늘어난다.**
열차 전체 차양 12는 칸 건설(5)의 2.4배 — 사막 진입 전에 모아 둘 만한 무게다.

> **초안(넓이 비례 `ceil(셀 수 × 0.25)`)을 개정한 것이다.** 그 규칙이면 열차 전체가 **39**로
> 칸 여덟 개 값이 되어, 정작 가장 필요한 "길게 덮기"가 가장 비싸졌다.
> 넓이 비례 경로 자체는 `_costPerCell > 0`으로 남겨 두었다 — 넓이가 곧 재료인 다음 종류를 위해서다.

### 4.5.1 첫 우클릭은 한 칸만 본다 (결정 ⑤′와 함께 개정)

**첫 클릭은 기둥 하나를 꽂는 것**이므로 그 셀 1칸만 비어 있으면 된다.
카탈로그 최소 발자국(2×2)으로 판정하면 **옆 세 칸이 막혔다는 이유로 시작점조차 못 잡는데**,
정작 그 세 칸은 기둥이 설 자리도 아니다. 확정 시점에 네 모서리를 다시 본다.

### 4.6 점유는 4기둥, 효과는 사각형 전체 (결정 ⑥) ★

**이 계획에서 가장 중요한 구분이다.** 천막은 지붕이지 방이 아니다.

| 축 | 범위 | 뜻 |
|---|---|---|
| **점유**(설치를 막는 자리) | **4모서리 셀 4개뿐** | 안쪽은 비어 있어 **난방기·제작대·화덕이 천막 안에 들어간다** |
| **그늘 효과** | 사각형 **전체** | 지붕이 덮은 만큼 그늘이 진다 (결정 ③) |
| **비용** | 사각형 **전체 셀 수** | 천이 넓으면 재료가 든다 (결정 ⑤) |

현재 `StructureGridLogic.CanPlace`는 **발자국 사각형 전체를 점유로 본다.**
여기에 점유 형태를 넣는다 — 카탈로그 `_occupancy`가 소유한다:

- **`Solid`** (기본값) — 사각형 전체. 기존 건축물 8종 전부 이 값이라 **무변경**
- **`Corners`** (천막) — 네 모서리 셀만. 나머지는 빈 자리로 취급

**양방향으로 성립해야 한다** — 천막 안에 난방기를 나중에 지을 수 있고, 이미 난방기가 선
자리 위로 천막을 덮을 수도 있다. **검증은 "겹치는 셀이 있는가"** 하나로 통일되므로
`Corners`가 자기 4셀만 내놓으면 두 방향이 자동으로 성립한다.

> **3×3보다 작으면?** 2×2는 네 셀이 곧 네 모서리라 `Solid`와 같아지고, 1×N은 모서리가
> 2개로 줄어든다. **최소 크기를 2×2로 강제**해 "기둥 4개"라는 형태가 늘 성립하게 한다.

### 4.7 뷰

기둥 + 천. 가변 크기라 **프리팹 하나를 스케일**한다 — 천은 X·Z로 늘리고 기둥은
네 모서리에 **스케일 보정으로 굵기를 유지**한다. 콜라이더는 두지 않는다(통행 자유).

## 6.4 Play 검증 1회차 — 결함 2건 (2026-08-30) ⚠

사용자가 실제로 세워 보고 잡은 것이다. **둘 다 EditMode가 잡을 수 없는 종류**였다 —
순수 로직은 전부 맞았고, 로직과 화면을 잇는 두 지점에서 어긋났다.

### ① 기둥 넷이 한 점에 겹쳐 "기둥 하나"로 보였다

**증상** — 두 번째 우클릭으로 천막이 서면 기둥이 하나만 가운데에 있다.

**원인** — `StructureViewSpawner`가 `TryGetComponent`로 `IStructureFootprintView`를 찾았다.
**Unity의 `TryGetComponent`는 인터페이스를 찾지 못하고 조용히 false를 돌려준다.**
`GetComponent`는 찾는다. 그래서 `ApplyFootprint`가 한 번도 불리지 않았고, 천막이
**프리팹 원본 상태**(기둥 넷이 한 점에 모인 채)로 섰다.

**처방** — `GetComponent`로 바꾸고, 프리팹 원본의 기둥 기본 위치도 2×2 모서리로 흩어
발자국이 적용되지 않는 경로가 또 생기더라도 천막 꼴이 유지되게 했다.
계기 2건(`발자국을_주면_기둥_넷이_모서리_끝으로_간다`·`프리팹_기본_상태에서도_기둥이_겹치지_않는다`).

> **오류도 경고도 없었다.** 이 계획에서 같은 종류의 침묵이 두 번째다(2차 §6.2-1의
> `SV_IsFrontFace`). 표현 계층은 실패해도 조용하다는 것을 기록해 둔다.

### ② 칸을 끝까지 덮을 수 없었다

**증상** — 열차 칸 전부를 채우지 못한다.

**원인** — 드래그 중 커서 스냅이 **카탈로그 발자국(2×2) 기준**이었다.
`TryWorldToPlacementCell`은 점유가 격자를 넘지 않도록 발자국만큼 안쪽으로 클램프하므로,
커서가 닿는 범위가 **본체 4열 중 3열 · 13행 중 12행**으로 줄어 있었다.

**처방** — 가변 크기에서 **커서는 기둥 하나가 갈 자리**이므로 언제나 1칸으로 스냅한다.
실제 크기는 두 점이 정하므로 커서 판정에 발자국을 쓸 이유가 없었다.

## 6.5 Play 검증 2회차 — 결함 3건 (2026-08-30) ⚠

### ① 가로로는 넓힐 수 없었다 (세로만 늘어남)

**원인** — `ResolveDragPreview`가 고스트 원점(사각형 좌하단)을 **커서 좌표에 덮어썼다.**

**원인** — `StructurePlacementGhostView`가 프리팹 사본을 **크기 반영 없이** 놓기만 했다.

**처방** — 프리뷰 이벤트에 발자국 칸 수를 실어 고스트에도 `ApplyFootprint`를 걸었다.

여기서도 `GetComponent`를 쓴다(§6.4 ①과 같은 이유).

**원인** — 겹침 판정이 "막는 셀이 겹치는가"뿐이라, 기둥 넷만 피하면 지붕 아래 또 지붕이 섰다.

## 6.6 Play 검증 3회차 — 결함 2건 (2026-08-30) ⚠

### ① 자리가 막히면 프리뷰가 통째로 사라졌다

**증상** — 천막 위에 천막을 겨누면 아무것도 안 보인다. 자원이 모자랄 때는 빨갛게 뜨는데,
자리가 막힐 때는 왜 못 짓는지 화면이 말해 주지 않았다.

**원인** — `TryUpdatePlacementAim`이 **그리드 판정 결과를 반환값으로 썼고**, 호출부는 그것이
false면 `PublishNoPlaceAim()`으로 고스트를 껐다. 자원 부족은 그리드 판정과 무관해서
(`canPlace`는 true) 프리뷰가 남아 빨갛게 보였던 것이다 — 두 실패가 서로 다른 대접을 받았다.

**처방** — 반환값을 **조준 성립**으로 바꾸고 설치 가능 여부는 `out canPlace`로 뺐다.
이제 자리가 막혀도 프리뷰가 **빨갛게 떠 있고** 우클릭만 막힌다. 두 실패가 같은 방식으로 보인다.

### ② 프리뷰가 여전히 원본 크기 덩어리였다

2회차 §6.5 ②에서 고스트에 `ApplyFootprint`를 걸었는데도 그대로였다.

**원인** — `StructurePlacementGhostView.StripStateBinding`이 **`StructureView`에 의존한다고
선언한 컴포넌트를 전부 떼어낸다.** `TentView`는 `[RequireComponent(typeof(StructureView))]`라
그 그물에 걸려 프리뷰 사본에서 사라졌고, 그래서 `GetComponent`가 null을 돌려줬다.

**처방** — `IStructureFootprintView`는 예외로 남긴다. 상태(`StructureEntry`)를 읽지 않고
**모양만** 맞추는 순수 표현이라 고스트에서도 그대로 쓸 수 있다.

> **이 계획에서 네 번째 침묵이다** — `SV_IsFrontFace`(2차) · `TryGetComponent`(1회차) ·
> 고스트 좌표 덮어쓰기(2회차) · 그리고 이번 둘. **표현 계층은 실패해도 오류를 내지 않는다.**

### ③ 그 처방이 곧바로 예외를 냈다 (같은 날 후속)

`Can't remove StructureView (Script) because TentView (Script) depends on it`

②의 처방으로 `TentView`를 프리뷰에 남겼더니, **그다음 줄에서 `StructureView`를 떼지 못했다.**
`TentView`에 붙은 `[RequireComponent(typeof(StructureView))]`가 제거를 막은 것이다.

**처방** — `TentView`에서 `RequireComponent`를 뺀다. 이 뷰는 `StructureView`의 API를
하나도 쓰지 않고, **고스트에서는 혼자 서야 하는** 순수 표현이다. 실물 프리팹에는 둘이 함께
붙고 그 배선은 계기(`천막_프리팹이_배선되어_있고_뷰를_갖췄다`)가 지킨다. 의존을 다시 선언하는
일이 없도록 계기 하나를 더 달았다(`발자국_뷰는_StructureView에_의존을_선언하지_않는다`).

> **편의로 붙인 `RequireComponent`가 결합이 됐다** — 실제로 참조하지 않는 의존은 선언하지 않는다.

## 6.7 천 다듬기 (2026-08-31) — Play 4회차 지적

> *"천의 끝 부분(막대 근처)이 약간 찢어지는 듯한 느낌이 있다"* · *"천의 높이가 지금보다 높으면 좋겠다"*

### 찢어져 보인 이유 두 가지

1. **처짐 곡선이 가장자리에서 꺾였다** — `sqrt(droop)`는 `droop→0`에서 기울기가 발산한다.
   처짐을 키우려고 넣은 제곱근이 천을 칼로 자른 모양으로 만들었다.
   → **sin곱(지수 1)으로 되돌리고 처짐 자체를 키웠다**(0.28 → 0.34). 미분이 유한해 매끄럽다.
2. **천이 기둥보다 반 칸씩 밖으로 떠 있었다** — 기둥은 모서리 셀 **중심**에 서는데
   천은 발자국 **끝까지** 늘어났다. 매달린 데 없는 천이 허공에서 꺾인 것이다.
   → 천을 **기둥 사이 + 처마**로 건다: `(칸 수 − 1) × 셀 + 처마 0.35 × 2`.

바람 감쇠도 원형에서 **사각형 기준**으로 바꿨다 — 반지름으로 접으면 네 변을 따라 진폭이
들쭉날쭉해 가장자리가 또 찢어져 보인다.

### 그 밖에 손댄 것

| 항목 | 이전 | 지금 |
|---|---|---|
| 천 높이 · 기둥 길이 | 2.4 m | **3.1 m** (기둥 길이를 뷰가 천 높이에 맞춰 세운다) |
| 처짐 | 크기와 무관하게 고정 | **넓이 비례** (기준 변 2.6 m · 0.75~2.6배) — 큰 천막일수록 더 처진다 |
| 표면 | 매끈 | **대각 잔주름 2겹** (가장자리에서 함께 잦아들어 기둥 근처는 팽팽) |
| 올 무늬 | 60주기 · 세기 0.12 | **26주기 · 0.06** — 줄무늬 패턴으로 읽히던 것을 질감으로 |
| tris | 288 | **648** (한 채 696) — 활성 9장 목표의 0.26 % |

> **프리팹에 직렬화된 값이 코드 기본값을 이긴다** — `_canopyHeight` 기본값만 3.1로 바꿨더니
> 프리팹의 옛 2.4가 그대로 떴다. 새 필드는 기본값이 들어가지만 기존 필드는 에셋 값이 남는다.

## 6.8 검토하고 접은 것 — 플레이어와 천의 상호작용 (2026-08-31)

사용자 질문: *"플레이어와 천막 천이 상호작용하게 만드는 것은 좋은 선택인가?"*
**결론: 지금은 하지 않는다** (결정 ⑦). 근거 셋.

### ① 닿지 않는다 — 높이와 양립하지 않는다

플레이어 캡슐 **1.8 m** · 천 **3.1 m**. 사이가 **1.3 m** 비어 있어 걷든 뛰든 천에 닿을 일이 없다.
성립시키려면 천을 사람 키 근처로 내려야 하는데, 그것은 §6.7에서 *"천의 높이가 지금보다
높으면 좋겠다"* 는 지시로 올린 것을 도로 무르는 일이다.
**높은 천막과 스치는 천은 양립하지 않는다.**

### ② 값이 가장 안 나오는 지점이다

천막은 사막 낮 45 ℃를 넘기는 **생존 장치**다. 그 아래서 플레이어가 하는 일은 제작·요리·전투·
채집이고 시선은 작업대와 몬스터에 있다. 천의 반응은 **고개를 들어야 보이는 연출**이다.
게다가 **이미 만든 바람 흔들림조차 아직 Play 판정을 못 받았다**(§6.3) — 확인 안 된 연출 위에
더 비싼 연출을 얹는 것은 순서가 뒤집힌 것이다.

### ③ 지금 구조의 가장 좋은 성질을 깎는다

천은 **셰이더 정점 변형**이라 CPU 물리 0 · 콜라이더 0 · `NetworkObject` 0 · 복제 0이다.
상호작용은 두 갈래인데 둘 다 이걸 무너뜨린다.

| 길 | 대가 |
|---|---|
| 싼 길 — 셰이더에 플레이어 위치 전달 | 피어마다 자기 화면만 계산해 **4인이 서로 다른 천을 본다.** 게임은 안 깨지지만 "누가 지나가 천이 밀렸다"가 나만 보이면 연출로서 뜻이 없다 |
| 비싼 길 — 천 물리 + 복제 | 대역폭·결정론 문제. 배경 오브젝트 **`NetworkObject` 0개**를 천 하나 때문에 넘게 된다 |

### 대신 — 바람을 날씨·국면에 묶는다 (3차 후보)

플레이어 위치 없이 같은 "살아 있다"는 인상을 만든다. **모래폭풍이 오면 크게 펄럭이고
밤에 잦아든다.** `_WindStrength`·`_WindSpeed`를 날씨·국면이 밀어 주기만 하면 되고,
순수 표현이라 복제도 물리도 늘지 않는다. 무엇보다 **사막의 핵심 사건과 화면이 연결되어
연출이 게임을 설명하게 된다.**
