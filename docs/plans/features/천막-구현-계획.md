# 천막 구현 계획 — 사막을 건너는 그늘

> **상태**: **1차 구현 완료 (2026-08-30) · 플레이 검증 대기** — as-built는 §5.3, 판정은 §5.4
> **기준 커밋**: `feat/region-biomes` = `29df33f` · EditMode **1,339/1,339**
> **핵심**: 사막 낮 45 ℃에서 **16초면 체력이 깎이기 시작하는데 피할 곳이 없다.**
> 그늘 시스템은 이미 다 서 있고 **건축물만 없다.**

---

## 0. 이 계획이 만들어진 경위

사용자 지시 — *"현재 천막이 없어 사막을 건널 수 없다. 천막은 이전 온실돔과 비슷하며,
천막에 들어갈 경우 햇빛을 피해 온도가 내려간다는 설정이다."*

사막 지역은 [사막 지역 구현 계획](사막-지역-구현-계획.md) 1~4차로 **화면이 다 섰다.**
그런데 **살아서 건널 수단이 없다.** 원인은 2026-08-16에 미뤄 둔 결정 하나다 —
[건축 시스템 개편 계획](건축-시스템-개편-계획.md) §1.2가 온실 돔을 *"통행 차단 문제로
이번 개편에서 제외, **출입 구조 포함해 차후 재설계**"* 로 남겼고, 그 재설계가 이 문서다.

### 0.1 시스템은 이미 다 서 있다 ★

이 계획이 싼 이유다. **더위 완화 경로는 M5 3차에 완성돼 지금도 살아 있다.**

| 이미 있는 것 | 위치 | 상태 |
|---|---|---|
| 그늘 효과 계산 | `TemperatureMath.ResolveAmbient` | 동작. 더울 때만 적용 |
| 그늘 판정 | `PlayerTemperature.ResolveShelter` → `hasShade` | 동작. **칸 단위** |
| 그늘 계수 | `TemperatureSettings._shelterFactor = 0.8` | 배선됨 |
| 그늘 제공 플래그 | `StructureCatalog` 돔 엔트리 `_providesShade: 1` | **켜져 있다** |
| 발자국 복제 | `StructureEntry.FootprintWidth/Length` (byte) | **직렬화까지 돼 있다** |

**없는 것은 딱 둘** — 설치 가능한 건축물(`_placeable: 0` · `_viewPrefab` 비어 있음)과
가변 크기 설치 입력.

## 1. 확정 결정 6건 (2026-08-30, 사용자 결정)

| # | 결정 | 영향 |
|---|---|---|
| ① | **새 종류 `StructureKind.Tent = 9` 신설** | 돔(0)은 온실로 남긴다 · §4.1 |
| ② | **가변 크기 차양** — 우클릭 2회로 시작점·끝점 | 이 계획의 본체 · §4.2 |
| ③ | **그늘은 발자국 안에서만** | 칸 단위 boolean을 깬다 ⚠ · §4.4 |
| ④ | **칸 경계를 넘으면 칸별로 쪼개 여러 채 생성** | 복제 규약 무변경 · §4.3 |
| ⑤ | **비용 = 셀 넓이 비례** | 카탈로그에 셀당 비용 신설 · §4.5 |
| ⑥ | **점유는 4기둥 셀만** — 내부는 비어 다른 건축물이 들어간다 ★ | 점유와 효과 범위가 갈린다 · §4.6 |

### 1.1 결정 ①의 근거 — 돔을 덮어쓰지 않는다

돔 엔트리를 천막으로 개명하는 쪽이 코드 변경 0으로 가장 쌌다. 그러나 **돔은 "온실"이고
작물 재배라는 미구현 역할이 이름에 남아 있다.** 값 0은 직렬화 규약상 어차피 유지해야 하므로
(`StructureKind` 주석), 덮어쓰면 그 역할이 갈 곳이 없어진다. `Tent = 9`를 세우고 돔은
`_placeable: 0`인 채로 둔다.

### 1.2 결정 ③이 깨는 것 ⚠

`ResolveShelter`는 주석에 *"효과 범위는 칸 단위 boolean 유지 (건축 개편 계획 §5 —
**의식적 선택**)"* 이라고 못박혀 있다. 결정 ③은 이 선택을 천막에 한해 뒤집는다.

**비대칭이 생긴다** — 난방기·강화 난방로는 칸 어디서든 듣고, 천막만 발자국 안에서 듣는다.
받아들이는 근거는 사용자 설정이다: *"천막에 들어갈 경우"*. 지붕이 있는 자리와 없는 자리가
같으면 크기를 정하는 의미가 사라진다.

**종류를 코드가 알지 않게 한다** — 카탈로그에 효과 범위 필드를 두고 데이터가 소유한다
(`GetHeaterFuelPerSecond`로 강화 난방로를 판별하는 기존 규약과 같은 방식).

## 2. 실측 기준선 — 이 계획이 쓰는 자

### 2.1 사막은 얼마나 위험한가

| 값 | 출처 |
|---|---|
| 사막 낮 **45 ℃** / 밤 2 ℃ | `Region_Desert.asset` `_dayAmbientTemperature` |
| 쾌적대 **10~32 ℃** | `TemperatureSettings._comfortMin/_comfortMax` |
| 표류율 **0.012 ℃/s per ℃** | `_driftRatePerDegree` |
| 고온 경고 **38 ℃** · 피해 **39 ℃** | `_heatWarnThreshold` / `_heatDamageThreshold` |
| 피해량 **3 HP/s per ℃** | `_damagePerDegreePerSecond` |

**계산** — 낮 초과분 45 − 32 = 13 ℃ → 표류 0.156 ℃/s.
정상 체온 36.5에서 **경고까지 9.6초 · 피해 시작까지 16.0초.**
사막은 Day 6~9 **4일**이다. 그늘 없이는 갑판 위조차 못 버틴다.

### 2.2 그늘이 들으면 얼마가 되는가

`ResolveAmbient` = `Lerp(45, ComfortCenter 21, 0.8)` = **25.8 ℃** → 쾌적대 안.
표류가 멈추고 회복(`_recoveryRate 0.35`)으로 돌아선다. **그늘 하나로 완전히 해결된다.**

> **밤에는 아무 일도 없다** — `hasShade && regionAmbient > ComfortMax`가 조건이라
> 밤 2 ℃에는 적용 자체가 안 된다. 코드 주석 그대로 *"지붕이 햇빛은 가려도 난방은 되지 않는다"*.
> **난방기와 역할이 겹치지 않는다**(건축물 1종 = 역할 1개 계약 유지).

### 2.3 설치 격자

| 값 | 출처 (**에셋 실값** — 코드 기본값과 다르다 ⚠) |
|---|---|
| 칸 길이 **15 m** · 폭 **4.6 m** | `TrainLayoutSettings.asset` (코드 기본값은 12·3) |
| 격자 셀 **1 m** | `_structureCellSize` |
| 갑판 가장자리 제외 **1행씩** | `_deckEdgeRows: 1` → `DeckLength` = 13 |
| 칸 본체 **4열** | `BodyColumns(4.6, 1)` = floor(4.6) |
| 판자 증축 좌우 **각 1열** | `TrainExpansionSettings._maxPlankColumns: 1` |
| **칸당 설치 격자 = 폭 4열(판자 포함 최대 6) × 길이 13행** | 위 값들의 곱 |
| 기본 편성 **3칸** | `ResolveCarIndexAt` 주석 |

기존 건축물 발자국 — 난방기 1×1 · 화덕 1×1 · 창고 2×1 · 제작대 2×1.
**열 좌표는 고정 예약계**다 — 열 0~1이 좌측 판자 자리라 칸 본체는 열 2부터 시작한다
(`StructureGridLogic.FirstBodyColumn`). 천막도 이 좌표계를 그대로 쓴다.

### 2.4 돔이 못 들어간 진짜 이유 ⚠

**돔 4×4는 칸에 들어간다** — 본체가 정확히 4열이라 폭이 딱 맞는다.
문제는 **폭 전체를 먹어 옆으로 지나갈 틈이 없다**는 것이었다(판자가 없으면 4열이 전부다).
2026-08-16의 "통행 차단" 진단이 정확했다.

**천막은 이 문제가 원천적으로 없다** — 점유가 4기둥뿐이라(결정 ⑥) 폭을 다 덮어도
안쪽이 뚫려 있다. 폭 상한은 그 칸의 유효 열 수(판자 포함 4~6)에서 읽어 클램프한다(§4.2).

## 3. 실측이 찾아낸 어긋남 3건 ⚠

### 3.1 설치는 좌클릭이 아니라 우클릭이다

사용자 설명은 *"처음 좌클릭"* 이었으나 `RepairHammerController`는
**좌클릭 홀드 = 수리 · 우클릭 = 설치**다. 천막만 좌클릭으로 하면 망치의 의미가 갈린다.
**우클릭 2회(시작 → 끝)로 맞춘다.** 조작 뜻은 그대로 살아 있다.

### 3.2 `StructureEntry`는 칸을 넘지 못한다

`CarIndex`가 byte 하나다. 열차 전체를 덮는 단일 엔트리는 그릇에 담기지 않는다.
결정 ④(칸별 분할)가 이걸 우회한다 — **칸이 이탈·파괴돼도 그 칸 몫만 사라진다**는
부수 효과가 오히려 옳다.

### 3.3 발자국은 이미 엔트리에 실려 복제된다

`TrainState.cs:925`가 카탈로그 값을 복사해 넣고 있다. 가변 크기는 **이 복사원을
카탈로그 고정값에서 사용자 드래그 값으로 바꾸는 것**이지, 새 복제 필드가 필요한 일이 아니다.
**복제 규약 무변경.**

## 4. 설계

### 4.1 종류와 카탈로그

`StructureKind.Tent = 9` 신설. 카탈로그 엔트리:

| 필드 | 값 | 근거 |
|---|---|---|
| `_displayName` | 천막 | |
| `_providesShade` | **1** | 기존 경로를 그대로 탄다 |
| `_providesHeat` | 0 | 역할 1개 계약 |
| `_placeable` | **1** | |
| `_footprintWidth/Length` | 1×1 | **최소값** — 실제 크기는 드래그가 정한다 |
| `_maxHealth` | 30 | 천이라 돔(50)보다 약하다 |
| **`_resizable`** (신설) | 1 | 가변 크기 플래그 |
| **`_costPerCell`** (신설) | 0.25 | 셀 4개당 자원 1 (결정 ⑤) |
| **`_shelterScope`** (신설) | Footprint | 결정 ③. 기본값은 Car(기존 규약) |
| **`_occupancy`** (신설) | Corners | 결정 ⑥. 기본값은 Solid(기존 규약) · §4.6 |

### 4.2 가변 크기 설치 — 우클릭 2회

1. 망치로 천막을 고르고 **첫 우클릭** → 그 셀이 **시작 앵커**로 고정된다
2. 조준을 옮기면 시작 앵커 ~ 현재 셀의 사각형이 고스트로 그려지고 **셀 수·비용이 표시**된다
3. **두 번째 우클릭** → 확정. 자원이 모자라면 거절(기존 비용 지불 경로 재사용)
4. 도중에 무기를 바꾸거나 조준이 열차를 벗어나면 **앵커 취소**

**폭은 그 칸의 유효 열 수(판자 포함 4~6)로 자른다.** 길이는 칸 경계에서 잘려 다음 칸으로 넘어간다.

### 4.3 칸 경계 분할 (결정 ④)

드래그 사각형을 칸별로 잘라 **칸마다 엔트리 1채**를 만든다. 3칸에 걸친 천막 = 엔트리 3개.
각 엔트리는 자기 칸 안의 `CellX·CellZ·FootprintWidth·FootprintLength`만 든다.
비용은 **전체 셀 수 기준으로 한 번** 계산해 지불한다(칸마다 반올림하면 쪼갤수록 비싸진다).

### 4.4 그늘 판정 (결정 ③)

`ResolveShelter`가 엔트리를 순회할 때, 카탈로그의 효과 범위가 `Footprint`면
**플레이어의 셀 좌표가 그 엔트리의 발자국 사각형 안인지** 본다. `Car`면 지금처럼 칸 단위.

필요한 데이터(`CellX`·`CellZ`·발자국)는 **이미 복제되고 있다**(§3.3). 플레이어 셀 좌표는
`ResolveCarIndexAt`이 이미 칸을 찾으므로 그 안에서 로컬 좌표로 환산한다.

### 4.5 비용 (결정 ⑤)

`ceil(셀 수 × _costPerCell)`. 2×2(4셀) = 1 · 4×4(16셀) = 4 · 칸 하나 전체(4×13 = 52셀) = 13 · 3칸 전체(156셀) = 39.
칸 건설이 5인 것과 견주면 **열차 전체 차양은 칸 4~5개 값**이다 — 사막 진입 전에
계획해서 모아야 하는 무게다(사막 자원 밀도 배율 2.0 — 가이드 §5.4).

### 4.6 점유는 4기둥, 효과는 사각형 전체 (결정 ⑥) ★

**이 계획에서 가장 중요한 구분이다.** 천막은 지붕이지 방이 아니다.

| 축 | 범위 | 뜻 |
|---|---|---|
| **점유**(설치를 막는 자리) | **4모서리 셀 4개뿐** | 안쪽은 비어 있어 **난방기·제작대·화덕이 천막 안에 들어간다** |
| **그늘 효과** | 사각형 **전체** | 지붕이 덮은 만큼 그늘이 진다 (결정 ③) |
| **비용** | 사각형 **전체 셀 수** | 천이 넓으면 재료가 든다 (결정 ⑤) |

현재 `StructureGridLogic.CanPlace`는 **발자국 사각형 전체를 점유로 본다.**
여기에 점유 형태를 넣는다 — 카탈로그 `_occupancy`가 소유한다:

- **`Solid`** (기본값) — 사각형 전체. 기존 건축물 8종 전부 이 값이라 **무변경**
- **`Corners`** (천막) — 네 모서리 셀만. 나머지는 빈 자리로 취급

**양방향으로 성립해야 한다** — 천막 안에 난방기를 나중에 지을 수 있고, 이미 난방기가 선
자리 위로 천막을 덮을 수도 있다. **검증은 "겹치는 셀이 있는가"** 하나로 통일되므로
`Corners`가 자기 4셀만 내놓으면 두 방향이 자동으로 성립한다.

> **3×3보다 작으면?** 2×2는 네 셀이 곧 네 모서리라 `Solid`와 같아지고, 1×N은 모서리가
> 2개로 줄어든다. **최소 크기를 2×2로 강제**해 "기둥 4개"라는 형태가 늘 성립하게 한다.

### 4.7 뷰

기둥 + 천. 가변 크기라 **프리팹 하나를 스케일**한다 — 천은 X·Z로 늘리고 기둥은
네 모서리에 **스케일 보정으로 굵기를 유지**한다. 콜라이더는 두지 않는다(통행 자유).

### 5.2 완료 기준

1. 사막 낮 갑판에서 **천막 밖은 16초에 피해가 시작되고, 천막 안은 안 깎인다**
2. 천막 **밖 한 걸음**에서 효과가 끊긴다 (결정 ③의 판정)
3. 3칸에 걸쳐 끌면 **엔트리 3채**가 생기고 화면에선 이어져 보인다
4. 폭은 어떻게 끌어도 **그 칸의 유효 열 수를 넘지 않는다** (판자 없으면 4열)
5. 비용이 셀 수를 따라간다 · 모자라면 거절
6. 밤 2 ℃에서 천막이 **아무 영향도 주지 않는다** (난방기와 역할 분리)
7. 칸이 이탈·파괴되면 **그 칸 몫만 사라진다**
8. **천막 안에 난방기·제작대를 지을 수 있고**, 이미 선 건축물 위로 천막을 덮을 수도 있다 (결정 ⑥)
9. **기둥 4셀에 뭔가 있으면 거절**된다 — 그 자리만 막힌다
10. 기존 건축물 8종의 설치 판정이 **1픽셀도 안 바뀐다** (`Solid` 기본값)
11. `NetworkObject` 0개 추가 · 복제 규약 무변경 · EditMode 전량 통과
