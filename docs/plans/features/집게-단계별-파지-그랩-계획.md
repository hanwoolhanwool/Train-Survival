> **목표**: 집게 등급이 사거리·무게 상한만 올리는 것이 아니라 **"어느 손으로 드는가"와
> "잡은 채로 무엇을 할 수 있는가"** 를 바꾼다. 1단계는 **오른손을 점유**해 잡는 동안 아무 무기도
> 들 수 없고, 2단계부터 **왼손으로 옮겨가** 오른손 한손 무기를 쓸 수 있다. 양손 무기를 고르면
> **그랩이 자동으로 풀린다**. 잡을 수 있는 대상도 등급을 따라 넓어진다 —
> 1단계 자원·이탈 칸·보따리 → 2단계부터 강화 자원·몬스터·플레이어 동료.

## 0. 범위

**코어**

1. **대상 등급 축 정리** — 기획서 §3.1 대상표를 기존 등급 축에 얹고, 이름을 의미에 맞춘다
   (`IGrabbable.GrabWeight` → `RequiredHarpoonTier`, 확정 ②)
2. **그랩 유지 중 무기 전환 게이트** — 1단계 거부 / 2·3단계 한손 허용 / 양손 무기 자동 해제
3. **파지 손 전환 표현** — 1단계 오른손, 2·3단계 왼손 + **왼손 집게와 오른손 무기 동시 표시**
4. **플레이어 동료 그랩** — 신규 `IGrabbable` 구현체 (2단계부터, **상시 그랩 + 끌어오기** — 확정 ⑤)
5. **거부 피드백** — 1단계가 그랩 중 슬롯을 바꾸려 할 때 왜 안 되는지 알린다 (문구 + 연출)

**비범위**

- **몬스터 요구 등급 상향** — **몬스터 재설계 대기 (확정 ①)**. 기획서 §3.1은 "몬스터 = 2단계부터"로
  확정됐지만, 변종 체계 자체를 다시 설계할 예정이므로 **이번에는 에셋 값을 건드리지 않는다**.
  그때까지 코드는 현행(일반형·돌진형 1)을 유지한다 — 의도적 편차는 §1.2에 기록
- **FP(1인칭) 뷰모델의 좌우 배치** — 진행 중인 1인칭 통합 시점 전환 작업
  ([1인칭-통합-시점-전환-계획.md](1인칭-통합-시점-전환-계획.md))과 같은 파일을 건드린다.
  파지 손 규칙이 확정된 뒤 그쪽 계획에서 흡수한다 (§3.3 말미)
- **집게 승급 밸런스** — `Recipe_HarpoonTier2/3` 재료·해금 시점은 이 계획이 바꾸지 않는다
- **총구 앵커** — 무기-총구-발사위치-계획(미작성)의 별건. 파지 손이
  바뀌면 앵커 부모도 바뀌지만, 앵커는 무기 프리팹 로컬이라 손과 무관하다

## 1. 현재 배선 — 무엇이 이미 있고 무엇이 없나

| 기획 요구 | 현재 상태 | 판정 |
|---|---|---|
| 등급별 대상 제한 | `GrabValidation.CanLift(grabberTier, targetWeight)` — 무게 축 1~3이 이미 있다 | **축 재사용 가능** — 데이터 값만 조정 |
| 자원·강화 자원 구분 | `ResourceCatalog._grabWeight` — type 6 = 2, type 7 = 3, 나머지 1 | **이미 성립** |

### 1.1 이 계획이 번복하는 기존 결정 — **M5 6차 2차**

`HarpoonController.cs:212`의 주석이 현재 규약을 명시한다:

> 무기를 바꿔도 파지는 유지된다 (M5 6차 2차 — 사용자 결정으로 "놓기 ② 무기 교체" 철회).
> 든 채 다른 무기로 쏠 수 있고, 놓기·투척은 집게로 돌아와서 한다.

즉 **지금은 등급과 무관하게 무기 전환이 자유**롭고, 전환해도 그랩이 유지된다. 기획서 v0.6은
이 결정을 **부분 번복**한다 — 자유 전환은 **2·3단계의 보상**으로 재배치되고, 1단계는 잡으면 손이
묶이며, 양손 무기는 전환 시 그랩을 잃는다. 따라서 이 작업은 **기능 추가가 아니라 제약 신설**이며,
M5 6차 이후의 플레이 감각(1단계로 몬스터를 잡아 들고 리볼버로 쏘기)이 **의도적으로 사라진다**.
검증 시 "회귀"가 아니라 "설계 변경"으로 읽어야 한다 (§6.1).

### 1.2 기획서와의 의도적 편차 — 몬스터 요구 등급 (확정 ①)

기획서 §3.1 대상표는 **몬스터를 2단계부터**로 확정했지만, **몬스터 변종 체계를 다시 설계할
예정이므로 이번 작업은 `MonsterSettings._grabWeight`를 건드리지 않는다.** 따라서 착수 후에도
당분간 **1단계 집게로 일반형·돌진형 몬스터를 잡을 수 있다** — 기획서가 앞서 있고 구현이 뒤따르는
상태다.

- 이 편차는 **버그가 아니다.** 플레이 검증에서 "1단계로 몬스터가 잡힌다"를 결함으로 올리지 않는다.
- 해소 시점: **몬스터 재설계 차수**. 그때 변종별 요구 등급을 한 번에 정하면, 이 계획이 정리해 둔
  `RequiredHarpoonTier` 축(§3.1)에 값만 대입하면 된다 — 코드 변경은 이미 끝나 있다.
- 반대로 **플레이어 동료는 이번에 2단계로 들어간다** (확정 ⑤). 즉 2단계의 첫 체감 보상은
  "몬스터를 잡을 수 있다"가 아니라 **"동료를 끌어올 수 있다 + 잡은 채로 총을 쏠 수 있다"** 가 된다.

## 3. 설계

### 3.1 대상 등급 게이트 — 축 이름을 바로잡고 값을 대입한다

판정 **로직**(`GrabValidation.CanLift`)은 부등식 그대로다. 바뀌는 것은 **이름**뿐이다 (확정 ②):

| 현재 | 변경 후 | 위치 |
|---|---|---|
| `IGrabbable.GrabWeight` | `IGrabbable.RequiredHarpoonTier` | 인터페이스 + 구현체 6곳 |
| `HarpoonSettings.Tier.GrabWeightLimit` | `MaxGrabTier` (또는 유지) | 설정 SO — **에셋 필드명 변경 시 값 유실 주의** |
| `GrabValidation.CanLift(grabberTier, targetWeight)` | `(harpoonTier, requiredTier)` | 인자명만 |

`[SerializeField] private int _grabWeight`를 그대로 두고 프로퍼티만 바꾸면 **에셋 값이 유지**된다.
필드명까지 바꾸려면 `[FormerlySerializedAs("_grabWeight")]`를 반드시 붙인다 —
빠뜨리면 `ResourceCatalog`·`MonsterSettings`·`StorageBundle`의 등급 값이 전부 0으로 리셋된다.

기획서 §3.1의 대상표를 이 축에 대입하면:

| 대상 | 요구 등급 | 현재 값 | 조치 |
|---|---|---|---|
| 기초 자원 | 1 | 1 | — |
| 강화 자원 (`ResourceType` 6·7) | 2·3 | 2·3 | — |
| 이탈 칸 손잡이 | 1 | 1 | — |
| 창고 보따리 | 1 (비행 중 3) | 동일 | — |
| 몬스터 (전 변종) | 2 *(기획)* | 일반형·돌진형 1 | **보류 — 몬스터 재설계 때 (확정 ①, §1.2)** |
| 플레이어 동료 | **2** | — | **신규 구현 (§3.5)** |

- 요구 등급은 **에셋 값**이므로 코드 변경 없이 밸런싱에서 되돌릴 수 있다. 몬스터 재설계 차수는
  이 표의 몬스터 행에 값을 넣는 것으로 끝난다.
- `HarpoonSettings.Tier`의 등급 상한이 1/2/3으로 등재돼 있어야 한다 — **착수 시 실측 확인**.
  비어 있으면 `GetTier` 폴백이 1단계 값으로 떨어져 2·3단계가 무력해진다.
  → **실측 완료 (2026-08-18): 1/2/3 전부 등재돼 있다** (`HarpoonSettings.asset`, `TierCount = 3`).
- **거부 사유는 이미 있다** — `GrabVerdict.InsufficientTier`. UI가 이 사유를 문구로 보여주는지는
  §3.6에서 함께 본다 (지금은 되감기 연출만 나갈 수 있다).
  → **실측 완료: 이미 문구가 나간다** — `SliceHud`가 "너무 무겁다 — 강화 집게가 필요하다"를 띄우고
  Game·Game_ArtTest 두 씬에 모두 배치돼 있다. 이 항목은 신규 작업 없이 성립했다.

**구현 결과 (2026-08-18)** — 필드명까지 개명하고 `[FormerlySerializedAs]`를 붙였다. 개명 후 에셋 값을
실물로 읽어 무변경을 확인했다: 집게 상한 1/2/3 · 원목 2 · 광맥 3 · 목재 1 ·
몬스터 일반형 1 / 돌진형 1 / 돌격형 2 / 도약형 2 (§1.2 편차 그대로 유지).
`GrabValidationTests`도 인자명만 바꿔 그대로 통과한다 — 로직 무변경의 증거다 (§6.3).

### 3.2 그랩 유지 중 무기 전환 게이트 — 순수 로직으로 분리

판정은 **소유자 로컬**에서 끝난다. "그랩 유지 중인가"는 `HarpoonState`가 이미 로컬에 있고
(서버 확정과 동기화됨), 등급 `_tier`도 복제 값이라 소유자가 읽을 수 있다.

**신설 — `HarpoonSwitchRules` (순수 정적, `Gameplay/Harpoon`)**

```
enum SwitchOutcome { Allow, Deny, ReleaseThenAllow }

SwitchOutcome Evaluate(HarpoonState state, int tier, bool targetIsTwoHanded)
```

| 상태 | 등급 | 대상 슬롯 | 결과 |
|---|---|---|---|
| 그랩 미유지 (`Ready`·`Cooldown`·`MissRecovery`·`Firing`) | — | — | `Allow` |
| 그랩 유지 (`PendingGrab`·`Reeling`·`Holding`) | 1 | 무엇이든 | **`Deny`** |
| 〃 | ≥2 | 한손 무기·자원·빈 칸 | `Allow` |
| 〃 | ≥2 | **양손 무기** | **`ReleaseThenAllow`** |

**양손 여부의 출처 (확정 ③)** — `WeaponHandednessSettings` SO를 신설한다
(`Gameplay/Inventory`, `HotbarItemType` → `Handedness { One, Two }` 표 1개).
현재 값은 샷건만 양손, 리볼버·집게·망치·근접은 한손이며, 라이플·화염방사기는 반입 시 등재한다.
→ **구현 시 수정 (2026-08-18, 사용자 확정):** 볼트액션 라이플은 이미 Player 프리팹에 배선된 현역
무기였다. 한손으로 두면 2단계 집게로 동료를 든 채 라이플을 쓰게 되므로 **라이플도 양손으로 등재**했다.
즉 등재 값은 **샷건·라이플 = 양손**, 나머지 전부 한손(미등재 폴백)이다.
표현용 `WeaponHoldSettings._twoHanded`와 **값이 겹치지만 출처는 분리**한다 — 파지 IK를 조정하다
게임 규칙이 바뀌는 사고를 막는다. 두 에셋의 불일치는 EditMode 테스트로 잡는다(§6.3).

- `Firing`(투사체 비행 중)은 아직 잡은 게 없으므로 막지 않는다 — 명중 전에 무기를 바꾸면
  기존 규약대로 `Firing`이 이어지다 승인 시점에 정리된다. **착수 시 실측 확인 대상**
  (`PendingGrab` 진입 후 전환의 경합).
  → **실측·해소 완료 (2026-08-18).** 기존 `TryCancel`은 `Reeling`·`Holding`만 받아 `PendingGrab`에서
  놓을 수단이 없었다 — 그대로 두면 "승인이 오는 사이에 양손 무기로 바꿨는데 뒤늦게 잡히는" 구멍이 남는다.
  상태 머신에 `TryReleaseForWeaponSwitch()`를 따로 두어 **승인 대기도 포함**시켰다 (우클릭 취소의
  의미는 건드리지 않는다). 서버 쪽 경합은 없다: RPC 순서 보장으로 서버는 그랩 요청을 먼저 처리한 뒤
  취소를 받고, 뒤따라 도착하는 승인 통지는 상태가 이미 쿨다운이라 무시된다.
- `Anchor` 그랩(손잡이)도 같은 규칙을 받는다 — 이탈 저항 중 1단계는 손이 묶인다. 이는 §3.1의
  "이탈 칸은 1단계도 잡는다"와 모순되지 않는다: **잡을 수는 있고, 잡은 동안 못 바꿀 뿐**이다.

**배선** — `HotbarController.Select(int)` (`HotbarController.cs:190`):

```
Select(index)
 ├ SwitchOutcome 조회 (집게 참조는 이미 있다 — _harpoon)
 ├ Deny            → 선택 무시 + 거부 이벤트 발행 (§3.6)
 ├ ReleaseThenAllow→ CancelGrab 경로 재사용(우클릭 취소와 동일) 후 선택 진행
 └ Allow           → 현행 그대로
```

해제는 **기존 경로를 그대로 쓴다** — `DiscardActiveProjectile()` + `CancelGrabServerRpc()`
(`HarpoonController.cs:251~257`). 새 RPC를 만들지 않는다. 이를 위해 `HarpoonController`에
`bool TryReleaseForWeaponSwitch()` 한 개만 공개한다 (내부 경로 재사용, 상태 머신 `TryCancel` 경유).

**테스트**: `HarpoonSwitchRulesTests` (EditMode) — 상태 7종 × 등급 3종 × 대상 3종 조합.
`Assets/_Project/Tests/EditMode/`에 둔다 (`StructureGridLogicTests` 등과 같은 자리).

### 3.3 파지 손 전환 표현 — 이 계획의 최대 작업

현재 `HeldWeaponSocket`은 **오른손 본 소켓 1개**를 만들고, 복제된 `PlayerAimView.HeldItem`
**하나**에 맞춰 모델 1벌만 켠다. 2단계 이후에는 **두 무기가 동시에 보여야 한다**.

| 항목 | 현재 | 변경 |
|---|---|---|
| 소켓 | 오른손 1개 | **오른손·왼손 2개** — 본 해석을 `HumanBodyBones` 인자로 일반화 |
| 표시 모델 | `HeldItem` 1벌 | **주손 1벌 + 보조손 1벌** (보조손은 집게 전용) |
| 복제 값 | `_heldItem` (`NetworkVariable<int>`, Owner write) | **상위 비트에 보조손 슬롯을 실어 필드 추가 없이 확장** (대역폭 증분 0 유지) |
| IK | 무기 1엔트리로 양손 목표 산출 | **손별 엔트리 조회** — 왼손은 집게 엔트리, 오른손은 주무기 엔트리 |
| 설정 에셋 | 집게 엔트리 1개 (오른손, `_twoHanded 0`) | **집게 왼손 엔트리 추가** — 미러 값이 그대로 맞지 않아 별도 수치가 필요 |

- **손 결정의 진실 출처**: 파지 손은 등급의 함수다. 표현 계층이 `HarpoonController._tier`를 직접
  읽으면 표현 → 게임플레이 역참조가 생기므로, **소유자가 `PlayerAimView`에 파지 손 비트를 함께
  기록**한다. 원격 피어는 복제 값만 보고 손을 정한다 (기존 `HeldItem` 규약과 동형).
- **승급 순간의 전환**: 2단계 승급은 제작대에서 일어나고 `_tier`는 복제된다. 손 전환은 다음
  `LateUpdate` 폴링에서 자연히 반영된다 — 별도 전환 연출은 두지 않는다 (그랩 중 승급은
  제작대 상호작용이 손을 요구하므로 사실상 발생하지 않는다).
- **1단계 = 오른손**은 현재 에셋 값과 같다 → **1단계 플레이는 표현상 무변경**이다. 이 계획의
  표현 작업은 전부 2단계 이후에만 눈에 보인다.
- **FP 뷰**: 1인칭 화면에서도 집게가 좌측으로 가야 하지만, 해당 배치는 진행 중인 1인칭 통합
  작업이 소유한 파일들과 겹친다. **파지 손 규칙(이 문서 §3.3)만 확정하고 배치는 그쪽에서 흡수**한다.

### 3.4 입력 소유권 — 손이 둘이면 클릭도 둘이다

2단계 이후 "왼손 집게 + 오른손 리볼버" 상태에서:

| 입력 | 주체 | 근거 |
|---|---|---|
| 좌클릭 | **오른손 무기** (사격) | 든 슬롯이 리볼버다. 집게 `InputEnabled`는 꺼져 있다 |
| 우클릭 | **아무것도 안 함** (확정 ④) | 총기는 우클릭 미사용 — 향후 조준 등에 쓸 자리로 비워 둔다 |
| R | 오른손 무기 (재장전) | 충돌 없음 |
| 1~5 | 슬롯 전환 (§3.2 게이트 적용) | — |
| 집게 슬롯 재선택 | 집게 입력 복귀 → 좌클릭 투척 / 우클릭 놓기 | 현행 규약 유지 |

즉 **입력 충돌은 없다** — 확정 ④로 우클릭을 비워 두었으므로, 그랩 유지 중에도 오른손 무기가
모든 입력을 온전히 갖는다.

### 3.5 플레이어 동료 그랩 — 신규 구현체

`IGrabbable`을 구현하는 `PlayerGrabTarget` (`Gameplay/Player`)을 신설한다. 기존 구현체
(`MonsterGrabTarget`·`SettleableGrabbable`)와 같은 계약을 따르므로 집게 쪽 코드는 **한 줄도
바뀌지 않는다** (OCP — 대상이 도착 결과를 정한다).

| 계약 | 값 | 비고 |
|---|---|---|
| `Kind` | `Reel` | 끌어당긴다 |
| `RequiredHarpoonTier` | 2 | 2단계부터 (확정 ⑤) |
| `TryClaimGrab` | **상태 조건 없음** — 살아 있고 미점유면 성립 | 멀쩡한 동료도 잡힌다 (확정 ⑤) |
| `TryCompleteGrab` | `Rejected` — 도착하면 그 자리에 선다 | 수납도, 파지 유지도 아니다. 들어 옮기기는 비범위 |

**상시 그랩이라 반드시 풀어야 하는 두 가지**:

1. **이동 권위 충돌** — 대상 플레이어의 이동은 소유자 권위(`OwnerNetworkTransform`)다. 끌려가는
   동안 호스트가 위치를 대입하려면 소유자 입력이 그걸 덮어쓰지 않아야 한다.
   `NetworkPlayerController`의 **호스트 개입 상태 머신**
   ([network-movement.md](../../specs/player/network-movement.md))이 낙하·이탈에서 이미 같은 문제를
   푼다 — **그 상태를 하나 늘려 재사용**한다. 새 권위 경로를 만들지 않는다.
   **착수 전 실측**: 그 상태 머신이 "외부 힘에 끌려감"을 표현할 수 있는지 확인. 못 하면 이 항목만
   따로 떼어 §4의 5단계를 늘린다.

   > **실측 결과 (2026-08-18) — 이 전제는 깨졌다.** `PlayerMovementState`(Normal/Grabbed/Carried)는
   > **골격뿐**이었다: `Grabbed`는 소유자 이동 입력을 정지시키기만 하고, **서버가 위치를 구동하는
   > 경로가 전혀 없다** (전환 경로도 F9 디버그 RPC 하나뿐). 즉 "상태를 하나 늘려 재사용"할 상태가
   > 없었고, 구동부를 새로 만들어야 했다.
   >
   > **확정 대안 (사용자 결정 2026-08-18) — 소유자 구동 견인.** 서버는 위치를 대입하지 않는다.
   > **"누가 나를 끄는가"(그래버 참조)와 릴 속도만 복제**하고, 끌려가는 계산은 소유자가 로컬에서
   > 수행한다 — 서버 견인과 **같은 앵커·같은 속도**를 쓰므로 판정과 화면이 갈리지 않는다.
   > 서버는 복제돼 올라온 실제 위치로 **도착만 판정**한다.
   >
   > | 항목 | 결과 |
   > |---|---|
   > | 위치 권위 | **변경 없음** — 소유자 권위 그대로 |
   > | 신규 위치 스트림 | **0** — 30 Hz 견인 채널을 새로 열지 않는다 |
   > | 끌리는 쪽 체감 지연 | **0** — 로컬에서 직접 움직인다 |
   > | 새로 생긴 표면 | `IExternalTow`(Player 계층 계약) · `NetworkPlayerController.ServerSetMovementState` |
   >
   > 이동 쪽은 **무엇이 끄는지 모른다** — `IExternalTow` 하나만 본다. 집게가 아닌 다른 것(폭풍·기중기)이
   > 끌게 되어도 이동 코드는 그대로다 (DIP). 골격뿐이던 `Grabbed`에 구동부가 채워진 셈이라,
   > 계획의 원래 의도("상태 머신 재사용")는 결과적으로 지켜졌다.
   >
   > **부수 결정**: 끌려가는 동안 **시선은 남긴다** — 주변을 볼 수 없으면 구조가 사고처럼 보인다.
   > 이동만 외부 힘에 넘어간다.
2. **동의 없는 끌기** — 살아 있는 동료를 잡아끄는 것이므로 장난의 여지가 생긴다. 이번 범위의
   최소 안전장치는 **끌려오는 방향이 언제나 그래버 쪽**이라는 점 하나다 (밀어낼 수단이 없으므로
   열차 밖으로 내보낼 수 없고, 도착 반경에서 멈춘다). **뿌리치기(대상의 저항 입력)는 두지 않는다**
   — 필요해지면 그때 얹는다. 이 판단은 실제 4인 플레이에서 다시 본다 (§6.1).

- **낙하 중 구조**는 이 설계로 **자동으로 성립**한다 — 떨어지는 동료도 살아 있는 그랩 대상이므로
  별도 분기가 필요 없다. 다만 낙하 상태의 호스트 개입과 그랩의 호스트 개입이 겹치는 구간의
  우선순위는 구현 중 판단한다 (권장: **그랩이 이긴다** — 구조가 목적이다).
  → **구현 확정: 그랩이 이긴다.** 견인 중에는 `ServerCheckFallBehind`의 사망선 판정을 건너뛴다.
  여기서 죽이면 "구해내는 중이었는데 죽었다"가 되어 동료 그랩의 존재 이유가 사라진다.
  놓치면 다음 프레임에 판정이 곧바로 돌아온다 — 무기한 면제가 아니다.

**구현 중 추가로 막은 구멍 (2026-08-18)**

| 구멍 | 처리 |
|---|---|
| 자기 자신 그랩 | `TryClaimGrab`이 `grabberClientId == OwnerClientId`를 거부 (훅의 `ignoreRoot`와 이중 방어) |
| 끌려오던 동료의 사망 | 대상이 디스폰되지 않는 종류라 집게 쪽 디스폰 감시에 안 걸린다 — 서버가 사망을 감지해 `HarpoonController.ServerForceReleaseTow()`로 **로프까지** 끊는다. 안 끊으면 부활 후에도 구속(`Grabbed`)이 남아 조작이 막힌다 |
| 대상 디스폰 | `OnNetworkDespawn`에서 같은 경로로 정리 |

### 3.6 거부 피드백

**확정 ⑥ — 문구 + 연출 둘 다.**

- **슬롯 전환 거부** (1단계, §3.2 `Deny`) — `HotbarSelectionRejectedLocalEvent` 신설 →
  `CoreLoopHud` 토스트("1단계 집게는 잡은 동안 무기를 바꿀 수 없다") + 슬롯 흔들림·거부음.
  **반복 억제**: 같은 그랩 동안 문구는 **첫 회만** 띄우고 이후는 연출만 남긴다 — 슬롯을 연타할 때
  토스트가 쌓이지 않게 한다.
- **그랩 대상 거부** (`InsufficientTier`) — 현재 되감기 연출만 나갈 가능성이 있다. 등급 부족은
  "빗맞음"과 다르게 읽혀야 하므로, 사유가 UI까지 오는지 착수 시 확인하고 없으면 같은 토스트에 얹는다.
  (몬스터가 보류되면서 이 경로를 실제로 밟는 것은 **강화 자원과 플레이어 동료**뿐이다 — §1.2)

**구현 결과 (2026-08-18) — 계획에서 바꾼 두 가지**

| 계획 | 실제 | 이유 |
|---|---|---|
| 문구를 `CoreLoopHud` 토스트로 | **`SliceHud`** — 기존 그랩 거부 안내와 **같은 자리·같은 수명(2초)** | 둘 다 "왜 안 되는지"를 알리는 안내다. 화면에서 다른 문법으로 보이면 안 된다. `CoreLoopHud`는 Day·지역 배너 담당이라 SRP상으로도 여기가 맞다 |
| 슬롯 흔들림 **+ 거부음** | 슬롯 흔들림·붉은 물듦만 (`InventoryHud`) | **프로젝트에 오디오 인프라가 없다** (`AudioSource`·재생 서비스 전무). 소리는 오디오 도입 차수로 넘긴다 |

문구는 "잡은 손이 묶였다 — 강화 집게라야 든 채로 무기를 바꾼다". 반복 억제는 **발행 쪽**(`HotbarController`)이
결정하고 UI는 시키는 대로만 띄운다. **연출은 누를 때마다** 나간다 — "눌렀는데 아무 반응이 없다"를 막는 것이
연출의 목적이라, 거기에 반복 억제를 걸면 목적이 사라진다.

대상만 건드리기 때문이다 (확정 ③ 덕분). **5단계만** 파지 시스템을 요구한다.

따라서 **1차 = 1~4 (게임 규칙 완성), 2차 = 5 (손 표현)** 로 쪼개는 것을 권한다. 1차만 끝나도
"2단계 집게는 잡은 채 리볼버를 쏘고, 샷건을 고르면 놓치고, 동료를 끌어올 수 있다"가 전부 성립한다
— 다만 **집게는 여전히 오른손에 보인다**. 규칙이 먼저 서고 그림이 뒤따르는 순서다.
