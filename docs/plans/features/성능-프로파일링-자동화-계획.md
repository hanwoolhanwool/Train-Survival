# 성능 프로파일링 자동화 계획 — 재고, 남기고, 회귀를 막는다

작성일: 2026-09-01 · 개정: 2026-09-02 (범위 축소 — L1 제외 · 스모크 모드 추가) ·
상태: **1차 완료** (2026-09-02 · 스모크·벤치 주행 성공 · 기준선 확정 · EditMode 1,406/1,406) ·
남은 결정 2건(④⑦ — 둘 다 ★로 진행 중) ·
상위 문서: [`아트 · 렌더링 예산 스펙`](../../design/Train-Survival-아트-렌더링-예산.md) (v0.2) §6 · §8 ·
관련: [`아키텍처 규칙`](../../conventions/architecture-rules.md) · [`CI 복구 계획`](CI-복구-계획.md)

> **이 계획이 하는 일**: 게임을 **빌드로 자동 실행해 정해진 시나리오를 주행시키고**, 프레임 시간·
> 드로우콜·GC를 **파일로 남긴 뒤**, 다음 실행과 **비교해 회귀를 잡는다**.
>
> **덤으로 따라오는 것**: 그 주행 인프라(`PerfRunner`)는 **빌드가 Boot → Main → Game을 통과해
> 살아 있는지 확인하는 스모크 테스트와 같은 물건**이다. 지표 수집을 끄는 `-smoke` 분기 하나면
> 이 프로젝트에 지금 없는 **자동 부팅 검증**이 같이 선다 (§3 · §4.8). 현재 PlayMode 테스트는 3개뿐이고,
> 씬 진입·NGO 호스트 시작을 자동으로 확인하는 수단은 하나도 없다.
>
> **이 계획이 하지 않는 일**: 최적화 자체를 하지 않는다. 예산 문서 §7의 실행 항목(GPU Resident
> Drawer, 캐스케이드 4→2 등)은 이 계획이 만든 **자를 써서 판정할 대상**이지 이 계획의 범위가 아니다.
> **마이크로 벤치(L1)도 하지 않는다** — 병목 후보가 렌더 쪽이라 값이 낮고, 도입 대가만 크다 (§3 비포함).

## 0. 왜 지금인가 — 예산 문서가 스스로 적어 둔 빚

[예산 스펙 §8 "미확정 · 확인 필요"](../../design/Train-Survival-아트-렌더링-예산.md#8-미확정--확인-필요)에 남은
6개 항목 중 **4개가 "재는 방법이 없어서" 미해결**이다. 그 문서의 표현을 그대로 옮기면:

| §8 미결 항목 | 문서가 적어 둔 말 |
|---|---|
| 드로우콜 1,110 | "**CPU 바운드인지 GPU 바운드인지 모르는 채로** 최적화 순서를 정하고 있다" |
| 빌드에서의 밀리초 | "지금까지 잰 것은 전부 에디터 게임 뷰의 삼각형 수다. **프레임 시간은 빌드 + Profiler로만 확인된다**" |
| 그림자 패스의 실제 몫 | "§7 우선순위 3·4의 값어치가 여기 달렸다" |
| 몬스터·캐릭터의 렌더 실측 | "배경만 절반으로 줄여 놓고 **합계를 논할 수 없다**" |
| 타일 교체 시 프레임 스파이크 | "실제로 튀는지는 플레이 검증에서 판정하고" |

즉 이 프로젝트는 **폴리곤은 6번 쟀지만 밀리초는 한 번도 잰 적이 없다.** 그런데 §7 우선순위 1
(GPU Resident Drawer)은 *드로우콜*을 줄이는 조치, 우선순위 3·4(그림자)는 *GPU*를 줄이는 조치다.
**어느 쪽이 병목인지 모르면 둘 중 무엇을 먼저 할지도 정할 수 없다.**

이 계획은 최적화를 하기 전에 **자를 먼저 만든다.**

## 1. 조사 실측 — 이 수치들이 설계를 정했다

착수 전 이 프로젝트에서 실제로 재 본 값들이다. **설계 판단은 전부 아래 4개에서 나왔다.**

### 1.1 `enableFrameTimingStats: 0` — GPU 시간을 못 재게 막고 있던 것의 정체

`ProjectSettings/ProjectSettings.asset:159`

```
enableFrameTimingStats: 0
```

`FrameTimingManager`를 호출해 봤다(2026-09-01, 에디터 편집 모드):

| 필드 | 값 | 해석 |
|---|---:|---|
| `cpu_frame_time_ms` | 99.1386 | 편집 모드 유휴 프레임 — 게임 부하가 아니다 |
| `cpu_main_thread_frame_time_ms` | 0.0008 | 〃 |
| **`cpu_render_thread_frame_time_ms`** | **0** | **스탯이 꺼져 있어 안 채워진다** |
| **`gpu_frame_time_ms`** | **0** | **〃 — §8 "CPU/GPU 바운드 모름"의 직접 원인** |

**§8이 3개월째 못 답한 질문의 답이 체크박스 하나에 막혀 있었다.** Frame Timing Stats를 켜면
`cpu_main_thread` · `cpu_render_thread` · `gpu` 세 값이 채워지고, **셋 중 가장 큰 것이 병목**이다.
이것이 CPU 바운드/GPU 바운드 판정의 표준 방법이고, 다른 우회로는 없다.

### 1.2 편집 모드에서 렌더 카운터는 전부 0이다

`Render` 카테고리의 카운터 **697종**을 전량 읽었다(2026-09-01, 편집 모드 · 플레이 아님):

| 카운터 | 값 |
|---|---:|
| `Draw Calls Count` | **0** |
| `SetPass Calls Count` | **0** |
| `Triangles Count` | **0** |
| `Shadow Casters Count` | **0** |
| `Vertices Count` | **0** |
| `Render Textures Bytes` | 158,898,444 (151.5 MB) |
| `Used Buffers Count` / `Bytes` | 383 / 13,730,772 |
| `Visible Skinned Meshes Count` | 1 |

**플레이 중이 아니면 프레임 카운터는 채워지지 않는다.** 리소스 계열(`Render Textures Bytes` 등)만
편집 모드에서 살아 있다. → **자동화는 플레이 모드 또는 빌드에서만 성립한다.**

### 1.3 에디터 플레이 모드는 포커스를 잃으면 멈춘다

이 프로젝트에서 이미 확인된 사실이다 — 창 포커스가 없으면 `Time.frameCount`가 고정되고
스크린샷 호출만 프레임을 민다. 예산 문서 §6도 같은 이유로 물러섰다:

> "창 포커스가 없으면 `frameTime`·`renderTime`은 **신뢰할 수 없어 재지 않았다**"

**자동화는 정의상 사람이 창을 보고 있지 않은 상태에서 돈다.** 따라서:

| 측정 장소 | 자동화 가능? | 이유 |
|---|---|---|
| 에디터 편집 모드 | ❌ | 카운터가 0 (§1.2) |
| 에디터 플레이 모드 | ❌ | 포커스 없으면 프레임이 안 간다 |
| **빌드 Player** | ✅ | `Application.runInBackground = true` + `-screen-fullscreen 0`로 백그라운드 주행 가능 |

**측정 장소는 빌드로 사실상 강제된다.** 이것이 §4 설계의 첫 번째 축이다.

### 1.4 시나리오 길이를 정하는 자 — 60초가 정확히 한 사이클이다

`WorldScrollSettings.asset` · `DayTimelineSettings.asset` 실측:

| 항목 | 값 | 출처 |
|---|---:|---|
| 주행 속도 | 6 m/s | `_baseScrollSpeed` |
| 타일 길이 | 40 m | `_tileLength` |
| 활성 타일 | 9장 (앞 5 + 뒤 3 + 현재) | `_tilesAhead: 5` · `_tilesBehind: 3` |
| **타일 교체 주기** | **6.67초** | 40 ÷ 6 |
| **활성 9장 전량 교체** | **60.0초** | 6.67 × 9 |
| 낮 / 밤 | 240초 / 150초 | `DayTimelineSettings` |
| 밤 웨이브 동시 생존 상한 | 12마리 | `WaveSettings._maxAliveCap` |
| 밤당 총 소환 상한 | 24마리 | `_totalCountCap` |
| 열차 편성 | 77.66 m | 예산 문서 §3.1 |

**측정 구간을 60초로 잡으면 활성 타일 9장이 정확히 한 번씩 전부 교체된다.** 타일 교체 스파이크
(§8 미결)를 재려면 이보다 짧을 수 없고, 더 길면 같은 사건의 반복일 뿐이다. **60초가 최소 유효 구간이다.**

밤 웨이브는 별개다 — 낮 240초를 지나야 밤이 오므로, 웨이브 시나리오는 **밤 상태로 직접 진입**시켜야 한다.

### 1.7 1차 실측 결과 (2026-09-02) — **이 저장소 최초의 밀리초**

개발 빌드를 굽고 `forest-day-60s`를 3회 주행했다. **60초 × 3회, 종료 코드 전부 0.**

| 지표 | run1 | run2 | run3 | 반복 편차 |
|---|---:|---:|---:|---:|
| 측정 프레임 | 48,697 | 48,251 | 48,121 | — |
| **`gpuMs.p95`** | 1.091 | **1.095** | 1.099 | **0.8 %** |
| **`cpuMainMs.p95`** | 1.107 | **1.112** | 1.112 | **0.7 %** |
| `cpuRenderMs.p95` | 0.513 | 0.515 | 0.516 | 0.6 % |
| 드로우콜 p50 | 1,027 | 1,032 | 1,024 | 0.8 % |
| SetPass p50 | 32 | 32 | 32 | 0 % |
| 삼각형 p50 | 1,086,310 | 1,085,838 | 1,082,228 | 0.4 % |
| GC 할당/프레임 p50 | 7,218 B | 7,218 B | 7,218 B | 0 % |
| 33 ms 초과 프레임 | 0 | 0 | 0 | — |

측정 환경: RTX 4060 Ti · Ryzen 5 7500F · 1920×1080 창 모드 · 개발 빌드 · Windows 11.

**§8이 3개월째 못 답한 질문들의 답**

| §8 미결 | 답 |
|---|---|
| **CPU 바운드인가 GPU 바운드인가** | **GPU** — `gpuMs.p50` 1.03 > `cpuMainMs.p50` 0.85 > `cpuRenderMs.p50` 0.40. 다만 **셋 다 1 ms대라 지금은 어느 쪽도 병목이 아니다**(아래 주석) |
| 빌드에서의 밀리초 | 프레임 **약 1.24 ms (≈ 805 FPS)** — 이 저장소 최초의 ms 기록 |
| 빌드 드로우콜 vs 에디터 1,110 | **1,027** (SRP Batcher 1,017 + Standard 10). 예산 문서 §6의 게임 뷰 값 1,110과 **7.5 % 차이로 사실상 같다** — 빌드가 더 배칭해 주지 않는다 |
| 타일 교체 스파이크 | **관측되지 않았다.** 스파이크 93건은 전부 3~5 ms이고 6.67초 주기성이 없다. 33 ms 초과 프레임 **0건** |
| 그림자 패스의 몫 | 셰도우 캐스터 p50 **225** (예산 문서 §6의 201과 근사). 패스별 분리는 L3 캡처가 필요하다 |

> **경고 — 이 수치는 "빠르다"의 근거가 아니다.** 1.24 ms는 **텅 빈 상태에 가까운 씬**의 값일 수
> 있다. 웨이브가 도는 밤도, 몬스터 12마리도, 기차역도 이 시나리오에 없다(결정 ④-A는 의도적으로
> 주간 주행만 잡았다). 예산 문서 §7의 최적화 우선순위를 이 값 하나로 뒤집으면 안 되고,
> **야간 웨이브 시나리오(④-B)를 잰 뒤에 판단해야 한다.** 지금 확정된 것은 딱 하나다 —
> **자가 생겼고, 그 자의 반복 편차가 1 % 미만이다.**

> **BRG 드로우콜이 0이다.** GPU Resident Drawer가 꺼져 있다는 것(`m_GPUResidentDrawerMode: 0`)이
> 실측으로 확인됐다. §7 우선순위 1을 켜면 SRP Batcher 1,017이 BRG 쪽으로 옮겨가야 하고,
> **그 이동을 이 자로 판정할 수 있다** — 4차의 첫 항목이 그것이다.

### 1.8 착수하며 드러난 사실 — `Draw Calls Count` 는 Unity 6에 없다

부록 B가 "1차 실행에서 값이 차는지 확인한 뒤 정한다"고 남겼던 지점에서 실제로 문제가 나왔다.
**첫 3회 주행에서 드로우콜이 전부 0으로 기록됐다.** 예외도 경고도 없었다.

카운터 **6,368종을 전량 열거**해 확인한 결과, Unity 6에는 `Draw Calls Count`라는 이름의 카운터가
**존재하지 않는다.** 드로우콜은 제출 경로별로 쪼개져 있다:

```
Standard Draw Calls Count · Standard Instanced Draw Calls Count
SRP Batcher Draw Calls Count · BRG Draw Calls Count
Dynamic/Static/Instanced Batched Draw Calls Count · Null Geometry Draw Calls Count
```

`ProfilerRecorder`는 **없는 이름을 줘도 예외를 던지지 않고 0을 돌려준다.** 그래서 60초를 세 번
주행하고 결과 파일까지 남긴 뒤에야 알 수 있었다. 대응은 네 경로를 합산하는 것이고
(`PerfSample.DrawCalls`), 그 합이 1,027로 예산 문서의 1,110과 맞아떨어져 **합산이 옳다는 것이
교차 검증됐다.**

> **다른 카운터 이름도 같은 위험을 안고 있다.** 값이 0인 카운터를 보면 "정말 0"과 "이름이 틀림"을
> 반드시 구분해야 한다 — 부록 B의 목록은 이제 **실행으로 검증된 이름**만 남긴다.

## 2. 착수 전 결정 — **2건 미결**

각 항목에 §1의 실측을 붙였다. 표시 없는 항목은 권장안(★)으로 진행한다.

> **2026-09-02 개정** — 착수 전 결정은 7건이었다. L1(마이크로 벤치)을 범위에서 빼면서
> **③(CI 게이트 범위)과 ⑥(성능 테스트 패키지)이 소멸**했다 — CI에 올릴 대상도, 패키지를 쓸 곳도
> 없어졌기 때문이다. 두 항목은 판단 이력으로 아래에 남겨 둔다.
> **지금 답이 필요한 것은 ④와 ⑦ 두 건이고, 둘 다 ★ 권장안이 있어 답이 없어도 착수는 가능하다.**

### ① Frame Timing Stats를 켤 것인가

| 안 | 내용 | 대가 |
|---|---|---|
| **★ A. 항상 켠다** | `enableFrameTimingStats: 1` 전역 | GPU 타임스탬프 쿼리 비용 — 통상 프레임당 0.05 ms 미만. **켜지 않으면 GPU 시간을 영영 못 잰다**(§1.1) |
| B. 벤치 빌드에서만 | `BuildScript`에 `-perfbuild` 분기 | 벤치 빌드와 배포 빌드의 조건이 갈린다 — "잰 건 그 빌드고 배포는 다른 빌드" 문제 |

**권장 A.** 재는 비용이 재지 않아 생긴 §8의 공백보다 싸다. B는 두 빌드의 성능이 다르다는 새 변수를 만든다.

### ② 측정 장소

§1.2·§1.3의 실측으로 **빌드 Player가 강제된다.** 선택 여지는 "에디터에서도 볼 수 있게 할 것인가"뿐이다.

| 안 | 내용 |
|---|---|
| A. 빌드 전용 | 측정 경로가 하나뿐이라 수치가 항상 비교 가능하다 |
| **★ B. 빌드 + 에디터 HUD** | 에디터 플레이 중 화면 오버레이로 대략치를 본다. **기록·비교에는 쓰지 않는다** (포커스 문제로 신뢰 불가) |

**권장 B** — 단, 에디터 HUD는 *눈으로 보는 용도*로만 두고 **파일로 남기지 않는다.** "보여주는 화면
우선" 방향과 맞고, 개발 중 즉시 피드백이 있으면 실제로 쓰인다. 기록 경로는 빌드 하나로 유지한다.
HUD는 3차 작업이고, 1차·2차의 **기록 경로는 A와 완전히 동일**하다.

### ③ CI 게이트의 범위 — **소멸 (2026-09-02) · C 확정**

현 CI는 `ubuntu-latest`(GPU 없음)에서 GameCI로 돈다. **씬 벤치는 여기서 못 돈다.**

| 안 | CI에서 도는 것 | 못 도는 것 | 대가 |
|---|---|---|---|
| ~~A. L1만 CI~~ | 순수 로직 마이크로 벤치 (CPU) | 프레임·드로우콜·GPU | **L1을 빼면서 대상 자체가 사라졌다** |
| B. self-hosted 러너 추가 | 전부 | — | 이 PC를 러너로 등록 = 상시 켜 둬야 하고, 그동안 이 PC의 다른 부하가 수치를 오염시킨다 |
| **★ C. CI 게이트 없음** | — | 전부 | 전부 로컬 수동. 가장 가볍지만 회귀는 사람이 기억해야 잡힌다 |

**C 확정.** 당초 권장은 A였으나 L1이 빠지면서 CI에 올릴 것이 남지 않았다. B는 "측정 머신은 조용해야
한다"는 전제를 이 PC가 못 지킨다 — 에디터·Blender·브라우저가 같이 돈다. 로컬 벤치는 **의도적으로
실행할 때만** 돌리는 편이 수치가 더 믿을 만하다.

> **CI가 아무것도 안 하는 것은 아니다** — `-smoke`(§4.8)는 GPU 없이도 돌므로, 원한다면 나중에
> **부팅 검증만** CI 잡으로 얹을 수 있다. 성능 게이트와 달리 판정이 "살아서 종료했는가" 하나뿐이라
> 머신 노이즈에 영향받지 않는다. 1차 범위는 아니고, 3차 이후 선택 항목으로 둔다.

### ④ 첫 시나리오 대상 — **결정 필요**

| 안 | 무엇을 재나 | §8 미결 중 해소되는 것 | 저작량 |
|---|---|---|---|
| **★ A. 숲 주간 주행 60초** | 배경 · 타일 교체 · 스크롤 | 빌드 밀리초 · 타일 스파이크 · **CPU/GPU 바운드 판정** | 최소 — 기존 흐름 그대로 |
| B. 숲 야간 웨이브 60초 | 몬스터 12마리 + 그림자 + 전투 | 몬스터 렌더 실측 · 그림자 몫 | 밤 강제 진입 코드 필요 |
| C. 5지역 순회 각 60초 | 지역별 부하 차 | 위 전부 + 지역 비교 | 5배 시간 (5분/회 × 3회 = 15분) |
| D. 기차역 통과 | 역 5장 + 소품 스폰 | 이벤트 구간 스파이크 | 역 등장을 강제해야 함 |

**권장 A → B 순.** A가 **§8의 최대 미결(CPU/GPU 바운드)을 혼자 해소**하고, 코드가 가장 적다.
지역 비교(C)는 자가 생긴 뒤 시나리오 파일만 추가하면 되므로 나중에 붙여도 값이 같다.

### ⑤ 측정 길이 · 반복 횟수

| 항목 | 권장 | 근거 |
|---|---|---|

Unity 공식 성능 테스트 확장. 현업에서 마이크로 벤치의 사실상 표준이다(`Measure.Method()` ·

## 3. 범위

**포함**

1. **L2 — 씬 벤치** *(본체)*: 빌드 Player를 커맨드라인으로 자동 실행해 결정론 시나리오를 주행, 프레임 지표를 JSON으로 남긴다
2. **스모크 모드**: 같은 주행 인프라의 `-smoke` 분기 — 지표 수집 없이 **Boot → Main → Game 통과와 N초 생존만 확인**하고 종료 코드로 판정한다 (§4.8)
3. **L3 — 심층 캡처**: L2가 회귀를 잡았을 때 Profiler `.raw`를 뜨는 경로 (수동)
4. **비교·리포트 도구**: `Perf/baseline` 대비 회귀 판정 + 마크다운 리포트 (node)
5. **에디터 원클릭 메뉴**: `Game/QA/Performance` — 빌드 → 3회 실행 → 비교 → 리포트
6. **에디터 플레이 중 HUD** (결정 ②-B) — 눈으로 보는 용도, 기록 없음

> **2번은 새 작업이 아니라 분기 하나다.** `PerfRunner`가 이미 "빌드를 띄워 인게임까지 들어가고
> 스스로 죽는" 일을 하므로, 측정을 건너뛰는 갈래를 두는 것으로 끝난다. 이 프로젝트에 지금
> 빌드 부팅을 자동 검증하는 수단이 하나도 없다는 점(§1.5)을 감안하면 비용 대비 회수가 가장 큰 항목이다.

**비포함**

| 항목 | 왜 빼나 |
|---|---|
| 최적화 조치 자체 | 예산 문서 §7의 몫. 이 계획은 **판정 도구**만 만든다 |
| **L1 — 마이크로 벤치** | 순수 로직이 프레임을 먹는다는 신호가 **아직 하나도 없다.** 병목 후보는 렌더 쪽이다(드로우콜 1,110 · 셰도우 캐스터 201 · 물리 쿼리 17건뿐 §1.6). 반면 도입하면 패키지 추가 → **CI Library 캐시 무효화** → asmdef 신설 → CI 잡 추가가 따라온다. **L2가 `cpu_main_thread` 바운드를 지목한 뒤에 열 결정이다** (결정 ⑥) |
| `com.unity.test-framework.performance` | 위와 같은 이유 — L1 전용 패키지다 (결정 ⑥) |
| self-hosted CI 러너 | 결정 ③-C. 이 PC가 "조용한 측정 머신" 조건을 못 지킨다 |
| 멀티플레이(2인 이상) 성능 측정 | 클라이언트를 하나 더 띄우면 같은 PC의 부하가 수치를 오염시킨다. 단일 호스트만 잰다 |
| 메모리 스냅샷 자동화 | `com.unity.memoryprofiler` 추가 필요. 프레임 시간이 먼저다 — 4차 이후 재검토 |
| 시계열 대시보드(Grafana 등) | 실행이 하루 몇 회 규모라 마크다운 리포트로 충분하다 |
| GPU 벤더별 비교 | 측정 머신이 하나뿐이다. **절대값이 아니라 같은 머신에서의 델타로만 판정한다** (§4.4) |

## 4. 설계

### 4.1 3층 구조 — 층마다 답하는 질문이 다르다

```
스모크 (-smoke)       "게임이 뜨긴 하나?"        빌드 Player · 초~분 단위
   ↓ (부팅 확인)
L2 씬 벤치            "게임이 느려졌나?"          빌드 Player · 로컬 · 분 단위
   ↓ (회귀 검출 시에만)
L3 심층 캡처          "어디가 느린가?"            Profiler .raw · 수동 · 십분 단위
```

**L2가 이 계획의 본체다.** 스모크는 L2의 주행 인프라에서 측정만 뺀 갈래라 사실상 공짜고,
L3는 이미 도구(Profiler·Frame Debugger)가 있으므로 **경로만 문서화**한다.

> **L1(마이크로 벤치)은 이 구조에서 빠졌다** — "이 함수가 느려졌나?"는 지금 물을 질문이 아니다.
> 무엇이 느린지조차 아직 모르는 상태에서 함수 단위부터 재는 것은 순서가 거꾸로다.
> L2가 `cpu_main_thread` 바운드를 지목하면 그때 L1을 이 위에 얹는다 (§3 비포함 · 결정 ⑥).

### 4.2 무엇을 재나 — 지표 정의

`ProfilerRecorder`(런타임 카운터)와 `FrameTimingManager`(스레드별 시간)로 매 프레임 수집한다.

**프레임 시간 — 병목 판정의 핵심**

| 지표 | 출처 | 왜 재나 |
|---|---|---|
| `cpu_main_thread_ms` | FrameTimingManager | 스크립트·컬링·드로우콜 제출 |
| `cpu_render_thread_ms` | 〃 | 그래픽스 API 호출 |
| **`gpu_ms`** | 〃 | **셋 중 최대값이 병목** — §8의 "CPU/GPU 바운드" 질문의 답 |

**렌더 카운터 — 예산 문서와 같은 자**

`Draw Calls Count` · `SetPass Calls Count` · `Triangles Count` · `Vertices Count` ·
`Shadow Casters Count` · `Batches Count`

> 예산 문서 §6이 남긴 **drawCalls 1,110 / setPass 36 / shadowCasters 201 / tris 698,531**과
> **같은 이름의 카운터**다. 에디터 게임 뷰 vs 빌드라 절대값은 다르겠지만, **처음으로 대조가 가능해진다.**

**메모리·GC**

| 지표 | 왜 재나 |
|---|---|
| `GC Allocated In Frame` | **매 프레임 할당이 스파이크의 1차 원인.** 목표는 정상 주행 시 0 |
| `GC Used Memory` · `Total Used Memory` | 누수 감지 — 60초 주행 중 단조 증가하면 신호 |
| `Texture Memory` · `Mesh Memory` | 지역 전환 시 해제 누락 감지 |

**게임 고유 마커** (2차 이후)

`WorldScrollController.Update` · `TerrainTileStreamer` 타일 교체 · `MonsterWaveSpawner` —
`ProfilerMarker`를 코드에 심고 `ProfilerRecorder`로 읽는다. **타일 교체 스파이크(§8)의 범인을
프레임 번호로 특정**할 수 있게 된다.

### 4.3 통계 — 평균 FPS는 쓰지 않는다

**평균은 스파이크를 감춘다.** 60초 중 1초가 200 ms여도 평균은 거의 안 움직인다. 남기는 값은:

| 값 | 의미 |
|---|---|
| **p50 (중앙값)** | 평상시 체감 |
| **p95** | "가끔 버벅인다"의 정체 — **회귀 게이트의 주 판정값** |
| **p99 · max** | 스파이크. **타일 교체(6.67초 주기)가 여기 잡힌다** |
| 표준편차 | 프레임 페이싱의 고름 |
| `>33.3ms 프레임 수` | 30 FPS 밑으로 떨어진 프레임 개수 (절대 기준) |

**스파이크 검출**: 프레임 시간이 직전 p50의 3배를 넘는 프레임의 **인덱스와 시각을 함께 기록**한다.
6.67초 간격으로 규칙적으로 찍히면 타일 교체가 범인이라는 것이 그 자리에서 증명된다.

### 4.4 결정론과 노이즈 제어 — 이게 없으면 비교가 무의미하다

성능 자동화가 실패하는 가장 흔한 이유는 **매 실행마다 다른 게임이 돌기 때문**이다. 고정할 것:

| 변수 | 고정 방법 |
|---|---|
| 지역·세그먼트 추첨 | 시나리오가 **고정 시드**를 주입 (`Random.InitState`) — 매번 같은 타일 순서 |
| 시작 지역 | 시나리오가 지정 (`Region_Forest`) |
| 낮/밤 상태 | 시나리오가 지정 — 시간 진행을 벤치 중 정지시킬 수도 |
| 웨이브 소환 | 시나리오가 지정 (끄기 / 고정 수 강제) |
| 해상도 | `-screen-width 1920 -screen-height 1080 -screen-fullscreen 0` — **창 크기가 GPU 시간을 지배한다** |
| vSync | 이미 0 (§1.5). `Application.targetFrameRate = -1`로 상한도 푼다 |
| 포커스 | `runInBackground: 1` — **프로젝트 설정에 이미 켜져 있다**(§1.5). 벤치가 손댈 것이 없고, 끄는 변경이 들어오면 측정이 깨진다는 뜻이기도 하다 |
| 품질 레벨 | 시나리오가 명시 — 기본은 PC 레벨 |

**여전히 고정 못 하는 것** — 이 PC의 다른 프로세스, GPU 온도에 따른 클럭. 그래서:

> **절대값으로 판정하지 않는다.** 같은 머신에서 **연속으로 잰 A와 B의 차이**로만 판정하고,
> 리포트에 머신·GPU 드라이버·실행 시각을 함께 남긴다. "예전에 12 ms였는데 지금 14 ms"는
> 하드웨어가 바뀌었으면 무의미하다는 것을 리포트가 스스로 밝히게 한다.

**리포트**(마크다운)는 기준선과 나란히 놓고 **변화율과 판정**을 낸다:

```
| 지표          | 기준선 | 이번  | 변화    | 판정 |

```

**병목 판정 한 줄을 리포트가 항상 출력한다** — 이 계획이 만드는 값의 핵심이다.

### 4.6 회귀 게이트 — 무엇을 실패로 볼 것인가

| 지표 | 임계 | 근거 |
|---|---|---|
| `gpuMs.p95` | 기준선 대비 **+5 %** | 실측 노이즈 **0.8 %**의 6배 — 거짓 실패 없이 회귀를 잡는 폭 |
| `cpuMainMs.p95` | 기준선 대비 **+5 %** | 실측 노이즈 **0.7 %** |
| `gcAllocPerFrameBytes.p50` | **8 KB 초과 시 실패 · 기준선 대비 증가 시 경고** | 현재 기준선이 이미 **7,218 B/프레임**이다. 4 KB로 두면 첫 실행부터 실패해 게이트가 무시된다 — 아래 주석 참조 |
| `framesOver33ms` | 기준선 대비 증가 시 **경고** | 절대 기준(30 FPS)이라 하드웨어 의존이 크다 — 실패로는 안 삼는다. 현재 기준선은 **0** |
| `drawCalls.p50` | **정보만** | 예산 문서 §7 우선순위 1의 진행을 보는 값. 게이트 아님 |

> **임계는 2026-09-02 첫 3회 실측으로 조정했다.** 착수 시 출발값은 +10 %였는데, 실제 반복 간
> 편차가 `gpuMs.p95` **0.8 %** · `cpuMainMs.p95` **0.7 %**로 매우 작았다(§1.7). 시드 고정과
> 해상도 고정이 실제로 듣는다는 뜻이므로 임계를 **절반으로 조였다.** 노이즈의 6배면
> 거짓 실패는 나지 않으면서 5 % 회귀는 잡힌다.
>
> **GC 임계만 반대로 느슨해졌다.** 계획은 "프레임당 할당 0"을 목표로 4 KB 실패를 걸었는데,
> 실측 기준선이 **7,218 B/프레임**(3회 전부 동일)이다. 이 값을 줄이는 것은 최적화 작업이고
> 이 계획의 범위가 아니므로(§3 비포함), **지금 상태를 8 KB로 봉인해 더 나빠지는 것만 막는다.**
> 7,218 B의 정체를 밝히는 것은 4차의 과제로 남긴다 — 개발 빌드의 프로파일러 자체 할당인지
> 게임 코드인지 아직 구분되지 않았다.

### 4.8 실행 흐름 — Boot를 우회하지 않는다

이 프로젝트는 `NetworkManager`가 Boot에 있어 **인게임 씬을 직접 열 수 없다.** 벤치도 정규 흐름을 탄다:

```
TrainSurvival.exe -perfrun forest-day-60s -perfout Perf/runs/xxx.json
                  -screen-width 1920 -screen-height 1080 -screen-fullscreen 0
   ↓
Boot        GameBootstrapper → 서비스 등록
            PerfRunner가 -perfrun 감지 → 벤치 모드 진입
   ↓
Main        메뉴를 자동 통과 (호스트 시작)
   ↓
Game_*      시나리오 적용(시드·지역·시간대) → 워밍업 300프레임 버림
            → 60초 수집 → JSON 기록 → Application.Quit(0)
```

**Steam 전송 모드가 아니라 로컬 전송으로 강제**한다 (`ActiveTransportMode`) — 벤치가 Steam 클라이언트에
의존하면 자동화가 깨진다.

**스모크 모드 — 같은 흐름에서 측정만 뺀다**

```
TrainSurvival.exe -smoke 30
   ↓
위와 완전히 같은 경로 (Boot → Main → Game)
   ↓
30초 생존 → Application.Quit(0)
실패하면 → 비 0 종료 + 마지막 로그를 stdout으로
```

판정은 **종료 코드 하나**다. 다음 중 하나라도 걸리면 실패로 끝낸다:

| 실패 조건 | 잡히는 사고 |
|---|---|
| 제한 시간 내 인게임 씬 진입 실패 | 씬 등록 누락 · 라우트 상수 오류 · 부트 서비스 등록 실패 |
| 호스트 시작 실패 / 접속이 끊김 | **`ClosedByRemote`** — 프리팹 `GlobalObjectIdHash` 오염 · NetworkPrefabs 목록 불일치 |
| `LogType.Exception` 발생 | missing script · null 참조 |
| 지정 시간 전 프로세스 종료 | 크래시 |

**이 네 가지는 지금 전부 사람이 손으로 확인하고 있고, 놓치면 다음 플레이 검증 때 발견된다.**
스모크가 서면 빌드 직후 30초 만에 잡힌다. 벤치(`-perfrun`)는 이 흐름에 **측정과 JSON 기록을 얹은 것**이므로,
스모크가 실패하는 빌드는 벤치를 돌릴 필요도 없다 — 순서상 스모크가 먼저다.

**Player 프로파일러 캡처(L3)** 는 같은 실행에 Unity 표준 인자를 얹어 얻는다:

```
-profiler-enable -profiler-log-file Perf/captures/xxx.raw -profiler-capture-frame-count 900
```

이 `.raw`를 에디터 Profiler로 열면 **마커별 breakdown**이 나온다. L2가 회귀를 잡았을 때만 쓴다.

- [x] EditMode 회귀 0 — **1,406/1,406 통과** (기존 1,383 + 신규 23)

**1차에서 계획과 달라진 것 3가지**

| 계획 | 실제 | 왜 |
|---|---|---|
| `PerfRunner`를 Boot 씬에 배치 | **`[RuntimeInitializeOnLoadMethod]`로 자기 생성** | 씬 파일을 건드리지 않는다. 씬 YAML 편집은 이 프로젝트에서 수천 줄 재정렬 diff를 만들고, 벤치 하나 때문에 Boot 씬이 매번 바뀌면 그 리뷰 비용이 벤치의 값을 넘는다 |
| `LogCategory.Performance` 신설 | **그대로 신설** (`1 << 16`) | `Diagnostics`(1 << 15)가 이미 있지만 그쪽은 "문제 해결 후 통째로 지우는 것이 전제"인 임시 계통이라, 상설인 벤치 로그를 섞으면 안 된다 |
| `BuildScript` 변경 없음 | **`PerformPerfBuild()` 추가** | `DEVELOPMENT_BUILD`가 켜져야 카운터가 찬다. 기존 `PerformWindowsBuild`(CI 경로)는 손대지 않고 갈랐다 |

**2차**

- [ ] `node tools/perf/compare.js <run> <baseline>`이 회귀 시 **비 0으로 종료**한다
- [ ] 리포트가 "병목: CPU / GPU" 중 하나를 **한 줄로 명시**한다 (§4.5)
- [ ] 에디터 메뉴 한 번으로 빌드→3회 실행→리포트가 끝난다

**3차**

- [ ] 시나리오 파일 추가만으로 새 측정이 되고 코드 변경이 없다
- [ ] *(선택 항목을 했다면)* CI에 스모크 잡이 있고 통과한다

**4차**

- [ ] §7 우선순위 1(GPU Resident Drawer)의 효과가 **ms 단위로 기록**돼 있다
- [ ] 예산 문서 §8의 미결 항목이 실측으로 갱신됐다

## 7. 미결 · 위험

| 항목 | 내용 | 대응 |
|---|---|---|
| **측정 머신이 하나뿐** | 이 PC에서 에디터·Blender가 같이 돈다. 수치가 오염될 수 있다 | 벤치 중 다른 앱을 닫는 절차를 리포트에 남기고, **절대값 대신 델타로만 판정**(§4.4) |
| **개발 빌드 vs 배포 빌드** | `DEVELOPMENT_BUILD`가 켜져야 카운터 다수가 채워진다. **배포판은 이 값보다 빠르다** | 리포트에 `development: true`를 명기. 배포 성능은 별도 1회 측정으로 보정 |
| 벤치 모드가 게임 상태를 바꿈 | 시드 고정·웨이브 강제가 실제 플레이와 다른 코드 경로를 탈 위험 | 시나리오는 **주입만** 하고 게임 로직은 건드리지 않는다. 강제 항목을 JSON에 기록해 무엇을 바꿨는지 남긴다 |
| 자동 호스트 시작 경로 | Boot→Main→Game을 코드로 통과시켜야 한다. 메뉴 UI 변경에 깨질 수 있다 | 메뉴 UI가 아니라 **서비스 계층을 직접 호출**(`ILobbyRoomService`·`NetworkManager`)해 UI 의존을 끊는다. 깨지면 `-smoke`가 먼저 알려준다 — 이 경로가 벤치와 스모크의 공통 뿌리다 |
| **스모크가 잡지 못하는 것** | 종료 코드는 "프로세스가 살아 있었다"만 말한다. 화면이 새까맣거나 열차가 안 보여도 통과한다 | 스모크를 **플레이 검증의 대체가 아니라 하한선**으로 규정한다. 화면 판정이 필요하면 3차에서 스크린샷 1장을 남기는 것을 검토 (골든 이미지 비교는 범위 밖) |
| Frame Timing Stats 비용 | 켠 뒤 오히려 프레임이 느려질 수 있다 | 1차 1.1 직후 **켜기 전/후를 한 번 대조**해 비용을 수치로 남긴다 |
| `GameplaySceneRoute.Name`이 검증 씬을 가리킴 | 현재 `Game_StationBlockout` (임시). 벤치 대상 씬이 바뀐다 | 시나리오 SO에 **씬 이름을 명시**해 라우트 상수와 분리한다 |
| 기준선을 언제 갱신하나 | 최적화로 좋아졌을 때만 갱신해야 하는데, 나빠진 뒤 갱신하면 게이트가 무력화된다 | 기준선 갱신은 **커밋 메시지에 사유 필수**로 규약화 |
