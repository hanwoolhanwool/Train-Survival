## 2. 배너를 어떻게 만들 것인가 — 결론: `Ver2` + TMP

### 2.1 초판의 A/B/C안이 왜 폐기됐는가

초판은 "3D 메시를 쓸 것인가, 이미지로 구울 것인가"를 물었다. 그 질문의 전제는
**"쓸 수 있는 이미지가 없다"** 였는데, `Ver2.png`의 존재로 전제가 무너졌다.

| 초판 안 | 판정 |
|---|---|
| A. 3D 메시 그대로 | **폐기** — §2.2 |
| B. Blender에서 부품별 굽기 | **폐기** — 원본 컨셉 아트가 3D 변환본보다 품질이 높다(§2.2-1) |
| B′. 외부 제공 스프라이트 | **채택** — `Ver2.png`가 §2.3의 세 조건을 만족한다 |
| C. 하이브리드 | **폐기** — 3D를 쓰지 않으므로 성립하지 않음 |

### 2.2 3D 메시를 쓰지 않는 근거 3가지

1. **원본 컨셉 아트가 3D 변환본보다 확연히 낫다.**
   Blender 메시는 `Ver1`을 Meshy로 3D 변환한 결과물인데, 변환 과정에서 디테일이 상당히 뭉개졌다.
   `TRAIN SURVIVAL` 각인이 원본은 **선명한 황금**인 데 반해 3D는 탁한 아이보리로 죽었고,
   명판 테두리의 황동 광택과 볼트 하이라이트도 원본이 훨씬 살아 있다.
   **원본이 있는데 그 열화본을 렌더할 이유가 없다.**
2. **실시간 조명이 이 에셋에서 거의 값을 하지 않는다.** 검증 결과다 —
   같은 3점 조명으로 **EEVEE(실시간 ≈ URP)** 와 **Cycles GPU 64샘플**을 렌더해 비교했더니
   차이가 작았다(Cycles 쪽 그림자가 조금 더 깊은 정도). 이 배너의 룩은 대부분 텍스처에
   구워진 음영에서 나오기 때문이다. 즉 **3D로 유지해서 얻는 것이 거의 없다.**
3. **얇은 디테일이 실시간에서 지글거린다.** 194만 tris의 상당량이 격자 기둥·볼트·잎사귀다.
   §6.4의 카메라 미세 드리프트를 걸면 계속 반짝인다. 2D 스프라이트에는 이 문제가 없다.

여기에 **194만 tris + 8K 텍스처가 통째로 사라진다**는 비용 이점이 더해진다.

### 2.3 `Ver2.png`가 만족하는 세 조건

외부 이미지를 배너로 쓰려면 아래를 전부 만족해야 한다.

| 조건 | 왜 필요한가 | `Ver2.png` |
|---|---|---|
| **문구와 판이 분리 가능** | 문구가 판에 구워져 있으면 로컬라이징·항목 증감이 막힌다 | ✓ **명판이 비어 있다** |
| **문구 있는 판과 픽셀 정렬** | TMP 문구를 얹을 때 위치·크기의 정답이 필요하다 | ✓ `Ver1`이 동일 프레임 |
| **선택 상태를 표현할 재료** | 호버·포커스가 그림으로 구분돼야 한다 (§8.2 색각 대응) | ✓ **1번 명판이 황금색, 2~4번이 어두움** |

**세 번째가 특히 중요하다** — Ver2 안에 이미 **기본 상태(어두운 판)와 선택 상태(황금 판)가
한 장씩** 들어 있다. 잘라내면 그대로 Normal / Hover 스프라이트가 된다(§4.2).

### 2.4 기차는 반대로 3D — 역할이 정반대이기 때문

배너와 기차는 같은 질문을 받지만 **화면에서의 역할이 정반대라 답도 반대**가 된다.

| | 배너 | 기차 |
|---|---|---|
| 역할 | **움직이지 않는 UI** | **이 화면에서 유일하게 움직이는 것** |
| 답 | **2D 스프라이트** | **3D 유지** |

1. **증기가 기차를 감싸야 한다.** 3D 파티클이 굴뚝 뒤에서 나와 차체 앞을 지나가려면 깊이가 필요하다.
   2D면 스프라이트를 여러 층으로 잘라야 하고, 차체를 스치는 실린더 배기(시안 하부에 보인다)는
   아예 만들 수 없다.
2. **§6.4의 카메라 드리프트는 기차에서만 값을 한다.** 2D 배경과 3D 기차의 **상대 이동**이
   곧 공간감이다. 기차까지 2D면 화면 전체가 한 장의 그림이 되고, 드리프트는
   "그림이 흔들리는 것"으로 보여 **역효과**다.
3. **헤드램프가 실제 광원이어야 한다.** 시안에서 가장 밝은 점이고, Bloom이 증기·레일에 반응해야 한다.
4. **감축 손실이 배너보다 훨씬 적다.** 실루엣이 단순한 금속 덩어리라 Decimate 0.15에서도
   육안 차이가 없다. 배너는 반대로 격자·잎사귀 투성이라 감축이 실루엣을 무너뜨린다.

**결정**: 3D 유지 + **Decimate 0.15** (1.94M → 약 29만 tris) + 텍스처 2048² — 2026-08-20 사용자 결정.

├─ Canvas_UI           Screen Space - Overlay, sortingOrder  20   ← L5
│   ├─ Panel_Play                  새 여정 / 친구 참가 / (개발) 씬 선택

**배경을 Camera가 아니라 Canvas에 두는 이유**: `Screen Space - Camera` + `sortingOrder −10`이면
3D 기차가 배경과 UI 사이에 자연히 들어간다. Skybox나 쿼드로 두면 FOV 변경마다 프레이밍을 다시 잡아야 한다.

### 3.2 배치 규칙

- **모든 UI 좌표는 §0.3 정규화 실측을 앵커로 환산한다.** 1920×1080 하드코딩 금지 —
  `anchorMin`/`anchorMax`에 정규화 값을 그대로 넣으면 해상도 변화에 자동 대응된다.
- **명판은 VerticalLayoutGroup을 쓰지 않는다** — 원근으로 피치가 불균등하다(§0.3).
- 배너는 화면 좌측 가장자리에 붙고 **상하가 의도적으로 잘린다.** 잘림이 화면 밖으로
  이어지는 느낌을 주므로 `Preserve Aspect`로 축소하지 말고 **cover 방식으로 넘치게** 둔다.

## 4. 에셋 반입 파이프라인

기존 규약([아트 반입 파이프라인 메모] · `Train_RailTrack` 선례)을 따른다 —
`zz_src_` 리네임, 머티리얼 사본 `M_<명>`, 텍스처 `T_<명>_<채널>`, FBX `path_mode='STRIP'`.

### 4.1 배경

1. `BackGround.png` (1672×941) → **1920×1080 업스케일**.
   1080p에서 픽셀 1:1이 되고 **BC7 압축 요건(4의 배수)** 을 만족한다.
   현재 세로 941은 4의 배수가 아니라 그대로는 압축이 걸리지 않는다.
2. `Art/Textures/UI/Menu/T_Menu_Background.png` — Sprite(2D and UI) · sRGB · Mip **off** ·
   Compression High Quality(BC7) · Max Size 2048.
3. **cover 스케일**: 16:10·21:9에서 여백이 없도록 화면 종횡비에 맞춰 스케일을 계산한다.
   계산은 순수 함수로 분리해 EditMode에서 고정한다(§8.1).

### 4.2 배너 — `Ver2.png` 처리

1. **배경 제거** — 배너 뒤 밝은 회색을 투명 알파로.
   배너가 어두운 금속이라 대비가 커서 **휘도 + 색조 임계 키잉**으로 충분하다.
   주의 지점 둘: **잎사귀 가장자리**와 **격자 기둥 사이의 틈**. 가장자리는 1~2px 페더링을 준다.
2. **명판 4장 잘라내기** — §0.3 좌표를 알파 바운즈로 정밀화한 뒤 각각 크롭.
   - `T_Menu_Plate_Normal.png` ← Ver2의 **2번 명판**(어두움)
   - `T_Menu_Plate_Hover.png` ← Ver2의 **1번 명판**(황금) — 화살표는 별도로 분리
   - 명판 크기는 원근으로 미세하게 다르므로, 슬롯별 RectTransform 크기에 맞춰 스케일한다.
     차이가 눈에 띄면 슬롯별로 4장씩 따로 크롭한다(§11 미결 1번).
3. **프레임 스프라이트** — 명판을 **지우지 않는다.** Ver2 전체를 그대로 프레임으로 쓰고,
   그 위 같은 자리에 명판 스프라이트를 겹친다. 겹치는 순간 원본과 동일해지므로
   **잘라낸 자리가 드러나지 않는다.** 호버 시 명판이 커지는 방향(1.00→1.02)으로만 움직여
   아래 원본을 항상 덮는다.
4. **문구는 TMP로 얹는다** — `Ver1.png`에서 문구의 위치·크기·색을 실측해 정답으로 삼는다.
   폰트는 §9 리스크 8 참조.
5. Import: Sprite · sRGB · Mip off · BC7 · Max Size 2048(프레임) / 512(명판).

### 4.3 기차

1. `steam locomotive 3d model` → `zz_src_Train_Locomotive_Menu` 리네임 후 사본 작업.
2. **Decimate 0.15 확정** (1.94M → 약 29만 tris, §2.4).
   감축 후 **실루엣 대조 렌더**로 굴뚝·난간·연결봉이 뭉개지지 않았는지 확인한다.
3. **텍스처 4장 반출** — packed가 유일본이므로 `im.filepath_raw = 경로; im.file_format='PNG'; im.save()`로
   명시 저장 → `T_Train_Menu_BaseColor/Normal/Roughness/Metallic.png`, **2048² 다운샘플**.
4. **창문 발광 마스크 생성** — BaseColor에서 창문의 따뜻한 노란 영역을 임계값으로 추출해
   `T_Train_Menu_Emission.png`. §6.2 명멸의 입력이다.
   BaseColor를 그대로 Emission에 넣으면 차체 전체가 발광한다.
5. FBX 반출 → `Art/Models/Train_Locomotive_Menu.fbx`. 메타는 RailTrack 메타를 템플릿으로
   **guid 수기 발급**, `globalScale`로 실치수 결정.
6. 머티리얼 `M_Train_Locomotive_Menu` — **URP Lit** (인게임 Simple Lit과 달리 금속 반사가 필요).
7. 시안의 차체 `∞-EXP` 명판은 3D 텍스처에 없다 — §11 미결 3번.

### 4.4 원근 정합 — 이 계획에서 가장 손이 많이 가는 지점

배경(2D)의 선로와 3D 기차의 선로가 어긋나면 **한눈에 가짜로 보인다.**
다행히 **`레퍼런스.png`가 정답지 역할을 한다** — 같은 배경 위에 기차가 놓인 그림이므로,
3D 기차를 그 실루엣에 겹치는 것이 목표가 된다.

1. `BackGround.png`의 두 레일을 직선 연장 → **소실점 픽셀 좌표** 산출.
2. 소실점의 화면 정규화 좌표에서 카메라 **yaw·pitch**를 역산.
3. 침목 간격의 원근 축소율로 **카메라 높이·FOV** 추정 (초기값 FOV 50~60).
4. Unity에서 배경 Canvas 위에 3D 기차를 놓고 **`레퍼런스.png`와 스크린샷 대조를 반복.**
   판정 기준은 **바퀴 접지선이 배경 레일에 얹히는가**와 **굴뚝·캐빈 실루엣이 정답지와 겹치는가** 둘이다.
5. 실패 시 폴백: `레퍼런스.png`(기차 포함)를 배경으로 쓰고 증기·불빛만 2D 오버레이로 얹는다.
   연출 §6.1~6.3은 그대로 성립하고, 잃는 것은 §6.4의 시차뿐이다.

### 5.2 기존 로직 이관 (버리지 않는다)

| 기존 (`MainMenuController`) | 이관 위치 |
|---|---|
| `ServiceLocator.TryGet<INetworkSessionService>` 대기 표시 | `MenuSessionActions` — 준비 전에는 "게임 시작" 명판을 Disabled로 |

| `GameplaySceneRoute` 씬 전환 | `Panel_Play` **개발 빌드 전용 코너** (`#if UNITY_EDITOR \|\| DEVELOPMENT_BUILD`) |

### 5.3 명판 4개로는 부족하다 — "참가"가 없다

시안의 메뉴는 **게임 시작 / 업적 / 설정 / 종료** 4개인데 이 게임은 **1~4인 협동**이다.
**"게임 시작"을 누르면 하위 패널을 연다**:

```
[게임 시작] → Panel_Play
                ├─ 새 여정 (호스트 시작)
                ├─ 친구 참가 (Steam 오버레이 안내 / Direct 모드에서는 주소 입력)
                └─ (개발 빌드) 인게임 씬 선택 — Game ↔ Game_ArtTest
```

**문구가 TMP이므로**(§2.3) 나중에 명판을 5장으로 늘려 "참가"를 1급 항목으로 올릴 수도 있다 —
Ver2의 빈 명판 한 장을 복제해 슬롯을 추가하면 된다. 1차에서는 하지 않는다.

### 5.4 운행 공고 게시판

가이드 §11의 **"Patch Note → 벽에 붙은 공고문 종이"** 치환이 시안에 이미 구현돼 있다.

- 기본 상태: 게시판에 최신 버전 요약 3줄 (시안은 더미 문자로 채워져 있다).
- 클릭 시: `Panel_Notice`가 열리고 패치 노트 전문을 표시.
- 문구는 TMP — **공고판 이미지에 문구를 굽지 않는다**(§11 미결 2번의 생성 요건).

### 7.1 이 순서인 이유

- **2차(기차)가 3차(배너)보다 앞인 이유**: 원근 정합이 실패하면 폴백(§4.4-5)으로 구도가 바뀐다.

- **4차가 5차보다 앞인 이유**: 연출 없이도 메뉴는 동작하지만 그 반대는 성립하지 않는다.
- **6차가 마지막인 이유**: 공고판 이미지가 아직 없다(§11 미결 2번). 생성 대기 중에도
  1~5차가 막히지 않도록 뒤로 뺐다.

### 8.2 플레이 검증 (짝 문서 `로비-메인메뉴-플레이-검증-항목.md`)

- ☐ 완성 화면이 `Lobby 시안.png`와 **나란히 놓고 구분이 안 될 만큼** 일치한다
- ☐ 기차 바퀴 접지선이 배경 레일에 얹혀 보인다 (§4.4 판정 기준)
- ☐ 배경의 램프 방향과 3D 기차의 하이라이트 방향이 **같은 쪽**이다
- ☐ 명판 4장이 각각 호버에 반응하고, 어느 것이 선택됐는지 **색 없이도** 구분된다 (색각 대응)
- ☐ TMP 문구가 `Ver1.png`의 위치·크기와 어긋나지 않는다
- ☐ 마우스 없이 키보드/게임패드만으로 4항목 전부 도달·실행된다
- ☐ 1080p / 1440p / 16:10 / 21:9에서 배경 여백이 없고 배너가 잘리지 않는다
- ☐ "게임 시작 → 새 여정"이 기존과 동일하게 호스트 세션을 열고 인게임 씬을 로드한다
- ☐ Steam 모드에서 로비 생성·초대 흐름이 이전과 동일하다
- ☐ 정지 상태로 30초 두었을 때 화면이 **그림 한 장으로 읽히지 않는다** (§6.4)
