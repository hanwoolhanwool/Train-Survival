### 0.1 왜 하는가

이 저장소는 SOLID 준수 규칙을 [별도 문서](../../conventions/solid-principles.md)로 내걸고
아키텍처 규칙을 컴파일 단계에서 강제한다. 그 주장과 **1,500줄 클래스**는 같이 서 있기 어렵다.
"알고 있고 설계안도 있다"(이 보고서)는 유효한 답이지만, **실행까지 끝낸 상태가 낫다.**

다만 이것은 부차적 이유다. 실질적 이유는 아래 §0.2다.

## 1. 먼저 — 이 코드베이스가 이미 잘하고 있는 것

리팩터링 보고서가 결함부터 나열하면 판단을 그르친다. **손대면 안 되는 것**을 먼저 확정한다.

### 1.1 순수 로직 분리가 확립돼 있다

`*Math`/`*Logic` **35개 파일**이 MonoBehaviour·NetworkBehaviour 밖에 있고, Unity·네트워크 의존이 없다.

| 예 | 분리된 것 |
|---|---|
| `TrainStateLogic` (414줄) | 칸 데미지·연쇄 이탈·수리·재결합·슬롯 재건 — `public static` 18개 |
| `StructureGridLogic` (392줄) | 그리드 좌표 변환·점유 판정·회전 |
| `PlankGridLogic` (140줄) | 판자 열 증축 가능 여부·갑판 반폭 파생 |
| `CarBuildAimLogic`·`CarRecoupleAimLogic`·`PlankAimLogic` | 조준 기하 계산 |
| `WorldScrollMath`·`TileStreamingLogic`·`HarpoonAimMath`·`WaveMath` 등 | 각 도메인의 계산 축 |

이것이 **EditMode 620개**의 기반이다. 게임 코드에서 이 정도 테스트 가능성은 드물다. **이 구조는 유지한다.**

### 1.2 UI가 상태를 소유하지 않는다는 규약이 이미 있다

`InventoryHud`의 클래스 주석(L13~16)이 명시한다:

> *"UI는 상태를 소유하지 않는다: `ILocalHotbar` 읽기 조회와 이벤트 구독으로만 그린다."*

즉 **Model 경계는 이미 의도적으로 설계돼 있다.** 아래 §3.2의 문제는 이 규약의 부재가 아니라 **규약을 지키는 코드가 한 파일에 다 들어간 것**이다.

### 1.3 읽기 계약과 변이 API가 분리돼 있다

`ITrainState`(16멤버)는 **조회 전용**이고, 변이는 `ServerXxx` 메서드로 인터페이스 밖에 있다.
소비자(HUD·CarView·몬스터)가 변이 API에 의존할 수 없는 구조다 — DIP·ISP를 의식한 설계다.

## 2. 정정 — 문제는 "계산의 집중"이 아니라 "배선의 집중"이다

초기 진단은 대형 파일 3개를 "SRP 심각 위반, 로직 덩어리"로 봤다. **조사 결과 이는 부정확하다.**

계산 로직은 §1.1대로 이미 빠져 있다. 남은 대형 파일에 실제로 들어 있는 것은 —

```
입력 읽기  +  레이캐스트  +  네트워크 상태 보유  +  RPC 송수신
         +  이벤트 발행 게이트  +  표시 보간  +  OnGUI 그리기
```

**전부 "배선"이다.** 그래서 순수 로직 추출(이 프로젝트가 이미 잘하는 기법)로는 줄지 않는다.
배선의 집중은 **다른 축의 분해**를 요구한다 — 계산을 빼는 게 아니라 **역할별 컴포넌트로 쪼개는 것**.

> 이 구분이 중요한 이유: "로직을 더 빼라"는 처방은 이 코드에 효과가 없다. 이미 뺐다.

### 3.2 `UI/InventoryHud.cs` — 1,169줄

**책임 목록**

| 책임 | 규모 |
|---|---|
| 이벤트 구독·미러링 필드 | 구독 **19개**, 상태 필드 **20개+** |
| 패널 그리기 | **7개** — 핫바 · 인벤토리 · 창고 · 보따리 · 엔진 프롬프트 · 건축 조준 · 망치 타깃 |
| 드래그 앤 드롭 상태 기계 | `_dragFromIndex`·`_dragFromStorage`·`_dragFromBundle`·`_dragFromEquip` |
| 표시 문자열 조립 | `BuildSpendPreview`·`BuildShortagePrompt`·`GetSlotLabel`·`GetHungerSuffix` |

**핵심 문제 — 같은 패턴을 7배로 늘린 것**

같은 어셈블리의 `BossHudView`(147줄)는 **동일한 패턴**을 쓴다: 이벤트 구독 → 로컬 필드 미러링 → `OnGUI` 그리기.
차이는 관심사가 **하나**(보스 체력바)라는 것뿐이다. 즉 `InventoryHud`는 **잘못된 패턴이 아니라 분할되지 않은 패턴**이다.

**진짜 결함 — UI가 서버 규칙을 복제한다**

`BuildSpendPreview`(L670~733)가 `HotbarLogic.TryRemoveAnyResource`를 호출해
**실제 자원 차감 순서를 UI에서 재현**한다. 소모 미리보기를 정확히 보여주려는 의도지만 —

> 차감 규칙이 바뀌면 **서버와 UI 두 곳**을 고쳐야 한다. 한 곳만 고치면 미리보기와 실제가 어긋난다.
> 이는 SRP가 아니라 **단일 진실 원천(SSOT)** 위반이며, 이 파일에서 가장 실질적인 위험이다.

**MVP 관점의 정확한 진술**

"MVP 부재"는 과한 표현이다. Model 경계(`ILocalHotbar`)는 있고 규약도 명문화돼 있다.
없는 것은 **Presenter** — 이벤트를 받아 표시용 상태로 가공하는 층이다. 지금은 View가 그 일을 겸한다.

| MVP 요소 | 현재 상태 |
|---|---|
| Model | ✅ `ILocalHotbar`·`ITrainState`·EventBus — 분리됨 |
| View | ⚠ `OnGUI` 직접 그리기 — 존재하나 Presenter와 미분리 |
| Presenter | ❌ 없음 — View가 구독·미러링·문자열 조립을 겸함 |

### 3.3 `Gameplay/Train/RepairHammerController.cs` — 1,115줄

**클래스 주석이 스스로 증언한다** (L13~24 요약):

**하나의 클래스가 4개의 상호작용 모드**를 담당한다. 각 모드는 조준 방식·비용 규칙·RPC·HUD 이벤트가 전부 다르다.

|---|---|

| 조준 4종 | `TryUpdatePlacementAim`·`TryUpdatePlankAim`·`TryGetBuildAim`·`TryGetRecoupleAim` |
| ServerRpc 7개 | 수리·건축물 설치·철거·판자 설치/제거·칸 건설·재결합 |

## 4. 분해 설계안

### 4.1 `TrainState` → 5개 컴포넌트

**설계 원칙**: 네트워크 상태(`NetworkList`)의 **소유자는 하나만** 유지한다. 나머지는 그 소유자를 참조해 규칙을 실행한다.
상태를 쪼개면 복제 단위가 늘어 재접속 복원(개발 가이드 §6.3)이 복잡해지므로 **상태는 쪼개지 않는다.**

```
TrainState (NetworkBehaviour, 유지)          ~380줄
├─ NetworkList 5개 소유 · 수명주기 · 변경 알림
└─ ITrainState 구현 위임

TrainQuery            (순수 조회)             ~350줄  ← ITrainState 구현체
TrainDamageService    (손상·수리 규칙)         ~250줄
TrainConstruction     (칸·건축물·판자 건축)     ~250줄
TrainEjectSimulation  (서버 이탈 물리)         ~120줄
TrainEjectDisplay     (클라 표시 보간)         ~90줄   ← 실행 주체가 다르므로 분리
```

| 왜 이렇게 나누는가 | |
|---|---|
| `TrainQuery` 분리 | 조회는 **읽기만** 한다 — 변이 코드와 섞일 이유가 없고, 소비자가 가장 많이 쓰는 면이다 |
| `TrainEjectSimulation` ↔ `TrainEjectDisplay` | **서버 전용 / 클라 전용**이라 실행 주체가 다르다. 한 파일에 있으면 매번 확인해야 한다 |
| `TrainConstruction` 독립 | 건축 개편이 3차까지 진행됐고 앞으로도 바뀐다 — 변경이 잦은 축을 격리한다 |
| 상태를 안 쪼갬 | 복제 단위 증가 = 재접속 복원 복잡화. **얻는 것보다 잃는 게 크다** |

**검증**: `TrainStateLogic` 순수 로직은 그대로 두므로 기존 EditMode 테스트가 전부 유효하다.

**순서 근거**

- **1번이 맨 앞인 이유**: 유일하게 **실제 버그로 이어질 수 있는** 항목이다(UI가 서버 차감 규칙을
  복제한다 — §3.2). 나머지는 가독성·유지보수 문제다. 공수도 가장 적고 재배선이 없다.
- **2번이 그다음인 이유**: 재배선이 있는 항목 중 **유일하게 `NetworkObject`가 아니다.**
  프리팹 해시 위험 없이 "분해 → 배선 → 검증" 절차를 한 번 돌려볼 수 있다. 넘길 곳(역할별 뷰)도
  이미 만들어져 있다(§3.5). 낮은 위험으로 절차를 검증하고 4~6번으로 간다.
- **4·5번의 공통 위험**: ServerRpc를 다른 컴포넌트로 옮기면 **`NetworkObject` 소유권 ·
  `GlobalObjectIdHash`** 문제가 생길 수 있다. 프리팹 해시 오염은 클라이언트 접속 거부
  (`ClosedByRemote`)로 나타나 원인 추적이 어렵다. 둘 다 **같은 `NetworkObject` 위에** 컴포넌트를
  더하는 방식으로 소유권 구조를 바꾸지 않는다.
- **6번이 마지막인 이유**: 가장 크고 위험한데, `TrainState`는 **재접속 복원의 원천**
  (개발 가이드 §6.3)이라 깨지면 M6 재접속 기능이 통째로 흔들린다. 얻는 것은 가독성뿐이다.
  **차수 예산이 부족하면 여기서부터 잘라낸다**(§0.4).

**전체 9일** — 2026.09 기반 정리 차수 안에서 다른 차단 요소 해소와 나란히 잡는다(§0).

## 7. 결론

**이 코드베이스의 SOLID 준수 상태는 양호하다.** 계산과 표현이 분리돼 있고, 읽기 계약과 변이가 나뉘어 있으며,
어셈블리 의존이 단방향이다. 테스트 선언 844개가 그 증거다.

문제는 **다섯 파일에 배선이 집중된 것**이고, 그중 **실제 위험은 하나**(§3.2 SSOT 위반)다.
나머지는 "지금 고치지 않아도 동작하지만, 다음 기능을 넣을 때 비용을 치르는" 종류다.

**결정 (2026-08-23)** — 다섯 건 **전부를 2026.09 「기반 정리」 차수에서 실행한다**(§0).
2026-08-20 시점의 권고("1번만 실행하고 나머지는 해당 도메인을 다시 건드릴 때")는
**문서 정비를 우선하기 위한 판단**이었고, 그 정비는 완료됐다. 이제 미루는 쪽의 비용이 더 크다 —
10월 M7 최종장이 `TrainState`·`RepairHammerController` 위에 직접 올라타고, 그 뒤로는
일정에 구조 변경을 넣을 자리가 없다(§0.2).

**남는 원칙은 그대로다**: 순수 로직 35파일(§1.1)은 건드리지 않는다. 이 차수는 **배선 분해**이지
로직 이동이 아니다. UI Toolkit 이행과 Presenter 계층 신설도 범위 밖이다(§6).
