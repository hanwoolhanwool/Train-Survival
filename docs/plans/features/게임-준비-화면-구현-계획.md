# 게임 준비 화면 구현 계획 — 방 만들기 이후의 대기실

> **상태**: **1~3차 완료** (2026-08-22, EditMode 731/731) — 혼자서 방 열고 → 대기실 → 출발까지 완주되고,
> 로스터가 접속·이탈에 따라 갱신된다. 4~5차 미착수 · 착수 전 미결 4건 결정 완료(§14 ①)
> · 차수별 실측·결정은 §14 ③(1차) · ④(2차) · ⑤(3차)
> **선행**: [로비·메인 메뉴 구현 계획](로비-메인메뉴-구현-계획.md) 1~7차 완료 (main = e2b69dd)
> **짝 문서**: `게임-준비-화면-플레이-검증-항목.md` (구현 완료 후 작성)

메인 메뉴에서 **방 만들기**를 누른 뒤, 그리고 **참가하기**로 남의 방에 든 뒤 도착하는 화면이다.
누가 모였는지 보고, 난이도를 고르고, 친구를 부르고, 호스트가 출발 신호를 준다.

**이 화면은 지금 없다.** 현행 흐름은 방 만들기 → `Panel_Host` → "새 여정"에서 곧바로
인게임 씬을 로드한다 — 즉 **모일 시간이 없다.** 이 계획이 그 사이에 대기실을 넣는다.

## 1. 범위

### 1.1 이 계획이 하는 것

- 시안 재현 — 로스터 패널(4슬롯) · 조작 패널(난이도·시작·초대·나가기), 배경은 기존 로비 그대로
- **대기 구간의 신설** — 호스트가 세션을 열고도 인게임으로 넘어가지 않는 상태
- **참가자 목록 동기화** — 누가 들어왔는지 네 명 모두의 화면에 뜬다
- **호스트 / 게스트 권한 분리** — 시작과 난이도는 호스트만
- 난이도 선택 **UI와 세션 전달**까지 — 3단계(쉬움·보통·어려움), 값은 인게임까지 실려 가되
  **웨이브 배율 적용은 비범위**다 (§12 미결 1번 결정)

### 1.2 하지 않는 것 (명시적 비범위)

| 항목 | 이유 |
|---|---|
| **준비(Ready) 토글** | 시안에 없다. 슬롯 상태는 "접속 중" 하나뿐이고, 출발은 호스트가 단독 결정한다 |
| 채팅 | 시안에 자리가 없다. Steam 오버레이가 대신한다 |
| 캐릭터·직업 선택 | 게임에 그 개념이 없다 |
| 슬롯 인원 확장(5인+) | 패널 그림이 **4장 고정**이고 Steam 로비도 친구 전용 4인이다 |
| 강퇴 | 친구 전용 로비라 우선순위가 낮다 — §12 미결 4번 |
| 난이도의 실제 게임플레이 배율 | **확정 비범위 (2026-08-21 결정)** — M4 지역·웨이브 시스템 수정이 필요하다. 값 전달까지만 하고 배율은 별도 마일스톤 |
| Steam 퍼소나 이름 표시 | **확정 비범위 (2026-08-21 결정)** — 이번에는 임시 닉네임(`플레이어 N`), Steam 이름은 차후 (§7.3) |

## 2. 어디에 만들 것인가 — 결론: `Main.unity` 안의 화면

새 씬(`Lobby.unity`)을 만들지 않는다.

| 근거 | 설명 |
|---|---|
| **배경이 같다** | 시안이 로비와 같은 배경·같은 해상도의 재생성본이다. 씬을 나누면 배경·평면 열차·연출(증기·창문 명멸·카메라 드리프트)을 **통째로 복제**해야 하고, 그 순간 두 벌이 따로 늙는다 |
| **전환이 끊기지 않는다** | 로드 없이 캔버스만 바꾸면 배경이 이어져 "같은 정차역에서 사람을 기다린다"는 감각이 유지된다 |
| **네트워크가 단순해진다** | `EnableSceneManagement = 1`이라 씬 전환은 곧 네트워크 씬 동기화다. 대기 중에 씬을 한 번 더 갈아타면 **호스트만 먼저 이동하고 접속 중이던 클라이언트가 어긋나는** 경우를 새로 만든다 |
| **되돌아오기가 싸다** | "나가기"가 씬 로드가 아니라 캔버스 전환이다 |

**대신 치르는 값**: `Main.unity`가 커진다. 그래서 준비 화면은 `Canvas_Ready` **한 루트 밑에
전부 모으고**, 배너 화면과는 `SetActive` 한 번으로 갈린다(§4.1).

## 3. 세션 흐름 — 지금 구조가 왜 못 버티는가

### 3.1 현행

```
[방 만들기] → Panel_Host → [새 여정]
                              └─ StartHost() + CreateLobby() + LoadGameplayScene()   ← 한 호출 안에서
```

`MenuSessionActions.StartNewJourney()`가 **세 가지를 한꺼번에** 한다. 대기실은 이 셋 사이에
들어가야 하는데, 지금은 들어갈 틈이 없다.

### 3.2 개편

```
[방 만들기] ─ OpenRoom()  = StartHost() + CreateLobby()          → 준비 화면 (호스트)
                                                                     │
[참가하기] ─ JoinDirect() / Steam 초대 수락 → 접속 성공             → 준비 화면 (게스트)
                                                                     │
                                              [게임 시작] ─ BeginJourney() = LoadGameplayScene()
```

`StartNewJourney()`를 **`OpenRoom()`과 `BeginJourney()`로 쪼갠다.** 기존 호출부는
`MainMenuRoot.OnNewJourney()` 하나뿐이라 이관 비용이 작다.

**쪼갠 뒤에도 "게임 시작 = 세션을 거친다"는 원칙은 유지된다** — 1인 플레이도 혼자 있는 대기실을
거쳐 출발한다. 예외 경로를 만들지 않는다(개발 원칙 2).

### 3.3 게스트가 준비 화면에 도착하는 경로

게스트는 **씬을 이동하지 않는다.** `Main.unity`에 머문 채 세션에 붙고, 화면만 준비 화면으로 바뀐다.
호스트가 `LoadGameplayScene()`을 부르면 그때 NGO 씬 동기화로 함께 끌려간다.

| 진입 | 트리거 | 감지 방법 |
|---|---|---|
| 직결 모드 | `Panel_Join`에서 주소 접속 성공 | `INetworkSessionService.IsSessionActive`가 참이 되는 시점 |
| Steam 모드 | 오버레이 초대 수락 → `JoinLobby` → 릴레이 접속 | 같음 |
| Steam 부팅 인자 | `+connect_lobby`로 실행 | 같음 — Boot → Main 도착 후 세션이 이미 살아 있으면 **곧바로 준비 화면** |

마지막 줄이 중요하다. **초대로 게임을 켠 사람은 메뉴 배너를 볼 이유가 없다.**

## 4. 화면 구조 설계

### 4.1 하이어라키 (추가분만)

```
Main.unity
├─ (기존) Canvas_Background · 평면 열차 · Canvas_Scene(Banner · NoticeBoard) · Canvas_UI
└─ Canvas_Ready              Screen Space - Overlay, sortingOrder 25   ← 배너보다 앞
   ├─ Panel_Roster                                    ReadyRosterView
   │   ├─ Image_RosterFrame     왼쪽 패널 전체 (프레임 + 빈 슬롯 4장이 그려진 원본)
   │   ├─ Text_Title            "게임 준비"  (TMP — 그림의 각인 위에 덮는다, §5.1-4)
   │   └─ Slots
   │       ├─ Slot_0 … Slot_3                         ReadySlotView
   │       │   ├─ Image_SlotFilled   금색 슬롯 (참가자 있을 때만 alpha 1)
   │       │   ├─ Image_Icon         왕관(호스트) / 사람+(빈자리)
   │       │   ├─ Text_Role          "HOST"
   │       │   ├─ Text_Name          "NightRail_01" / "플레이어 대기 중"
   │       │   └─ Status
   │       │       ├─ Image_Dot      접속 표시 (UiPalette 경유)
   │       │       └─ Text_Status    "접속 중"
   ├─ Panel_Controls                                  ReadyControlsView
   │   ├─ Image_ControlsFrame   오른쪽 패널 전체 (흰 배경 제거본)
   │   ├─ Group_Difficulty                            DifficultyStepper
   │   │   ├─ Text_DifficultyLabel  "난이도"
   │   │   ├─ Button_Prev  ◀ / Button_Next  ▶
   │   │   └─ Text_DifficultyValue  "보통"
   │   ├─ Button_Start          게임 시작 (호스트 전용)
   │   ├─ Button_Invite         초대 하기
   │   └─ Button_Leave          나가기
   └─ Text_RoomStatus           하단 상태줄 — "호스트를 기다리는 중" 등 (§6.3)
```

`Canvas_Ready`는 **하나의 `MenuPanel`로 감싼다** — 취소(Esc·B) 처리와 포커스 회수를
이미 검증된 경로(`MenuPanel.InstallCancelRelays`)로 그대로 얻는다. 다만 취소의 뜻이
"닫기"가 아니라 **"나가기 확인"** 이므로, `Cancelled` 수신부에서 세션 종료로 잇는다(§6.5).

### 4.2 좌표 규약 — `ReadyPanelLayout`

`MenuPlateLayout`과 **같은 방식**을 쓴다. 새 클래스를 만드는 이유는 출처 이미지가 다르기 때문이다
(1024×1536 · 1048×1501 vs 940×1672).

```csharp
internal static class ReadyPanelLayout
{
    public const int RosterSourceWidth = 1024;
    public const int RosterSourceHeight = 1536;
    // §0.2 실측 — 슬롯 좌·우변, 슬롯별 상·하변
    // ToAnchorMin/Max(slot) → 프레임 RectTransform 기준 앵커
    // 오른쪽 패널도 같은 방식 (Controls*)
}
```

- **1920×1080 하드코딩 금지** — 전부 정규화 후 앵커 환산
- 패널 크기는 **높이 기준**으로 정한다 — 폭 기준이면 21:9에서 패널이 화면을 삼킨다
  (`MenuPlateLayout.BannerSize`가 이미 이 규칙을 쓴다)
- 두 패널은 **서로 독립 배치**다. 로스터는 화면 좌변, 조작 패널은 우변에 붙는다

## 5. 아트 반입 파이프라인

기존 규약을 따른다 — `zz_src_` 원본 보관, `T_<명>_<용도>` 명명, Sprite(2D and UI) · sRGB ·
Mip **off** · BC7 · guid 수기 발급.

### 5.1 왼쪽 패널 (`T_Ready_Roster*`)

1. **하단 여백 크롭** — 알파 바운즈 하단이 1331인데 캔버스는 1536이다. 205px가 빈 글로우다.
   크롭 후 4의 배수로 맞춰야 BC7이 걸린다(배경 업스케일 때와 같은 함정).
2. **반투명 글로우 검수** — 알파 < 16 기준 투명이 25.2%인데, 시안에서는 패널 바깥이
   갈색 비네트로 보인다. **가장자리 글로우가 반투명으로 남아 있을 가능성**이 있고,
   그대로 쓰면 밤하늘 위에서 사각형 얼룩으로 뜬다. 확대 검수 후 필요하면 알파 임계 재적용.
3. **슬롯 2종 크롭** — §0.2 좌표를 알파 바운즈로 정밀화한 뒤
   - `T_Ready_Slot_Empty.png` ← 슬롯 2 (어두운 빈 판)
   - `T_Ready_Slot_Filled.png` ← 슬롯 1 (금색 테두리)
   높이 차가 178 vs 176(1%)이라 **1장씩 재사용으로 충분하다** — 기존 명판이 7% 차이에서도
   재사용으로 결론 났다(로비 계획 §13 ⑱).
4. **프레임은 명판을 지우지 않는다** — 원본 전체를 프레임으로 쓰고 그 위 같은 자리에 슬롯을 겹친다.
   잘라낸 자리가 드러나지 않는 검증된 방식이다(로비 계획 §4.2-3).
5. **구운 문구 제거** — "게임 준비" · "HOST" · "NightRail_01" · "접속 중" · "플레이어 대기 중"이
   전부 그림에 구워져 있다. **한국어 구운 문구 0건 원칙**에 따라 전부 TMP로 덮는다.
   - 타이틀 "게임 준비"는 금속 각인이라 **지우지 않고 TMP를 정확히 겹친다**
     (기존 배너 타이틀과 같은 처리 — 로컬라이징 시 TMP만 바꾸면 각인이 비쳐 보이는 문제는
     §12 미결 5번)
6. **아이콘 분리** — 왕관 · 사람+ 를 각각 `T_Ready_Icon_Crown.png` · `T_Ready_Icon_Empty.png`로.
   슬롯 상태에 따라 교체된다.
7. **접속 점(녹색)은 스프라이트로 굽지 않는다** — 상태색이므로 흰 원 스프라이트 + `UiPalette` 틴트.

### 5.2 오른쪽 패널 (`T_Ready_Controls*`)

1. **흰 배경 제거가 이 계획의 최대 아트 작업이다.** 배경이 (253,253,253) 단색이라 키잉 자체는
   쉽지만 두 곳이 위험하다.
   - **금색 "게임 시작" 버튼의 밝은 하이라이트** — 흰색에 가까운 화소가 함께 날아간다
   - **패널 모서리의 밝은 베벨**
   처방: 순수 휘도 임계가 아니라 **채도 동반 판정**(휘도 > 240 **그리고** 채도 < 0.06)을 쓰고,
   1~2px 페더링. 크롭 기준은 §0.3의 본체 바운즈 (78,58)-(983,1448).
2. **버튼 4종 크롭** — 스테퍼 · 게임 시작 · 초대 하기 · 나가기. 프레임은 왼쪽과 같은 방식으로
   원본 전체를 유지하고 그 위에 겹친다.
3. **Hover 소스가 없다.** 원본에는 각 버튼이 **한 상태씩**만 있다. 처방 두 가지 중 택일:
   - ①안 **밝기 변조** — Normal 스프라이트에 `Color` 틴트(1.0 → 1.18)와 1.02 스케일.
     추가 자산 0장. 기존 명판이 Normal/Hover 두 장을 가졌던 것과 달라지지만, 여기서는
     **버튼마다 색이 이미 다르므로**(금색·황동·적색) 상태 구분이 색 대비가 아니라 밝기로 읽힌다
   - ②안 슬롯별 Hover 재생성 — 자산 4장 추가, 톤 일관성 위험
   **①안 권장** — 색각 대응은 §9.2의 포커스 테두리로 따로 보장한다.
4. **"게임 시작"이 시각적으로 최상위다** — 크기·금색·발광이 전부 이 버튼에 몰려 있다.
   게스트에게는 이 버튼이 비활성이므로(§6.3) **비활성 스타일이 반드시 필요하다** —
   채도를 뺀 회색 변조 + 라벨 교체.

### 5.3 배경

**새로 반입할 것이 없다.** `T_Menu_Background` · 평면 열차 · 공고대를 그대로 쓴다.
준비 화면에서는 **공고대(`NoticeBoard`)만 숨긴다** — 시안에 없고, 오른쪽 조작 패널과 자리가 겹친다.

### 5.4 이전에 데인 함정 — 오른쪽 패널이 정확히 같은 케이스다

`T_Train_Menu_Flat.png`(평면 열차)가 **알파 없는 체커 배경**이라 키잉이 필요했고,
그 결과 흰 테두리가 남아 **사용자 지적으로 재작업**했다(커밋 `f285466`).
`게임_준비_오른쪽_패널.png`는 **알파 없는 24bit · 흰 배경** — 같은 함정이 그대로 기다린다.
오히려 더 위험하다. 체커는 배경이 회색이었지만 **이번엔 흰색이고, 금색 버튼의 하이라이트가
흰색에 가깝기 때문**이다.

**그때 확립한 절차를 그대로 쓴다.**

1. **알파는 어두움과 채도 중 큰 쪽**으로 잡는다 (단일 휘도 임계 금지)
2. **전경색을 역혼합으로 되돌린다** — `(관측색 − 국소배경색 × (1−a)) / a`.
   국소 배경색은 바깥 화소의 상자 평균으로 잡는다
3. **소프트 알파는 실루엣 경계 2px 띠에서만.** 실루엣 전체에 걸면 밝은 안쪽 화소가
   반투명이 되어 **안쪽에 배경색 점이 뜬다** — 평면 열차에서 실제로 났다
4. **"뚫린 틈"은 큰 덩어리(120px 이상)만 인정한다.** 작은 밝은 점까지 틈으로 보면
   금색 버튼의 볼트 하이라이트에 구멍이 뚫린다

**판정 수치도 그때 기준을 쓴다** — 경계 화소의 밝기 평균과 "0.55 초과 화소 수"를 안쪽 평균과
대조한다. 평면 열차는 재작업으로 0.388 → **0.150**, 3,573 → **377**이 됐다.

**NPOT 스케일을 반드시 끈다.** 임포터 기본값 `nPOTScale: 1`이 1268×816을 **1024×1024로 눌러**
세로가 늘어난 적이 있다. 이번 두 패널도 1024×1536 · 1048×1501로 **둘 다 NPOT**다.

> **왼쪽 패널은 이 절차가 필요 없다** — 알파가 이미 있다(§0.2). 로비 7차의 공고대 원화 두 판
> 중 알파가 있는 v2를 채택했던 것과 같은 판단이다. 다만 **어두운 후광**(검정 매트에서 뽑은 그림의
> 잔상)은 그때도 의심했던 지점이라, 밝은 색 위에 올려 경계 1px 밝기비를 확인한다.

### 6.2 권한표

| 조작 | 호스트 | 게스트 |
|---|---|---|
| 난이도 변경 (쉬움·보통·어려움) | ○ | **×** — 값은 보이되 화살표 비활성 |
| 게임 시작 | ○ | **×** — 비활성 + 라벨 "호스트를 기다리는 중" |
| 초대 하기 — Steam 모드 = 오버레이 | ○ | ○ (로비 멤버도 초대 가능) |
| 초대 하기 — 직결 모드 = **주소 복사** | ○ | **×** — 게스트는 호스트 주소의 출처가 아니다 |
| 나가기 | ○ — 방을 닫는다 | ○ — 나만 나간다 |

**직결 모드의 "초대 하기"는 접속 주소를 클립보드에 복사한다**(§12 미결 8번 결정).
`GUIUtility.systemCopyBuffer`에 `IP:포트`를 넣고 토스트로 알린다. 호스트의 IP는
`UnityTransport`의 바인드 주소가 아니라 **실제 접속 가능한 주소**여야 하므로, 같은 PC 테스트에서는
`127.0.0.1:7777`(= `MenuSessionActions.DefaultAddress`·`DefaultPort`)을 그대로 쓰고,
LAN 주소 판별은 4차에서 확인한다.

### 6.3 게스트 뷰가 시안과 달라지는 지점

시안은 **호스트 화면**이다. 게스트 화면에는 시안에 없는 상태가 둘 생긴다.

1. **"게임 시작"이 눌리지 않는다** — 버튼을 숨기지 않고 **비활성 + 라벨 교체**로 남긴다.
   숨기면 패널 레이아웃이 무너지고(그림에 자리가 파여 있다), 무엇을 기다리는지도 알 수 없다.
2. **난이도 화살표가 사라진다** — 화살표만 alpha 0으로 내리고 값은 남긴다.

### 6.4 `Panel_Host`의 운명

기존 `Panel_Host`(새 여정 / 초대 / 개발용 씬 선택)는 **역할을 잃는다.**

| 기존 항목 | 이관처 |
|---|---|
| 새 여정 | **방 만들기 클릭 = `OpenRoom()`** — 중간 패널이 사라진다 |
| 초대 | 준비 화면의 "초대 하기" |
| (개발) 인게임 씬 선택 | **준비 화면 하단에 개발 전용 줄로 이동** — `#if UNITY_EDITOR \|\| DEVELOPMENT_BUILD` |

즉 **명판 "방 만들기"를 누르면 곧바로 준비 화면이 뜬다.** 패널을 하나 줄이는 것이 이 개편의
부수 이득이다 — 시안의 "게임 시작"이 이제 진짜 출발 버튼이 된다.

**실패 처리**: `OpenRoom()`이 실패하면(포트 점유·Steam 초기화 실패) 준비 화면을 열지 않고
배너에 머문 채 사유를 표시한다. 반쯤 열린 대기실이 남지 않게 한다.

### 6.5 나가기 · 취소

| 상황 | 동작 |
|---|---|
| 호스트가 나가기 | `Shutdown()` → `LeaveLobby()` → 배너 복귀. **게스트는 연결이 끊긴다** |
| 게스트가 나가기 | `Shutdown()` → 배너 복귀 |
| 게스트 화면에서 호스트가 먼저 나감 | 연결 끊김 감지 → 배너 복귀 + "방이 닫혔습니다" |
| Esc / 게임패드 B | **나가기와 동일** (확인 대화상자는 §12 미결 3번) |

## 7. 네트워크 동기화 설계

### 7.1 무엇을 동기화해야 하는가

| 데이터 | 방향 | 갱신 시점 |
|---|---|---|
| 멤버 목록 (표시 이름 · 호스트 여부 · 접속 상태) | 호스트 → 전원 | 접속·이탈 |
| 선택된 난이도 | 호스트 → 전원 | 호스트가 스테퍼 조작 |

### 7.2 어떻게 — 결론: 스폰되는 `LobbyRoomState`

| 안 | 판정 |
|---|---|
| **A. `NetworkList`를 가진 `NetworkObject` 스폰** | **채택** — NGO 표준 경로. 늦게 들어온 클라이언트가 **스폰 시 전체 상태를 자동으로 받는다** |
| B. `NamedMessage` 브로드캐스트 | 폐기 — 늦게 접속한 쪽에 대한 초기 동기화를 직접 짜야 하고, 그게 정확히 버그가 나는 자리다 |
| C. Steam 로비 데이터 | 폐기 — **직결 모드에 대응이 없다.** 개발 흐름이 직결이라 곧바로 막힌다 |

**구현 주의 (기존에 데인 지점)**

- `LobbyRoomState` 프리팹은 **`NetworkPrefabs` 목록에 중복 등록하지 않는다**
- 프리팹 편집 후 **`GlobalObjectIdHash` 정규화**를 반드시 확인한다 —
  오염되면 클라이언트가 `ClosedByRemote`로 튕긴다
- 풀링 대상이 아니다 — `PoolManager`를 태우지 않고 호스트가 `StartHost()` 직후 1개만 스폰
- `DontDestroyOnLoad`에 두어 인게임 씬 전환에서 살아남게 할지는 §12 미결 6번
  (넘어간 뒤 난이도 값을 누가 읽는가에 달렸다)

### 7.3 표시 이름은 어디서 오는가 — 결정: 임시 닉네임 (2026-08-21)

**이 계획에서는 양 모드 모두 호스트가 슬롯 번호로 이름을 만든다** — `"플레이어 1"` … `"플레이어 4"`.
Steam 퍼소나 이름 연결은 **차후 작업**이다(사용자 결정).

**이 결정이 설계를 하나 지운다.** 이름을 호스트가 만들면 **클라이언트가 이름을 보낼 필요가 없다** —
즉 **승인 페이로드(`ConnectionData`)를 건드리지 않는다.** 초안은 여기에 이름을 덧붙일 생각이었고,
그것이 재접속 식별(M6 1차)을 조용히 깨뜨릴 수 있는 자리였다(구 리스크 4번 — 소멸).

| 모드 | 이번 구현 | 차후 |
|---|---|---|
| 직결 | `"플레이어 " + (슬롯 + 1)` | 그대로 — 개발 전용 모드다 |
| Steam | **같음** | Steam 퍼소나 이름 — `SteamIdentityProvider`에 이름 조회 추가 |

**교체 지점을 한 곳으로 묶는다.** 이름을 만드는 코드는 `NgoLobbyRoomService`의 슬롯 배정
**한 군데**에만 둔다. 차후 Steam 이름을 붙일 때는 "클라이언트가 보낸 이름이 있으면 그것을 쓰고,
없으면 슬롯 번호"로 **한 줄이 늘어날 뿐**이며, `ILobbyRoomService` 계약도 `ReadyRosterView`도
바뀌지 않는다. 그때는 승인 페이로드 확장이 다시 논점이 되므로, **구 리스크 4번의 처방을
이 문서에 남겨 둔다** — 형식을 바꾸지 말고 덧붙일 것, `MaxTokenPayloadBytes = 256` 상한을
재계산할 것, 파싱 실패 시 이름만 비우고 토큰은 살릴 것.

`IPlayerIdentityProvider`는 **재접속 식별 토큰**만 준다 — 사람이 읽을 이름이 아니다.
표시 이름은 별도 개념이므로 계약을 섞지 않는다(ISP).

**시안과 달라지는 지점**: 시안의 호스트 이름은 `NightRail_01`이지만 구현은 `플레이어 1`이 된다.
검증에서 "시안과 문구가 다르다"로 잡히지 않도록 §9.2에 명시했다.

| **4차** | **난이도 · 초대 · 게스트 뷰** — 3단계 스테퍼 동기화, 권한 분리, 오버레이 초대/주소 복사, 난이도 인게임 전달 | 시안 기능 완비 | 1일 |
| **5차** | **연출 · 대응** — 호버/포커스, 슬롯 입·퇴장 연출, 키보드·게임패드 내비, 종횡비, 검증 문서 | 완성 | 1일 |

**합계 5일** — 표시 이름 결정(§7.3)으로 승인 페이로드 작업이 통째로 빠져 3차가 0.5일 줄었다.

### 8.1 이 순서인 이유

- **1차가 아트인 이유**: 패널 그림의 실제 알파 상태(왼쪽 반투명 글로우 · 오른쪽 흰 배경)가
  §5의 최대 불확실성이다. 여기서 막히면 레이아웃 상수부터 흔들린다.
- **2차가 3차보다 앞인 이유**: 혼자서 완주되지 않는 화면에 동기화를 얹으면,
  버그가 났을 때 그게 화면 상태 기계 탓인지 네트워크 탓인지 가릴 수 없다.
- **4차의 난이도가 3차 동기화 뒤인 이유**: 난이도는 로스터와 **같은 동기화 채널**을 탄다.
  채널이 서고 나서 얹으면 추가 배선이 거의 없다.

## 9. 테스트 · 검증

### 9.1 EditMode — 순수 계산만 (현행 방침 유지)

| 대상 | 고정할 것 |
|---|---|
| `ReadyPanelLayout` | 슬롯 4개가 **서로 겹치지 않는다**, 패널 밖으로 나가지 않는다, 앵커가 0~1 범위 |
| `DifficultyStepper` | **3단계 순환**(어려움 → 쉬움, 쉬움 ← 어려움), 기본값이 **가운데 "보통"**, 인덱스 범위 밖 입력 방어, 단계 수가 1일 때 예외 없음 |
| `RosterOrdering` | 호스트가 **항상 슬롯 0**, 빈자리가 뒤로 몰린다, 정원 초과 입력에서 예외 없음, 이탈 후 재정렬, **이름이 `"플레이어 " + (슬롯+1)`로 매겨진다** |

기존 EditMode **707항목은 전부 유지된다** — 이 계획은 인게임을 건드리지 않는다.

### 9.2 플레이 검증 (짝 문서로 분리, 구현 후 작성)

- ☐ 완성 화면이 `게임 준비.png`와 나란히 놓고 구분이 안 될 만큼 일치한다
      — **단, 이름은 다르다.** 시안은 `NightRail_01`이지만 구현은 `플레이어 1`이다(§7.3 결정).
      난이도 값도 시안의 "보통"이 기본값이므로 일치한다
- ☐ 왼쪽 패널 가장자리에 **회색·갈색 얼룩이 없다** (§5.1-2 글로우 검수)
- ☐ 오른쪽 패널 금색 버튼의 하이라이트가 **키잉으로 파먹히지 않았다** (§5.2-1)
- ☐ 오른쪽 패널 경계에 **흰 자국이 남지 않았다** — 어두운 밤하늘 위에서 확대 검수 (§5.4)
- ☐ 두 패널이 임포트에서 **세로로 눌리지 않았다** — NPOT 스케일 (§10 리스크 2-b)
- ☐ 방 만들기 → 준비 화면 → 게임 시작이 **혼자서** 완주된다
- ☐ 같은 PC 두 벌로 **둘이 모이고**, 게스트 화면에도 두 명이 보인다
- ☐ 게스트가 나가면 호스트 화면의 슬롯이 **비워진다**
- ☐ 호스트가 나가면 게스트가 **메뉴로 복귀**하고 사유가 표시된다
- ☐ 게스트 화면에서 게임 시작·난이도 화살표가 **눌리지 않는다**
- ☐ 호스트가 난이도를 바꾸면 게스트 화면의 값도 바뀐다
- ☐ 난이도 순환이 **쉬움 ↔ 보통 ↔ 어려움 3단계**로 돌고, 처음 열었을 때 **"보통"** 이다
- ☐ 고른 난이도가 **인게임 씬까지 실제로 도달한다** (로그·인스펙터로 확인 — 배율 적용은 비범위)
- ☐ 직결 모드에서 "초대 하기"가 접속 주소를 클립보드에 복사하고 토스트가 뜬다
- ☐ 마우스 없이 키보드/게임패드만으로 모든 버튼에 도달·실행된다
- ☐ 어느 버튼이 선택됐는지 **색 없이도** 구분된다 (색각 대응)
- ☐ 1080p / 1440p / 16:10 / 21:9에서 두 패널이 잘리지 않고 겹치지 않는다
- ☐ Steam 초대 수락으로 게임을 켰을 때 **곧바로 준비 화면**이 뜬다 (§3.3)

### ② 표시 이름 결정이 지운 설계 (2026-08-21)

초안은 접속 시 **클라이언트가 자기 이름을 승인 페이로드(`ConnectionData`)에 실어 보내는** 그림이었다.
이미 재접속 식별 토큰이 실려 가고 있으니 왕복이 늘지 않는다는 이유였고, 그 대가로
**리스크 4번**(형식을 잘못 바꾸면 M6 1차의 재접속 식별이 조용히 깨진다)을 안고 있었다.

이름을 **호스트가 슬롯 번호로 만들기로** 하면서 이 그림 전체가 필요 없어졌다.

- 클라이언트 → 호스트 방향의 **추가 데이터가 0**이 된다 → 승인 페이로드를 손대지 않는다
- 리스크 4번 **소멸** (차후 Steam 이름 작업에서 되살아나므로 처방은 §7.3에 보존)
- 3차 추정이 1.5일 → **1일**, 합계 5.5일 → **5일**

**교훈이 있다면**: "임시로 간다"는 결정이 단순히 미루기가 아니라 **구조 하나를 통째로 지웠다.**
차후 Steam 이름을 붙일 때 되살아나는 것은 페이로드 확장 한 곳뿐이고, 계약과 뷰는 그대로다.

### ⑤ 3차 — 로비 상태 동기화 (2026-08-22 완료)

#### ㉠ 나르는 것이 **클라이언트 id 하나로 줄었다**

계획 §7.1은 멤버마다 이름·호스트 여부·접속 상태를 함께 나르는 그림이었다. 셋 다 **파생값**이었다.

| 계획이 나르려던 것 | 실제 | 어디서 나오는가 |
|---|---|---|
| 표시 이름 | 안 나른다 | 칸 번호 → `RosterOrdering.DisplayName(slot)` |
| 호스트 여부 | 안 나른다 | "첫 칸이 호스트"라는 배정 규칙 |
| 접속 상태 | 안 나른다 | **목록에 있음 = 접속 중** |

그래서 `NetworkList<ulong>` 하나로 끝났고 `INetworkSerializable` 구조체가 필요 없었다.
§7.3이 요구한 "이름을 만드는 곳은 한 군데"도 그대로다 — 고칠 곳은 `DisplayName` 하나뿐이다.

#### ㉡ `RosterOrdering`은 `Game.Systems`에 뒀다

계획 §6.1 표는 `Game.UI`로 적었지만, **이름을 짓는 일이 호스트의 일**이라(§7.3) 거기 두면
`Game.Systems`가 `Game.UI`를 참조해야 한다 — 어셈블리 의존은 단방향이라 불가능하다.
UI는 서비스가 준 이름을 그대로 받는다.

#### ㉢ 게스트가 도착하는 문이 하나로 모였다

직결 접속 · Steam 초대 수락 · `+connect_lobby` 부팅이 전부 **"접속이 완료됐다"**는 같은 신호로
끝난다. 그래서 `MainMenuRoot.CheckRoomArrival()` 한 곳이 셋을 다 받는다 — 경로별 분기가 없다.

그 신호를 위해 `INetworkSessionService.IsConnectedClient`를 새로 뒀다. `IsSessionActive`는
**주소를 누른 순간** 참이 되므로 "방에 들어갔다"와 구분되지 않는다 — 그걸로 대기실을 열면
접속이 실패해도 대기실이 뜬다.

#### ㉣ 미결 6번이 **저절로 풀렸다**

`LobbyRoomState`를 인게임까지 살릴지가 3차의 숙제였는데, NGO가 씬 동기화에서 스폰 오브젝트를
**새 씬으로 그대로 옮겼다**(실측). 4차의 난이도는 여기 실으면 되고, 정적 라우트와 달리
클라이언트도 같은 값을 본다.

#### ㉤ 2인 접속은 **서버 콜백으로 갈랐다**

에디터 한 벌로는 클라이언트를 붙일 수 없어, `LobbyRoomState`의 접속·이탈 콜백을 직접 태워
로스터 갱신 경로를 확인했다. 셋이 모인 화면이 시안대로 떴고, **가운데 사람이 나가자 뒤가 앞으로
당겨졌다**(§10 리스크 6의 "유령 칸" 방지). 실제 두 벌 접속은 §9.2의 플레이 검증 항목으로 남는다.
