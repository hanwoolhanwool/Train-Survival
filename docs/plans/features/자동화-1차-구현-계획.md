> **왜 이것이 먼저인가**: 작동하지 않는 자동화는 없는 것보다 나쁘다. 있다고 착각하게 만들기 때문이다.

### 1.7 두 번째 스택 — 죽는 자리가 하나가 아니다

게이트 복구 뒤 크래시 감지(§4.4)가 처음 잡은 스택은 **§1.2와 다르다.**

```
#1  MemoryManager::GetAllocator(MemLabelId const&)
#2  MemoryManager::TryDeallocateWithLabel(void*, MemLabelId, char const*, int)
#3  free_alloc_internal(void*, MemLabelId const&, char const*, int)
#4  MonoMenuItem::~MonoMenuItem()          ← 메뉴 항목을 해제하는 중
```

§1.2는 메뉴 항목을 **찾다가**(`DoFindItem`) 죽었고, 이번은 메뉴 항목을 **해제하다가** 죽는다.
둘을 합치면 증상은 하나로 모인다 — **스크립트 정의 메뉴 항목(`MonoMenuItem`)의 수명 관리가 깨져 있다.**
조회와 해제 양쪽에서 터지므로, 우리 C# 코드 한 곳을 고쳐서 막을 수 있는 종류가 아니다.
`MonoMenuItem`은 `[MenuItem]`으로 만든 항목의 네이티브 표현이므로 **메뉴 항목의 수 또는 구성**이
여전히 유력한 방아쇠다(§1.4). — **이 추정이 §1.8에서 맞은 것으로 확정된다.**

**작업 트리는 건드리지 않고** `git commit-tree`로 커밋 객체만 만들어 밀었다(부록 참조).

| # | 무엇을 태웠나 | 변경량 | 결과 |

| 2 | `065d253` — 그 다음 커밋 | **파일 1개 추가** | 세그폴트 |

**2번이 범인을 한 파일로 좁혔다.** `065d253`은 `RailTrackMeshBuilder.cs`(294줄) **하나만** 추가하고
다른 것은 아무것도 건드리지 않는다. 단일 변수 실험이라 해석의 여지가 없다.

**3번이 가설 하나를 더 죽였다.** §1.4는 "새 하위 메뉴(`Game/Art`)가 생긴 것"을 의심했는데,

**메뉴 항목이 하나 늘어난 것 자체**다.

**4번이 확정했다.** 파일 294줄을 그대로 두고 어트리뷰트 한 줄만 주석 처리하면 통과한다.

```csharp
[MenuItem("Game/Art/Rebuild Rail Track Mesh")]   ← 이 한 줄이 CI 를 아흐레 멈춰 세웠다
public static void Rebuild()
```

**처방** — Windows 에디터에서는 같은 코드가 멀쩡하므로 플랫폼으로 가른다(`3f70a82`).

```csharp

#endif

```

메뉴는 로컬에서 그대로 쓰고, 메서드가 남으므로 필요하면 `-executeMethod`로 부른다.
이어서 `ci.yml`의 `continue-on-error`를 걷어내 **PlayMode를 다시 게이트로 세웠다**(`0e9fb63`).

> **이것은 회피이지 해결이 아니다.** 메뉴 항목 하나가 늘었다고 리눅스 batchmode에서
> `MonoMenuItem`의 수명 관리가 깨지는 것은 정상이 아니며, 원인은 Unity 안에 있다.

### 1.9 같은 날 재발 — 개별 대응을 그만두고 전부 감쌌다

§1.8의 처방을 넣은 지 몇 시간 만에 **같은 크래시가 다시 났다**(실행 `33815287667`).
`6f29cf1 chore(art): 한글 폰트 아틀라스를 비우고 훅으로 고정한다`가 `Game/QA/Font/` 메뉴
**2개**를 더했기 때문이다. 하나를 뺀 자리에 둘이 들어왔다.

항목 수를 세어 보면 임계가 드러난다.

| 시점 | 리눅스 기준 `[MenuItem]` | CI |
|---|---:|:---:|
| 08-30 마지막 성공 | 6 | 통과 |
| `065d253`(선로 메뉴 추가) | 7 | **죽음** |
| §1.8 이등분 실험 4번(그 메뉴만 주석) | 6 | 통과 |
| `3f70a82`(가드) + `6f29cf1`(폰트 메뉴 2개) | 8 | **죽음** |
| `5314665`(전부 감쌈) | **0** | 통과 |

**임계는 7로 보인다.** 개별 대응은 두 가지 이유로 실패한다 — 메뉴를 추가할 때마다 CI가 한 번은
깨져야 알 수 있고(사후 대응), 6개는 임계 바로 아래라 여유가 없다.

그래서 프로젝트의 `[MenuItem]` **9개 전부**를 `#if !UNITY_EDITOR_LINUX`로 감쌌다(`5314665`).
리눅스 CI에서 프로젝트 메뉴가 0개가 되어 **임계와 무관해진다.** 이것이 규칙이다 —
[`SETUP.md` §4](../../../Assets/SETUP.md)에 "에디터 메뉴에는 항상 리눅스 가드를 씌운다"로 적었다.

> **판단 착오였다.** §1.8 직후 문서에 적은 대응은 "메뉴를 추가한 뒤 경고가 뜨면 가드를 씌운다"였다.
> 그것은 **CI가 한 번 깨지는 것을 전제한 사후 대응**이고, 임계가 7인데 현재가 6이라는 것을
> 그때 이미 셀 수 있었다. 처음부터 전부 감쌌어야 했다.

### 1.5 실패의 2차 피해 — 빌드가 4일째 돌지 않았다

```
Test  (EditMode + PlayMode)   failure   11:35:11 → 11:42:24   (7분 13초)
Build (StandaloneWindows64)   skipped   11:42:25 → 11:42:25   (0초)
```

`build` 잡에 `needs: test`가 걸려 있어 **테스트가 죽으면 빌드는 시도조차 하지 않는다.**
그 결과 2026-08-30 이후 "빌드가 되는가"라는 질문의 답을 **아무도 갖고 있지 않다.**

마지막 성공 실행의 잡별 소요는 이렇다.

| 잡 | 소요 | 비고 |
|---|---:|---|
| Test (EditMode + PlayMode) | **7분 25초** | 23:41:14 → 23:48:39 |
| Build (StandaloneWindows64) | **10분 10초** | 23:48:42 → 23:58:52 |
| **합계 (순차)** | **17분 38초** | 두 잡이 줄 서서 돈다 |

두 잡은 Library 캐시 키가 이미 분리돼 있어(`Library-test-` / `Library-build-`) **서로를 기다릴
기술적 이유가 없다.** 병렬로 돌리면 벽시계가 `max(7:25, 10:10)` ≈ **10분**이 된다.

|---|---|---|
| A. `Validate()` 통째 제거 | 체크 표시를 포기한다 | 메뉴만 보고는 **현재 트랜스포트 모드를 알 수 없다**. 토글이 무상태처럼 보인다 |
| **★ B. 배치모드 가드** | `Application.isBatchMode`면 `SetChecked`를 건너뛴다 | 근본 원인(재구축 중 조회)은 남는다 — 다른 코드가 같은 관용구를 쓰면 재발 |
| C. `EditorApplication.delayCall`로 미룸 | 재구축이 끝난 뒤 체크한다 | 메뉴를 열 때마다 큐에 쌓인다. 체크 표시가 한 프레임 늦는다 |
| D. 메뉴를 창으로 이전 | `MenuItem` validate 자체를 없앤다 | 변경 범위 최대. 토글 하나 때문에 창을 여는 것은 후퇴다 |

**권장 B.** `Menu.SetChecked`는 **메뉴 UI에 체크 표시를 그리는 API**인데 배치모드에는 그릴 메뉴가
없다 — 배치모드에서 부르는 것 자체가 무의미하다. 즉 B는 크래시 회피이기 이전에 **원래 하지 않아도
되는 일을 하지 않게 만드는 수정**이고, 로컬 에디터의 기능은 그대로 남는다.

B로 고쳐도 CI가 계속 죽으면 §1.4의 가설이 틀린 것이고, 그때 A로 간다(§5 1단계가 이 분기를 판정한다).

### ② `build` 잡의 의존 구조

| 안 | 내용 | 대가 |
|---|---|---|
| A. 현행 유지 (`needs: test`) | 테스트가 통과해야 굽는다 | §1.5 — 테스트가 죽은 4일 동안 **빌드 가능 여부를 몰랐다** |
| **★ B. 의존 제거 (병렬)** | 두 잡이 동시에 돈다 | 테스트가 깨진 커밋의 아티팩트가 생긴다. 다만 워크플로 자체는 여전히 **실패로 표시**되고, 아티팩트는 수동 다운로드다 |
| C. `if: always()` | 의존은 두되 실패해도 실행 | 순차라 시간 이득이 없다 (17분 38초 유지) |

**권장 B.** 얻는 것이 둘이다 — 테스트와 무관하게 **빌드 회귀를 즉시 안다**, 그리고 벽시계가
**17분 38초 → 약 10분**으로 준다. "깨진 코드를 굽지 않는다"는 원래 의도는 **빨간 체크 표시**가
이미 수행한다.

### ③ PlayMode 테스트를 CI에 유지할 것인가

| 안 | 대가 |
|---|---|
| **★ A. 유지** | 크래시가 재발하면 또 CI가 통째로 멈춘다 |
| B. EditMode만 CI · PlayMode는 로컬 | PlayMode 3종(`NgoNetworkSessionService` · `PoolManager` · `PooledNetworkPrefabHandler`)이 **CI에서 영영 안 돈다**. 이 셋은 EditMode로 대체 불가다 |

**권장 A 유지.** 이번 크래시의 원인은 **PlayMode 테스트가 아니라 에디터 메뉴**다(§1.2 — 스택에
테스트 코드가 없다). 테스트를 빼도 같은 크래시가 PlayMode를 쓰는 다른 곳에서 난다. 원인을 두고
증상을 없애는 선택이다.

### ④ 크래시를 어떻게 보고할 것인가

현재 요약 스크립트는 이미 절반을 해냈다 — 결과 XML에 실패가 없자 이렇게 말했다.

```
실패로 기록된 테스트는 없다 — 잡 실패 원인은 테스트 바깥에 있다.
```

**이 한 줄이 조사 방향을 정했다.** 다만 그 다음(로그에서 `Caught fatal signal`을 찾아 스택을 읽는 일)은
사람이 손으로 했다.

| 안 | 대가 |
|---|---|
| A. 현행 유지 | 다음에도 사람이 14,000줄 로그를 뒤진다 |
| **★ B. 크래시 요약 추가** | `test-results/*.log`에서 `Caught fatal signal`을 찾으면 스택 상위 6줄을 `::error::`로 올린다. 스크립트 20줄 안쪽 |

**권장 B.** 이번에 손으로 한 일을 그대로 코드로 옮기는 것이라 설계 위험이 없다.

## 4. 설계

### 4.1 원인 확정 절차 — 가설을 코드로 검증한다

§1.4의 가설은 정황일 뿐이므로, **처방을 넣기 전에 처방으로 판정한다.**

```
1) B안(배치모드 가드)만 담은 커밋 하나를 푸시한다.
2) CI 1회를 본다. 이때 다른 변경을 섞지 않는다 — 섞으면 무엇이 고쳤는지 모른다.
3) 녹색  → 원인 확정. §5 2단계로 간다.
   빨강  → 가설 기각. 스택을 다시 읽고 A안(Validate 제거)으로 1회 더 본다.
           그것도 빨강이면 원인은 메뉴 바깥이다 — 이 계획을 중단하고 재조사한다.
```

**CI 왕복 1회에 7~10분**이 든다. 로컬(Windows)에서는 재현되지 않으므로(같은 코드로 로컬 플레이가
정상) **검증 수단이 CI뿐**이라는 점을 감수한다.

### 4.2 처방 (B안)

```csharp
[MenuItem(MenuPath, true)]
private static bool Validate()
{
    // 배치모드에는 그릴 메뉴가 없다. 그런데도 부르면 메뉴 목록을 재구축하는 중에
    // 그 목록을 조회하게 되고, CI(Linux · 6000.5.3f1)에서 PlayMode 진입 시
    // MenuController::GetChecked → DoFindItem 에서 세그폴트가 난다.
    if (!Application.isBatchMode)
    {
        Menu.SetChecked(MenuPath, EditorPrefs.GetBool(ActiveTransportMode.EditorPrefsKey, false));
    }

    return true;
}
```

주석에 **크래시 지점과 조건을 남긴다.** 이 가드는 지우면 다시 터지는 종류라, 이유가 코드 옆에
없으면 나중에 "불필요한 분기"로 정리될 위험이 있다.

### 4.3 잡 구조

```yaml
  build:
    name: Build (StandaloneWindows64)
    # needs: test 를 제거한다 — 두 잡은 Library 캐시가 이미 분리돼 있어 서로를 기다릴 이유가 없고,
    # 붙여 두면 테스트가 죽는 동안 "빌드는 되는가"를 아무도 모르게 된다(2026-08-31~09-02에 실제로 그랬다).
    # "깨진 코드를 굽지 않는다"는 의도는 워크플로 실패 표시가 이미 수행한다.
    runs-on: ubuntu-latest
```

한 줄 삭제 + 주석이다. 다른 스텝은 건드리지 않는다.

### 4.4 크래시 요약

기존 `Summarize failed tests` 스텝의 스크립트에 분기를 하나 더한다. **결과 XML에 실패가 없을 때**만
로그를 훑는다 — 테스트가 정상적으로 실패한 경우에는 지금 출력이 이미 충분하기 때문이다.

```
if (실패 테스트 0건) {
  test-results/*.log 에서 "Caught fatal signal" 을 찾는다
  찾으면: 그 줄 + 뒤이은 스택 6줄을 ::error:: 로 올린다
  못 찾으면: 지금 문구를 그대로 유지한다
}
```

이번 사고에서 사람이 한 일(`grep "Caught fatal signal"` → 스택 상위 프레임 읽기)을 그대로 옮긴 것이다.

### 6.1 되돌린 것 — 테스트 스텝을 쪼개면 두 번째가 멈춘다

격리할 때 `testMode: all`을 `editmode` / `playmode` **두 스텝**으로 나눴다. 잡을 늘리면 LFS
체크아웃이 1회(약 892 MB) 더 들어서 같은 잡 안에 두려던 것인데, **원인을 고치고 나니 이 구조가
드러났다.**

```
Run EditMode tests   success    3분 46초   1,406/1,406
Run PlayMode tests   cancelled  2시간 0분 31초   ← "Testing in playmode" 배너 뒤 무응답
```

같은 잡에서 `unity-test-runner`를 **두 번 부르면 두 번째 에디터가 뜨지 못한다.** 격리하던 동안에는
PlayMode가 세그폴트로 먼저 죽어 이 문제가 보이지 않았다 — **크래시가 행(hang)을 가리고 있었다.**

`testMode: all`로 되돌렸다. 그 구조는 08-30에도, §1.8의 이등분 실험 4번에서도 **PlayMode 11/11로
정상 완료**한다. 워크플로에 "스텝을 쪼개지 말 것"을 실행 번호와 함께 주석으로 남겼다.

**교훈** — 증상 하나를 격리하면 그 뒤에 가려져 있던 증상이 나온다. 격리는 임시 조치로만 쓰고,
원인을 고친 뒤에는 **격리 자체를 되돌려 원래 구조로 검증**해야 한다.

**과거 커밋을 CI에 태우는 법** — 작업 트리를 건드리지 않는다. 브랜치를 체크아웃하면 LFS 에셋
수 GB가 오가고 Library가 흔들리므로, `commit-tree`로 커밋 객체만 만들어 민다.

```sh
export GIT_INDEX_FILE=/tmp/probe-index      # 실제 인덱스를 쓰지 않는다
git read-tree <검증할 커밋>

git show <커밋>:<파일> > /tmp/f.cs          # 한 줄만 바꿔 단일 변수를 만든다
sed -i 's#^\( *\)\[MenuItem(#\1// \[MenuItem(#' /tmp/f.cs
blob=$(git hash-object -w /tmp/f.cs)
git update-index --add --cacheinfo 100644,$blob,<파일>

tree=$(git write-tree)
commit=$(echo "메시지" | git commit-tree $tree -p <커밋>)
git push origin $commit:refs/heads/develop --force
```

`develop`을 쓰는 이유는 `ci.yml`의 트리거가 `[main, develop]`이기 때문이다.
**한 가지 함정** — `paths-ignore`가 `docs/**`를 무시하므로 **docs만 바뀐 커밋은 CI가 돌지 않는다.**
`bd115b7`이 그런 커밋이라 처음엔 아무 일도 일어나지 않았고, 주석 한 줄을 `.cs`에 얹어 해결했다.
실험이 끝나면 `git push origin --delete develop`으로 지운다.
