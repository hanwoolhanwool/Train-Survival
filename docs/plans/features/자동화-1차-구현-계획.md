작성일: 2026-09-03 · 대상: `.github/workflows/ci.yml` · `Assets/_Project/Scripts/Editor/SteamTransportEditorMenu.cs` ·
상태: **계획 수립 — 착수 전 결정 4건(전부 ★ 권장안 있음)** ·
상위 문서: [`자동화 개선 로드맵`](자동화-개선-로드맵.md) §5.1 ·
관련: [`CI 복구 계획`](CI-복구-계획.md) (2026-08-23 · 라이선스 관문) ·
[`성능 프로파일링 자동화 계획`](성능-프로파일링-자동화-계획.md) §2 결정 ③

> **이 계획이 하는 일**: CI가 **5회 연속 실패**하는 원인을 확정해 고치고, **한 잡이 죽으면 다른 잡까지
> 함께 멈추는 구조**를 끊는다. 그리고 같은 일이 다시 나면 **로그 맨 끝에서 바로 보이게** 만든다.
>
> **이 계획이 하지 않는 일**: 새 자동화를 짓지 않는다. 검증기도, 기획자 툴도, 성능 게이트의 CI
> 연결(이미 불가 판정 — 로드맵 §2.3)도 범위 밖이다. **이 차수는 이미 지은 것을 되살리는 일만 한다.**
>
> **왜 이것이 먼저인가**: 작동하지 않는 자동화는 없는 것보다 나쁘다. 있다고 착각하게 만들기 때문이다.
> 실제로 2026-08-31부터 오늘까지 **빌드가 CI에서 한 번도 성공하지 않았는데**, 그 사이에 커밋 5개가
> main에 들어갔다.

읽으면 이렇다 — **PlayMode에 들어가며 도메인이 리로드되고, 그 끝에서 메뉴 명령 목록을 다시
만드는데, 아직 다 만들어지지 않은 그 목록에서 항목을 찾다가 죽는다.**

### 1.3 `Menu.SetChecked` 사용처는 프로젝트에 하나뿐이다

```
Assets/_Project/Scripts/Editor/SteamTransportEditorMenu.cs:24
    Menu.SetChecked(MenuPath, EditorPrefs.GetBool(ActiveTransportMode.EditorPrefsKey, false));
```

이 호출은 **MenuItem validate 함수 안**에 있다 — 즉 메뉴 시스템이 항목 상태를 물어보는 도중에
같은 메뉴 시스템을 다시 건드린다.

```csharp
[MenuItem(MenuPath, true)]
private static bool Validate()
{
    Menu.SetChecked(MenuPath, EditorPrefs.GetBool(ActiveTransportMode.EditorPrefsKey, false));
    return true;
}
```

`MenuController::GetChecked`는 이 API의 내부 구현이다. **스택이 가리키는 함수와 프로젝트의 유일한
사용처가 일치한다.**

### 1.4 그 사이에 메뉴가 하나 늘었다

```
2026-08-31 10:15:49 +0900   065d253  feat(art): 선로 메시 생성기를 만든다
```

이 커밋이 `[MenuItem("Game/Art/Rebuild Rail Track Mesh")]`를 추가했다 — **`Game/Art`라는 하위 메뉴가
새로 생겼다.** 시각이 마지막 성공(08-30 23:41)과 첫 실패(08-31 16:25) **사이**다.

메뉴 항목이 늘면 `ScriptCommands::Rebuild()`가 다루는 목록의 크기와 순서가 바뀐다. 원래 있던
경합이 그때 드러났다고 보는 것이 §1.1~§1.3과 모순 없이 맞는 유일한 설명이다.

> **다만 이것은 아직 가설이다.** 정황 넷(시각·스택·유일한 사용처·메뉴 추가)이 한 방향을 가리키지만
> **재현으로 확정하지 않았다.** 그래서 §5 1단계를 "원인 확정"으로 따로 둔다.

### 1.5 실패의 2차 피해 — 빌드가 4일째 돌지 않았다


그 결과 2026-08-30 이후 "빌드가 되는가"라는 질문의 답을 **아무도 갖고 있지 않다.**

마지막 성공 실행의 잡별 소요는 이렇다.

## 2. 착수 전 결정 — 4건 (전부 ★ 권장안이 있어 답이 없어도 착수 가능)

### ① 세그폴트 처방

| 안 | 내용 | 대가 |
|---|---|---|
| A. `Validate()` 통째 제거 | 체크 표시를 포기한다 | 메뉴만 보고는 **현재 트랜스포트 모드를 알 수 없다**. 토글이 무상태처럼 보인다 |
| **★ B. 배치모드 가드** | `Application.isBatchMode`면 `SetChecked`를 건너뛴다 | 근본 원인(재구축 중 조회)은 남는다 — 다른 코드가 같은 관용구를 쓰면 재발 |
| C. `EditorApplication.delayCall`로 미룸 | 재구축이 끝난 뒤 체크한다 | 메뉴를 열 때마다 큐에 쌓인다. 체크 표시가 한 프레임 늦는다 |
| D. 메뉴를 창으로 이전 | `MenuItem` validate 자체를 없앤다 | 변경 범위 최대. 토글 하나 때문에 창을 여는 것은 후퇴다 |

**권장 B.** `Menu.SetChecked`는 **메뉴 UI에 체크 표시를 그리는 API**인데 배치모드에는 그릴 메뉴가
없다 — 배치모드에서 부르는 것 자체가 무의미하다. 즉 B는 크래시 회피이기 이전에 **원래 하지 않아도
되는 일을 하지 않게 만드는 수정**이고, 로컬 에디터의 기능은 그대로 남는다.

B로 고쳐도 CI가 계속 죽으면 §1.4의 가설이 틀린 것이고, 그때 A로 간다(§5 1단계가 이 분기를 판정한다).

### ② `build` 잡의 의존 구조

| 안 | 내용 | 대가 |
|---|---|---|
| A. 현행 유지 (`needs: test`) | 테스트가 통과해야 굽는다 | §1.5 — 테스트가 죽은 4일 동안 **빌드 가능 여부를 몰랐다** |
| **★ B. 의존 제거 (병렬)** | 두 잡이 동시에 돈다 | 테스트가 깨진 커밋의 아티팩트가 생긴다. 다만 워크플로 자체는 여전히 **실패로 표시**되고, 아티팩트는 수동 다운로드다 |
| C. `if: always()` | 의존은 두되 실패해도 실행 | 순차라 시간 이득이 없다 (17분 38초 유지) |

**권장 B.** 얻는 것이 둘이다 — 테스트와 무관하게 **빌드 회귀를 즉시 안다**, 그리고 벽시계가
**17분 38초 → 약 10분**으로 준다. "깨진 코드를 굽지 않는다"는 원래 의도는 **빨간 체크 표시**가
이미 수행한다.

### ③ PlayMode 테스트를 CI에 유지할 것인가

| 안 | 대가 |
|---|---|
| **★ A. 유지** | 크래시가 재발하면 또 CI가 통째로 멈춘다 |
| B. EditMode만 CI · PlayMode는 로컬 | PlayMode 3종(`NgoNetworkSessionService` · `PoolManager` · `PooledNetworkPrefabHandler`)이 **CI에서 영영 안 돈다**. 이 셋은 EditMode로 대체 불가다 |

**권장 A 유지.** 이번 크래시의 원인은 **PlayMode 테스트가 아니라 에디터 메뉴**다(§1.2 — 스택에
테스트 코드가 없다). 테스트를 빼도 같은 크래시가 PlayMode를 쓰는 다른 곳에서 난다. 원인을 두고
증상을 없애는 선택이다.

### ④ 크래시를 어떻게 보고할 것인가

현재 요약 스크립트는 이미 절반을 해냈다 — 결과 XML에 실패가 없자 이렇게 말했다.

```
실패로 기록된 테스트는 없다 — 잡 실패 원인은 테스트 바깥에 있다.
```

**이 한 줄이 조사 방향을 정했다.** 다만 그 다음(로그에서 `Caught fatal signal`을 찾아 스택을 읽는 일)은
사람이 손으로 했다.

| 안 | 대가 |
|---|---|
| A. 현행 유지 | 다음에도 사람이 14,000줄 로그를 뒤진다 |
| **★ B. 크래시 요약 추가** | `test-results/*.log`에서 `Caught fatal signal`을 찾으면 스택 상위 6줄을 `::error::`로 올린다. 스크립트 20줄 안쪽 |

**권장 B.** 이번에 손으로 한 일을 그대로 코드로 옮기는 것이라 설계 위험이 없다.

## 4. 설계

### 4.1 원인 확정 절차 — 가설을 코드로 검증한다

§1.4의 가설은 정황일 뿐이므로, **처방을 넣기 전에 처방으로 판정한다.**

```
1) B안(배치모드 가드)만 담은 커밋 하나를 푸시한다.
2) CI 1회를 본다. 이때 다른 변경을 섞지 않는다 — 섞으면 무엇이 고쳤는지 모른다.
3) 녹색  → 원인 확정. §5 2단계로 간다.
   빨강  → 가설 기각. 스택을 다시 읽고 A안(Validate 제거)으로 1회 더 본다.
           그것도 빨강이면 원인은 메뉴 바깥이다 — 이 계획을 중단하고 재조사한다.
```

**CI 왕복 1회에 7~10분**이 든다. 로컬(Windows)에서는 재현되지 않으므로(같은 코드로 로컬 플레이가
정상) **검증 수단이 CI뿐**이라는 점을 감수한다.

### 4.2 처방 (B안)

```csharp
[MenuItem(MenuPath, true)]
private static bool Validate()
{
    // 배치모드에는 그릴 메뉴가 없다. 그런데도 부르면 메뉴 목록을 재구축하는 중에
    // 그 목록을 조회하게 되고, CI(Linux · 6000.5.3f1)에서 PlayMode 진입 시
    // MenuController::GetChecked → DoFindItem 에서 세그폴트가 난다.
    if (!Application.isBatchMode)
    {
        Menu.SetChecked(MenuPath, EditorPrefs.GetBool(ActiveTransportMode.EditorPrefsKey, false));
    }

    return true;
}
```

주석에 **크래시 지점과 조건을 남긴다.** 이 가드는 지우면 다시 터지는 종류라, 이유가 코드 옆에
없으면 나중에 "불필요한 분기"로 정리될 위험이 있다.

### 4.3 잡 구조

```yaml
  build:
    name: Build (StandaloneWindows64)
    # needs: test 를 제거한다 — 두 잡은 Library 캐시가 이미 분리돼 있어 서로를 기다릴 이유가 없고,
    # 붙여 두면 테스트가 죽는 동안 "빌드는 되는가"를 아무도 모르게 된다(2026-08-31~09-02에 실제로 그랬다).
    # "깨진 코드를 굽지 않는다"는 의도는 워크플로 실패 표시가 이미 수행한다.
    runs-on: ubuntu-latest
```

한 줄 삭제 + 주석이다. 다른 스텝은 건드리지 않는다.

### 4.4 크래시 요약

기존 `Summarize failed tests` 스텝의 스크립트에 분기를 하나 더한다. **결과 XML에 실패가 없을 때**만
로그를 훑는다 — 테스트가 정상적으로 실패한 경우에는 지금 출력이 이미 충분하기 때문이다.

```
if (실패 테스트 0건) {
  test-results/*.log 에서 "Caught fatal signal" 을 찾는다
  찾으면: 그 줄 + 뒤이은 스택 6줄을 ::error:: 로 올린다
  못 찾으면: 지금 문구를 그대로 유지한다
}
```

이번 사고에서 사람이 한 일(`grep "Caught fatal signal"` → 스택 상위 프레임 읽기)을 그대로 옮긴 것이다.

## 7. 미결 · 위험

| 항목 | 내용 | 대응 |
|---|---|---|
| **원인이 아직 가설이다** | 정황 넷이 한 방향을 가리키지만 재현으로 확정하지 않았다 | §4.1 — 처방 하나만 담은 커밋으로 판정한다. 기각되면 A안, 그것도 아니면 재조사 |
| **로컬에서 재현되지 않는다** | 같은 코드로 Windows 에디터 플레이는 정상이다. 검증 수단이 CI뿐 | 왕복 1회 7~10분을 감수한다. 한 번에 한 변경만 넣어 판정을 흐리지 않는다 |
| Unity 버전 고유일 수 있다 | `6000.5.3f1` · Linux · batchmode 조합 | 가드는 버전과 무관하게 안전하다(배치모드에서 안 부를 뿐). 버전을 올릴 때 가드를 빼도 되는지 다시 본다 |
| 병렬화로 러너를 2개 쓴다 | 동시 실행이 늘어난다 | public 저장소라 Actions 사용량 제한이 없다. LFS 대역은 **잡 수가 아니라 체크아웃 수**에 비례하므로 지금과 동일(2회) |
| **5회 실패를 4일간 못 봤다** | 자동화가 아니라 **관찰**의 문제다 | 완료 기준의 "연속 3회 녹색"이 복구를 확인 가능하게 만든다. 알림 도입은 로드맵 §6에서 보류(1인 개발이라 대상이 자신뿐) |
| 실패 커밋의 빌드 아티팩트 | ②B의 대가 | 워크플로는 여전히 실패로 표시되고, 아티팩트는 수동 다운로드다. 자동 배포 경로가 없으므로 오배포 위험이 없다 |
