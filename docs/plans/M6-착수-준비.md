# M6 착수 준비 — Steam 통합·수명 주기

작성일: 2026-08-11 · 대상: `feat/m6-steam-lifecycle` (main에서 분기) · 상태: **착수 준비 —
차수 분할·착수 전 결정 대기 (사용자 확정 후 1차 계획 문서를 연다)**

> **M6 범위** (개발 가이드 §5): Steam 트랜스포트 + 로비/프렌드 초대 + 재접속(rejoin) +
> 메타 진행 저장(업적·수집품, Steam 업적 연동 검토) + 사망/부활/게임오버 규칙.
> **완료 기준**: Steam 릴레이로 외부 네트워크의 친구와 세션을 시작·완주할 수 있고,
> 중도 이탈한 클라이언트가 재접속으로 같은 플레이어로 복귀한다.
> **불변 지침**: 트랜스포트 전환은 빌드 설정/실행 인자 — CI는 계속 UnityTransport 직결 ·
> 게임 중간 저장 없음(기획서 §9.1 확정 — 세이브/로드를 만들지 않는다) ·
> 접속 끊김 ≠ 사망(게임오버 판정 제외 — 네트워크 §2.3).

## 2. 기술 현황 (착수 시점 스냅샷)

- 패키지: NGO `com.unity.netcode.gameobjects` **2.13.0** · MPPM 2.0.2 · Multiplayer Tools 2.2.9.
  Steam 관련 패키지는 **미도입** (네트워크 §7 — 구현체 선정 후 추가).
- 세션 시작은 전부 `INetworkSessionService.StartHost()/StartClient()` 경유 (1인 = 혼자 호스트인
  세션 원칙) — 트랜스포트 이원화의 진입점이 이미 한 곳이다.
- CI·MPPM 가상 플레이어는 UnityTransport 직결 유지 (Steam 클라이언트 의존 금지).

### Steam 트랜스포트 구현체 — 유지보수 상태 조사 (2026-08-11, 미결 결정의 입력)

네트워크 §8의 "도입 시점에 유지보수 상태 비교 후 확정"에 따른 사전 조사:

- **커뮤니티 Facepunch 트랜스포트**(`com.community.netcode.transport.facepunch`,
  Unity multiplayer-community-contributions)는 의존하는 Facepunch.Steamworks가
  **2020년의 2.3.2로 고정**되어 있고(최신은 2.4.x~2.5.x), 신선한 프로젝트 임포트 시
  타입 충돌(Posix/Win64) 이슈 보고가 있다 — **그대로 쓰기엔 위험, 포크·수선 전제**.
- **Steamworks.NET**은 Valve C++ API의 충실 래퍼로 활발히 유지보수 중 — 대응하는 NGO
  커뮤니티 트랜스포트가 별도로 있다.
- 결론: **문서만으로 확정하지 않는다** — 1차에서 두 구현체 스파이크(로비 생성·릴레이 왕복)로
  비교 검증 후 확정하는 것을 권장 (아래 결정 ①).

## 3. 착수 전 결정 목록 (사용자 확정 대기)

| # | 결정 | 선택지 (권장 굵게) |
|---|---|---|
| ① | Steam 트랜스포트 구현체 | ⓐ Facepunch 최신 + 커뮤니티 트랜스포트 포크 ⓑ Steamworks.NET + 대응 트랜스포트 — **스파이크로 비교 후 확정** (조사 결과 §2 — 문서 비교만으로는 위험) |
| ② | 재접속 식별 방식 | **Steam ID ↔ 플레이어 슬롯 매핑 (릴리스) + 개발용 대체 식별자 (UnityTransport에는 Steam ID가 없다 — 예: 로컬 GUID 토큰)** — 개발·CI에서 재접속을 테스트할 수 있어야 하므로 이원화가 사실상 필수 |
| ③ | 재접속 유예 시간 | 끊긴 플레이어의 슬롯·상태를 얼마나 보존하는가 — ⓐ 세션 끝까지 ⓑ 유예 N분. **게임 중간 저장이 없으므로 "세션 끝까지"가 단순** (슬롯 상한 4인이라 메모리 부담 없음) |
| ④ | 중도 난입(drop-in) 허용 범위 | ⓐ 재접속(복귀)만 허용 ⓑ 신규 난입도 허용. **1안 — 완료 기준이 요구하는 것은 복귀뿐**, 난입은 밸런스 파급(인원 비례 난이도)이 별도 |
| ⑤ | 사망/부활/게임오버 규칙 상세 | 현행(개별 부활 5 s 고정 + 이탈 사망 통합)을 기반으로 — **전멸 = 게임오버 판정 신설**(끊긴 플레이어 제외 — §2.3), 부활 대기 Day 비례(M2 미결)와 함께 확정 |
| ⑥ | 메타 진행 저장 범위 | 업적·수집품의 최소 집합 — ⓐ 로컬 파일만 ⓑ **로컬 + Steam 업적 연동 검토**(범위는 기획 협의). 런 내 저장은 없음(불변) |
| ⑦ | M5 잔여 검증 편입 시점 | ⓐ M6 1차 검증 문서에 즉시 편입 ⓑ **M6 재접속 검증과 무관한 것(E·H·K 등)은 별도 "잔여 소화" 검증 세션으로 분리** — M6 검증이 56건에 파묻히지 않게 |

## 4. 차수 분할 제안 (권장안 — 확정은 사용자)

M5와 같은 방식(차수별 구현 계획 + 플레이 검증 문서)을 유지한다.

| 차수 | 내용 | 근거 |
|---|---|---|
| 1차 (재접속 — 기반) | 세션 수명 주기 정리(끊김 감지·슬롯 보존) + 재접속 식별(개발용 식별자 먼저) + **같은 플레이어로 복귀**(인벤토리·장비·스탯·집게 티어 커스텀 복원 — 열차·월드는 NGO 후발 동기화) + M4 지형 표시 ④ | **Steam 의존 0** — UnityTransport·MPPM으로 지금 즉시 개발·검증 가능. M3·M5 이월이 전부 이 축이고, 열차 상태 모델(§6.3)이 준비돼 있다 |
| 2차 (Steam 통합) | 구현체 스파이크(결정 ①) → 트랜스포트 이원화(빌드 설정/실행 인자) + 로비/프렌드 초대 + 릴레이 접속 (임시 AppID 480) + 재접속 식별을 Steam ID로 교체 | 외부 의존(Steam 클라이언트·AppID)이 있는 축을 분리 — 1차의 재접속이 식별자만 바꿔 그대로 탄다 |
| 3차 (수명 주기 규칙) | 게임오버 판정(전멸 — 끊긴 플레이어 제외) + 부활 규칙 확정(Day 비례 검토 — M2 미결 해소) + 메타 진행 저장(업적·수집품 최소 집합) | 규칙·데이터 축 — 트랜스포트와 독립이라 마지막에 몰아도 위험이 없다 |
| 검증 | **완료 기준**: Steam 릴레이로 외부 네트워크 친구와 세션 시작·완주 + 중도 이탈 클라이언트가 같은 플레이어로 복귀. + M5 이월 4인 세션 역할 분담 검증(외부 세션과 겸사 가능) | 릴레이 테스트는 실제 외부 네트워크 2대 이상 필요 — 검증 세션 준비물에 명시 |

**차수 순서의 원칙**: 외부 의존이 없는 것부터 (1차는 오늘 착수 가능, 2차는 Steam
클라이언트·AppID·외부 테스트 환경 준비가 병행 선행), 재접속 축은 식별자만 갈아 끼우게
설계해 1차 결과물이 2차에서 재작업되지 않게 한다.
