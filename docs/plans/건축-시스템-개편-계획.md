## 0. 범위

**코어** (그리드 축):

1. **그리드 설치** — 칸 바닥 콜라이더 규격(4.6 × 15 m,
   `TrainLayoutSettings.asset`)을 **1.0 m 정사각 셀 4열 × 15행(칸당 60셀)**으로
   분할 (결정 ①). 건축물마다 점유 면적(가로 × 세로 셀 수)을 정의하고, 빈 셀
   묶음 위에만 설치. 한 칸에 여러 건축물 공존
2. **설치 회전** — 설치 프리뷰 중 **Q/E**로 90° 단위 회전 (점유 면적의 가로·세로
   스왑 포함)
3. **망치 철거** — 망치를 든 상태에서 **X 짧은 홀드(0.5 s)**로 조준한 건축물
   철거 (결정 ④). 건설 비용의 **50% 반환** — 가방에 들어가는 만큼 수납, 잔여는
   보따리로 갑판 배출 (결정 ⑤)
4. **몬스터 파괴 시 자원 미회수** — 현행이 이미 이 규칙 (파괴 시 자원 반환 로직
   자체가 없음). 창고(Storage)만 보따리(`StorageBundle`) 배출 — **이것도 구현
   완료** (`TrainState.cs` `ServerDropStorageAsBundleIfPresent`). 개편 후에도
   유지되는지 회귀 확인만 하면 됨
5. **판자 증축** — 칸 옆면에 판자를 붙여 그리드 폭(열)을 확장 — 셀 열 단위
   (결정 ⑥). **판자 에셋은 차후 추가** — 이번에는 프리미티브 판 + 상태
   모델·판정만

**부수** (그리드화가 강제하는 재작업):

6. **건축물 시각 표현 교체** — 씬 정적 배치(`StructureView._kindVisualRoots`,
   칸마다 7종 메시 미리 배치 후 on/off) 방식은 다중 설치와 양립 불가 →
   프리팹 + `PoolManager` 스폰으로 전환
7. **종류별 기능 조회 재배선** — 그늘/난방(`PlayerTemperature`),
   제작대·화덕·정수기(`CraftingStation`)가 "칸 인덱스 → 건축물 1개" 전제로
   조회 중 — 다중 설치 전제로 변경 (§2.7)
8. **창고 저장 모델 개편** — 다중 창고 허용 확정(결정 ⑦)에 따라
   `TrainStorage`의 "저장 블록 = 칸 인덱스" 규약을 "저장 블록 = 건축물 Id"로
   개편 (§2.8)

**비범위** (후속):

- **온실 돔(Dome)** — 이번 개편에서 **설치 목록 제외** (결정 — 2026-08-16).

- **스폰·부활 지점 재설계** — 이월 확정. 임시 조치도 두지 않음 (결정 ⑪ —

- **몬스터 이동 AI 재설계** (회피·경로) — 이월. 단 **건축물 관통 금지 규칙

- 건축물 종류별 재료 비용(목재 3 + 돌 2 등) 체계 — 현행 "건자재 아무거나 N개"

### 1.1 결정 ⑤ 상술 — 철거 반환 흐름 (확정)

반환량 = `floor(buildCost × 0.5)` (예: 화덕 비용 3 → 1개, 창고 4 → 2개, 강화
난방로 7 → 3개).

1. 반환분을 1개씩 `ServerTryAdd` (현행 `ServerTryAdd`는 전량 아니면 실패
   규약이므로, 1개 단위 반복 호출로 부분 수납을 구성)
2. 다 안 들어가면 **잔여분을 보따리 1개로 묶어 갑판 배출** — 창고 파괴 시의
   `ServerSpawnDeckResting`(갑판 휴지 스폰) 경로 재사용, 스폰 위치는 철거한
   건축물의 점유 영역 중심
3. 정상 상황(가방 여유)에서는 보따리가 생기지 않음 — 자원 소실 0

검토했던 대안: 전량 갑판 드롭(가방이 널널해도 줍기 필요 — UX 저하), 철거
차단(긴급 재배치 불가 — 답답함). 둘 다 기각.

### 2.2 데이터 — `StructureEntry`와 카탈로그 확장

```
struct StructureEntry : INetworkSerializable
{
    ushort Id;          // 서버 발급 일련번호 (철거·피해 RPC의 안정 참조)
    byte   CarIndex;
    byte   CellX;       // 점유 영역 좌하단 셀 (열) — 고정 예약 좌표계 (§2.3)
    byte   CellZ;       // 점유 영역 좌하단 셀 (행)
    byte   Rotation;    // 0~3 (× 90°)
    StructureKind Kind;
    float  Health;
    float  MaxHealth;
}
```

- 기존 `StructureState`(Present/Kind/Health/MaxHealth)는 대체·삭제. `Present`는
  리스트 존재 여부로 대신한다.
- `StructureCatalog.Entry`에 필드 3종 추가:
  - **`_footprintWidth` / `_footprintLength`** (셀 수)
  - **`_placeable`** (설치 가능 플래그) — 돔 제외용 (§1.2). `NextKind`(R 순환)와
    `CanPlace`가 이 플래그를 함께 본다 — false면 순환에서 건너뛰고 설치 기각
  - **`_refundResource`** (철거 반환 자원 종류, 결정 ⑧) — 초기값 전부
    Wood(목재)
- **확정표 (결정 ② — 셀 1.0 m 기준 환산)**:

| 종류 | 점유 (가로 × 세로) | 물리 크기 | 근거 |
|---|---|---|---|
| 화덕 Campfire | 1 × 1 | 1.0 m | 소형 스탠드형 |
| 난방기 Heater | 1 × 1 | 1.0 m | 〃 |
| 정수기 Purifier | 1 × 1 | 1.0 m | 〃 |
| 제작대 Workbench | 2 × 1 | 2.0 × 1.0 m | 가로로 긴 작업대 (회전 의미 발생) |
| 공유 창고 Storage | 2 × 1 | 2.0 × 1.0 m | 〃 |
| 강화 난방로 Furnace | 2 × 2 | 2.0 m 각 | 상위 티어 존재감 |
| 온실 돔 Dome | (설치 제외) | — | **`_placeable = false`** — 통행 차단 문제로 차후 재설계 (§1.2). enum 값 0은 유지 |

### 2.3 그리드 순수 로직 — `StructureGridLogic` (신규, EditMode 대상)

`TrainLayoutMath`와 같은 결의 순수 static 클래스. 전부 에셋 파라미터
(`cellSize = 1.0`, `carWidth`, `carLength`)를 인자로 받는다.

- **고정 예약 좌표계** (§1.2 기술 확정): 열 좌표는 "좌측 최대 판자열 = 열 0"으로
  고정 예약한다 — 예약 폭은 컴파일 상수 `MaxPlankColumnsPerSide = 2`
  (에셋 상한 `_maxPlankColumns`는 이 상수를 초과할 수 없음 — 초과 시 좌표
  재색인이 필요해지므로 클램프). 열 0~1 = 좌측 판자, 열 2~5 = 칸 본체,
  열 6~7 = 우측 판자. 좌측 판자를 나중에 설치해도 **기존
  항목의 CellX 재색인이 영원히 불필요**하다. 판자가 없는 열은 `CanPlace`의
  유효 열 검사에서 걸러질 뿐 좌표 자체는 항상 유효
- `WorldToCell(hitPoint, carCenterZ, ...) → (cellX, cellZ)` — 월드 좌표 →
  칸 로컬 → 셀 (위 고정 좌표계 기준). 열차는 X=0 고정 주행이므로 X는 월드
  그대로, Z만 칸 중심 보정
- `RotatedFootprint(w, l, rotation) → (w', l')` — 홀수 회전이면 스왑
- `CanPlace(entries, carIndex, cellX, cellZ, w, l, columns(carIndex))` —
  유효 열 내부(판자 상태 반영) + 기존 항목들과 셀 교차 없음 + 칸 생존 +
  기관차 제외 + 설치 가능 플래그(`_placeable`) 참
- `CellToWorld(...)` — 점유 영역 중심의 월드 좌표 (뷰 스폰·프리뷰 위치)
- (성능 여지) 칸당 점유를 `ulong` 비트마스크(기본 60셀 ≤ 64비트)로 캐시 —
  1차에서는 리스트 순회로 시작, 프로파일 후 필요 시 전환

기존 `TrainStateLogic`의 건축 관련 함수(`CanBuildStructureAt` /
`BuildStructure` / `ApplyStructureDamage`)는 이 클래스로 이관·재작성한다.
칸 이탈 중 피해 Ignored·칸과 운명 공유 규칙은 그대로 이관.

### 2.4 설치 플로우 — `RepairHammerController` 개편

1. **조준**: 현행 레이캐스트 유지. hit이 칸 갑판이면 `WorldToCell`로 스냅
2. **프리뷰**: `CarBuildGhostView` 패턴(LineRenderer 와이어박스 + EventBus 로컬
   이벤트)을 재사용해 **점유 셀 영역**을 초록(가능)/빨강(불가)으로 표시.
   기존 `HammerTargetLocalEvent` 결의 `StructurePlaceAimLocalEvent` 신설
3. **회전**: `Keyboard.current.qKey/eKey.wasPressedThisFrame` → `_previewRotation
   = (r ± 1) & 3`. 프리뷰 즉시 반영. 종류 변경(R)·망치 해제 시 0으로 리셋
4. **확정**: 우클릭 → `RequestBuildStructureServerRpc(carIndex, cellX, cellZ,
   rotation, kind)` — 호스트가 생존·사거리 재검증 후 `CanPlace` **재판정**
   (프리뷰와 같은 순수 함수 — 칸 건설의 소유자/호스트 동일 함수 규약 준수),
   지불은 현행 원자 관용구 `inventory.ServerTrySpend(cost, () => confirm())` 유지
5. **전파**: `BroadcastStructureBuiltRpc` → `EventBus<StructureBuiltEvent>`
   (페이로드에 entry 포함) → 뷰 스폰

### 2.5 철거 플로우 (신규)

1. 망치 활성(`InputEnabled`) 상태에서 조준 대상이 건축물(`TryResolvePart` →
   `TrainPartKind.Structure`)이면 HUD에 "X 홀드 — 철거 (반환: N개)" 노출
2. `Keyboard.current.xKey.isPressed` 홀드 게이지(0.5 s, 결정 ④) 충족 →
   `RequestDemolishStructureServerRpc(structureId)`
3. 호스트: 생존·사거리 재검증 → 항목 제거 → **반환 처리 (결정 ⑤·⑧)**: 반환량
   `floor(cost × 0.5)`, 자원 종류는 카탈로그 `_refundResource`(초기값 목재).
   1개씩 `ServerTryAdd`, 잔여분은 보따리로 갑판 배출 (§1.1 — 검증 결과 기존
   `IStorageBundleSpawner.ServerSpawnResting(contents, position)`이 1슬롯
   내용물도 그대로 받으므로 신규 스폰 코드 불필요) →
   `BroadcastStructureDemolishedRpc`
4. **창고 철거 시**: 내용물 보따리 배출(§2.8) 후 철거 — 반환 자원 보따리와
   내용물 보따리는 별개로 스폰 (묶으면 해체 UI가 혼합 목록이 되어 혼란)
5. 몬스터 파괴(`ServerApplyStructureDamage` 경유)는 반환 경로를 **타지 않음** —
   요구사항 "몬스터 파괴 시 자원 회수 X"는 코드상 자연 성립. 회귀 테스트로
   못 박는다

### 2.6 시각 표현 — 씬 정적 배치 폐기, 프리팹 스폰

- 종류별 프리팹 `Structure_<Kind>.prefab` 신설 (M8에서 반입한
  Campfire/Storage/Workbench 아트 재사용, 나머지는 기존 프리미티브 메시 이관 —
  돔은 설치 제외라 프리팹 미제작).
  루트에 `StructureView` + BoxCollider — **NetworkObject 없음** (상태는
  `NetworkList`가 가지므로 뷰는 각 클라이언트가 이벤트/리스트 동기화로 로컬
  스폰). 따라서 NetworkPrefabs 등록·GlobalObjectIdHash 이슈 없음,
  `PoolManager.Spawn/Despawn` 사용
- `StructureView`는 "칸 인덱스 보유자"에서 "entry Id 보유자"로 재작성.
  `IDamageable.ApplyDamage` → `sink.ApplyStructureDamage(structureId, amount)`.
  몬스터 타깃 등록(`ITrainTargetRegistry`)은 스폰/디스폰 시점으로 이동
- 후발 접속: `NetworkList` 초기 동기화 완료 시점에 리스트 전체 순회 스폰
  (현행 `SyncFromState` 역할의 재구성 루틴)
- 칸 이탈 시: 뷰는 칸과 함께 숨김/이동(현행 `CarView` 규약), 상태 항목은 유지
- 씬(`Game.unity` / `Game_ArtTest.unity`)의 `Structure` 정적 오브젝트 5세트 제거

### 2.8 창고 저장 모델 개편 (결정 ⑦ 확정 — 다중 허용)

- **저장 구조**: `NetworkList<ushort> _blockOwners`(블록 i를 소유한 건축물 Id) +
  `NetworkList<NetworkSlot> _slots`(블록 i의 슬롯 = `i × 10 + slot`). 설치 시
  블록 append(빈 슬롯 10개), 파괴·철거 시 해당 블록 내용물 보따리 배출 후
  swap-remove (마지막 블록을 빈자리로 이동 — Id 매핑은 `_blockOwners`가 담보)
- **슬롯 규칙 재사용**: 슬롯 단위 입출·정렬은 현행 `StorageLogic` 순수 함수
  그대로 — 블록 오프셋 계산만 바뀜
- **UI 접근 판정**: 현행 거리·시선 판정(`_interactRadius: 3`,
  `_lookDotThreshold: 0.8`)의 대상이 "칸의 창고"에서 "**조준한 창고 실물**
  (`StructureView` → Id)"로 — 프리팹 실물이 생기므로 자연스럽게 성립. 한 칸에
  창고 여러 개일 때도 조준한 그것이 열림
- **칸 이탈·재결합**: 블록은 Id 기준이라 칸 이탈에 무관하게 유지 — 현행 "이탈은
  소실 아님, 재결합 시 보존" 규약 자동 성립. 칸 파괴 시에는 그 칸 건축물 제거
  루프에서 창고마다 보따리 배출(`deckAlive: false` — 지상 투척, 현행과 동일)
- **슬롯 재건 시 소실 처리**(`ServerClearStorageIfPresent` — 이중 생성 방지)는
  "칸 파괴 시점에 블록이 이미 제거"되는 새 구조에서는 불필요해짐 — 삭제

### 2.9 판자 증축 (결정 ⑥ 확정 — 셀 열 단위)

- 상태: `CarState`에 `LeftPlanks` / `RightPlanks` (byte) 추가 — 열 단위.
  최대치는 에셋 필드 `_maxPlankColumns` (초기값 1 — 좌/우 각 1 m씩, 최대 폭
  6.6 m)
- 설치: 망치 조준이 칸 **옆면**(그리드 밖 인접 열)일 때 판자 프리뷰 →
  우클릭 건설 (비용은 에셋 필드 신설, 초기값 제안 3)
- 판정 확장: `IsWithinDeckAperture`(승차·낙하 판정)와 `CanPlace`의 유효 열
  범위가 판자 상태를 반영. **몬스터 승차·온도 실내 판정이 칸 폭에서
  파생되므로** (커밋 2288126 메시지 참조) 영향 범위 회귀 필수
- 시각: 프리미티브 판(1.0 × 15 × 0.15 m) + 확장분 BoxCollider. 실제 에셋은
  차후 교체 (반입 시 머티리얼/메시 스왑만으로 끝나게 홀더 구조 유지)
- 좌표계: §2.3의 고정 예약 좌표계 사용 — 판자 설치·제거가 기존 건축물의
  `CellX`에 영향을 주지 않는다. 판자 제거(있다면)는 그 열 위 건축물이 있으면
  기각하는 것으로 단순화
- 판자 자체도 파괴 가능 여부(몬스터 타깃 등재)는 **1차에서는 불가(파괴 대상
  아님)**로 두고, 필요해지면 후속 결정

### 2.10 몬스터 관통 방지 — 최소 구현 (결정 ⑩)

**규칙 확정**: 건축물은 몬스터의 공격 대상이면서, **몬스터가 관통할 수 없다**.
이동 AI 재설계(제대로 된 회피·경로)는 이월 — 이번에는 관통 방지만.

- 현행 몬스터 이동은 물리가 아니라 `transform.position` 직접 대입 + 진행 방향
  레이 1발 회피(`ProbeObstacle`)라, 회피가 실패하면 콜라이더를 그대로 통과한다
- **최소 구현**: 갑판 위 몬스터의 이동 적용 직전, 이동 후 위치가 건축물 점유
  셀과 겹치면 **이동을 취소(또는 접촉면까지 클램프)** — 판정은 물리 쿼리가
  아니라 그리드 순수 로직(`StructureGridLogic`의 셀 점유 조회) 재사용. 서버
  시뮬레이션에만 존재하므로 복제 비용 없음
- 막힌 몬스터의 행동은 추가 AI 없이 성립한다 — 타깃을 매 프레임 재조회하고
  건축물이 `ITrainTargetRegistry`에 등재되므로, 길을 막은 건축물이 곧 최근접
  타깃이 되어 **"막히면 부순다"**가 자연 발생
- 지상 몬스터·플레이어 이동은 건드리지 않는다 (플레이어는 CharacterController가
  이미 콜라이더와 충돌)

## 3. 구현 순서 (차수 분할)

1. **1차 — 그리드 코어**: `StructureGridLogic` + `StructureEntry` 상태 모델 교체
   + 설치·회전(Q/E)·프리뷰 + 프리팹 스폰 전환(§2.6) + 기능 조회 재배선(§2.7)
   + 몬스터 관통 방지 최소 구현(§2.10).
   여기까지가 "다중 설치가 실제로 도는" 최소 단위 — 상태·뷰·소비처가 한 몸이라
   쪼갤 수 없음. **단, 창고만 1차에서는 임시 가드(칸당 1개 기각) 한 줄로 제한**
   — 저장 모델 개편 전까지 현행 `TrainStorage` 유지
2. **2차 — 철거 + 창고 개편**: X 홀드 + 50% 반환 + 잔여 보따리 배출 + **저장
   모델 개편(§2.8) + 1차 임시 가드 해제** + 몬스터 파괴 무반환 회귀 고정.
   철거의 보따리 배출과 창고 개편이 같은 코드(보따리 스폰 경로)를 만지므로
   같은 차수로 묶는다
3. **3차 — 판자 증축**: `CarState` 확장 + 옆면 조준·건설 + 폭 파생 판정 확장

각 차수마다 짝 문서 `건축-개편-N차-플레이-검증-항목.md`를 두는 기존 관례를
따른다.

### 3.1 품질 규약 — 구현 중 하드코딩 허용, 마무리 게이트는 엄격

**구현 중 (각 차수 진행 단계)**: 동작 확인이 목적인 임시 코드를 허용한다 —
매직 넘버, 임시 분기, 구체 타입 직접 참조 등. 단, 임시임을 `// TODO(정리)`
주석으로 표시해 마무리 게이트에서 누락되지 않게 한다.

**마무리 게이트 (각 차수 완료 선언 전 필수 통과)**:

1. **MVP(Model-View-Presenter) 분리** — 이 프로젝트의 기존 규약(순수 로직
   static / View / Controller)과 같은 축:
   - **Model**: `StructureGridLogic`·상태 규칙은 Unity 비의존 순수 static —
     전부 EditMode 테스트 대상. `NetworkList` 스냅샷을 인자로 받고 결과를
     반환할 뿐, 직접 쓰지 않는다
   - **View**: `StructureView`·고스트 프리뷰는 상태를 소유하지 않는다 —
     `EventBus` 구독·리스트 동기화 반영만 (`CarBuildGhostView` 규약 동일)
   - **Presenter**: `RepairHammerController` 등 컨트롤러는 입력 해석·프리뷰
     이벤트 발행·RPC 중개만 — 판정은 Model 호출로 위임 (소유자/호스트 동일
     함수 규약)
2. **SOLID** ([docs/conventions/solid-principles.md](../conventions/solid-principles.md) 전 항목):
   - SRP — 설치·철거·창고 블록·판자 로직이 한 클래스에 뭉치지 않게 분리
   - OCP — 건축물 종류·점유 면적·비용·판자 상한 추가/변경이 **코드 수정 없이
     에셋(`StructureCatalog` 등)으로** 끝나는 구조 확인
   - DIP — 시스템 간 통신은 `EventBus<T>`, 전역 접근은 `ServiceLocator`
     인터페이스(`ITrainDamageSink` 등) 경유. 구체 클래스 직접 참조 잔존 금지
3. **수치의 에셋화** — 셀 크기·철거 홀드 시간·반환 비율(50%)·판자 비용/상한
   등 임시 하드코딩 수치를 전부 `ScriptableObject` 필드로 이관
4. **어셈블리 단방향 의존** (`Utilities ← Core ← Systems ← Gameplay ← UI`)
   위반 없음 + `PoolManager`/`EventBus` 인프라 경유 확인
5. **TODO(정리) 주석 0건** — grep으로 확인

마지막 차수(3차) 완료 후에는 차수 단위 게이트와 별도로 **전체 리팩터링 패스**
(`/simplify` 수준의 중복·단순화 점검 + 코드 리뷰)를 한 번 더 돌려, 차수를
거치며 누적된 이음새(1차 임시 창고 가드 잔재 등)를 정리하고 종료한다.

## 4. 테스트·검증 계획

**EditMode (순수 로직 — 기존 452개에 추가)**:

- `StructureGridLogic`: 셀 변환 왕복(고정 예약 좌표계 — 본체 열 2~5), 회전
  footprint 스왑, 경계(가장자리 여백 0.3 m 쪽 기각), 셀 교차 기각, 파괴된 자리
  재설치, 기관차 기각, 판자 확장 열 포함 판정, 설치 불가 플래그(돔) 기각 +
  R 순환에서 제외
- 철거: 반환량 `floor(cost × 0.5)` 표 (비용 3→1, 4→2, 7→3), 반환 자원 종류 =
  카탈로그 `_refundResource`, 부분 수납 → 잔여 보따리 구성 분기
  (가방 여유/일부/전무 3케이스)
- 관통 방지: 이동 후 위치가 점유 셀과 겹치면 취소/클램프, 겹치지 않으면 통과
  (순수 로직 케이스)
- 창고 블록: 설치 → 블록 할당, 철거·파괴 → 배출 + swap-remove 후 잔여 블록
  Id 매핑 무결, 칸 이탈 → 블록 보존
- 회귀: 몬스터 파괴 경로에 반환 없음, 칸 파괴 → 그 칸 창고 전부 지상 투척

**플레이 검증 (호스트 + 클라 1)**:

- 한 칸에 소형 3개 + 제작대(회전 상태) + 창고 2개 공존, 후발 접속 시 전원 동일
  재구성
- 셀 점유 겹침 시 프리뷰 빨강 + 호스트 기각 (클라 조작으로 위조 시도 포함)
- 철거 반환 — 가방 여유/가득 두 케이스 (가득 시 잔여 보따리 확인, 보따리 해체로
  전량 회수)
- 창고 2개 각각 조준해 서로 다른 내용물 열림, 하나 파괴 시 그 창고 내용물만
  보따리 배출
- 칸 파괴 시 그 칸 건축물 전원 소멸 + 창고 보따리 지상 투척 (현행 규칙 유지)
- 몬스터가 강화 난방로(2×2)에 막혀 관통하지 못하고, 막은 건축물을 공격 대상으로
  전환하는지
- 판자 위 승차·건설·온도 판정

## 5. 미해결·위험

- **`Game.unity` 구 치수 (3 × 3 × 12)** — 그리드는 `TrainLayoutSettings.asset`
  (4.6 × 15)에서 파생되므로 `Game.unity` 정렬(별도 커밋 예고분)이 선행돼야 함.
  당분간 인게임 진입이 `Game_ArtTest` 고정이라 착수는 가능
- **`StructureKind` 직렬화 값 규약** — enum 값이 `NetworkList`에 실리므로 개편
  중에도 기존 값(0~6) 불변 유지
- **스폰·부활 지점과 건축 셀 겹침 (알려진 이슈 — 임시 조치 없음, 결정 ⑪)** —
  부활 지점(후미 칸 중앙 고정 1점)·초기 스폰(첫 화차 중앙) 셀에 건축물이 서
  있으면, 텔레포트가 오버랩 검사 없이 좌표를 대입하므로 부활자가 콜라이더 안에
  낙하할 수 있다. 스폰·부활 재설계(이월)에서 해소 예정 — 그전까지 플레이 검증
  시 해당 셀 설치를 피해서 진행
- **1.0 m 셀 × 다중 설치의 밀도** — 칸당 60셀이라 이론상 소형 건축물 수십 개가
  들어감. 밀도 상한(칸당 설치 수 제한)이 필요해지면 에셋 필드로 후속 추가 —
  1차에서는 미설정
- **경미 (의식적 선택 메모)** — 그늘/난방 판정은 칸 단위 boolean 유지: 건축물
  점유 영역(예: 난방기 1×1)과 효과 범위(칸 4×15 전체)가 공간적으로 불일치하지만
  현행 규칙 계승. 난방기를 한 칸에 여러 대 설치하면 효과 중복 없이 연료만
  각각 소모 — 밸런스 조정 대상 메모
- 프리팹화 과정에서 M8 아트 패스 결과물(미커밋 상태)과 병합 순서 조율 필요 —
  **M8 커밋·머지 후 착수** 전제
