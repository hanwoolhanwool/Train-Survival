# 1인칭 통합 시점 전환 계획 — FP/TP 이원 표현 제거

작성일: 2026-08-18 · 대상 브랜치: **`feat/structure-grid`**(단계 1~3) / **`feat/weapon-hold`**(단계 4 이후) ·
상태: **단계 1~3 구현 완료 · 플레이 검증 대기** (2026-08-18 —
짝문서 [1인칭-통합-1차-플레이-검증-항목.md](1인칭-통합-1차-플레이-검증-항목.md))
(선행 실측: `Player.prefab` 계층·카메라 파라미터 · `WeaponHoldSettings.asset` 홀드 타깃 5종 ·
`PlayerAimView`/`PlayerCharacterView`/`HeldWeaponSocket`/`WeaponHoldIk` 코드 분석 —
**실측은 `feat/weapon-hold` 기준**이다. §5.0의 브랜치 제약을 먼저 읽을 것)

> **목표**: 소유자 화면에서 보이는 무기를 **캐릭터가 실제 손에 쥔 그 무기**로 통일한다.
> 화면 전용 FP 뷰모델(AimPivot 아래 피벗 5종)을 없애고, 카메라가 캐릭터의 눈 위치에서
> **자기 몸과 손과 무기를 그대로** 본다.
>
> **필수 요구 (사용자 확정)**: 현행 FP/TP 분리 표현과 **런타임에 번갈아 전환**하며 QA할 수 있어야 한다.
> 따라서 이 계획의 1차 산출물은 "교체"가 아니라 **모드 스위치가 달린 병존 구현**이고,
> FP 경로의 물리적 제거는 QA 합격 뒤 §8에서 별도 단계로 닫는다.

## 0. 범위

**코어**

1. **시점 모드 스위치 신설** — `PlayerViewMode`(분리 ↔ 통합) · `PlayerViewSettings` SO ·
   `PlayerViewModeController`(소유자 로컬, 런타임 토글) · 로컬 이벤트 1종
2. **소유자 자기 표현 개방** — 몸체 `ShadowsOnly` → `On`, 손 무기 `ShadowsOnly` → `On`,
   **머리 은닉**(카메라를 가리는 부위 처리)
3. **1인칭 파지 프로파일** — 홀드 타깃·팔꿈치 힌트·손목 값을 1인칭용으로 별도 보유
   (현행 TP 값과 **동시 보존** — QA 비교의 전제)
4. **카메라 파라미터 모드화** — near clip · FOV를 모드별 값으로
5. **FP 뷰모델 게이트** — 통합 모드에서 FP 피벗 5종 비표시
6. **발사 원점 재정의** — 표시 총구를 손 무기 기준으로 (판정 원점은 무변경)
7. **근접 스윙 표현 이관** — `MeleeSwingView`(FP 피벗 절차 회전)의 통합 모드 대체 경로
8. **뷰랩 확장** — 통합 모드 미리보기 · 1인칭 프로파일 편집 (네트워크 없이 자세 튜닝)

**비범위** (의도적 제외)

- **판정 변경 일절 없음** — 레이캐스트 원점은 계속 `_aimSource`(카메라), 호스트 검증도 무변경.
  두 모드가 **같은 판정**을 공유해야 QA 비교가 "표현 차이"만 남는다 (§4.2)
- **원격 피어가 보는 모습 변경 없음** — TP 월드모델·상체 절차 피치는 그대로. 모드는 **각 피어 로컬 화면**에만 적용된다
- **네트워크 채널 추가 0** — 모드는 복제하지 않는다 (표현 로컬 선택)
- **FP 전용 팔 뷰모델 반입** — 통합 모드에서는 캐릭터의 실제 팔이 그 역할을 한다
- **파지 애니메이션 클립 반입** — [무기-파지-품질-업그레이드-계획.md](무기-파지-품질-업그레이드-계획.md) C축 유지
- **3인칭 관전 시점** — 이 계획은 1인칭 통합만 다룬다

## 1. 현재 구조와 진단

### 1.1 계층 (Player.prefab 실측)

```
Player (루트)
├─ CameraRig                        ← NetworkPlayerController.cs:126  SetActive(isOwner)
│  └─ CameraPivot   local (0, 1.6, 0)      ← 마우스 피치 (소유자 입력)
│     ├─ PlayerCamera   near 0.3 · FOV 60 · local (0,0,0)
│     └─ Muzzle         local (0.35, -0.25, 0.5)   (무기와 무관한 더미 총구)
│
├─ AimPivot         local (0, 1.6, 0)      ← PlayerAimView가 복제 피치로 전 피어 회전
│  ├─ MeleePivot → Blade         (MeleeSwingView — FP 절차 스윙)
│  ├─ HammerPivot                (RepairHammerView)
│  ├─ RevolverPivot              (GunView)
│  ├─ ShotgunPivot               (GunView)
│  └─ HarpoonPivot               (HarpoonView)          ★ 이 5벌이 FP 뷰모델
│
├─ Body
│  ├─ Character_Girl / Character_Man   (Animator · WeaponHoldIk · WeaponHoldPoseDriver)
│
└─ TpWeaponHolder → 런타임에 오른손 본 소켓으로 이동 (HeldWeaponSocket)
   └─ TpMelee · Tp망치 · Tp리볼버 · Tp샷건 · Tp집게   ★ 이 5벌이 TP 월드모델
```

**현행 표현 규약** (무기 손 파지 계획 기술 확정 ④)

| 대상 | 소유자 화면 | 원격 화면 |
|---|---|---|
| 캐릭터 몸체 | `ShadowsOnly` (`PlayerCharacterView.cs:88`) | `On` |
| TP 월드모델 (손 무기) | `ShadowsOnly` (`HeldWeaponSocket.cs:158`) | `On` |
| FP 뷰모델 (피벗 5종) | `IsOwner && InputEnabled`일 때만 `On` | 항상 `off` |

즉 **소유자는 지금도 자기 손의 무기를 이미 갖고 있고, 렌더러만 그림자로 눌러 놓은 상태**다.
"통합 1인칭"은 이 두 줄의 `ShadowsOnly`를 여는 것에서 출발한다 — 다만 그것만으로는 성립하지 않는다 (§1.3).

### 1.2 좌표계가 둘로 갈라져 있다

| 계열 | 기준 원점 | 회전 주체 | 근거 |
|---|---|---|---|
| FP 뷰모델 | `AimPivot` — 루트 로컬 **(0, 1.6, 0)** = 눈높이 | `PlayerAimView.cs:87` 복제 피치 | 프리팹 실측 |
| 손 IK 홀드 타깃 | `WeaponHoldSettings`의 조준 피벗 — **(0, 1.08, 0)** = 어깨 높이 (에셋 실측값. 스크립트 기본값 1.25가 아니다) | `WeaponHoldMath.ComputeHoldPose` | `WeaponHoldSettings.asset` |
| 카메라 | `CameraPivot` — 루트 로컬 (0, 1.6, 0) | 마우스 피치 (`NetworkPlayerController.cs:276`) | 프리팹 실측 |

FP 뷰모델은 **눈 기준**으로, 손 파지는 **어깨 기준**으로 튜닝되어 있다.
두 계열이 같은 피치를 보지만 회전 중심이 0.52 m 다르다 — 통합하면 이 차이가 그대로 화면에 나타난다.

### 1.3 진단 — "렌더만 켜면 된다"가 성립하지 않는 이유

현행 홀드 타깃을 루트 좌표로 환산하고, 카메라(0, 1.6, 0)에서 본 각도를 계산한 결과다
(피치 0 · 어깨 실측 rest = 오른쪽 `(0.16, 1.091, 0.141)` · 왼쪽 `(-0.237, 1.081, 0.141)` ·
팔 길이 0.475 m — `WeaponHoldSettings.asset` · 메모리 실측):

| 무기 | 손 (루트 좌표) | 카메라 기준 **수직각** | 수평각 | 어깨→손 (팔 사용률) |
|---|---|---|---|---|
| 리볼버 · 집게 (오른손) | (0.378, 0.973, 0.448) | **46.9° 아래** | 40.2° | 0.394 m (83 %) |
| 샷건 (오른손) | (0, 0.937, 0.346) | **62.4° 아래** | 0° | 0.302 m (64 %) |
| 샷건 (왼손) | (0, 0.897, 0.416) | **59.4° 아래** | 0° | 0.407 m (86 %) |

FOV 60의 **수직 반각은 30°**(16:9 수평 반각 45.8°)다.
→ **세 무기 모두 손이 화면 아래 경계 밖에 있다.** 렌더러만 켜면 리볼버 총구 끝이 화면 하단에
살짝 걸리고, 샷건은 아예 보이지 않는다.

원인은 명확하다. 현행 파지 자세는 **원격 피어가 옆에서 보는 그림**을 기준으로 맞춰졌다.
1인칭은 **자기 눈에서 보는 그림**이 기준이므로, 홀드 타깃 전면 재튜닝이 필요하다.

### 1.4 팔 길이가 배치를 제약한다 (통합 1인칭의 본질적 난점)

FP 뷰모델은 카메라의 자식이라 팔 길이와 무관하게 화면 어디에나 놓을 수 있었다.
통합 1인칭에서 손은 **어깨에서 0.475 m 안**에 있어야 한다. 두 조건이 동시에 걸린다:

- **시야 조건** — 카메라 기준 수직각 ≤ 30°(FOV 60 하단 경계)
- **도달 조건** — 어깨→손 ≤ 0.40 m 권장 (팔 길이의 85 % — 팔꿈치를 펴지 않고 남기는 여유)

카메라(눈 1.6 m)와 어깨(1.091 m)의 **0.51 m 낙차**가 이 둘을 서로 밀어낸다.
손을 화면 중앙으로 올릴수록 팔이 펴지고, 팔을 편하게 둘수록 손이 화면 아래로 내려간다.

**해가 존재하는 구간은 있다.** 리볼버 예시 (계산 검산 포함):

```
손 = 루트 (0.22, 1.36, 0.40)        ← 홀드 로컬 (1.25 기준) = (0.22, 0.11, 0.40)
  어깨→손 = (0.06, 0.269, 0.259)  → 0.378 m  = 팔의 80 %      ✓ 도달
  카메라 기준 = (0.22, -0.24, 0.40)
    수직각 = atan(0.24 / 0.457) = 27.7°                        ✓ 화면 안 (하단 근처)
    수평각 = atan(0.22 / 0.40)  = 28.8°                        ✓ 화면 안
    카메라~손 거리 = 0.516 m                                   ✓ near clip 여유
```

즉 **"손은 화면 하단·오른쪽 가장자리, 총열이 화면 안으로 뻗는" 배치**가 두 조건을 동시에 만족한다.
이는 실사 지향 1인칭 슈터의 관용 배치와 같고, 팔을 억지로 들어올리지 않아도 된다.

**양손 무기(샷건)가 가장 빠듯하다.** 왼손이 총열 앞까지 가야 하는데 왼 어깨에서의 거리가
빠르게 0.475 m에 닿는다 (§7 리스크 R3). 소켓 스케일 축소·무기를 몸 쪽으로 당기는 조정이 함께 필요하다.

### 1.5 나머지 걸림돌 4가지

| # | 항목 | 현행 | 통합 시 문제 |
|---|---|---|---|
| ① | **머리** | 소유자 몸 전체 `ShadowsOnly` | 렌더를 열면 카메라(눈 1.6)가 **머리 메시 안**에 들어가 시야를 막는다 |
| ② | **near clip 0.3** | FP 뷰모델은 카메라 자식이라 0.3보다 앞에 배치됨 | 손 무기의 개머리판·그립이 0.3 m 안쪽으로 들어와 **잘린다** |
| ③ | **근접 스윙** | `MeleeSwingView`가 **FP 피벗**을 절차 회전 (`MeleeSwingView.cs:63`) | FP 피벗을 끄면 **소유자 화면에서 휘두르기 모션이 사라진다** |
| ④ | **총구** | `Muzzle`은 카메라 리그 자식의 더미 | 화면의 무기가 손 무기로 바뀌면 트레이서·로프가 **엉뚱한 데서** 나온다 |

③은 현재 원격 화면에서 이미 사라진 상태다 (파지 계획 §0이 수용한 회귀).
통합 모드에서는 **소유자 화면에서도** 사라지므로, 대체 경로가 이번 범위에 들어온다.

### 1.6 [무기-총구-발사위치-계획.md](무기-총구-발사위치-계획.md)와의 관계 — **전제가 바뀐다**

그 계획은 총구 앵커를 **FP 피벗 아래 `MuzzleTip`**에 두기로 확정했다 (§2 결정 ①).
근거는 "FP 피벗 계열은 루트 × 복제 피치 × 고정 로컬 TRS라 전 피어 결정론적으로 일치한다"였다.

통합 1인칭에서 **FP 피벗의 모델은 사라지지만 결정론 근거는 그대로 유효하다** — `AimPivot` 계열을
**렌더러 없는 앵커 계층**으로 남기면 된다. 다만 그 앵커는 이제 **화면에 보이는 무기와 다른 위치**다.

| 용도 | 현행 계획 | 통합 1인칭에서 |
|---|---|---|
| 발사 판정 원점 | `_aimSource`(카메라) — 무변 | **무변** |
| 훅 스폰 origin (RPC 전달) | FP `MuzzleTip` | **AimPivot 앵커 유지** (전 피어 동일 유지) |
| 트레이서 시작점 · 로프 시작점 · 되감기 앵커 (**표시**) | FP `MuzzleTip` | **손 무기의 `MuzzleTip`** — 보이는 무기에서 나와야 한다 |

이는 그 계획 §6이 이미 확장 경로로 적어 둔 **"FP·TP 이중 앵커"** 그대로다.
총구 계획의 산출물(앵커 규약·뷰랩 조정 경로)은 **전부 재사용**되고, 배선 대상만 늘어난다.

> **착수 순서 권고**: 총구 계획을 **먼저** 닫는 편이 싸다. `MuzzleTip` 규약과 뷰랩 조정 UI가
> 서 있으면 이 계획은 "TP 모델 쪽 앵커 추가 + 모드별 참조 선택"만 얹으면 된다.
> 반대 순서면 총구 계획의 검증 항목(V7~V11)을 두 모드에서 두 번 치러야 한다.

## 2. 착수 전 결정

### 2.1 착수 전 결정 — **확정 (2026-08-18, 사용자 "시작" 지시 = 권장안 채택)**

권장안이 모두 되돌리기 쉬운 선택이고 단계 1은 어느 결정에도 영향받지 않으므로, 권장 열의 안으로
확정하고 착수했다. 튜닝 단계(6)에서 결과가 기준에 못 미치면 ①·③은 재검토 대상이다.

| # | 항목 | 선택지 | **확정** | 영향 |
|---|---|---|---|---|
| ① | **카메라 부착** | **ⓐ 현행 유지** — `CameraPivot`을 루트 로컬 (0,1.6,0) 고정 / ⓑ **머리 본 추종** — 애니메이션의 머리 움직임을 카메라가 따라감 | **ⓐ** | ⓑ는 몰입이 크지만 걷기·점프 클립의 상하 흔들림이 그대로 화면에 실려 **멀미와 조준 흔들림**을 만든다. ⓐ면 무기만 흔들리고 시선은 안정적 — 스웨이는 홀드 타깃 쪽(`ShoulderFollow`)에서 원하는 만큼 조절할 수 있다 |
| ② | **몸 표시 범위** | **ⓐ 전신 표시 + 머리만 은닉** / ⓑ 팔·손·무기만 표시 | **ⓐ** | Girl·Man은 **단일 SkinnedMesh**라 부위별 렌더러 분리가 불가능하다. ⓑ는 메시 분할(아트 재작업)이 전제 — 이번 범위 밖. ⓐ면 내려다볼 때 자기 몸통·다리가 보인다(통합 1인칭의 이득) |
| ③ | **머리 은닉 방식** | **ⓐ 머리 본 스케일 0** / ⓑ near clip만 좁혀 머리 내부를 통과 / ⓒ 둘 다 | **ⓒ** | ⓐ 단독은 **자기 그림자에서 머리가 사라진다**. ⓑ 단독은 목·턱·모자챙이 화면에 남는다. ⓒ가 관용해이며, 그림자 결손은 §6 V8에서 눈으로 판정한다 |
| ④ | **QA 토글 범위** | **ⓐ 로컬 표현만** (판정·복제 무변) / ⓑ 카메라 파라미터까지 포함 / ⓒ 판정 원점도 함께 전환 | **ⓑ** | ⓒ는 두 모드의 명중 결과가 달라져 **비교의 기준선이 사라진다**. ⓑ면 "같은 판정, 다른 그림"이 보장되고 near/FOV까지 한 키로 비교된다 |
| ⑤ | **FP 경로 최종 처리** | **ⓐ QA 합격 후 제거** (§8) / ⓑ 영구 병존 (옵션으로 유지) | **ⓐ** | 사용자 요청은 "구분을 없앤다"이므로 ⓐ가 목표 상태. ⓑ면 무기 추가마다 두 벌을 튜닝해야 해 유지비가 계속 든다 |

## 3. 설계

### 3.1 모드 스위치 (신규 3종)

```
Assets/_Project/Scripts/Gameplay/Player/
  PlayerViewMode.cs              enum { SplitFpTp = 0, UnifiedFirstPerson = 1 }
  PlayerViewSettings.cs          SO — 기본 모드 · 모드별 카메라 파라미터 · 머리 은닉 계수
  PlayerViewModeController.cs    소유자 로컬 — 기본값 로드 · F10 토글 · 이벤트 발행
  PlayerViewEvents.cs            PlayerViewModeChangedLocalEvent (struct)
```

`PlayerViewModeController`는 **상태만 소유하고 아무것도 직접 만지지 않는다**.
각 표현 컴포넌트가 이벤트를 받아 자기 몫을 적용한다 (SRP · 개방 폐쇄 — 소비자 추가 시 컨트롤러 무변경).

```
PlayerViewModeController (소유자 전용)
   │  PlayerViewModeChangedLocalEvent
   ├──→ PlayerCharacterView      몸 렌더 모드 · 머리 본 은닉
   ├──→ HeldWeaponSocket         손 무기 렌더 모드
   ├──→ PlayerCameraTuner (신규) near clip · FOV
   ├──→ WeaponHoldIk             홀드 프로파일 선택
   ├──→ GunView / HarpoonView / RepairHammerView   FP 뷰모델 게이트
   └──→ MeleeSwingView           FP 절차 스윙 게이트
```

**원격 피어에는 컨트롤러가 없다** (`IsOwner`에서만 활성). 소비자는 컨트롤러를 못 찾으면
현행 동작(분리 모드)을 그대로 유지한다 — 원격 표현이 모드와 무관함을 코드 수준에서 보장한다 (LSP).

### 3.2 컴포넌트별 변경

| 파일 | 변경 | 규모 |
|---|---|---|
| `PlayerCharacterView.cs` | 소유자 렌더 모드를 모드에 따라 `ShadowsOnly`/`On`. 통합 모드에서 머리 본 스케일 은닉 (LateUpdate — 애니메이터 뒤) | 중 |
| `HeldWeaponSocket.cs` | `ApplyVisibility`의 `ownerShadowOnly`를 모드에서 결정 | 소 |
| `WeaponHoldIk.cs` | `TryGetEntry`가 돌려준 엔트리에서 **모드에 맞는 프로파일**을 고르는 한 단계 추가 | 소 |
| `WeaponHoldSettings.cs` | `Entry`를 `{ 소켓 · TpProfile · FpProfile }`로 재구성 (§3.3) | 중 |
| `GunView` · `HarpoonView` · `RepairHammerView` | `visible` 조건에 `모드 == 분리` AND 추가 | 각 소 |
| `MeleeSwingView.cs` | 통합 모드에서 절차 스윙 비재생 (§3.6) | 소 |
| `PlayerCameraTuner.cs` (신규) | 모드별 near/FOV 적용 | 소 |
| `MeleeWeaponController` · `GunController` · `HarpoonController` | 표시 총구 참조를 모드에 따라 선택 (§3.5) | 소 |

### 3.3 파지 데이터 — 프로파일 2벌 (기술 확정 ⑧)

```csharp
[Serializable] public sealed class Entry
{
    // 모드 공통 — 손에 쥐는 방식
    _itemType, _socketLocalPosition, _socketLocalEulerAngles, _socketLocalScale,
    _aimPose, _twoHanded, _pose

    // 모드별 — 팔이 어디로 가는가
    [SerializeField] private HoldProfile _tpProfile;   // 현행 값 그대로 이전
    [SerializeField] private HoldProfile _fpProfile;   // 1인칭용 (신규 튜닝)
}

[Serializable] public sealed class HoldProfile
{
    _rightHandLocalPosition, _rightHandLocalEulerAngles,
    _leftHandLocalPosition,  _leftHandLocalEulerAngles,
    _straightenWrist, _right/_leftWristRoll/BendDegrees,
    _right/_leftElbowHintLocalPosition, _right/_leftElbowHintWeight,
    _ikResidualWeight, _leftIkResidualWeight
}
```

**마이그레이션**: 기존 필드를 그대로 `_tpProfile`로 옮기고 `_fpProfile`은 §1.4의 산출값으로 초기화한다.
`WeaponHoldSettings.asset`은 YAML 직접 편집(들여쓰기 한 단계 이동)이 diff가 깨끗하다.

**조준 피벗도 모드별이다.** 1인칭은 회전 중심을 **눈높이 1.6**에 둔다 — 시선과 무기가 같은 중심으로
돌아 **화면에서 무기 위치가 피치와 완전히 무관해진다** (`FirstPersonHoldMathTests`가 ±85° 전 구간에서
오차 1 mm 미만으로 고정). 부수 효과로 프로파일의 손 좌표가 곧 **카메라 기준 오프셋**이라 읽기도 쉽다.

어깨 높이(1.08) 중심을 그대로 쓰면 위를 볼 때 무기가 화면 아래로 밀리는 정도가 아니라,
**손이 카메라를 스쳐 지나 옆으로 돌아간다** — 피치 −60°에서 화면 깊이(z)가 0.448 → −0.002로
무너져 각도와 무관하게 시야를 벗어난다 (같은 테스트로 고정).

단, 눈높이 중심은 **극단 피치에서 팔 도달을 악화시킨다** — R2의 트레이드오프다.

**1인칭 프로파일 초기값** (§1.4 산출 — 뷰랩 튜닝의 **출발점**이지 최종값이 아니다):

| 무기 | 오른손 (눈 1.6 기준 로컬) | 왼손 | 비고 |
|---|---|---|---|
| 리볼버 | (0.22, -0.24, 0.40) | — | 수직 27.7° · 팔 80 % |
| 집게 | (0.20, -0.25, 0.42) | — | 리볼버 준용, 무기가 길어 약간 앞 |
| 샷건 | (0.10, -0.23, 0.38) | (-0.05, -0.27, 0.45) | 왼손 도달률 92 % — R3 |
| 망치 · 마체테 | 파지 IK 없음 (`_aimPose = 0`) | — | 소켓 부착만 — 통합 모드에서도 손에 든 채 팔은 로코모션 |

### 3.4 카메라 파라미터

| 파라미터 | 분리 모드 (현행) | 통합 모드 | 근거 |
|---|---|---|---|
| near clip | 0.3 | **0.08** | 손~카메라 0.5 m지만 개머리판·그립이 뒤로 뻗는다. 0.08이면 여유가 충분하다 |
| FOV | 60 | **60 유지** (튜닝 여지 65~70) | §1.4의 배치가 60에서 성립한다. 넓히면 도달 여유가 늘지만 원근 왜곡이 커진다 — QA 항목 |

near clip 축소는 depth 정밀도를 낮춘다. URP는 reversed-Z float depth라 far 1000 / near 0.08
비율에서도 실사용상 문제가 없는 범위지만, 원거리 지형 z-fighting을 §6 V12에서 확인한다.

### 3.5 발사 원점 (§1.6의 이중 앵커 구현)

| 참조 | 분리 모드 | 통합 모드 |
|---|---|---|
| 판정 원점 (`_aimSource`) | 카메라 | **동일** |
| 훅 스폰 origin (RPC로 전 피어 전달) | `AimPivot/…/MuzzleTip` | **동일** |
| 트레이서 시작 · 로프 시작 · 되감기 앵커 (표시) | `AimPivot/…/MuzzleTip` | **`TpWeaponHolder/…/MuzzleTip`** (손 무기) |

표시 총구는 각 피어 로컬 값이라 피어 간 소수 cm 어긋날 수 있다 —
**표시 전용이므로 수용**한다 (총구 계획 §1.4가 판정에서 배제한 이유와 같은 사유).

구현은 컨트롤러에 `Transform _displayMuzzleFp` 필드 1개를 추가하고 모드에 따라 고르는 수준이다.
무기가 늘어도 필드 배선만 늘어난다 (총구 계획 §2.2의 "레지스트리 불채택" 근거 유지).

### 3.6 근접 스윙 (걸림돌 ③의 대체)

| 안 | 내용 | 판정 |
|---|---|---|
| **ⓐ Hold 레이어 Swing 트리거** | `WeaponHoldPoseDriver.PlaySwing()`이 이미 있다 — `MeleeWeaponController.cs:130-133`이 원격 경로에서 호출 중. 소유자도 같은 경로를 타게 한다 | **클립이 반입되면 최선** — 현재 `HoldLayerWeight = 0`이라 **아무 일도 일어나지 않는다** |
| **ⓑ 소켓 절차 스윙** | `MeleeSwingView`와 같은 트윈을 **손 소켓 아래 무기**에 적용 (홀드 타깃을 스윙 궤적으로 밀어냄) | 클립 없이 즉시 성립. IK 타깃을 시간 곡선으로 흔드는 형태라 기존 구조에 얹힌다 |
| ⓒ 이번 차수 회귀 수용 | 통합 모드에서 근접 스윙 모션 없음 | 근접이 "최후 수단" 무기라 체감 비중이 낮으나, **1인칭에서는 눈앞이라 부재가 크게 티난다** |

**권장: ⓑ를 1차로 넣고 ⓐ로 이관할 자리를 남긴다.** ⓑ의 스윙 곡선을 `WeaponHoldMath`에 순수 함수로
두면, 클립이 반입될 때 `IkResidualWeight`를 내리는 것만으로 ⓐ로 넘어간다 (품질 업그레이드 계획 C축과 같은 합성 규약).

## 4. QA 전환 설계 (사용자 요구의 핵심)

### 4.1 조작

| 조작 | 동작 |
|---|---|
| **F10** | 분리 ↔ 통합 즉시 전환 (Play 중, 재접속 불요) |
| 화면 표시 | 전환 시 좌상단에 현재 모드를 2초 토스트 (`Debug.Log` 병행) |
| 기본값 | `PlayerViewSettings._defaultMode` — 빌드·에디터 공통 |
| 뷰랩 | 패널 버튼으로 같은 전환 (네트워크 없이 자세만 볼 때) |

**전환은 멱등이어야 한다.** 되돌리면 정확히 원래 그림이어야 QA가 성립한다:

- 머리 본 스케일은 **복원값을 기억**했다가 되돌린다 (모델 교대 시 재해석 — `_cachedAnimator` 패턴)
- IK 가중치 블렌드 잔량은 프로파일이 바뀌어도 이어진다 (손이 튀지 않게 — 반감기 0.1 s)
- 카메라 near/FOV는 SO 값에서 매번 다시 쓴다 (누적 연산 금지)

### 4.2 두 모드가 **공유하는 것** (비교의 기준선)

| 항목 | 보증 |
|---|---|
| 사격·근접·집게 **판정** | `_aimSource`(카메라) 기준 — 코드 경로가 하나다 |
| 호스트 검증·데미지 | 무변경 |
| **원격 피어가 보는 내 모습** | TP 월드모델·상체 절차 피치 — 모드는 원격에 전달되지 않는다 |
| 네트워크 대역폭 | 채널 추가 0 |
| 이동·충돌·카메라 피치 입력 | 무변경 |

→ **"F10을 눌렀을 때 달라지는 것은 내 화면뿐"**이 QA의 판정 기준이다.
여기서 벗어나는 차이가 관측되면 그 자체가 결함이다 (§6 V13).

### 4.3 2인 비교 매트릭스

호스트와 클라이언트가 **서로 다른 모드**로 붙을 수 있다 (모드가 로컬이므로).
이것이 이 설계의 QA상 이점이다 — 한 세션에서 네 조합을 모두 관측한다.

## 5. 작업 순서

### 5.0 브랜치 제약 — **해소됨** (2026-08-18 병합 `aff8c98`)

> **현재 상태**: `feat/weapon-hold`를 `feat/structure-grid`로 병합해 파지 구현이 합류했다.
> 아래 제약 기록은 단계 1~3이 왜 파지 없이 먼저 닫혔는지에 대한 경위이며, **단계 4 이후는
> 이제 이 브랜치에서 진행한다.**
>
> **병합 시 주의 (재발 방지)**: `.gitattributes`의 `merge=unityyamlmerge` 드라이버는 자동 병합에
> 실패하면 **PlasticSCM의 대화형 `mergetool`로 넘어가 응답 없이 멈춘다** (`.prefab`·`.asset`·`.meta`
> 전부 이 드라이버를 탄다). 백그라운드 실행이면 그 창이 보이지도 않아 병합이 영원히 진행되지
> 않는 것처럼 보인다. 우회: `git -c merge.unityyamlmerge.driver="git merge-file %A %O %B" merge …`로
> 표준 3-way를 쓰고 충돌을 손으로 푼다.
>
> **프리팹 충돌 해결법**: 양쪽이 파일 끝에 서로 다른 YAML 블록을 덧붙이면 hunk 경계가 블록
> 중간을 갈라 단순 채택이 위험하다. 스테이지에서 `:1`(base)·`:2`(ours)·`:3`(theirs)를 꺼내
> **base→ours 차이가 순수 추가인지 확인**한 뒤, theirs를 기반으로 그 추가분만 다시 얹는 편이 안전하다.
> `GlobalObjectIdHash`가 세 버전에서 같은지 반드시 대조한다.

착수 시점의 작업 브랜치는 `feat/structure-grid`였는데, **이 계획이 전제하는 파지 구현이 여기에 없었다.**

| 문서 | 파지 계획 §0의 "FP/TP 표현 분리" 기술을 이 계획으로 갱신 |

`AimPivot` 자체는 **남긴다** — 발사 origin의 전 피어 결정론(§1.6)이 이 계층에 걸려 있다.
이름이 실체와 어긋나므로 `FireAnchors`류로 개칭하는 편이 읽기 좋다 (선택).

## 9. 규약 준수 (착수 시 자체 점검)

| 원칙 | 이 계획에서의 적용 |
|---|---|
| **SRP** | 모드 컨트롤러는 상태만 소유. 렌더 모드·카메라·IK 프로파일은 각 소유 컴포넌트가 적용 |
| **OCP** | 소비자 추가 시 컨트롤러 무변경 (이벤트 구독). 무기 추가는 SO 엔트리 + 프리팹 배선만 |
| **LSP** | 원격 피어에는 컨트롤러가 없고, 소비자는 부재 시 현행 동작 유지 |
| **ISP** | `WeaponHoldIk`·`HeldWeaponSocket`·`PoseDriver`는 서로 모른다 (현행 유지) |
| **DIP** | 표현 컴포넌트는 SO 데이터와 복제 값만 읽는다 — 무기 컨트롤러 구체 타입 무참조 |
| **판정-표현 분리 (MVP)** | 이 계획의 **전 범위가 표현 층위**다. 판정 경로 수정은 §0 비범위 |
| **순수 로직 테스트** | `FirstPersonHoldMath` (시야각·팔 도달률·스윙 곡선·반경 클램프) → EditMode |
| **인프라 규약** | 통신은 `EventBus`, 신규 스폰 없음 (`PoolManager` 무관), 신규 어셈블리 없음 |
