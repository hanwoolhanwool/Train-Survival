# M4 — D7 이탈 칸 위 건축물 차폐 실패 수정 (계획)

> 2026-08-03 · 대상: `feat/m4-region-weather` · 상태: **완료** — 방안 A 구현,
> EditMode 216개 통과, 플레이 재검증 4항목 통과 (2026-08-03)
>
> [M4 플레이 검증 항목](M4-플레이-검증-항목.md) "재검증 필요 항목"의 **D7** 실패를 한 단위로 추적한다.
> 같은 재검증 회차에서 D5·D8과 E는 통과했고, F는 TBD로 이월했으므로 **D7이 M4의 마지막 결함**이다.

## 증상

건축물이 살아 있는 **이탈 칸** 위에 서 있어도 체온이 완화되지 않는다 (사막 낮 기준으로 계속 상승).
붙어 있는 칸에서는 정상 동작한다.

D7의 의도는 [검증 문서 §발견 이슈 #2](M4-플레이-검증-항목.md)에서 확정한 사양이다 —
**차폐 판단 기준은 "지붕의 존재"이고 칸의 편성 이탈 여부는 보지 않는다** (이탈 칸에 고립된
플레이어가 체온으로 이중 처벌받지 않게 한다). 즉 사양이 아니라 구현이 틀렸다.

## 구조 배경 (관련 코드 지도)

| 요소 | 파일 | 역할 |
|---|---|---|
| 차폐 판정 | `PlayerTemperature.IsSheltered` (`:109`) | 호스트 권위. 밟은 칸을 Z로 역산 → 그 칸의 건축물 생존 확인 |
| 칸 인덱스 역산 | `TrainLayoutMath.TryGetCarIndexAtZ` (`:21`) | Z → 편성 인덱스 (순수) |
| 규격 데이터 | `TrainLayoutSettings` | 칸 길이 12 m · 연결부 간격 1.5 m · 선두 Z 19.5 |
| 이탈 오프셋 | `ITrainState.GetEjectOffset` | 칸이 슬롯 기준 뒤로 밀려난 거리(m). 서버는 시뮬 원값, 클라는 표시 보간값 |
| 칸 배치 | `CarView.Update` (`:140`) | `_originalLocalPosition + Vector3.back * offset` — 칸을 실제로 뒤로 민다 |
| 탑승 | `NetworkPlayerController.UpdateMove` (`:255`) | 밟은 칸의 위치 델타만큼 플레이어를 실어 나른다 (무빙 플랫폼) |

## 원인 — 판정이 "슬롯 위치"를, 플레이어는 "실제 위치"를 쓴다

`TrainLayoutMath.TryGetCarIndexAtZ`는 `GetCarCenterZ`의 역함수를 반올림해 칸을 고른다.

```csharp
int nearest = Mathf.RoundToInt((frontZ - carLength * 0.5f - z) / pitch);   // pitch = carLength + couplingGap
```

이 수식은 **모든 칸이 편성 슬롯 위치에 그대로 있다**고 가정한다. 그런데 이탈 칸은 `CarView`가
오프셋만큼 실제로 뒤로 밀어 놓고, 플레이어는 무빙 플랫폼으로 그 칸에 실려 함께 뒤로 간다.

→ **플레이어의 Z는 밀려 있는데 판정은 원래 슬롯을 조회한다.**

기본 편성(칸 12 m · 연결부 1.5 m · pitch 13.5) 기준, 이탈 오프셋 `d`에 따른 판정 결과:

| 오프셋 `d` | 판정 | 결과 |
|---|---|---|
| 0 ~ 6 m | 원래 칸으로 잡힘 | 정상 (아직 `carLength/2` 안) |
| 6 ~ 7.5 m | "연결부 간격 위" → `false` | **차폐 끊김** |
| 7.5 ~ 19.5 m | **인덱스 + 1** 로 잡힘 | 엉뚱한 칸의 건축물을 조회 |
| 뒤 칸이 없으면(후미 칸) | 편성 범위 밖 → `false` | **차폐 끊김** |

목표 밀림 속도는 `스크롤 + EjectExtraSpeed(2 m/s)` ≈ 8 m/s이고 소실 거리는 45 m다.
즉 **이탈 1~2초 만에 6 m를 넘어가므로 실플레이에서는 사실상 항상 실패**한다. 관측 증상과 일치한다.

### 지난 수정에서 놓친 이유

`6e9c04e`(발견 이슈 #2)는 **"이 칸의 건축물이 살아 있는가"** 쪽만 고쳤다 —
`Present`만 보던 것을 `Health > 0`까지 보도록 기준을 통일했다. 그 앞단인
**"어느 칸 위에 서 있는가"** 는 손대지 않았고, EditMode 테스트(`TrainLayoutMathTests`)도
붙어 있는 편성만 다뤄 이탈 오프셋 케이스가 통째로 비어 있었다.

## 수정 방안 A — 판정에 이탈 오프셋을 반영한다 (채택)

오프셋은 칸마다 다르므로 O(1) 역함수가 성립하지 않는다. 칸 수가 적으므로(기본 3, 증설해도 한 자릿수)
**실제 중심 Z가 가장 가까운 칸을 순회로 고른다.**

### 1. `TrainLayoutMath` — 순수 판정 조각 추가

```csharp
/// <summary>이탈 오프셋만큼 뒤로 밀린 칸의 실제 중심 Z. 오프셋 0이면 슬롯 중심과 같다.</summary>
public static float GetCarCenterZ(
    int index, float frontZ, float carLength, float couplingGap, float ejectOffset)
{
    return GetCarCenterZ(index, frontZ, carLength, couplingGap) - Mathf.Max(0f, ejectOffset);
}

/// <summary>Z가 그 칸의 갑판 범위 안인가 — 이탈 오프셋을 반영한다.</summary>
public static bool IsZOnCar(
    float z, int index, float frontZ, float carLength, float couplingGap, float ejectOffset)
{
    if (index < 0 || carLength <= 0f)
    {
        return false;
    }

    float centerZ = GetCarCenterZ(index, frontZ, carLength, couplingGap, ejectOffset);
    return Mathf.Abs(z - centerZ) <= carLength * 0.5f;
}
```

`TrainLayoutSettings`에 같은 이름의 얇은 래퍼를 더한다 (`CarCenterZ(index, ejectOffset)` ·
`IsZOnCar(z, index, ejectOffset)`) — 기존 래퍼와 동일한 규약.

### 2. `PlayerTemperature` — 순회로 칸을 고른다

```csharp
if (!_trainLayout.TryGetCarIndexAtZ(position.z, train.CarCount, out int carIndex))   // 삭제
```

를 아래로 교체한다.

```csharp
/// <summary>
/// Z 위에 있는 칸 — 이탈 칸은 슬롯에서 뒤로 밀려나 있어 슬롯 기준 역산이 성립하지 않는다.
/// 칸 수가 적으므로(기본 3) 실제 중심이 가장 가까운 칸을 순회로 고른다.
/// </summary>
private int ResolveCarIndexAt(float z, ITrainState train)
{
    int best = -1;
    float bestDistance = float.PositiveInfinity;

    for (int i = 0; i < train.CarCount; i++)
    {
        float offset = train.GetEjectOffset(i);
        if (!_trainLayout.IsZOnCar(z, i, offset))
        {
            continue;
        }

        float distance = Mathf.Abs(z - _trainLayout.CarCenterZ(i, offset));
        if (distance < bestDistance)
        {
            bestDistance = distance;
            best = i;
        }
    }

    return best;
}
```

`IsSheltered`의 갑판 높이·열차 폭 사전 조건과 건축물 생존 조건은 그대로 둔다 — 바뀌는 것은
가운데 "어느 칸인가" 한 줄뿐이다.

> **최근접 선택을 쓰는 이유**: 앞 칸이 pitch(13.5 m) 가까이 밀리면 뒤 칸 슬롯과 Z가 겹칠 수 있다.
> M3의 연쇄 이탈 규칙상 앞 칸이 이탈하면 뒤 칸도 함께 이탈하므로 실제로는 발생하지 않지만,
> 첫 매치를 쓰면 겹침 시 결과가 편성 순서에 좌우된다. 최근접은 그 의존을 없앤다.

### 3. 기존 `TryGetCarIndexAtZ` 처리 — 제거를 권한다

유일한 소비자가 `PlayerTemperature`였으므로 교체하면 미사용 API가 된다.
**"슬롯 = 실제 위치"라는 틀린 가정을 담은 채로 남으면 다음 소비자가 같은 함정에 빠진다.**
`TrainLayoutMath`·`TrainLayoutSettings`에서 함께 제거하고 해당 테스트를 새 판정 기준으로 옮긴다.

(남겨야 한다면 요약 주석에 "이탈 오프셋을 반영하지 않는다 — 붙어 있는 편성 전용"을 명시할 것.)

## 수정 방안 B — `_ridingCar`를 재사용한다 (기각)

`NetworkPlayerController.ProbeGround`(`:275`)는 이미 레이캐스트로 밟고 있는 `CarView`를 정확히
알고 있다. 이것을 쓰면 Z 역산 자체가 필요 없다.

**기각 사유**: `UpdateMove`/`ProbeGround`는 소유자 클라이언트에서만 도는 로컬 값이다.
`PlayerTemperature`는 호스트 권위이므로 원격 플레이어의 값을 알 수 없고, 쓰려면 밟은 칸 인덱스를
복제하는 경로를 새로 만들어야 한다. **클라이언트가 자기 차폐 여부를 주장하는 구조**가 되어
권위 분담표에도 어긋난다. M4 범위에 과하다.

## 영향 범위

- **체온 차폐 판정만** 바뀐다. `CarView`·`HandrailAnchor`·`StructureView`는 이미
  `GetEjectOffset`을 반영해 배치하므로 무관하다.
- 붙어 있는 칸(오프셋 0)에서는 새 수식이 기존과 정확히 같은 결과를 낸다 — D5·D8 등 통과 항목에 회귀 없음.
- 클라이언트 소유 플레이어도 호스트가 판정하므로 G8(클라 차폐)에 그대로 적용된다.
  호스트는 시뮬 원값을 쓰므로 클라 표시 보간과의 차이는 판정에 영향이 없다.
