로직 명세: [specs/cycle/day-night-cycle.md](../specs/cycle/day-night-cycle.md)

> **2차 목표**: **낮 → 밤 전환이 한 프레임 도약이 아니라 시간의 경과로 읽힌다.**
> 이 차수는 게임플레이를 한 줄도 바꾸지 않는다 — `DayPhase`·`DayPhaseChangedEvent`·
> `IDayCycleService`는 **읽기만** 하고, 새 네트워크 상태를 만들지 않으며, 산출물은
> `RenderSettings`와 `Light` 하나에 대한 **순수 로컬 표현**이다.

## 0. 이 계획의 위치 — 왜 A안과 B안이 한 문서인가

M8 착수 준비 §4는 연출을 **2차(A안: 전환 크로스페이드)** 와 **4차(B안: 태양 이동·하늘 색)** 로
나눴다. 그러나 같은 문서 §2.2가 이미 **"파일 2개가 아니라 컨트롤러 1개 + 모드 필드"** 로
결정했다 — 즉 **차수는 둘이지만 산출물은 하나다.** 계획을 둘로 쪼개면 같은 클래스의 설계를
두 문서가 나눠 갖게 되므로, 계획은 하나로 쓰고 **B안의 "활성화"에만 3차 렌더 실측 통과를
조건으로 건다**(§2.8).

또 하나의 이유는 원래 문제 제기다. 이 마일스톤은 **"낮과 밤이 갑작스럽게 바뀐다 — 시간이
흘러간다는 표현이 없다"** 는 관찰에서 출발했다(착수 준비 §0). A안은 **전환 순간**만
부드럽게 만들 뿐, 낮 4분·밤 2분 30초 동안 화면은 여전히 정지해 있다. **"시간이 흐른다"를
끝까지 성립시키는 것은 B안**이므로, A안만 계획하면 목표 문장의 절반만 설계하게 된다.

### 0.1 사용자 결정 (2026-08-18)

|---|---|---|---|

### 1.1 씬 조명 실측 스냅샷 — **A안의 숨은 전제가 여기 있다**

| 항목 | 실측값 | 근거 |
|---|---|---|
| **AmbientMode** | **`0` = Skybox** | `Game_ArtTest.unity:27` · `Game.unity:27` (두 씬 동일) |
| ambient 3색 (Sky·Equator·Ground) | 값은 있으나 **현재 무효** | 〃 `:23`–`:25` |
| AmbientIntensity | `1` | 〃 `:26` |
| SkyboxMaterial | **빌트인 `Default-Skybox`** (guid `0000…f000…`) | 〃 `:29` |
| **Sun** | **미지정 (`fileID: 0`)** | 〃 `:40` |
| Directional Light | 색 `(1, 0.957, 0.839)` · 강도 `1` · Soft Shadow | `Game_ArtTest.unity:4751` |
| Fog | 꺼짐 — `WeatherVisualController`가 백업·복원 소유 | 〃 `:17` · `WeatherVisualController.cs:53-84` |

> **핵심 — 착수 준비 §2.2의 A안 정의는 지금 씬에서 그대로는 성립하지 않는다.**
>
> `AmbientMode.Skybox`에서는 `RenderSettings.ambientSkyColor` / `ambientEquatorColor` /
> `ambientGroundColor`가 **읽히지 않는다.** 환경광은 스카이박스에서 구면 조화로 굽혀지고,
> 스크립트가 만질 수 있는 것은 `ambientIntensity` 하나뿐이다. 즉 **"ambient 색을 수 초에
> 걸쳐 보간"하는 코드를 그대로 작성하면 화면에서 아무 일도 일어나지 않는다.**
>
> **처방**: 컨트롤러가 활성화 시점에 `RenderSettings.ambientMode`를 **`AmbientMode.Trilight`**
> (하늘·지평·땅 3색 그라디언트)로 전환하고, 비활성화 시점에 원래 모드로 되돌린다.
> `WeatherVisualController`의 fog 백업·복원과 **같은 패턴**이며, 씬 YAML을 건드리지 않으므로
> 씬 diff가 0이다. 이 전환은 "착수 전 확인 사항"이 아니라 **구현의 일부**다(§4 단계 3).

#### 1.1.1 두 번째 함정 — Trilight에서는 이번엔 `ambientIntensity`가 무시된다 (구현 중 실측, 2026-08-18)

위 처방을 넣고 나면 곧바로 다음 벽이 나온다. **`AmbientMode.Trilight`에서 `RenderSettings.ambientIntensity`는
아무 효과가 없다.** 에디터에서 `ambientProbe`를 직접 읽어 확인한 값:

| 설정 | `ambientProbe[0,0]` |
|---|---|
| Trilight · 흰색 · **강도 1.0** | **1.0000** |
| Trilight · 흰색 · **강도 0.1** | **1.0000** ← 변화 없음 |
| Trilight · **색을 0.1로** · 강도 1.0 | **0.0100** ← 색만 반영된다 |

즉 §1.1의 처방만 적용하면 **색은 바뀌지만 밤에 강도를 낮춰도 어두워지지 않는다.** 두 함정은 짝이다 —
Skybox 모드는 색을 무시하고, Trilight 모드는 강도를 무시한다.

**처방**: 강도를 프로퍼티로 넘기지 않고 **색에 곱해서** 대입한다(`DayCycleVisualController.Scale`).
곱셈은 인스펙터에서 보는 것과 같은 감마 공간에서 하므로, 밝기 하한(§2.4)이 쓰는 휘도 기준과도 일치한다.
`ambientIntensity`에는 중립값 1을 넣어 모드를 오갈 때 잔여값이 섞이지 않게 한다.

## 2. 설계

### 2.1 입력 — 인터페이스를 고치지 않고 진행도를 얻는다

`IDayCycleService`가 노출하는 것은 `DayNumber` · `Phase` · `PhaseRemaining` · `PhaseDuration`
넷뿐이다. 여기서 필요한 진행도가 전부 나온다.

```
phaseElapsed = PhaseDuration − PhaseRemaining
phaseT       = PhaseDuration > 0 ? phaseElapsed ÷ PhaseDuration : 0      // 국면 내 0 → 1
cycleT       = Phase == Day ? phaseT × 0.5 : 0.5 + phaseT × 0.5          // 하루 전체 0 → 1
```

**`cycleT`는 실시간 비례가 아니라 국면 균등 매핑이다.** 낮 240 s / 밤 150 s로 길이가 다르므로
태양의 각속도가 낮과 밤에서 달라진다. 이는 버그가 아니라 의도다 — 화면에서는 "낮이 더
길다"로 읽히고, 밸런스가 길이를 바꿔도(`DayTimelineSettings`) 연출 수식은 무수정이다.

#### 왜 이벤트 구독이 아니라 매 프레임 파생인가

`DayPhaseChangedEvent`를 구독해 자체 타이머를 굴리는 구조는 아래 세 경우에서 표시가 어긋난다.

| 경우 | 이벤트+타이머 | 진행도 파생 |
|---|---|---|
| **후발 접속** (세션 중간 진입) | 전환을 놓쳐 초기 색이 틀린다 | 현재 진행도에서 바로 정확한 색 |
| **디버그 국면 점프** (숫자패드 1·2·3 — `DayCycleController:107-119`) | 점프 후 타이머가 0부터라 크로스페이드가 다시 돈다 | 점프한 지점의 진행도가 그대로 반영 |
| **새벽 보류** (M7 2차 — `NightHoldMath`) | 밤 끝에서 누적 시간이 멈추는데 타이머는 계속 간다 | 누적 시간이 멈추면 표시도 멈춘다 |

이 프로젝트가 `DayTimelineMath`에서 이미 쓰고 있는 규약(**"상태 전이는 시간의 함수"** —
as-built 명세 §6.2)과 동일하다. 연출도 같은 규약을 따른다.

### 2.2 A안 — 국면 전환 크로스페이드

```
blend  = clamp01(phaseElapsed ÷ FadeSeconds)          // FadeSeconds 기본 6 s (제안)
from   = Phase == Day ? NightAmbient : DayAmbient      // 직전 국면 = 반대 국면
to     = Phase == Day ? DayAmbient   : NightAmbient
결과   = Lerp(from, to, blend)
```

**직전 국면 색을 상태로 보관하지 않고 "반대 국면 색"으로 정의**하는 것이 핵심이다. 이렇게
하면 함수가 무상태가 되어 §2.1의 세 경우가 전부 자동으로 맞고, EditMode에서 입력만으로
검증된다.

A안이 만지는 것은 **ambient 3색 + `ambientIntensity`** 뿐이다. 태양·하늘·fog는 건드리지
않는다. 전환 구간이 끝나면 국면이 끝날 때까지 화면은 정적이다 — **이것이 A안의 한계이자
정의이며, B안이 필요한 이유다.**

### 2.3 B안 — 상시 보간 (태양 각도·색·강도 + 하늘)

`cycleT`에서 매 프레임 유도한다.

| 대상 | 수식 개요 | 제안 기본값 |
|---|---|---|
| 태양 피치 | 낮 구간: 일출각 → 정점 → 일몰각 / 밤 구간: 야간 최저각까지 | 낮 `10° → 80° → 10°` · 밤 최저 **`8°`** (§11.5 실측으로 −5°에서 상향) |
| 태양 야우 | `cycleT`에 선형 (그림자 방향이 하루 동안 도는 느낌) | `-30° → 210°` |
| 광원 색 | 낮 백황 → 일몰 주황 → 밤 청백(달빛) | 낮 `(1, 0.957, 0.839)` · 밤 `(0.55, 0.62, 0.85)` |
| 광원 강도 | 낮 1.0 → 밤 하한 | 낮 `1.0` · 밤 **`0.3`** (〃) |
| ambient 3색 | A안과 **같은 색 데이터**를 `cycleT`로 상시 보간 (전환 구간 한정이 아님) | A안 값 재사용 |

**태양을 지평선 아래로 완전히 내리지 않는다.** 착수 준비 리스크 2의 처방("밝기 하한 + 색조
위주")을 각도 설계에 그대로 반영한 것이다 — 전조등·모닥불 같은 점광원이 M8 비범위이므로,
밤에 광원을 정직하게 없애면 **아무것도 보이지 않는 화면**이 된다.

> **밤 고도는 반드시 양수여야 한다** (§11.5 실측). 고도가 0 이하가 되면 방향광의 진행 방향이
> 위를 향해 **지면 그림자가 통째로 사라지고 명암이 뒤집힌다** — 밤에 방향광을 두는 의미가 없어진다.
> 초기값 −5°는 이 때문에 **8°** 로 올렸고, 일출각(10°)보다는 낮게 두어 "밤은 광원이 더 낮다"가
> 성립하게 했다.

#### 하늘 — 전용 머티리얼 인스턴스로 (에셋 오염 방지)

현재 씬은 **빌트인 `Default-Skybox`** 를 참조한다(§1.1). 빌트인 머티리얼의 프로퍼티를
런타임에 쓰면 **에디터 세션 동안 값이 남아 다른 씬까지 오염된다.**

| 단계 | 처리 |
|---|---|
| 원본 | `Assets/_Project/Art/Materials/M_Sky_DayNight.mat` (`Skybox/Procedural`) 신규 — 명명은 1차 규약(`M_*`) 준수 |
| 런타임 | `RenderSettings.skybox = new Material(원본)` — 인스턴스에만 쓴다 |
| 보간 대상 | `_SkyTint` · `_GroundColor` · `_AtmosphereThickness` · `_Exposure` |
| 태양 원반 | `RenderSettings.sun`을 씬 Directional Light로 지정 → 원반이 실제 광원 방향을 따라간다 (현재 `fileID: 0` = 미지정) |
| 해제 | `OnDisable`에서 원본 머티리얼 참조로 복원 + 인스턴스 `Destroy` |

> 씬 에셋(`m_SkyboxMaterial`)은 **바꾸지 않는다.** Off 모드에서 화면이 지금과 완전히 같아야
> 하므로(§7-5) 하늘 교체도 런타임 적용·복원 대상이다.

### 2.4 밝기 하한 — 밤을 정직하게 어둡게 하지 않는다

착수 준비 리스크 2를 데이터로 고정한다. **전부 SO 필드**이며, 플레이 검증에서 사용자가
조정할 것을 전제로 초기값을 잡는다(연출 수치는 코드 수정 없이 조정 — 착수 준비 불변 지침).

| 필드 | 제안 기본 | 의도 |
|---|---|---|
| `NightSunIntensity` | 0.15 | 달빛 하한 — 실루엣이 읽히는 최소 |
| `NightAmbientIntensity` | 0.45 | 그늘진 면이 완전 검정이 되지 않게 |
| `MinLuminanceGuard` | 0.08 | 순수 함수가 출력 직전에 거는 **최종 클램프** — 색 조합을 어떻게 잡아도 이 밑으로는 내려가지 않는다 |

`MinLuminanceGuard`는 밸런싱 실수 방어다. 색을 손으로 잡다 보면 "예쁜데 안 보이는" 조합이
나오는데, 그것을 코드가 아니라 **데이터 상한선**으로 막는다.

### 2.5 `RenderSettings` 소유 경계 — fog는 접촉하지 않는다 (결정 ②)

착수 준비 리스크 3(fog 이중 소유)의 처방을 **프로퍼티 단위 표**로 확정한다.

| 프로퍼티 | 소유자 | 비고 |
|---|---|---|
| `fog` · `fogMode` · `fogColor` · `fogDensity` | **`WeatherVisualController`** | 낮/밤은 읽지도 쓰지도 않는다 |
| `ambientMode` · `ambientSkyColor` · `ambientEquatorColor` · `ambientGroundColor` · `ambientIntensity` | **`DayCycleVisualController`** (신규) | 모드 A·B 공통 |
| `skybox` · `sun` | **`DayCycleVisualController`** | **모드 B에서만** |
| `Light.color` · `Light.intensity` · `Light.transform.rotation` | **`DayCycleVisualController`** | **모드 B에서만** |

**교집합이 없다** → 두 컨트롤러가 매 프레임 서로를 덮어쓰는 경합이 발생하지 않는다.
이 표는 검증 항목(§5 C 구역)의 판정 기준이기도 하다.

### 2.6 모드 — `Off` / `A` / `B` (결정 ⑥)

```
[SerializeField] private DayVisualMode _mode = DayVisualMode.A;   // Off, A, B
[SerializeField] private bool _enableModeToggleKey = true;         // 릴리스에서 끈다
```

| 모드 | ambient 보간 | 태양·하늘 | 용도 |
|---|---|---|---|
| `Off` | — | — | **회귀 기준선** — 화면이 현재와 같아야 한다 |
| `A` | 전환 구간 한정 | — | 2차 기본값 |
| `B` | 상시 | 상시 | 3차 실측 통과 후 기본값 승격 |

#### 토글 키 — **숫자패드는 이미 전부 점유됐다** (실측)

| 키 | 현재 용도 | 출처 |
|---|---|---|
| 숫자패드 1·2·3 | 아침 / 저녁 / 다음 Day 점프 | `DayCycleController.cs:107-119` |
| 숫자패드 0·4·5·6·7·8·9 · `+` · `−` · `*` · `/` · `.` | QA 12종 (재시작·연결부 파괴·증설·지급·부위 데미지·웨이브 토글·창고 경합·피해 실측·동시 그랩·단건 스폰·보스 소환·보스 처치) | `QaDebugHotkeys.cs:78-146` |

**남은 숫자패드 키가 없다.** 반면 **F1~F12는 프로젝트 전체에서 사용 0건**(`grep` 확인)이므로
**`F7`** 을 모드 순환(`Off → A → B → Off`)에 배정한다. 착수 준비 §7의 **"모드 토글이 곧 검증
도구"** — 같은 장면에서 즉시 오가며 비교하는 것이 이 차수의 판정 방식이다.

### 2.7 네트워크 — 없다

`MonoBehaviour`이며 `NetworkBehaviour`가 아니다. 피어마다 모드가 달라도 게임플레이가 갈라지지
않는다(착수 준비 불변 지침 — "시각 연출은 순수 로컬 표현"). `IDayCycleService`가 이미 전
피어에서 같은 값을 주므로, 같은 모드라면 표시도 저절로 같다.

### 2.8 B안 활성화 게이트

B안은 **매 프레임 그림자맵을 다시 그린다**(착수 준비 §2.2 — 밤 시나리오 약 4배). 3차의
캐스케이드 4 → 2 · LOD1 그림자 Off 없이 기본값으로 켜면 비용이 그대로 배수로 붙는다.

| 시점 | `_mode` 기본값 | 조건 |
|---|---|---|
| 이 차수 (2차) | **`A`** | B는 `F7`로 **수동 확인만** |
| 3차 렌더 실측·조정 완료 후 | **`B`** 로 승격 | 착수 준비 §4 3차 항목 2·3·4 완료 |

**B안 코드는 이 차수에서 완성한다.** 3차에서 하는 일은 값 하나(기본 모드) 승격과 재측정이지
구현이 아니다 — 이것이 A·B를 한 문서로 묶은 실질적 이득이다.

## 7. 완료 기준

1. **`F7`로 `Off`/`A`/`B`가 같은 장면에서 즉시 전환**된다 — 비교가 검증 도구다
2. **낮 → 밤 전환이 시간의 경과로 읽힌다** (사용자 확인 — 착수 준비 §6-2)
3. **게임플레이 회귀 0** — `DayPhase`·`DayPhaseChangedEvent`·`IDayCycleService` 시그니처 무변경,
   **신규 네트워크 상태 0**, 밤 웨이브·보스·새벽 보류 동작 동일
4. **EditMode 전량 통과** + `DayVisualMathTests` 신규 추가
5. **`Off` 모드에서 화면이 현재와 동일**하다 — ambient 모드·스카이박스·광원이 전부 원복된다
6. **fog 경합 없음** — 모래폭풍 중 국면 전환에서 fog가 깜빡이지 않는다 (§2.5 표가 지켜짐)
7. B안 코드가 완성되어, **3차 이후 승격이 값 하나 변경으로 끝난다**

### 11.2 계획 대비 변경 1건

**§1.1.1 (결정 ⑫)** — 환경광 강도 전달 방식. 계획은 `RenderSettings.ambientIntensity`에 대입하는
것이었으나, 실측에서 그 값이 Trilight 모드에서 무시된다는 것이 드러나 **색에 곱하는 방식**으로 바꿨다.
데이터 구조(`AmbientTone.Intensity`)와 SO 필드는 그대로이므로 계획의 다른 부분은 무수정이다.

### 11.3 구현 단계에서 수치로 확인한 것

플레이 검증 전에 **"화면에 실제로 반영되는가"** 를 `RenderSettings.ambientProbe` 실측으로 닫았다.

| 상태 | probe RGB | 강도 |
|---|---|---|
| A안 낮 / B안 정오 | (0.2843, 0.2922, 0.2981) | 1.00 |
| A안 전환 중(3 s / 6 s) / B안 일몰 | (0.0496, 0.0542, 0.0675) | 0.73 |
| A안 밤 / B안 한밤 | (0.0040, 0.0050, 0.0093) | 0.45 |

- 낮 → 밤 환경광이 **약 71배** 어두워진다 (§1.1·§1.1.1의 두 함정이 실제로 해소됐다는 증거)
- 밤 probe에서 **B > R** — 달빛 청색조가 살아 있다
- **A안 전환 중간값과 B안 일몰값이 완전히 일치** — 두 모드가 같은 색 데이터를 쓴다
- 태양: 정오 80° / 1.00 → 일몰 10° / 0.55 → 한밤 −5° / 0.15
- 밝기 하한(0.08)은 밤 기본값(0.0953)에서 **걸리지 않는다** — 여유를 두고 방어만 한다

### 11.5 그림자 실측 — 밤 고도가 음수면 그림자가 사라진다 (2026-08-18)

**질문**: "해의 방향에 따라 그림자가 생기는 기능이 있나?"
**답**: **이미 전부 켜져 있고, B안이 태양을 회전시키므로 방향이 그대로 따라간다.** 신규 기능 불요.

| 항목 | 실측값 |
|---|---|
| 씬 방향광 | `Shadows = Soft` · `Strength 1` |
| URP `PC_RPAsset` | `MainLightShadowsSupported 1` · 셰도우맵 **2048** · 거리 50 (런타임 40) · 캐스케이드 4 · `SoftShadowQuality 3` |
| 씬 렌더러 | `CastShadows` 7/7 · `ReceiveShadows` 7/7 (끈 것 0개) |
| 1차 A5 | 방향광 회전 → 명암·그림자 변화 **통과** 기록 있음 |

**단, 초기값 `_nightElevation = −5°`에는 결함이 있었다.** 방향광의 진행 방향을 실측하니
`forward.y = +0.087` — **빛이 아래에서 위로 향한다.** 이 상태에서는 지면이 빛을 등져
그림자가 생기지 않고, 물체는 밑면만 밝아져 명암이 뒤집힌다. 씬 뷰 렌더로도 열차가 통째로
검은 실루엣이 되는 것을 확인했다.

**조치 (결정 ⑬)**: `_nightElevation` **8°** (양수 유지 + 일출각 10°보다 낮게) ·
`_nightSunIntensity` **0.3** (형태가 읽히도록). 밤 환경광 강도(0.45)는 **손대지 않았다** —
지형·몬스터가 있는 실제 플레이에서 판단할 값이라 검증 E 구역에 남긴다.

### 11.6 시간 배속 QA 키 (사용자 요청, 결정 ⑭)

**`F8` = 시간 배속 순환 `×1 → ×4 → ×16`** — `DayCycleController`에 추가.

| 설계 | 내용 |
|---|---|
| 곱하는 대상 | `ServerAccumulate`의 **가산량뿐** (`Time.deltaTime × 배율`). `Time.timeScale`이 아니다 |
| 왜 | 시간축만 빨라지고 **이동·물리·전투 속도는 그대로** — 판정이 왜곡되지 않는다 |
| 복제 | **없음.** 배율은 호스트 로컬 필드이고, 결과인 누적 시간이 이미 복제된다 |
| 권위 | 클라이언트가 눌러도 `ServerRpc` 경유 — 국면 점프(숫자패드 1·2·3)와 같은 패턴 |
| 새벽 보류 | 무영향 — `NightHoldMath`는 previous/next만 보므로 배율을 몰라도 규칙이 같다 |
| 부작용 | 밤이 자주 와서 **웨이브가 잦아진다.** 격리 관찰은 숫자패드 5(웨이브 토글)와 병용 |
| 릴리스 | 기존 `_enableDebugPhaseKeys` 플래그에 묶임 (결정 ⑥과 같은 처리) |

배속 ×16이면 낮 240 s → **15 s**, 밤 150 s → **9 s**. 검증 A4(국면 내내 변하는가)·A7(자연
전환)이 실시간 기다림 없이 가능해진다.

### 11.8 태양 궤적 결함 — Day 경계 240° 순간이동 (2026-08-18, 사용자 관찰에서 발견)

**관찰**: "해가 한 방향이 아닌, 여러 방향으로 움직이는 것 같다."

**원인 1 — 버그.** 야우가 하루에 **240°만** 돌게 잡혀 있었다(`_yawStart −30` → `_yawEnd 210`).
한 바퀴는 360°이므로 120°가 모자라고, **Day가 바뀌는 순간 태양이 반대편으로 튄다.**

| 시점 | 야우 | 빛 방향 (x, y, z) |
|---|---|---|
| 밤 끝 (수정 전) | 210° | (−0.49, −0.17, **−0.85**) |
| 다음 낮 시작 (수정 전) | −30° | (−0.49, −0.17, **+0.85**) ← z가 뒤집힌다 |

**테스트가 이 구멍을 놓쳤다.** `상시_보간도_국면_경계에서_이어진다`는 **낮↔밤 경계만** 검증했고
`SunYaw`는 비교 대상에도 없었으며, **Day 경계는 아예 보지 않았다.** 국면 경계만 지키면
연속이라고 착각한 것이 원인이다.

**조치**: `_yawEnd` **210 → 330** (= 시작각 + 360). 검증 3개 신설 —
`태양_방위는_Day가_바뀔_때도_이어진다`(`Mathf.DeltaAngle`로 최단 각도차 0 확인) ·
`태양_방위는_하루에_정확히_한_바퀴_돈다` · `태양_방위는_하루_동안_되돌아가지_않는다`.
수정 후 밤 끝 330° ≡ 다음 낮 −30°, 각도차 **0.00°**. EditMode **615/615**.

**원인 2 — 설계 선택의 부작용 (미조치).** 낮은 고도 10 → **80** → 10의 큰 아치인데
밤은 10 → **8** → 10으로 거의 평평하다. "한 원을 도는 천체"가 아니라 **높은 아치 + 낮은 직선을
이어 붙인 궤적**이며, 밤에 광원을 지평선 아래로 내리지 않기로 한 결정(리스크 2)의 대가다.
정오 고도 80°는 천정에 가까워 야우가 돌 때 짧은 그림자가 빠르게 회전하는 원인이기도 하다.
**이 축은 플레이 검증(E5)에서 판단한다** — `_noonElevation`·`_nightElevation` 둘 다 에셋 값이다.

> **해가 달을 겸하는 것은 의도된 설계다.** 방향광 1개로 낮에는 해, 밤에는 달 역할을 한다 —
> 별도 달 광원은 추가 광원 축이라 M8 비범위(착수 준비 §3)이므로, 같은 광원의 색·강도·고도만 바꾼다.
